# 5.2 분기 만들기 — `fork()` + 새 node

## 이 챕터에서 배우는 것

- 5.1에서 "묶어야 한다"고 한 두 축을, 이번엔 *가르는* 첫 동작 — 분기
- `fork()`가 원본 세션을 *건드리지 않고* 대화를 가르는 법
- 데이터 트리에 `parent_id`로 새 `node`를 잇는 법
- 그 둘을 **하나의 `branch` 연산**으로 묶어, 두 축이 같은 지점에서 갈라지게 하는 법
- 분기점에 무엇을 남겨야 나중에 길을 잃지 않는가

---

## 가르기부터 시작한다

5.1에서 우리는 대화 축과 데이터 축이 따로 흐른다는 걸 봤고, 갈라질 때 둘을 *같이* 움직여야 한다고 결론지었다. Part 5의 첫 동작은 **가르기**, 즉 분기다.

**분기(branch)**는 한 지점에서 두 갈래로 길을 내는 일이다. wafer 수율을 분석하다가 B 지점 — `lot_id` 머지까지 끝낸 상태 — 에서 "피처를 이렇게도 얹어보고 저렇게도 얹어보자"며 갈래를 치는 것이 분기다.

핵심은 5.1에서 못박았다. 갈래를 칠 때 **대화와 데이터를 같이** 갈라야 한다. 한쪽만 가르면 조용한 버그가 된다.

## 비유: 노트북을 통째로 복제한다

5.1에서 대화는 셀, 데이터는 커널이라고 했다. 그럼 분기는 무엇일까. **노트북 파일을 통째로 복제하는 것**이다.

`analysis.ipynb`를 `analysis-featureB.ipynb`로 복사하면, 새 파일은 원본의 셀(과 저장된 출력)을 그대로 물려받되 이제부터는 독립이다. 새 파일에서 뭘 하든 원본은 그대로다. 분기가 정확히 이 일을 한다 — 단, 파일 복사가 셀만 가져오는 것과 달리 우리는 셀(대화)과 커널(데이터)을 *각각* 떠서 둘을 다시 묶어야 한다는 점이 다르다.

> 💡 **복사본과 원본은 부모를 공유한다**: 복제 시점까지의 역사는 둘이 똑같다. 갈라지는 건 *그 이후*뿐이다. 그래서 트리에서 두 갈래는 같은 `parent`를 가리킨다.

## 대화 축을 가른다 — `fork()`

먼저 대화. SDK는 세션을 이어받는 `resume`에 `fork_session` 옵션을 더해, **원본 세션은 그대로 둔 채 새 갈래 세션을 만든다.**

```python
forked_session_id = None
async for msg in query(
    prompt=branch_prompt,
    options=ClaudeAgentOptions(resume=parent_session_id, fork_session=True),
):
    if isinstance(msg, SystemMessage) and msg.subtype == "init":
        forked_session_id = msg.data["session_id"]
```

`resume`만 주면 그 세션을 *이어서* 쓰지만, `fork_session=True`를 함께 주면 원본을 보존하고 *새 id*의 갈래가 갈라져 나온다. 우리가 할 일은 그 새 `session_id`를 초기화 메시지에서 꺼내 붙잡아 두는 것뿐이다.

> 🔬 **Deep Dive — `fork`는 안에서 무엇을 복제하나?**
>
> `fork_session=True`가 트랜스크립트를 어떻게 복사하고 새 세션 id를 어떻게 발급하는지는 엔진의 일이다. 자매서 『클로드 핸드북』의 세션 부분에 있다. 우리는 *옵션을 주고 새 id를 받을* 뿐, 복제 자체를 들여다보지 않는다.

## 데이터 축을 가른다 — 새 `node`

데이터 쪽은 4장의 트리에 새 `node`를 잇는 일이다. 분기점이 될 부모 노드를 `parent_id`로 가리키며 새 노드를 만든다.

```python
new_node_id = store.create_node(parent_id=parent_node_id)
```

아직 아무 `event`도 쌓이지 않은 빈 노드다. 여기서부터 이 갈래의 변경들이 쌓인다.

## 둘을 한 동작으로 — `branch`

이제 핵심. 두 가르기를 *따로* 하면 5.1의 함정에 다시 빠진다 — 대화만 갈라지고 데이터는 안 갈라지는 순간이 생긴다. 그래서 **하나의 연산으로 묶는다.**

```python
async def branch(parent_node_id: str, branch_prompt: str) -> str:
    """parent_node_id에서 대화와 데이터를 함께 가른다."""
    parent = store.get_node(parent_node_id)

    # 1) 데이터 축: parent_id로 새 node를 잇는다
    new_node_id = store.create_node(parent_id=parent_node_id)

    # 2) 대화 축: parent의 세션을 fork (원본은 보존)
    forked_session_id = None
    async for msg in query(
        prompt=branch_prompt,
        options=ClaudeAgentOptions(resume=parent.session_id, fork_session=True),
    ):
        if isinstance(msg, SystemMessage) and msg.subtype == "init":
            forked_session_id = msg.data["session_id"]

    # 3) 두 축을 묶는다: 새 node ↔ fork된 세션
    store.bind_session(new_node_id, forked_session_id)
    return new_node_id
```

이 함수 하나가 "B에서 갈래를 친다"의 전부다. 데이터 노드와 대화 세션이 *같은 부모*에서 갈라져 나와, 새 노드 하나에 함께 묶인다.

> ⚠️ **묶기는 트랜잭션이어야 한다**: 위 코드는 한 축은 성공하고 다른 축은 실패하는 경우 — 노드는 생겼는데 세션 fork가 깨지는 — 를 막지 못한다. "한쪽만 갈라진" 상태를 어떻게 방어하는지는 5.5에서 정면으로 다룬다. 지금은 *세 단계가 하나로 묶여야 한다*는 것만 쥐고 가자.

## 분기점에 이름표를 단다

갈래가 여럿 생기면 "이게 왜 갈라졌더라"를 잊는다. 그래서 분기 노드에 **왜 갈랐는지**를 첫 `event`로 남긴다.

```python
store.append_event(new_node_id, op="branch_reason",
                   payload={"from": parent_node_id, "note": "lot_id 대신 wafer_id로 머지 시도"})
```

이 한 줄이 5.4에서 트리를 그릴 때 각 갈래의 *이정표*가 된다.

> ✅ **fork 동작 검증됨 / 스토어 묶기는 하네스 대기**: `resume`+`fork_session=True`의 세 동작 — 원본 보존·새 id 발급·분기점까지 역사 상속 — 을 실제 SDK(`claude-agent-sdk` 0.2.87, Bedrock)로 확인했다. `forked_session_id`를 init `SystemMessage.data["session_id"]`에서 읽는 것도 정상이다(그 값이 곧 새 fork id). 단 `store.create_node`·`bind_session` 등 *우리 데이터 스토어* 묶기는 정본 하네스(검증 레포)에서 확인할 부분이다.

---

## 핵심 정리

- **분기는 두 축을 같은 지점에서 가르는 한 동작이다.** `fork()`로 대화를, 새 `node`로 데이터를 가르되 반드시 하나의 `branch` 연산으로 묶는다.
- **`fork_session=True`는 원본을 보존한다.** `resume`에 얹으면 원본 세션은 그대로 두고 새 id의 갈래가 생긴다. 우리는 그 id를 붙잡아 노드에 묶을 뿐, 내부 복제는 엔진에 맡긴다.
- **노트북을 통째 복제하는 그림이다.** 복사본과 원본은 분기점까지의 역사를 공유하고 그 이후만 갈라진다 — 그래서 둘은 같은 `parent`를 가리킨다.
- **묶기는 트랜잭션이어야 한다.** 한쪽만 갈라진 상태가 5.1이 경고한 어긋남의 씨앗이며, 그 방어는 5.5에서 다룬다.
