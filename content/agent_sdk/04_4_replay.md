# 4.4 replay — 로그를 접어 상태를 만들기

## 이 챕터에서 배우는 것

- 쌓인 이벤트를 실제 테이블로 바꾸는 단 하나의 동작 — `replay`(접기, fold)
- 이벤트는 *레시피*이고 테이블은 *요리*라는 그림, 그리고 그 비유가 깨지는 자리
- 저장소 역할 분리 — 이벤트는 SQLite, 90GB 베이스는 불변 Parquet, 변환 실행은 DuckDB
- 매번 접는 비용을 누르는 법 — 스냅샷을 *진실*이 아니라 *캐시*로 되살려 쓰기
- Part 4 전체가 어떻게 Part 5의 롤백·분기를 떠받치는지

---

## 접는다는 게 무슨 뜻인가

4.3에서 우리는 재료를 깔았다. `nodes`로 갈래의 길을 그리고, `events`로 각 갈래에서 무슨 일이 순서대로 일어났는지 쌓았다. 재귀 CTE로 루트에서 현재 노드까지의 길도 뽑아낼 수 있다.

그런데 아직 "지금 테이블의 실제 모양"은 어디에도 없다. 4.2에서 말한 그대로다 — 상태는 저장된 명사가 아니라, 쌓인 동사들을 접은 결과다. 그 **접기(fold)**가 바로 `replay`다.

**`replay`**는 루트부터 목표 노드까지의 이벤트를 *순서대로 다시 실행해* 실제 테이블을 만들어내는 동작이다. 저장된 결과를 불러오는 게 아니라, 그때그때 *다시 계산*한다. 이 한 가지 동작이 Part 4의 마침표다.

## 레시피와 요리

이 그림은 부엌에 있다. **이벤트 로그는 레시피이고, 테이블은 요리다.**

레시피는 짧다. "베이스 CSV를 깔고, lot_id로 공정 파라미터를 머지하고, 수율 컬럼의 결측을 버려라." 한 장의 종이다. 요리는 그 레시피를 *실제로 조리한* 결과물 — 1.2M행짜리 테이블이다. 우리는 요리를 냉장고에 쟁여두지 않는다. 레시피만 들고 있다가, 먹고 싶을 때 조리한다. 그게 `replay`다.

이 비유가 모든 조각을 제자리에 놓는다.

- **레시피(이벤트)**는 가볍다 — 글자 몇 줄. SQLite에 담는다.
- **재료(베이스 데이터)**는 팬트리에 있다 — 90GB의 원본. 불변 Parquet으로 한 번 변환해 두고 누구도 건드리지 않는다.
- **조리(변환 실행)**는 부엌에서 한다 — DuckDB가 머지·필터를 실제로 돌린다.
- **롤백**은 레시피를 중간까지만 읽고 조리를 멈추는 일이다. 다 된 요리를 *되돌릴* 필요가 없다.

> 💡 **비유의 한계 — 재료가 변하면 같은 레시피도 다른 요리가 된다**: 레시피가 늘 같은 요리를 내려면 재료가 늘 같아야 한다. 그래서 베이스 Parquet은 *불변*이어야 한다. 누가 베이스를 갈아끼우면 같은 이벤트를 접어도 다른 테이블이 나온다 — 4.2에서 "외부 부작용 없음"을 전제로 못박은 이유가 여기서 다시 확인된다.

## 누가 무엇을 맡나 — 저장소 역할 분리

그래서 저장소가 셋으로 나뉜다. 각자 잘하는 일만 한다.

- **SQLite** — 이벤트 로그와 트리(`nodes`/`events`). 작고 트랜잭션이 확실하다. 레시피 보관소.
- **Parquet** — 90GB 원본을 한 번 변환한 불변 베이스. 컬럼 저장이라 압축이 좋고 스캔이 빠르다. 팬트리.
- **DuckDB** — 머지·필터를 실제로 실행하는 분석 엔진. 부엌의 화구.

`replay`는 이 셋을 한 줄기로 꿴다. SQLite에서 이벤트를 읽어, Parquet 베이스 위에서, DuckDB로 차례차례 실행한다.

```python
def replay(
    store: Store, duck: duckdb.DuckDBPyConnection, node_id: str, base_parquet: str
) -> str:
    """루트→node_id의 이벤트를 순서대로 실행해 현재 테이블을 만든다."""
    duck.execute(
        "CREATE OR REPLACE TABLE state AS SELECT * FROM read_parquet(?)",
        [base_parquet],                        # 베이스 경로도 값이니 바인딩
    )
    for nid in store.ancestry(node_id):        # 루트→node_id (4.3 재귀 CTE)
        for ev in store.events_of(nid):        # 노드 안 seq 순
            APPLY[ev.op](duck, "state", ev.payload)
    return "state"
```

각 이벤트는 `op`에 따라 정해진 변환 함수로 간다. `merge` 하나만 펼쳐 보면 이렇다.

```python
def _apply_merge(duck: duckdb.DuckDBPyConnection, table: str, payload: dict) -> None:
    on = _safe_ident(payload["on"])        # 식별자(컬럼명)는 화이트리스트로 검증 (7.3)
    duck.execute(
        f"CREATE OR REPLACE TABLE {table} AS "
        f"SELECT * FROM {table} "
        f"LEFT JOIN read_parquet(?) USING ({on})",   # 경로(값)는 바인딩, 컬럼(식별자)은 검증 후 삽입
        [payload["table"]],
    )

def _apply_noop(duck: duckdb.DuckDBPyConnection, table: str, payload: dict) -> None:
    """데이터 op가 아닌 이벤트(branch_reason 등)는 상태에 영향이 없다."""


APPLY = {
    "merge": _apply_merge,
    "drop_nulls": _apply_drop_nulls,
    "branch_reason": _apply_noop,   # 분기 이정표(5.2)는 상태 무영향 — 안 넣으면 replay가 터진다
}
```

`replay`는 "무슨 연산인지"는 `APPLY` 사전에 위임하고, 자기는 *순서대로 부르는* 일만 한다. 새 연산을 추가하고 싶으면 `APPLY`에 한 줄 더하면 된다 — `replay` 본체는 손대지 않는다.

> ⚠️ **`op`·식별자는 신뢰 경계다**: `payload`의 테이블 이름·컬럼명이 SQL에 직접 들어간다. 위 코드는 *값*(파일 경로)만 `?`로 바인딩하고, *식별자*(컬럼명)는 바인딩(`?`)이 안 돼 `_safe_ident`로 화이트리스트 검증 후 넣었다. 어떤 `op`·식별자를 허용할지는 7.3(권한·견고)에서 정면으로 다룬다.

## 접기 비용과 스냅샷 캐시

여기서 4.2가 미뤄둔 정직한 약점을 마주한다. **매번 루트부터 다시 조리하는 건 비싸다.** 이벤트가 수백 개면 괜찮지만, 90GB 위에서 수천 번의 머지를 매 조회마다 다시 돈다면 사람이 기다리지 못한다.

답은 부엌의 상식 그대로다. **자주 먹는 요리는 만들어 냉장고에 넣어둔다.** 특정 노드까지 접은 결과를 Parquet으로 한 번 저장해 두면(materialized snapshot), *그 노드*를 다시 조회할 땐 접지 않고 바로 읽는다. (가장 가까운 조상 스냅샷에서 *이후 이벤트만* 다시 접는 더 본격적인 캐시는 8.2에서 판다 — 위 스케치는 동일 노드 캐시까지다.)

```python
def replay(store, duck, node_id, base_parquet):
    cached = store.snapshot_of(node_id)        # 이 노드까지 접어 둔 결과가 있나?
    if cached is not None:
        duck.execute("CREATE OR REPLACE TABLE state AS SELECT * FROM read_parquet(?)",
                     [cached])                 # 경로도 값이니 ? 바인딩 (본문 규율 그대로)
        return "state"
    ...  # 없으면 base_parquet 위에 루트부터 접는다 (앞 본체)
```

여기서 규율 하나가 중요하다. **스냅샷은 진실의 원천이 아니라 캐시일 뿐이다.** 단일 진실은 여전히 이벤트 로그다. 스냅샷은 지워도 되고(다시 접으면 그만), 이벤트와 어긋나면 이벤트가 이긴다. 4.2의 ADR-001이 "스냅샷이 아니라 append"라고 한 건 *스냅샷을 절대 쓰지 말라*가 아니라 *진실을 스냅샷에 두지 말라*는 뜻이었다. 캐시로서의 스냅샷은 환영이다. 언제·어느 간격으로 캐시할지는 8.2(기술부채)에서 더 판다.

## Part 4를 닫으며

이제 토대가 섰다. 되짚어 보면 Part 4는 한 줄로 줄어든다.

데이터 상태는 세션이 아니라 **앱이 소유한다**(4.1). 앱은 그걸 스냅샷이 아니라 **이벤트의 누적**으로 들고(4.2), **`nodes`와 `events` 두 테이블**에 담아(4.3), 필요할 때 **접어서 임의 시점을 복원**한다(4.4).

이 네 조각이 Part 5의 두 동작을 거의 공짜로 만든다. **롤백**은 더 이른 노드까지만 접는 것이고, **분기**는 새 노드를 더하고 거기에 대화 세션을 묶는 것이다. Part 5가 할 "두 축을 하나로 묶는" 그 일을, 이제 우리는 떠받칠 바닥을 갖고 맞는다.

> ✅ **검증됨 (검증 레포)**: `replay`의 fold(조상 경로만 따라 격리)와 `_apply_merge`의 `LEFT JOIN … USING` + `read_parquet(?)` 값 바인딩을 harness(`replay.py`)로 돌려 확인했다(test_replay 7건 — 조인 구문·파라미터 바인딩 OK, 형제 갈래 격리). 머지 결과의 *값 정합*까지 ground-truth 전체 행 대조로 못박았다(`tests/test_ground_truth.py`, 양방향 `EXCEPT ALL`). 단 **스냅샷 캐시(`snapshot_of`)는 아직 미구현 — 설계 스케치**이며, 캐시 시점·무효화는 8.2(기술부채)로 남긴다.

## 핵심 정리

- **`replay`는 이벤트를 순서대로 실행해 테이블을 만드는 접기다.** 저장된 결과를 불러오는 게 아니라 그때그때 다시 계산한다 — 이벤트가 레시피, 테이블이 요리다.
- **저장소는 셋으로 나뉜다 — SQLite(레시피)·Parquet(불변 재료)·DuckDB(부엌).** 각자 잘하는 일만 맡아, 90GB 베이스를 모든 갈래가 공유한다.
- **접기 비용은 스냅샷 캐시로 누른다.** 단, 스냅샷은 진실이 아니라 캐시다 — 이벤트와 어긋나면 이벤트가 이긴다. ADR-001의 진의는 "진실을 스냅샷에 두지 말라"였다.
- **Part 4는 Part 5의 바닥이다.** 소유(4.1)→누적(4.2)→모델(4.3)→접기(4.4)가 서고 나면, 롤백은 "덜 접기", 분기는 "노드 더하기"가 된다.
