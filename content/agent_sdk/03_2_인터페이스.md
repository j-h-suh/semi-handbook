# 3.2 인터페이스 — CLI와 그 너머

## 이 챕터에서 배우는 것

- 4·5장에서 쓰던 동사 `merge`·`show-tree`·`rollback`·`branch`에 *CLI라는 집*을 주는 법
- 명령 계층은 얇게, 연산 코어는 두껍게 — 인터페이스와 코어의 분리
- 에이전트가 *수행*하는 명령과 운영자가 *직접* 내리는 명령의 구분
- CLI가 한 어댑터일 뿐, 웹은 그 너머에 같은 코어로 선다는 것

---

## 동사에 집을 준다

3.1에서 우리는 스트림을 소비하는 엔진을 세웠다. 그리고 이 책 곳곳에서 동사를 써 왔다 — `merge`로 합치고, `rollback`으로 되돌리고, `branch`로 가르고, `show-tree`로 본다. 이 동사들에 사용자가 *칠 수 있는 집*을 줄 차례다. 가장 먼저, CLI.

## 리모컨 — 명령은 얇고, 코어는 두껍다

3.1의 관제석이 흘러나오는 스트림을 *받아 운전*하는 쪽이었다면, CLI는 반대 방향이다 — 사용자 명령을 코어로 *넘기는* 쪽. 그 넘기는 손을 **리모컨**으로 생각하자. 리모컨의 버튼은 얇다 — 누르면 신호를 보낼 뿐, 그 안에 영상 처리 로직이 들어 있지 않다. 진짜 일은 TV(코어)가 한다. 좋은 리모컨은 버튼과 신호의 *얇은 변환층*일 뿐이다.

CLI도 그래야 한다. `merge` 명령은 인자를 파싱해 *이미 있는 연산*(2.2의 도구, 5.x의 `rollback`/`branch`)에 넘기는 얇은 층이다. 비즈니스 로직을 CLI 핸들러에 넣지 마라 — 그건 코어(연산)의 몫이다. 이 분리 덕에 같은 코어 위에 *다른 리모컨*(웹)을 얹을 수 있다.

> 💡 **비유의 한계 — 얇다고 다가 아니다**: 리모컨이 얇다는 건 *로직이 없다*는 뜻이지 *대충 만들어도 된다*는 뜻이 아니다. 버튼을 잘못 고르거나 한 버튼에 너무 많은 걸 묶으면, 얇은 리모컨도 나쁜 인터페이스가 된다. 얇되 *정확히 코어로 넘기는* 게 좋은 리모컨이다.

## 네 명령을 잇는다

`argparse`로 서브명령을 정의하고, 파싱한 인자를 코어로 디스패치한다.

```python
import argparse
from pathlib import Path

def build_parser() -> argparse.ArgumentParser:
    p = argparse.ArgumentParser(prog="analyze")
    p.add_argument("--db", type=Path, default=Path("events.db"))   # 이벤트 로그 경로
    sub = p.add_subparsers(dest="command", required=True)

    m = sub.add_parser("merge", help="현재 노드에서 테이블을 머지")
    m.add_argument("--on", required=True)
    m.add_argument("--table", required=True)

    sub.add_parser("show-tree", help="갈래 트리를 그린다")

    r = sub.add_parser("rollback", help="과거 노드로 current 이동")
    r.add_argument("node")

    b = sub.add_parser("branch", help="현재 노드에서 갈래 치기")
    b.add_argument("--note", default="")
    return p
```

```python
async def dispatch(args, client, ui) -> None:
    if args.command == "merge":
        # 에이전트가 수행: 자연어로 넘겨 도구를 부르게 한다 (3.1)
        await run_turn(client, ui, f"{args.table}을 {args.on}로 머지해줘")
    elif args.command == "show-tree":
        ui.show(show_tree(store))                      # 5.4: 앱이 직접
    elif args.command == "rollback":
        await rollback(store, duck, args.node)         # 5.3: 앱이 직접
    elif args.command == "branch":
        await branch(store, store.get_current(), args.note)   # 5.2: 앱이 직접
```

```bash
$ analyze merge --on lot_id --table process_params   # wafer 수율에 공정 파라미터 붙이기
$ analyze show-tree
$ analyze rollback B
$ analyze branch --note "wafer_id로 다시"
```

## 에이전트 명령 vs 조작 명령

위 디스패치에 미묘한 갈림이 있다. `merge`는 `run_turn`을 거쳐 *에이전트가* 수행하는데, `rollback`·`branch`·`show-tree`는 앱이 *직접* 코어를 부른다. 왜 다를까.

**`merge`는 데이터 변환이다.** 어떤 키가 맞는지 판단이 필요하고, 그 판단과 실행은 에이전트의 일이다 — 그래서 도구로 흐르고 이벤트로 적힌다(2.2). 반면 **`rollback`·`branch`는 트리 조작이다.** "B로 돌아가자", "여기서 갈래 치자"는 *운영자의* 결정이지 에이전트가 알아서 할 일이 아니다. 그래서 앱이 직접 코어를 부른다.

> ⚙️ **누가 결정의 주인인가로 가른다**: 데이터를 *어떻게 바꿀지*는 에이전트에게, 트리를 *어디로 움직일지*는 사람에게. 이 구분이 CLI 디스패치의 두 갈래를 만든다.

## 웹은 그 너머

CLI는 첫 리모컨일 뿐이다. 코어(3.1의 소비 엔진 + 연산)는 인터페이스를 가리지 않으니, 같은 `dispatch`를 웹 요청 핸들러에 연결하면 웹 UI가 된다. `merge`는 버튼이 되고, `show-tree`는 화면의 트리 그림이 된다 — 코어는 한 줄도 안 바뀐다.

이로써 Part 3이 닫힌다. 부르던 에이전트(Part 1)에 능력을 주고(Part 2) 앱으로 감쌌다(Part 3). 이제 이 앱이 다루는 *상태* — 되돌릴 수 있는 그 데이터 상태 — 를 어떻게 표현하는지로, 예제가 가장 깊어지는 Part 4로 들어간다.

> ✅ **코어 연결 검증 / argparse는 SDK 무관 표준안**: `dispatch`가 부르는 코어 — `run_turn`의 스트림 소비 + 도구 구동(3.1) — 는 검증 레포 e2e에서 실증됐다(`harness/run.py`·`probes/c5c_full_scenario.py`에서 에이전트가 실제로 `merge_tables`를 호출). 위 `argparse` 서브명령·`build_parser`·비동기 진입점 자체는 SDK와 무관한 표준 라이브러리 패턴이라 검증 레포가 별도로 돌리지 않는다. CLI는 그 코어를 부르는 얇은 껍데기다.

---

## 핵심 정리

- **CLI는 동사에 주는 집이다.** `merge`·`show-tree`·`rollback`·`branch`를 `argparse` 서브명령으로 잇되, 명령 계층은 얇게 코어는 두껍게 — 리모컨처럼.
- **명령에 비즈니스 로직을 넣지 마라.** 핸들러는 파싱해 코어에 넘기는 변환층일 뿐이다. 그래야 같은 코어 위에 다른 인터페이스를 얹는다.
- **에이전트 명령과 조작 명령을 가른다.** 데이터를 *어떻게 바꿀지*(`merge`)는 에이전트가, 트리를 *어디로 움직일지*(`rollback`·`branch`)는 운영자가 결정한다.
- **웹은 그 너머다.** 코어가 인터페이스를 안 가리니, 같은 `dispatch`를 웹에 연결하면 코어 변경 없이 웹 UI가 된다.
