# 7.1 비결정 에이전트 테스트 · eval

## 이 챕터에서 배우는 것

- 같은 질문에 *다른 길*로 답하는 에이전트를 어떻게 테스트하나
- 결정적인 코드(store·replay)와 비결정적인 판단(에이전트)을 갈라 다루는 법
- 결정적 코어는 평범한 단위 테스트로 — 사실 위험의 대부분이 여기 있다
- 비결정적 행동은 *합격률*로 보는 eval로
- 우리 이벤트 설계가 왜 테스트를 *쉽게* 만드는가

---

## 같은 질문, 다른 길

여기까지 우리는 에이전트를 만들고, 관측하고, 내보냈다. 이제 가장 무거운 질문이다 — **이걸 믿고 출시할 수 있나?**

전통적 테스트는 "입력 X면 출력은 정확히 Y"를 단언(`assert ==`)한다. 그런데 에이전트는 **비결정적(non-deterministic)**이다 — 같은 "lot 데이터에 공정 파라미터를 붙여줘"라는 요청에, 어떤 날은 곧장 머지하고 어떤 날은 먼저 컬럼을 살핀다. 도구 호출 순서가 매번 다를 수 있다. `assert ==`는 첫 줄에서 깨진다.

그렇다고 못 믿을 물건으로 둘 순 없다. 테스트하는 *방식*을 바꿔야 한다.

## 객관식과 서술형

시험을 떠올리면 쉽다. **객관식**은 정답이 하나다 — 채점은 맞다/틀리다, 곧 `assert ==`다. **서술형**은 정답이 여럿이다 — 좋은 답이 여러 모양일 수 있어, 채점 기준(rubric)으로 점수를 매기고, 한 번이 아니라 여러 답안을 보고 *합격률*을 본다.

우리 시스템엔 둘이 섞여 있다. store·`replay`·`branch` 같은 코드는 객관식이다 — 같은 이벤트엔 같은 테이블, 정답이 하나다. 반면 에이전트의 *판단* — 어떤 키로 머지할지, 어떤 순서로 갈지 — 은 서술형이다. 둘을 같은 잣대로 채점하면 안 된다.

> 💡 **비유의 한계 — 서술형도 기준이 있어야 채점된다**: 서술형이 "아무 답이나 정답"은 아니다. 명확한 채점 기준이 있어야 점수가 나온다. eval의 어려움이 바로 여기다 — "좋은 결과란 무엇인가"를 먼저 정의해야 한다. 다행히 우리 도메인은 그걸 준다: 머지된 테이블이 ground truth와 맞는가.

## 결정적인 부분은 곧장 단위 테스트

먼저 객관식부터. 사실 *위험의 대부분*이 여기 있다 — 롤백이 정말 과거를 복원하는가, `replay`가 같은 이벤트에 같은 결과를 내는가. 이건 LLM과 무관한, 순수하게 결정적인 코드다. 평범한 단위 테스트로 못박는다.

```python
def test_replay_is_deterministic():
    """같은 이벤트 로그는 늘 같은 테이블을 낳는다."""
    n = store.create_node(parent_id=root)
    store.append_event(n, op="merge", payload={"on": "lot_id", "table": str(params)})

    replay(store, duck, n, base)                  # base 위에 이벤트를 접는다 (4.4)
    first = duck.execute("SELECT * FROM state ORDER BY ALL").fetchall()
    replay(store, duck, n, base)
    second = duck.execute("SELECT * FROM state ORDER BY ALL").fetchall()
    assert first == second        # 두 번 접어도 행·값까지 같다 (ORDER BY ALL로 순서 고정)
```

`store`와 `replay`가 결정적이라는 걸 여기서 보증하면, 나머지 비결정성은 *에이전트의 판단 한 곳*으로 격리된다. 테스트하기 어려운 부분을 최대한 좁히는 것이다.

## 비결정적인 부분은 eval로

이제 서술형. 에이전트가 "lot 데이터에 공정 파라미터를 붙여줘"를 *제대로 해내는가*를 본다. 경로가 매번 달라도 상관없다 — **결과**가 맞으면 통과다. 한 번이 아니라 여러 번 돌려 합격률을 잰다.

```python
async def eval_merge_task(runs: int = 10) -> float:
    """경로는 달라도 결과가 맞는 비율을 잰다."""
    passed = 0
    for _ in range(runs):
        result_node = await run_agent("lot 데이터에 공정 파라미터를 붙여줘")
        table = replay(store, duck, result_node, base)   # base 위에 결과 상태를 접어서
        if merged_correctly(table):                      # 기준과 대조
            passed += 1
    return passed / runs        # 합격률 (예: 0.9)

# 회귀 게이트: 합격률이 기준 아래로 떨어지면 출시 막기
assert await eval_merge_task() >= 0.9
```

핵심은 채점 대상이 *대화*가 아니라 *결과 상태*라는 것이다. 에이전트가 무슨 말을 했는지, 도구를 몇 번 불렀는지가 아니라, `replay`로 접은 테이블이 맞는지를 본다. 비결정적인 *과정*을 결정적인 *결과*로 채점하는 셈이다.

## 왜 우리 설계가 테스트를 돕나

여기서 Part 4의 결정이 또 한 번 배당을 준다. 에이전트의 모든 행동이 이벤트로 적히고(2.2), 그 이벤트를 접으면 결정적 상태가 나온다(4.4). 그래서 우리는 비결정적 에이전트를 *결정적 결과*로 묶어 채점할 수 있다.

만약 상태가 대화 속에만 있었다면, 에이전트의 말투·순서까지 채점에 끌려 들어왔을 것이다. 행동을 이벤트로 떼어낸 덕에, 비결정성은 "어떤 이벤트를 쌓을지 정하는 판단"에만 남고 그 아래는 전부 객관식이 된다. **테스트하기 좋은 에이전트는 좋은 상태 설계에서 나온다.**

다음 챕터는 이 eval을 구체화한다 — 5장에서 정의한 인수 조건 TC-1~4를, 실제로 도는 테스트 코드로 옮긴다.

> ✅ **검증됨 (검증 레포) — 결정성 + eval 합격률**: 결정적 코어 `test_replay_is_deterministic`이 통과하고(`tests/test_replay.py` — 같은 이벤트를 두 번 접어 `ORDER BY ALL` 동등, 공허한 통과까지 차단), 결과 정합의 ground-truth 전체 행 대조도 닫혔다(7.2). **비결정 eval도 실행했다** — 같은 'lot_id 머지' 지시를 10회 주고 매번 replay 결과를 ground-truth(`base ⋈ params`)와 전체 행 대조한 합격률이 **10/10 = 1.00 ≥ 0.9**였다(`probes/eval_probe.py`, opus-4-8). `run_agent`는 새 세션 머지 턴, `merged_correctly`는 '대화가 아니라 결과 상태' 채점으로 구현했다. 이 task는 지시가 명확해 합격률이 높다 — 핵심은 *eval 인프라가 돌고 합격률을 실제로 잰다*는 것이고, 임계·횟수는 task 난도에 맞춰 조정한다.

## 핵심 정리

- **에이전트는 비결정적이라 `assert ==`로 못 잡는다.** 같은 요청에 도구 순서가 매번 다를 수 있다 — 객관식 채점이 안 통한다.
- **결정적 코어와 비결정 판단을 가른다.** store·`replay`·`branch`는 객관식이니 평범한 단위 테스트로. 위험의 대부분이 사실 여기 있고, 여기를 못박으면 비결정성이 한 곳으로 좁혀진다.
- **비결정 행동은 합격률 eval로.** 여러 번 돌려 *결과 상태*가 기준과 맞는 비율을 재고, 그 비율을 회귀 게이트로 쓴다 — 대화가 아니라 접은 테이블을 채점한다.
- **좋은 상태 설계가 테스트를 쉽게 만든다.** 행동을 이벤트로 떼어낸 덕에 비결정성은 판단에만 남고 그 아래는 전부 결정적이 된다.
