# 2.1 내장 도구 고르기 — 가용성 vs 권한

## 이 챕터에서 배우는 것

- 에이전트에 도구를 줄 때 *서로 다른 두 질문* — 무슨 도구가 있나(가용성)와 무엇을 하게 둘까(권한)
- 최소 권한 원칙을 SDK 옵션으로 옮기는 법 — `allowed_tools` / `disallowed_tools`
- 켜고 끄기로 안 끝나는 회색지대를 다루는 권한 콜백 — `can_use_tool`
- 분석 에이전트라면 *읽기는 넓게, 쓰기·실행은 좁게* 가야 하는 이유
- 위험한 도구를 끄는 규율이 왜 이 책 뒷부분(되돌리기)의 첫 벽돌인가

---

## 능력을 주기 전에, 못 하게 할 것부터

1장에서 우리는 `query()`와 `ClaudeSDKClient`로 에이전트를 *호출*했다. 이제 능력을 쥐어줄 차례다. SDK는 파일 읽기·쓰기, 셸 실행, 웹 접근 같은 **내장 도구(built-in tools)**를 기본으로 딸려 보낸다.

그런데 능력을 주는 첫걸음은 의외로 *빼는 일*이다. wafer 수율을 분석하는 에이전트에게 셸로 아무 명령이나 실행할 힘을 쥐어주면, 그 힘은 분석에 쓰이기 전에 사고로 먼저 쓰인다. 그래서 도구를 고를 때 우리는 두 가지를 *따로* 묻는다.

- **가용성(availability)**: 이 에이전트가 손댈 수 있는 도구가 *애초에* 무엇인가?
- **권한(permission)**: 그 도구로 *무엇까지* 하게 둘 것인가?

## 두 개의 다른 질문 — 가용성과 권한

이 둘은 신입에게 사원증을 발급하는 일과 닮았다.

**가용성**은 사원증에 등록된 출입문 목록이다. 데이터 라이브러리, 회의실엔 들어갈 수 있지만, 애초에 등록조차 안 된 문(예: 운영 DB 서버실)은 카드를 대도 반응하지 않는다. **권한**은 등록된 문 중에서도 *어떤 키가 실제로 돌아가는지*, 어떤 문은 매니저의 공동 서명이 있어야 열리는지다.

소프트웨어에서 이건 **최소 권한 원칙(principle of least privilege)** — 일을 해내는 데 꼭 필요한 만큼만 권한을 준다 — 그 자체다. 분석 에이전트의 일은 데이터를 *읽고 변환*하는 것이지, 시스템을 *휘젓는* 게 아니다. 그러니 읽기 도구는 넓게 열고, 쓰기·실행 도구는 좁게 닫는다.

> 💡 **비유의 한계 — 우리 경비원은 전화를 걸 수 있다**: 사원증은 정적이다. 등록돼 있거나 아니거나 둘 중 하나다. 도구 권한은 더 똑똑할 수 있다 — "이 문은 열되, 이번 요청이 수상하면 관리자에게 물어봐"가 가능하다. 그 동적인 판단이 아래의 권한 콜백이다.

## 위험한 도구를 끈다

가용성부터. `ClaudeAgentOptions`로 어떤 내장 도구를 허용하고 막을지 정한다.

```python
options = ClaudeAgentOptions(
    allowed_tools=["Read", "Grep", "Glob"],   # 읽기·탐색은 넓게 연다
    disallowed_tools=["Bash", "Write", "Edit"],  # 임의 실행·파일 쓰기는 끈다
)
```

`Read`·`Grep`·`Glob`은 lot CSV들을 뒤지고 읽는 데 필요하니 연다. 반면 `Bash`(임의 셸 실행), `Write`·`Edit`(임의 파일 쓰기)은 끈다. 분석 에이전트가 셸로 운영 DB에 접속하거나 작업 폴더 밖 파일을 덮어쓸 길을 *처음부터* 없애는 것이다.

> ⚠️ **끄는 것이 가장 싼 방어다.** 도구가 아예 없으면, 그 도구로 인한 사고는 *발생할 수 없다*. 정교한 권한 검사보다 "그 능력을 안 주는 것"이 언제나 더 확실하다. 의심스러우면 끄고, 필요해질 때 켠다.

## 회색지대는 콜백으로

켜고 끄기로 안 끝나는 도구가 있다. "쓰기를 *완전히* 막을 순 없지만, 우리 제어 저장소 안에만 허용하고 싶다" 같은 경우다. 이때 **`can_use_tool`** 콜백을 쓴다 — 도구가 호출되기 직전, 그 요청을 보고 허용·거부를 *그 자리에서* 판단한다.

```python
async def can_use_tool(tool_name: str, tool_input: dict, context) -> PermissionResult:
    # 쓰기는 허용하되, 제어 저장소 밖 경로면 거부
    if tool_name == "Write":
        path = tool_input.get("file_path", "")
        if not path.startswith(STORE_DIR):
            return PermissionResultDeny(message=f"제어 저장소 밖 쓰기 금지: {path}")
    return PermissionResultAllow()

options = ClaudeAgentOptions(
    allowed_tools=["Read", "Grep", "Glob", "Write"],
    can_use_tool=can_use_tool,
)
```

이제 `Write`는 켜져 있되, 경로가 `STORE_DIR` 안일 때만 실제로 돈다. 경비원이 문은 열어두되 수상한 출입은 막는 셈이다. *어떤 정책을 콜백에 담을지*가 곧 이 에이전트의 안전 설계다.

## 이 규율이 뒤에서 빛나는 곳

지금은 "안전하니까 끈다"로 들리겠지만, 이 규율은 이 책 뒷부분의 토대가 된다. 4장과 5장에서 우리는 분석 상태를 *되돌릴 수 있게* 만든다. 그런데 되돌리기가 깨끗하려면 한 가지 전제가 필요하다 — 에이전트가 *제어 밖 세상에 흔적을 남기지 않을 것*. 셸로 외부 DB에 써넣은 행은 우리가 되돌릴 수 없기 때문이다.

위험한 도구를 끄는 지금 이 선택이, 바로 그 전제를 코드로 깔아두는 첫 벽돌이다. 도구를 좁히는 건 단지 안전 때문만이 아니라, *되돌릴 수 있는 에이전트*를 만들기 위한 설계이기도 하다.

다음 챕터에선 방향을 뒤집는다. 위험한 도구를 끈 자리에, *내 비즈니스 로직을 담은 안전한 도구*를 직접 만들어 끼운다.

> ⚠️ **코드 미검증 — 검증 레포 실행 필요**: 위 `allowed_tools`/`disallowed_tools`·`can_use_tool` 시그니처와 `PermissionResultAllow`/`PermissionResultDeny` 반환 형태는 설계 초안이다. 옵션 이름과 콜백 규약은 검증 레포에서 실제 SDK 버전으로 확인해야 한다.

## 핵심 정리

- **도구 선택은 두 질문이다 — 가용성과 권한.** 무슨 도구가 있나(사원증에 등록된 문)와 무엇을 하게 둘까(어떤 키가 돌아가나)는 따로 정한다.
- **읽기는 넓게, 쓰기·실행은 좁게.** 분석 에이전트의 일은 데이터를 읽고 변환하는 것이다. `allowed_tools`로 읽기를 열고 `disallowed_tools`로 `Bash`·`Write`를 끈다 — 최소 권한 원칙 그대로다.
- **끄는 것이 가장 싼 방어다.** 없는 도구는 사고를 못 낸다. 회색지대만 `can_use_tool` 콜백으로 그 자리에서 판단한다.
- **도구를 좁히는 건 되돌리기의 전제다.** 제어 밖 세상에 흔적을 안 남겨야 4·5장의 롤백이 깨끗하다. 지금 위험한 도구를 끄는 것이 그 첫 벽돌이다.
