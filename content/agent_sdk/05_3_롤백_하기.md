# 5.3 롤백 하기 — 과거로 `current` 옮기기

## 이 챕터에서 배우는 것

- 롤백이 "지우기"가 아니라 **현재 위치를 과거로 옮기기**라는 것
- 앱이 "지금 어느 노드에 서 있나"를 들고 있는 포인터 — `current`
- 롤백 때 두 축을 함께 되돌리는 법 — 데이터는 `replay`로 접고, 대화는 *고른다*(resume / re-fork)
- 떠나온 갈래가 그대로 살아남는다는 인수 조건 — **TC-1**
- 되돌린 자리는 대개 새 분기의 출발점이 된다는 것 (5.4로 이어짐)

---

## 되돌린다는 건 지운다가 아니다

5.2에서 우리는 B 지점에서 갈래를 쳤다. 대화(`fork()`)와 데이터(새 `node`)를 한 동작으로 갈라, C라는 새 노드를 만들었다 — wafer 수율 데이터에 피처를 몇 개 얹은 갈래다. 그런데 C까지 가 보니 피처 설계가 틀렸다. B로 돌아가고 싶다.

여기서 가장 흔한 오해를 먼저 깨자. **롤백은 C를 지우는 게 아니다.** 4.2에서 못박았듯 우리 모델은 append-only다 — 한번 쌓인 건 사라지지 않는다. 롤백이 하는 일은 C를 없애는 게 아니라, *"지금 여기"라는 표시를 B로 옮기는* 것뿐이다. C는 트리에 그대로 남는다. 나중에 다시 볼 수도 있다.

이 한 끗이 이 챕터의 전부다. 되돌림은 *삭제*가 아니라 *이동*이다.

## `current` — 지금 어디 서 있나

그 "지금 여기"를 앱이 들고 있어야 한다. 우리는 그걸 **`current`**라 부른다 — 트리의 수많은 노드 중 지금 서 있는 단 하나를 가리키는 포인터다.

git을 떠올리면 정확하다. `current`는 git의 **`HEAD`**다. 커밋이 트리로 쌓여 있고, `HEAD`는 그중 지금 체크아웃된 한 점을 가리킨다. `git checkout`으로 과거 커밋에 `HEAD`를 옮겨도 떠나온 커밋이 삭제되지 않듯, `current`를 B로 옮겨도 C는 사라지지 않는다.

```python
class Store:
    def set_current(self, node_id: str) -> None:
        """'지금 여기' 포인터를 옮긴다. 트리 구조는 건드리지 않는다."""
        self._conn.execute(
            "UPDATE meta SET current_node_id = ? WHERE id = 1", (node_id,)
        )

    def get_current(self) -> str:
        row = self._conn.execute("SELECT current_node_id FROM meta WHERE id = 1").fetchone()
        return row[0]
```

`current`는 노드도 이벤트도 아니다. 그저 *어느 노드를 보고 있는지*를 가리키는 한 칸짜리 상태다. 그래서 옮기는 비용이 거의 없다.

> 💡 **비유의 한계 — 우리 과거는 GC되지 않는다**: git에서는 아무 브랜치도 가리키지 않는 커밋이 언젠가 가비지 컬렉션으로 사라질 수 있다. 우리 트리엔 그런 일이 없다. 모든 노드는 영원히 남는다 — append-only의 약속이 git보다 한 발 더 세다. 그래서 "떠나온 갈래가 사라질까" 걱정할 필요가 아예 없다.

## 롤백의 두 축 — 데이터는 접고, 대화는 고른다

5.1이 명령한 건 분명했다. 되돌릴 땐 두 축을 *함께* 되돌려야 한다. 롤백도 예외가 아니다.

**데이터 축**은 간단하다. 4.4의 `replay`를 target 노드까지만 돌리면 된다. C의 이벤트는 읽지 않으니, 테이블은 B 모양으로 돌아온다.

**대화 축**은 선택이 있다. B 시점의 대화로 돌아가는 데 두 길이 있기 때문이다.

- **resume** — B에 묶였던 세션을 *그대로 이어* 연다. "그때 그 대화를 계속하겠다."
- **re-fork** — B의 세션에서 *새 갈래*를 친다(5.2의 `fork()`). "그 지점으로 돌아가되, 거기서부턴 새 대화로."

```python
async def rollback(store, duck, target_node_id: str, *, fresh: bool = False) -> str:
    """current를 target으로 옮기고 두 축을 그 시점으로 되돌린다.
    떠나온 갈래는 지우지 않는다."""
    target = store.get_node(target_node_id)

    # 1) 데이터 축: target까지만 접는다 (C의 이벤트는 안 읽는다)
    replay(store, duck, target_node_id)

    # 2) 대화 축: 두 선택지
    if fresh:
        session_id = await fork_from(target.session_id)   # re-fork: 새 갈래
    else:
        session_id = target.session_id                    # resume: 그대로 이어

    # 3) current를 옮긴다 — 떠나온 노드는 트리에 그대로 남는다
    store.set_current(target_node_id)
    return session_id
```

언제 무엇을 고르나. **그 대화를 정말 *이어가려면* resume**이다 — B에서 멈췄던 생각을 그대로 잇는다. **B로 돌아가 *다른 길*을 갈 거면 re-fork**가 깔끔하다 — B의 원래 대화는 박제해 두고, 새 시도는 새 세션에서 시작한다. 실무에선 후자가 잦다. 되돌렸다는 건 보통 "여기서 다르게 가보자"는 뜻이라서다.

> ⚙️ **resume이 데이터 축과 어긋날 수 있는 자리**: resume으로 B 세션을 이어 연 뒤 새 머지를 하면, 그 변경은 어느 노드에 쌓여야 하나? B에 더 쌓으면 B의 역사가 오염된다. 정답은 "새 노드"이고, 그래서 롤백 다음은 대개 분기가 된다(아래). 이 경계의 정밀한 방어는 5.5에서 다룬다.

## 떠나온 갈래는 남는다 — TC-1

이게 이 챕터가 통과해야 할 인수 조건이다. **TC-1: 롤백 후에도 떠나온 갈래는 트리에 잔존한다.**

B로 롤백한 뒤 트리를 그려 보면, C는 여전히 거기 있다.

```text
$ rollback B          # current: C → B
$ show-tree
  A
  └─ B        ← current (지금 여기)
     └─ C     ← 떠나왔지만 그대로 남아 있다
```

`current`만 B로 왔을 뿐, C 노드도 C의 이벤트도 손대지 않았다. 이건 우연이 아니라 설계의 직접적 결과다 — `rollback`은 `set_current` 한 번과 `replay` 한 번뿐, 어디에도 `DELETE`가 없다. append-only 모델에서 롤백이 안전한 이유가 코드에 그대로 드러난다.

> ⚠️ **`DELETE` 없는 롤백**: 만약 롤백이 "C를 지운다"였다면, 나중에 "아까 그 C 방식이 맞았네" 하고 돌아갈 길이 사라진다. 되돌림이 또 다른 손실이 되는 것이다. 지우지 않기에, 우리는 마음 놓고 되돌린다.

## 되돌린 다음은 대개 분기다

롤백은 끝이 아니라 출발이다. B로 돌아온 건 보통 거기서 *다르게 가보려는* 것이다. B에서 lot_id로 머지했던 걸 이번엔 wafer_id로 머지해 보는 식이다 — 그 새 머지를 하는 순간, 그건 B 아래 새 노드 — D — 가 된다. 5.2의 분기 그대로다.

그럼 트리엔 B 아래 C와 D가 나란히 매달린다. 둘 다 살아서, 둘 다 B를 부모로 본다. 이 **공존**을 어떻게 다루고, 그 사이를 어떻게 오가며, `current`가 왜 늘 하나여야 하는지 — 그게 다음 챕터다.

> ⚠️ **코드 미검증 — 검증 레포 실행 필요**: 위 `set_current`/`get_current`/`rollback`은 설계 초안이다. `meta` 테이블의 단일 행 보장, `fork_from`의 실제 시그니처, resume 후 새 변경의 노드 귀속은 검증 레포에서 돌려 확인해야 한다.

## 핵심 정리

- **롤백은 삭제가 아니라 이동이다.** `current` 포인터를 과거 노드로 옮길 뿐, 떠나온 갈래는 트리에 그대로 남는다 — git의 `HEAD`를 옮기는 것과 같되, 우리 과거는 GC되지 않아 더 안전하다.
- **두 축을 함께 되돌린다.** 데이터는 target까지 `replay`로 접고, 대화는 resume(이어가기)이나 re-fork(새 갈래로)로 *고른다*. 되돌려 다르게 갈 거면 re-fork가 깔끔하다.
- **TC-1 — 떠나온 갈래는 잔존한다.** `rollback`에 `DELETE`가 없다는 게 그 보증이다. 지우지 않기에 마음 놓고 되돌린다.
- **롤백 다음은 대개 분기다.** B로 돌아와 다르게 가면 B 아래 D가 생기고, C와 D가 공존한다 — 5.4의 주제로 곧장 이어진다.
