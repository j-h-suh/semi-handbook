# 2.2 커스텀 도구로 내 로직 노출

## 이 챕터에서 배우는 것

- 위험한 내장 도구를 끈 자리에, *내 비즈니스 로직*을 안전한 도구로 끼우는 법
- 함수 하나를 에이전트가 부를 수 있는 도구로 바꾸는 `@tool`
- 도구를 묶어 등록하고 이름 공간을 붙이는 `create_sdk_mcp_server`
- 커스텀 도구가 왜 *유일한 통로*여야 하는가 — 모든 변경이 한 길로 흐를 때 얻는 것
- 좋은 도구의 결 — 한 도구 한 책임, 또렷한 설명, 입력 검증

---

## 끈 자리에 무엇을 끼우나

2.1에서 우리는 `Bash`와 `Write`를 껐다. 그런데 에이전트는 여전히 *일을 해야* 한다 — lot 테이블에 공정 파라미터를 lot_id로 머지하고, wafer 수율 컬럼의 결측을 버리고, 피처를 얹어야 한다. 임의 셸을 막았으니, 그 일들을 할 *다른 길*을 줘야 한다.

그 길이 **커스텀 도구(custom tool)**다. 에이전트에게 "셸을 줄 테니 알아서 해"가 아니라, "머지는 이 버튼, 결측 제거는 저 버튼"을 쥐어준다. 버튼 하나하나가 우리가 직접 짠, 안전하고 또렷한 연산이다.

## 버튼이 달린 패널 — `@tool`

비유하자면, 에이전트에게 부엌 전체를 내주는 대신 **버튼이 달린 제어 패널**을 준다. 부엌(임의 셸·SQL)을 통째로 주면 못 할 게 없지만 그만큼 사고도 못 막는다. 패널에는 우리가 라벨을 붙인 버튼만 있다 — `merge`, `drop_nulls`. 에이전트는 버튼을 누를 뿐, 화구에 직접 손대지 않는다.

엔지니어의 말로 옮기면, **우리는 에이전트가 호출할 API 표면을 설계하는 것**이다. `execute_sql()` 같은 날것을 노출하는 대신, `merge_tables()`라는 의도가 분명한 함수를 노출한다. `@tool` 데코레이터가 평범한 함수를 그 버튼으로 바꾼다.

```python
from claude_agent_sdk import tool

@tool("merge_tables", "현재 테이블에 다른 테이블을 지정한 키로 머지한다",
      {"on": str, "table": str})
async def merge_tables(args: dict) -> dict:
    on, table = args["on"], args["table"]
    node_id = store.get_current()
    # 핵심: 곧장 실행하지 않고, 먼저 '변경 이벤트'로 기록한다
    store.append_event(node_id, op="merge", payload={"on": on, "table": table})
    result = replay(store, duck, node_id)
    return {"content": [{"type": "text", "text": f"{on}로 머지 완료: {row_count(result)}행"}]}
```

`@tool`의 세 인자가 곧 버튼의 라벨이다 — 이름(`merge_tables`), 설명, 입력 스키마(`{"on": str, "table": str}`). 특히 설명은 *에이전트가 읽고* 언제 이 버튼을 누를지 판단하는 근거다. 사람용 주석이 아니라 에이전트용 사용설명서다.

> 💡 **비유의 한계 — 버튼은 미리 정해야 한다**: 자판기는 버튼이 고정이라, 우리가 *미리 떠올린* 연산만 할 수 있다. 임의 셸의 유연함은 포기하는 셈이다. 하지만 분석 파이프라인의 연산은 사실 몇 종류로 수렴한다(머지·필터·피처). 유연함을 조금 내주고 안전과 되돌림을 얻는 거래다.

## 도구가 곧 안전한 통로다

위 코드에서 가장 중요한 줄은 머지 실행이 아니라 그 앞이다.

```python
store.append_event(node_id, op="merge", payload={"on": on, "table": table})
```

에이전트는 데이터를 *직접* 바꾸지 않는다. 에이전트가 "lot_id로 공정 파라미터를 머지해줘"라고 판단해 이 버튼을 눌러도, 그 머지는 우리 도구를 통해서만 일어나고, 도구는 변경을 *먼저 이벤트로 기록한 뒤* 실행한다. 이게 결정적이다. **에이전트의 모든 데이터 변경이 단 하나의 통로로 흐르고, 그 통로가 변경을 차곡차곡 적는다.**

그래서 에이전트가 무슨 머지를 하든, 그건 자동으로 *되돌릴 수 있는* 변경이 된다. 4장에서 상태를 "이벤트의 누적"으로 표현하고 5장에서 그걸 되감을 때, 그 이벤트들이 바로 여기 커스텀 도구에서 적힌 것들이다. 위험한 도구를 끄고(2.1) 안전한 통로만 연 지금 이 설계가, 뒤에서 롤백을 가능케 하는 길을 미리 깔아둔다.

> ⚠️ **날것의 도구는 통로를 우회한다.** 만약 에이전트에게 `Bash`로 직접 `DuckDB`를 두드릴 길을 열어두면, 그 변경은 이벤트로 안 적힌다 — 되돌릴 수 없는 변경이 샌다. 커스텀 도구가 *유일한* 변경 경로여야 하는 이유다.

## 도구를 등록하고 이름 붙이기

만든 도구는 묶어서 SDK에 등록한다. `create_sdk_mcp_server`로 도구 묶음을 하나의 서버로 싸고, 옵션에 매단다.

```python
from claude_agent_sdk import create_sdk_mcp_server

server = create_sdk_mcp_server(name="analysis", tools=[merge_tables, drop_nulls])

options = ClaudeAgentOptions(
    mcp_servers={"analysis": server},
    allowed_tools=["mcp__analysis__merge_tables", "mcp__analysis__drop_nulls"],
)
```

도구 이름이 `mcp__analysis__merge_tables`처럼 길어진 데 주목하자. `mcp__<서버이름>__<도구이름>` 꼴로 이름 공간이 붙는다. 2.1에서 배운 `allowed_tools`에 이 전체 이름을 넣어야 에이전트가 실제로 쓸 수 있다 — 만들었다고 자동으로 켜지진 않는다.

## 좋은 도구의 결

마지막으로, 버튼을 잘 만드는 몇 가지.

- **한 도구는 한 책임.** `merge_tables`는 머지만, `drop_nulls`는 결측 제거만. 한 도구가 여러 일을 하면 에이전트가 언제 누를지 헷갈리고, 이벤트도 뭉뚱그려진다.
- **설명은 에이전트가 읽는다.** "현재 테이블에 다른 테이블을 지정한 키로 머지한다"처럼, *언제 쓰는지*가 드러나게 쓴다.
- **입력은 검증한다.** `on`이 실제 컬럼인지, `table`이 허용된 테이블인지 도구 안에서 확인한다. 외부에서 들어온 값을 그대로 SQL에 흘리지 않는다(7.3에서 더).

이렇게 내 로직을 도구로 노출했다. 그런데 그 로직이 이미 *다른 시스템*(사내 DB, 기존 API)에 살아 있다면? 매번 새로 짜는 대신 그걸 그대로 연결하는 길 — MCP — 이 다음 챕터다.

> ⚠️ **코드 미검증 — 검증 레포 실행 필요**: 위 `@tool` 시그니처·반환 형식(`{"content": [...]}`)·`create_sdk_mcp_server`·`mcp__` 이름 규칙은 설계 초안이다. 데코레이터 인자 순서와 도구 반환 스키마는 검증 레포에서 실제 SDK 버전으로 확인해야 한다.

---

## 핵심 정리

- **커스텀 도구는 에이전트에게 주는 버튼 패널이다.** 임의 셸 대신 `merge`·`drop_nulls` 같은 의도가 분명한 연산만 노출한다 — 우리가 설계하는 API 표면이다.
- **`@tool`이 함수를 도구로 바꾼다.** 이름·설명·입력 스키마를 붙이며, 그 설명은 에이전트가 *읽고* 언제 쓸지 판단하는 사용설명서다.
- **도구가 유일한 변경 통로여야 한다.** 도구가 변경을 먼저 이벤트로 적은 뒤 실행하므로, 에이전트의 모든 데이터 변경이 자동으로 되돌릴 수 있게 된다(4·5장의 토대).
- **등록은 `create_sdk_mcp_server` + `allowed_tools`.** `mcp__서버__도구` 전체 이름을 허용 목록에 넣어야 켜진다. 한 도구 한 책임, 또렷한 설명, 입력 검증이 좋은 도구의 결이다.
