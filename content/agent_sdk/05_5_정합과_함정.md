# 5.5 두 축을 어긋나지 않게 — 정합과 함정

## 이 챕터에서 배우는 것

- 분기·롤백·탐색을 다 만들고도 두 축이 *여전히* 어긋날 수 있는 자리들
- 대화 세션과 데이터 노드가 **1:1로 묶여야** 한다는 불변식, 그리고 그게 깨지는 모습
- 한쪽 축만 갈라진 상태를 *쓰기 시점에* 막는 법 (5.2가 미뤄둔 트랜잭션)
- 롤백 후 재시도가 이전 실패에 오염되지 않는다는 인수 조건 — **TC-4**
- 그래도 남는 함정을 잡는 장부 감사, 그리고 Part 8로 넘기는 스냅샷 부채

---

## 공짜에는 늘 청구서가 따른다

5.2부터 5.4까지, 우리는 두 축을 함께 움직이는 동작들을 만들었다. 분기는 둘을 함께 가르고, 롤백·`checkout`은 둘을 함께 옮긴다. 잘 굴러간다.

그런데 "함께"라는 말에는 늘 *함께가 깨지는 순간*이 숨어 있다. 분기 도중 한 축만 성공하면? 한 세션이 실수로 두 노드에 묶이면? 롤백해서 다시 머지했는데 옛 갈래의 흔적이 새 갈래에 묻어 들어오면? 5.1이 경고한 조용한 버그는 이런 *이음매*에서 되살아난다. 이 마지막 챕터는 그 이음매를 하나씩 짚어 막는다. 이 책에서 가장 *꺼림칙한* 챕터이고, 그래서 가장 정직한 챕터다.

## 두 장부는 맞아야 한다 — fork↔node 1:1

회계의 복식부기를 떠올려 보자. 모든 거래는 두 장부에 동시에 적힌다 — 한쪽에 차변, 한쪽에 대변. 두 장부의 합이 어긋나면, 그건 바로 *틀렸다는 신호*다. 회계사는 장부가 맞는지(balance) 늘 확인한다.

우리 두 축이 그 두 장부다. **데이터 노드 하나에는 대화 세션 하나가 묶인다 — 정확히 1:1.** 이 불변식이 맞아야 "지금 이 데이터에는 이 대화가 짝"이라는 게 모호하지 않다. 어긋나는 모습은 셋이다.

- **노드에 세션이 없다** — 데이터만 갈라지고 대화가 안 따라온 경우. 가장 위험하다. 데이터 갈래는 멀쩡해 보이는데 딛고 설 대화가 없다.
- **세션에 노드가 없다** — 대화만 갈라진 경우. 떠 있는 대화가 어느 데이터를 보는지 알 수 없다.
- **한 세션이 두 노드에 묶였다** — 1:1이 1:N으로 깨진 경우. 한 대화가 두 데이터 상태를 가리켜 좌표가 흔들린다.

> 💡 **비유의 한계 — 우리는 사후 정산이 아니라 사전 차단을 노린다**: 회계 장부는 보통 *나중에* 맞춰 본다(월말 결산). 우리는 두 가지를 같이 한다 — 쓰는 *순간* 어긋남을 막고(트랜잭션), 그래도 새어 나온 어긋남을 *감사*로 잡는다. 사전 차단과 사후 감사, 둘 다.

## 한쪽만 갈라진 상태를 막는다

5.2에서 `branch`를 보며 ⚠️로 약속했다 — "한 축은 성공하고 다른 축은 실패하는 경우를 막지 못한다, 그 방어는 5.5에서." 이제 갚는다.

문제의 본질은 분기가 *두 시스템*에 걸쳐 있다는 것이다. 데이터 노드는 SQLite에, 대화 세션은 SDK 쪽에 만들어진다. 둘을 한 트랜잭션으로 완벽히 묶는 건 어렵다. 그래서 순서로 푼다. **실패할 수 있는 외부 작업(`fork`)을 먼저 하고, 우리 장부(SQLite)는 맨 마지막에 한 트랜잭션으로 커밋한다.**

```python
async def branch(store, parent_node_id: str, branch_prompt: str, note: str) -> str:
    parent = store.get_node(parent_node_id)
    if parent.session_id is None:                    # 부모가 세션에 묶여 있어야 분기 가능
        raise ValueError(f"부모에 세션 없음: {parent_node_id}")

    # 1) 먼저 실패할 수 있는 외부 작업: 대화 세션 fork
    #    (5.2의 fork — 검증 레포에선 주입해 stub으로 시험한다)
    forked_session_id = await fork_and_get_id(parent.session_id, branch_prompt)

    # 2) 그다음 우리 장부를 한 트랜잭션으로: 노드 생성 + 1:1 바인딩 + 분기 사유(5.2)
    with store.transaction():
        new_node_id = store.create_node(parent_id=parent_node_id)
        store.bind_session(new_node_id, forked_session_id)
        store.append_event(new_node_id, op="branch_reason",
                           payload={"from": parent_node_id, "note": note})

    # 3) 새 노드로 current를 옮긴다 — 분기 쳤으니 이제 거기 선다
    store.set_current(new_node_id)
    return new_node_id
```

이 순서가 핵심이다. `fork`가 실패하면 우리 트리는 *아예 손대지 않은* 상태로 남는다 — 반쪽 노드가 안 생긴다. SQLite 트랜잭션이 실패하면 노드와 바인딩이 *함께* 무효가 된다 — 둘 다 또는 둘 다 아님.

> ⚙️ **남는 잔여물 — 고아 세션은 덜 나쁘다**: `fork`는 됐는데 SQLite 커밋이 깨지면, 노드 없는 세션이 하나 떠돌 수 있다. 하지만 이건 *덜 위험한* 쪽이다 — 노드 없는 세션은 트리에 안 나타나니 분석에 끼어들지 않는다. 진짜 위험한 건 반대, *세션 없는 노드*다. 그래서 위험한 쪽을 0으로 만들고, 덜 나쁜 잔여물(고아 세션)은 주기적 청소(GC)가 회수한다. `audit`은 *위험한* 어긋남 — 세션 없는 노드·1:N 바인딩 — 을 잡고, 노드 없는 세션은 트리에 안 나타나니 청소가 따로 맡는다.

## 머지 재시도는 깨끗해야 한다 — TC-4

가장 미묘한 함정이다. C에서 lot_id로 머지했다 실패해서 B로 롤백하고, D에서 wafer_id로 다시 머지했다. 이때 **D의 결과에 C의 흔적이 조금이라도 묻으면 안 된다.** 만약 C에서 만든 임시 컬럼이나 잘못 붙은 행이 D에 새어 들어오면, 재시도는 깨끗한 재시도가 아니라 *오염된* 재시도가 된다. 이게 인수 조건 **TC-4**다.

다행히 우리 모델이 이걸 구조적으로 보장한다. D의 상태는 `replay(D)`로 만들어지고, `replay`는 D의 *조상만* 따라 접는다(4.4). D의 조상은 B와 A뿐 — **C는 D의 조상이 아니다.** C의 이벤트는 읽히지 않는다. 그러니 오염될 길이 없다.

```python
# TC-4: 롤백 후 재시도가 깨끗한가
await rollback(store, duck, B, base)                 # C → B
D = await branch(store, B, "wafer_id로 다시 머지", "wafer_id 가설")  # D ← B (C는 조상 아님)

cols = columns_of(duck, replay(store, duck, D, base))
assert "lot_id" in cols          # D는 wafer_id 기준이지만 원본 키는 살아 있고
assert "c_temp_feature" not in cols   # C에서만 만든 흔적은 단 하나도 없다
```

> ⚠️ **오염은 보통 "공유 상태"에서 샌다.** 만약 우리가 append-only가 아니라 한 테이블을 제자리에서 고쳐 썼다면, C가 남긴 변경이 D에서도 보였을 것이다. TC-4가 공짜로 통과하는 건 4.2의 결정 — 갈래마다 상태를 *접어서 새로* 만든다 — 덕분이다. 설계가 테스트를 미리 통과시킨 셈이다.

## 남는 함정 — 장부 감사와 스냅샷

사전 차단을 다 해도, 운영 중엔 어떻게든 어긋남이 샌다. 그래서 장부를 주기적으로 맞춰 보는 **감사(audit)**를 둔다.

```python
def audit(store) -> list[str]:
    """두 축이 1:1로 맞는지 장부를 맞춰 본다. 빈 리스트면 정상."""
    problems = []
    for node, _ in store.walk_preorder():            # 트리의 모든 노드를 훑는다
        if node.parent_id is not None and node.session_id is None:
            problems.append(f"{node.id}: 세션 없는 노드 (위험: 한쪽만 분기)")
    for session_id, node_ids in store.sessions_to_nodes().items():
        if len(node_ids) > 1:
            problems.append(f"{session_id}: 노드 {node_ids}에 중복 바인딩 (1:1 위반)")
    return problems
```

`audit`이 빈 리스트를 주면 두 장부가 맞는 것이다. 무엇이 어긋났는지 *이름까지* 짚어 주니, 6장에서 이 감사를 hook 신호와 엮어 상시 관측으로 끌어올린다.

마지막 함정 하나는 여기서 닫지 않고 넘긴다. **스냅샷 캐시(4.4)가 이벤트 로그와 어긋나는 경우** — 캐시를 무효화하지 않은 채 로그가 더 쌓이면, 접은 결과가 거짓이 된다. 이건 정합이라기보다 *캐시 수명 관리* 문제라, 기술부채로 8.2에서 정면으로 다룬다.

이로써 Part 5가 닫힌다. 5.1에서 "두 축을 하나로 묶는다"고 한 약속을, 분기(5.2)·롤백(5.3)·공존(5.4)·정합(5.5)으로 지켰다. 심장은 뛴다. 다만 우리는 그 옆에 감사관을 한 명 세워 두고 다음으로 간다.

> ✅ **검증됨 (검증 레포)**: `branch`의 순서(외부 `fork` 먼저 → 장부 한 트랜잭션 → `current` 이동)·원자성(`fork` 실패 시 트리 무변경)·`audit`(세션 없는 노드 + 1:N)·`sessions_to_nodes`·**TC-4(재시도 무오염)**를 harness로 확인했다(test_ops·test_store·test_acceptance). 단 검증은 **stub fork** 기준 — **실제 `fork` 실패 시 고아 세션 회수와 `store.transaction()`의 동시성/격리는 미검증**(C-5·단일 스레드 전제).

## 핵심 정리

- **두 축은 1:1로 묶인 두 장부다.** 노드 하나에 세션 하나. 세션 없는 노드(위험)·노드 없는 세션·1:N 바인딩이 어긋남의 세 모습이다.
- **분기는 외부 작업 먼저, 장부는 마지막에.** `fork`를 먼저 하고 SQLite를 한 트랜잭션으로 커밋하면, 위험한 "세션 없는 노드"가 0이 된다. 고아 세션이라는 덜 나쁜 잔여물은 주기적 청소(GC)가 회수한다.
- **TC-4 — 재시도는 깨끗하다.** D는 C를 조상으로 두지 않으니 `replay`가 C 이벤트를 읽지 않는다. append-only 결정(4.2)이 이 테스트를 미리 통과시킨다.
- **사전 차단 + 사후 감사 + 넘긴 부채.** 쓰는 순간 막고(트랜잭션), 새는 건 `audit`으로 잡고(→6장), 스냅샷-로그 정합은 기술부채로 넘긴다(→8.2).
