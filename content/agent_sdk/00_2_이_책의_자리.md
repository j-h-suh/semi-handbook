# 0.2 이 책의 자리 — 경계 긋기 + 네 갈래 선택

## 이 챕터에서 배우는 것

- 이 책이 가르치는 것(활용·통합·운영)과 *안* 가르치는 것(엔진 메커니즘)의 경계
- Claude로 무언가를 만드는 네 갈래 — Agent SDK / Client SDK / CLI / Managed Agents
- 그 넷을 *통제↔수고*의 한 축으로 읽는 법, 그리고 언제 무엇을 고르나
- 이 책이 Agent SDK를 고른 이유
- 왜 이 책이 자매서와 *직교*하는가

---

## 이 책이 가르치는 것, 안 가르치는 것

먼저 경계부터 긋자. 이 책은 **활용서**다 — Claude Agent SDK로 에이전트 앱을 어떻게 설계하고, 통합하고, 운영하고, 무엇을 고를지를 다룬다. 그 길잡이로 *되돌릴 수 있는 분석 에이전트*라는 관통 예제를 끝까지 끌고 간다. 운전석에 앉는 법을 가르친다.

이 책은 **메커니즘서가 아니다.** 에이전트 루프가 안에서 어떻게 도는지, 세션이 어떻게 복제되는지, hook이 어떤 순서로 발화하는지 — 그 *엔진 내부*는 다루지 않는다. 그건 자매서 『클로드 핸드북』의 몫이다. 같은 단어(세션·hook·도구)가 나와도, 우리는 그걸 *어떻게 쓰는가*에만 선다.

> 💡 **왜 굳이 가르고 두 권으로?**: 엔진을 *모르고도* 차를 잘 몰 수 있고, 잘 몰다 보면 엔진이 궁금해진다. 두 관심사를 한 권에 섞으면 둘 다 흐려진다. 그래서 *모는 법*(이 책)과 *엔진 원리*(자매서)를 갈라, 각자 깊게 판다. 막히면 서로를 가리킨다.

## 네 가지 탈것

Claude로 무언가를 만들 때 길은 하나가 아니다. 네 갈래가 있고, **통제↔수고**라는 한 축 위에 늘어선다 — 내가 통제할수록 내가 조립할 게 많다.

- **Managed Agents** — 택시다. 플랫폼이 루프와 호스팅을 다 운전한다. 수고는 가장 적고, 내부 통제도 가장 적다.
- **CLI(Claude Code)** — 콜택시 앱 같은 턴키 도구다. 그대로 부르면 일하고, 설정·hook으로 손보되 라이브러리처럼 깊이 끼워 넣진 않는다.
- **Agent SDK** — 내가 모는 차다. 에이전트 루프라는 구동계는 이미 얹혀 있고, 나는 그 위에 내 앱을 짓고 조향한다.
- **Client SDK** — 엔진·변속기 부품이다. 모델 호출(`messages.create`)만 주어지고, 루프는 내가 처음부터 조립한다. 통제는 최대, 조립도 최대.

## 의사결정표 — 언제 무엇

어느 탈것을 고를지는 세 질문으로 갈린다 — *루프·상태를 얼마나 통제해야 하나*, *운영 부담을 얼마나 질 텐가*, *에이전트가 제품의 핵심인가 곁가지인가*.

| 고른다 | 이럴 때 | 대가 |
|---|---|---|
| **Managed Agents** | 운영을 맡기고 싶고, 표준 동작으로 충분 | 내부·상태 모델 통제를 내준다 |
| **CLI (Claude Code)** | 코딩 보조가 그대로 필요, 빠르게 | 내 앱에 깊이 박아 넣긴 어렵다 |
| **Agent SDK** | 내 앱·내 상태 모델을 짓되 루프는 빌려 쓴다 | 앱과 운영은 내가 진다 |
| **Client SDK** | 루프 자체를 내 손으로 빚어야 한다 | 가장 많이 조립해야 한다 |

> ⚙️ **섞어 써도 된다**: 한 여행에 탈것은 하나지만, 시스템은 섞을 수 있다. 주력은 Agent SDK로 가되 특정 하위 작업만 Client SDK로 모델을 직접 부르는 식이다. 표는 *주력*을 고르는 기준이다.

## 왜 이 책은 Agent SDK인가

우리 관통 예제를 다시 보자. *내 코드 안에서*, lot 데이터를 머지하고 wafer 수율을 분석하는, *되돌릴 수 있는* 앱. 이 예제가 요구하는 통제 수준이 탈것을 정한다.

- **Managed Agents**는 안 된다. 우리 예제의 핵심인 이벤트 로그 상태 모델(4장)과 두 축을 묶는 분기(5장)는 우리가 *직접 쌓는* 층이라, 플랫폼 추상에 맡길 수 없다.
- **CLI**도 아니다. 턴키 코딩 보조이지, 우리 도메인 상태 모델을 품은 앱이 아니다.
- **Client SDK**는 과하다. 루프를 처음부터 조립하는 건 자매서의 일이고, 우리는 루프를 *빌려* 그 위에 분석 앱을 짓고 싶다.

남는 건 **Agent SDK**다. 루프·도구·세션은 빌려 쓰고, 그 위에 되돌리기라는 우리만의 층을 얹는다. 딱 우리 목표의 자리다.

## 그래서 직교 — 메커니즘은 자매서

이 선택이 책의 경계를 정한다. 우리는 루프를 *빌려 타지* 뜯어보지 않으니, 루프 내부는 이 책에 없다. 세션을 *fork해 쓰지* 복제 구현을 캐지 않는다. hook을 *걸어 신호를 뽑지* 발화 순서를 설명하지 않는다.

그래서 이 책은 자매서와 **직교**한다. 겹치는 단어가 나와도 시점이 다르다 — 자매서는 "어떻게 동작하나", 이 책은 "어떻게 부려 쓰나". 막히면 우리는 자매서를 가리키고, 계속 운전석에 남는다. 다음 챕터에서 그 운전석에 처음 앉아 본다 — 설치하고, 인증하고, 첫 호출을 돌린다.

## 핵심 정리

- **이 책은 활용서, 자매서는 메커니즘서다.** 모는 법(설계·통합·운영·선택)은 여기, 엔진 원리(루프·세션·hook 구현)는 자매서. 막히면 서로를 가리킨다.
- **네 갈래는 통제↔수고 축 위에 있다.** Managed(택시)→CLI(턴키)→Agent SDK(내가 모는 차)→Client SDK(부품). 통제할수록 조립이 는다.
- **이 책은 Agent SDK를 고른다.** 되돌리기 상태 모델을 *직접 쌓되* 루프는 빌려 쓰는 게 목표라, Managed(통제 못 함)·CLI(못 박음)·Client(과한 조립) 사이에서 Agent SDK가 맞다.
- **그래서 자매서와 직교한다.** 루프를 빌려 타지 뜯어보지 않으니, 같은 단어가 나와도 "동작 원리"가 아니라 "부려 쓰는 법"에 선다.
