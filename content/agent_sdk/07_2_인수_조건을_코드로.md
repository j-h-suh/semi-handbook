# 7.2 인수 조건을 코드로 — TC-1~4

## 이 챕터에서 배우는 것

- 5장에서 말로 약속한 인수 조건 TC-1~4를 *실행 가능한 명세*로 옮기기
- 한 픽스처에 A→B→C→(롤백 B)→D 시나리오를 세우는 법
- 네 개의 인수 조건 각각을 단언 한 줄로 못박기
- 머지 정합성을 ground truth와 대조해 검증하는 법
- 체크리스트가 증명하는 것과 *증명하지 못하는* 것

---

## 5장의 약속을 코드로

5장 내내 우리는 인수 조건을 하나씩 명명했다. 롤백해도 떠난 갈래가 남고(TC-1, 5.3), 갈래가 공존하고(TC-2, 5.4), `current`는 늘 하나고(TC-3, 5.4), 재시도가 깨끗하다(TC-4, 5.5). 말로 약속했으니, 이제 *코드로* 증명한다.

이건 단순한 테스트가 아니라 **실행 가능한 명세(executable specification)**다 — "이 시스템은 이래야 한다"는 요구를, 사람이 읽고 기계가 매번 확인하는 형태로 적는 것이다.

## 준공 검사 체크리스트

팹이 새 라인을 들이면, 가동 전 **준공 검사(acceptance test)**를 한다. "이 조건들을 실제로 보여줘야 인수한다"는 체크리스트다. 조명이 켜지나, 진공이 잡히나, 웨이퍼가 흐르나 — 하나씩 시연해 사인을 받는다.

TC-1~4가 우리 에이전트의 그 체크리스트다. 다른 점은, 우리는 체크리스트를 *코드로* 써서 *스스로 시연*하게 만든다는 것이다. 사람이 매번 손으로 확인하지 않아도, 테스트가 그 검사를 대신 돈다(8.1의 CI에서).

## 한 픽스처에 시나리오를 세운다

네 조건 모두 같은 무대 위에서 검사한다. 5장의 그 시나리오 — A에서 시작해 B까지 머지하고, C로 갈래 쳤다 B로 롤백하고, D로 다시 갈래 친 — 를 픽스처 하나로 세운다.

```python
@pytest.fixture
async def scenario(store, duck):
    """A → B → C(lot_id) → 롤백 B → D(wafer_id)"""
    A = store.create_node(parent_id=None)
    B = await branch(store, A, "공정 파라미터 머지 준비")
    C = await branch(store, B, "lot_id로 머지")
    await rollback(store, duck, B)             # current: C → B
    D = await branch(store, B, "wafer_id로 머지")
    return SimpleNamespace(A=A, B=B, C=C, D=D)
```

이 픽스처가 끝나면 트리는 B 아래 C와 D가 매달리고 `current`는 D다 — 5.4에서 그린 그 그림 그대로다. 이제 그 위에서 네 가지를 단언한다.

## 네 개의 단언

```python
async def test_tc1_rollback_keeps_branch(scenario, store):
    """TC-1: B로 롤백해도 떠나온 C는 트리에 남는다."""
    assert store.get_node(scenario.C) is not None      # C는 살아 있다

async def test_tc2_branches_coexist(scenario, store):
    """TC-2: B→C와 B→D가 동시에 존재한다."""
    children = set(store.children_of(scenario.B))
    assert {scenario.C, scenario.D} <= children        # 둘 다 B의 자식

async def test_tc3_single_current(scenario, store, duck):
    """TC-3: 어느 시점에도 current는 정확히 하나다."""
    assert store.get_current() == scenario.D
    await checkout(store, duck, scenario.C)
    assert store.get_current() == scenario.C           # 옮겨도 늘 단 하나

async def test_tc4_clean_retry(scenario, store, duck):
    """TC-4: D는 C의 흔적 없이 깨끗하다."""
    cols = columns_of(replay(store, duck, scenario.D))
    assert "lot_id" in cols                            # 원본 키는 살아 있고
    assert "c_only_feature" not in cols                # C에서만 만든 흔적은 없다
```

네 단언이 5장 전체의 결론을 *한 화면에* 못박는다. 각 테스트의 독스트링이 곧 명세고, `assert` 한 줄이 곧 시연이다. TC-4는 5.5에서 이미 한 번 봤지만, 거기선 예시였고 여기선 *상시 도는 회귀 게이트*다.

## 머지 정합성을 ground truth와 대조

인수 조건 넷에 더해, 머지 결과 자체가 맞는지도 검사한다. 7.1의 "결과 상태를 기준과 대조"를 머지에 적용한 것이다.

```python
async def test_merge_matches_ground_truth(scenario, store, duck):
    """D의 wafer_id 머지가 사람이 만든 정답과 행 단위로 맞는가."""
    result = replay(store, duck, scenario.D)
    expected = load_ground_truth("wafer_id_merge.parquet")
    assert_frame_equal(result, expected)
```

이 대조가 있어야 "되돌림은 잘 되는데 머지가 틀린" 사고를 잡는다. 인프라(TC-1~4)와 도메인 정답(머지 정합)을 *따로* 검사하는 게 핵심이다.

## 체크리스트가 증명하는 것과 못 하는 것

마지막으로 정직하게. 이 네 단언이 통과한다고 에이전트가 *완벽*해지는 건 아니다. 체크리스트는 *적힌 항목*을 증명할 뿐, 적지 않은 경우는 손대지 못한다.

그래서 7장은 셋이 한 묶음이다 — 결정적 코어 단위 테스트와 비결정 eval(7.1), 인수 조건 명세(7.2), 그리고 *예상 못 한* 상황에 대한 견고함(7.3). 체크리스트로 "반드시 되는 것"을 못박고, eval로 "대체로 잘하는지"를 재고, 견고함으로 "틀어질 때 안전한지"를 막는다. 다음 챕터가 그 마지막 한 겹이다.

> ⚠️ **코드 미검증 — 검증 레포 실행 필요**: 위 픽스처·TC-1~4 테스트·`assert_frame_equal` 대조는 설계 초안이다. `children_of`·`columns_of`·ground truth 픽스처 형식은 검증 레포에서 실제로 돌려 확인해야 한다.

## 핵심 정리

- **TC-1~4는 실행 가능한 명세다.** 5장에서 말로 한 약속(롤백 잔존·공존·current 단일·재시도 정합)을 사람이 읽고 기계가 매번 확인하는 코드로 옮긴다.
- **한 시나리오 픽스처 위에서 네 단언으로 검사한다.** A→B→C→롤백→D를 세우고, 각 인수 조건을 `assert` 한 줄로 못박는다 — 독스트링이 명세, 단언이 시연이다.
- **인프라와 도메인 정답을 따로 검사한다.** TC-1~4(되돌림이 잘 되나)와 머지 정합(결과가 맞나)을 분리해, "되돌림은 되는데 머지가 틀린" 사고를 잡는다.
- **체크리스트는 적힌 것만 증명한다.** 그래서 단위 테스트·eval(7.1)·견고함(7.3)과 한 묶음으로 간다.
