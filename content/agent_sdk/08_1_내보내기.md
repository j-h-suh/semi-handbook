# 8.1 내보내기 — 헤드리스·CI·컨테이너

## 이 챕터에서 배우는 것

- 대화형 개발에서 *무인 실행*으로 에이전트를 옮기는 일 — 헤드리스
- 사람이 없으니 권한을 *미리* 정리해야 한다는 것
- 컨테이너에 담을 때 무엇을 *밖*에 둬야 하는가 — 영속해야 할 단 하나
- CI에서 분석을 재현하는 법 — 저장된 이벤트 로그를 접어 검증
- 자동조종이 잘하는 일과 못 하는 일의 경계

---

## 조종석에서 자동조종으로

지금까지 우리는 에이전트를 *옆에 앉아* 돌렸다. 머지를 보고, 갈래를 치고, 비싸면 멈췄다. 대화형 개발이다.

운영은 다르다. 밤새 도는 배치 작업, CI 파이프라인의 한 단계, 컨테이너 속 무인 실행 — 사람이 매 순간 지켜보지 않는다. 비행으로 치면 **조종석에서 손으로 모는** 단계에서 **자동조종(autopilot)**으로 넘어가는 것이다.

## 자동조종은 비행계획을 미리 낸다

자동조종의 핵심은 *비행계획을 미리 낸다*는 데 있다. 조종사가 매 갈림길에서 판단하는 대신, 출발 전에 항로를 정해 둔다. 항로를 벗어나는 새 판단이 필요하면? 그건 자동조종이 못 한다 — 사람을 부른다.

헤드리스 에이전트도 같다. "이 분석을 이 순서로 — lot 로드 → lot_id 머지 → 결측 제거 → 피처"처럼 *결정을 미리 스크립트로* 박아 둔다. 탐색(어느 키가 맞을까)은 사람이 옆에 있을 때 하고, 헤드리스는 *이미 검증된 분석 레시피*를 무인으로 재현하는 데 쓴다. 이 경계를 지키는 게 첫 단추다.

> 💡 **비유의 한계 — 자동조종은 예상한 것만 한다**: 자동조종은 비행계획 안에서만 안전하다. 난기류 같은 새 상황은 결국 사람이 받는다. 헤드리스 에이전트도 *알려진* 분석엔 강하지만, 처음 보는 데이터에서 "어느 키로 머지하지?"를 무인으로 정하게 두면 위험하다. 탐색은 조종석, 재현은 자동조종.

## 권한을 미리 정리한다

사람이 없다는 건 *물어볼 데가 없다*는 뜻이다. 2.1의 `can_use_tool`이 대화형에선 "이 쓰기 허용할까요?"를 사람에게 물을 수 있었지만, 헤드리스엔 그 사람이 없다. 그래서 권한을 *출발 전에* 다 정해 둔다.

```python
options = ClaudeAgentOptions(
    allowed_tools=["mcp__analysis__merge_tables", "mcp__analysis__drop_nulls"],
    disallowed_tools=["Bash", "Write", "Edit"],
    permission_mode="default",       # 사전 허용된 도구만, 멈춰서 묻지 않는다
    can_use_tool=deny_unknown,        # 미리 정한 정책으로 자동 판단 (사람 호출 없음)
)
```

규율은 2.1과 같되 더 엄하다. 헤드리스에선 "애매하면 사람에게"가 불가능하니, **애매하면 거부**가 기본값이어야 한다. 권한을 느슨하게 열어둔 채 무인으로 돌리는 것이 가장 흔한 사고다.

> ⚠️ **무인 실행에서 권한을 넓히지 마라.** "어차피 자동이니 편하게 다 열자"는 정반대로 가야 한다. 지켜보는 눈이 없을수록 허용 목록은 *더* 좁아야 한다.

## 상태를 컨테이너 밖에 둔다

컨테이너에 담을 때 질문은 하나다 — **무엇이 영속해야 하나?** 우리 구성요소를 나눠 보자(4.4의 역할 분리 그대로).

- **이벤트 로그(SQLite)** — *반드시 영속.* 이게 단일 진실이다. 컨테이너가 죽어도 살아야 하니, 영속 볼륨에 둔다.
- **Parquet 베이스** — 불변 원본. 읽기 전용으로 마운트한다. 이미지에 굽지 않는다(90GB를 이미지에 넣을 순 없다).
- **DuckDB 작업 공간** — 휘발성. `replay`로 언제든 다시 만드니, 컨테이너와 함께 사라져도 된다.

```dockerfile
# 영속: 이벤트 로그(단일 진실). 휘발: DuckDB 작업본
VOLUME ["/data/events.db"]
# Parquet 베이스는 읽기 전용 마운트로 주입 (이미지에 굽지 않음)
# docker run -v /fab/wafer_base.parquet:/data/base.parquet:ro ...
```

핵심은 이거다. **이벤트 로그만 살아남으면, 나머지는 어디서든 다시 접을 수 있다.** 컨테이너는 일회용이고, 갈래의 역사는 볼륨에 남는다.

## CI에서 분석을 재현한다

영속 이벤트 로그의 진가가 CI에서 드러난다. 저장된 로그를 가져와 `replay`로 접으면, *그때 그 분석*이 그대로 재현된다. 그래서 CI 단계에서 7.2의 인수 테스트(TC-1~4)를 무인으로 돌릴 수 있다.

```bash
# CI 단계: 저장된 이벤트 로그를 접어 결과가 기준과 맞는지 검증
$ agent replay --events fixtures/yield_run.db --node D
$ pytest tests/acceptance/   # TC-1~4: 롤백 잔존·공존·current·재시도
```

분석이 코드처럼 *재현 가능*해진다 — 같은 이벤트 로그는 같은 테이블을 낳으니(4.4의 불변 베이스 전제), CI가 "지난번 그 wafer 수율 분석, 지금도 같은 답인가"를 매번 확인한다.

다음 챕터는 마지막 솔직한 정리다 — 이 책이 *남겨둔 부채*와, 언젠가 Managed Agents로 옮길지의 판단.

> ⚠️ **코드 미검증 — 검증 레포 실행 필요**: 위 `permission_mode` 값·`VOLUME` 구성·`agent replay` CLI는 설계 초안이다. 헤드리스 권한 모드의 정확한 이름과 컨테이너 볼륨 전략은 검증 레포에서 확인해야 한다.

## 핵심 정리

- **헤드리스는 자동조종이다 — 비행계획을 미리 낸다.** 결정을 스크립트로 박아 *검증된 레시피*를 무인 재현하는 데 쓰고, 탐색은 조종석(대화형)에 남긴다.
- **권한은 출발 전에, 더 좁게.** 물어볼 사람이 없으니 "애매하면 거부"가 기본값. 무인일수록 허용 목록은 더 좁아야 한다.
- **이벤트 로그만 영속하면 된다.** SQLite 로그는 영속 볼륨에, Parquet 베이스는 읽기 전용 마운트로, DuckDB는 휘발. 로그만 살면 나머지는 다시 접는다.
- **CI는 분석을 재현해 검증한다.** 저장된 로그를 `replay`로 접어 TC-1~4를 무인으로 돌린다 — 분석이 코드처럼 재현 가능해진다.
