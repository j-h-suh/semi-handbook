# 2.3 MCP로 기존 시스템 연결 — 커스텀 도구 vs MCP, 언제 무엇

## 이 챕터에서 배우는 것

- 능력이 이미 *다른 시스템*에 살아 있을 때, 다시 짜지 않고 연결하는 길 — MCP
- 커스텀 도구(`@tool`)와 외부 MCP 서버를 가르는 의사결정 기준
- 외부 시스템을 *읽기 전용*으로만 붙여 되돌림을 지키는 법
- 내가 만든 도구와 외부 도구를 한 에이전트에 함께 매다는 설정
- "쓰기는 내 통로, 읽기는 어디서든"이라는 운영 규율

---

## 이미 있는 걸 또 만들 텐가

2.2에서 우리는 비즈니스 로직을 `@tool`로 직접 짰다. 그런데 분석에 필요한 능력이 *이미 어딘가에 있는* 경우가 많다. 사내 데이터 카탈로그가 lot_id별 wafer 메타데이터를 API로 내주고 있고, 기존 조회 시스템이 공정 파라미터와 수율 이력을 쥐고 있다. 이걸 Python으로 다시 구현하는 건 낭비고, 곧 원본과 어긋난다.

그래서 다른 길이 있다. **MCP(Model Context Protocol)**는 외부 시스템의 능력을 에이전트에 연결하는 *표준 규약*이다. 다시 만들지 않고, 이미 있는 걸 꽂는다.

## MCP — 표준 콘센트

비유는 콘센트다. 2.2의 커스텀 도구가 *가전을 직접 만드는* 일이라면, MCP는 *이미 있는 가전을 벽 콘센트에 꽂는* 일이다.

콘센트가 표준이라는 게 핵심이다. 시스템마다 다른 배선을 납땜하는 대신, MCP라는 규격에 맞춰 한 번 꽂으면 된다. 카탈로그 시스템이 MCP 서버를 내주면, 우리는 그 서버를 옵션에 한 줄로 매단다 — 내부 동작을 몰라도.

> 🔬 **Deep Dive — MCP는 안에서 어떻게 말을 주고받나?**
>
> SDK가 MCP 서버와 어떤 메시지 규약으로 도구 목록을 받아오고 호출을 주고받는지 — 그 *프로토콜 내부*는 엔진의 일이다. 자매서 『클로드 핸드북』의 MCP 부분에 있다. 이 책은 *어떤 서버를 어떤 권한으로 꽂을지*만 정한다.

> 💡 **비유의 한계 — 표준 콘센트가 안전을 주진 않는다**: 콘센트가 규격이어도, 꽂는 가전이 위험하면 위험한 채로 돌아간다. MCP는 *연결*을 표준화할 뿐 *안전*을 보장하진 않는다. "운영 DB에 써넣는" 외부 서버를 꽂으면, 2.1에서 막았던 그 위험이 MCP라는 새 문으로 들어온다. 그래서 무엇을 꽂느냐를 우리가 골라야 한다.

## 커스텀 도구 vs MCP — 언제 무엇

그럼 새 능력이 필요할 때 직접 짤까, 꽂을까. 기준은 둘이다 — *누구의 로직인가*, 그리고 *되돌릴 수 있어야 하나*.

| 상황 | 고르는 것 | 이유 |
|---|---|---|
| 내 로직이고, 되돌릴 수 있어야 한다 (머지·필터) | **커스텀 도구** | 변경을 내 이벤트 통로로 흘려야 한다(2.2) |
| 이미 외부에 있고, 읽기만 한다 (lot 카탈로그 조회) | **외부 MCP** | 다시 만들 이유가 없고, 읽기는 상태를 안 바꾼다 |
| 외부에 있고, 쓰기를 한다 (운영 DB 기록) | **둘 다 아님 / 감싸기** | 제어 밖 쓰기는 되돌림을 깬다 — 분기 바깥 최종 단계로 민다 |

규칙은 한 줄로 준다. **상태를 바꾸는 일은 내 도구로, 데이터를 가져오는 일은 외부 MCP로.**

## 연결하기 — 그리고 쓰기는 막은 채로

설정은 2.2의 `mcp_servers`를 그대로 잇는다. 내가 만든 서버 옆에 외부 서버를 한 줄 더 매단다.

```python
options = ClaudeAgentOptions(
    mcp_servers={
        "analysis": in_process_server,          # 2.2: 내가 만든 도구 (쓰기 통로)
        "catalog": {                            # 외부: 기존 lot 카탈로그
            "command": "catalog-mcp",
            "args": ["--readonly"],             # 읽기 전용으로 띄운다
        },
    },
    allowed_tools=[
        "mcp__analysis__merge_tables",          # 쓰기: 내 도구만
        "mcp__catalog__lookup_lot",             # 읽기: 외부 MCP 허용
    ],
)
```

두 가지를 의도적으로 했다. 외부 카탈로그는 `--readonly`로 띄우고, `allowed_tools`엔 그 *조회* 도구만 올렸다. 카탈로그가 쓰기 도구를 내주더라도 허용 목록에 없으니 에이전트는 못 쓴다 — 2.1의 최소 권한을 외부 도구에도 똑같이 적용하는 것이다.

> ⚠️ **외부 쓰기는 되돌림의 구멍이다.** 외부 MCP로 운영 DB에 한 줄이라도 써넣으면, 그 변경은 우리 이벤트 로그 밖에서 일어난다 — 5장에서 롤백해도 그 행은 안 사라진다. 그래서 외부 시스템은 읽기로만 붙이고, 결과를 바깥에 반영하는 일은 *분기가 다 끝난 뒤의 별도 단계*로 분리한다.

## 두 종류를 한 에이전트에

이제 에이전트는 두 손을 갖는다. 한 손은 내가 만든 도구 — lot 테이블을 lot_id로 머지하고 그 변경을 되돌릴 수 있게 적는 통로. 다른 손은 외부 MCP — 카탈로그에서 wafer 수율 메타데이터를 *읽어오는* 창구. 쓰기는 안으로, 읽기는 밖에서. 이 분리가 "능력은 넓히되 되돌림은 지킨다"를 동시에 만족시킨다.

여기까지가 Part 2다 — 에이전트에 능력을 쥐어줬다. 도구를 고르고(2.1), 내 로직을 노출하고(2.2), 외부를 연결했다(2.3). 이제 이 조각들을 *사용자가 부르는 앱*으로 감쌀 차례다. 그게 다음 Part다.

> ✅ **검증됨 (검증 레포)**: in-process('analysis')와 **외부 stdio('catalog')를 함께 매달고** `allowed_tools`로 좁히는 구성을 실증했다(`probes/mcp_external_probe.py` + `probes/catalog_server.py` — FastMCP stdio 서버를 subprocess로 띄움). 외부 config `{"command": …, "args": […]}`(`McpStdioServerConfig`)·`mcp__catalog__lookup_lot` 이름 규칙·두 서버 병존이 실제로 동작해, 에이전트가 외부 도구를 호출하고 메타데이터를 받아왔다. 단 `--readonly`는 *서버 구현 의존* 관례라 여기선 '조회 도구만 노출'로 구현했다 — SDK 차원의 읽기 전용 표시는 도구 단위 `readOnly` 주석(`McpToolAnnotations`)이 따로 있다.

## 핵심 정리

- **MCP는 외부 능력을 꽂는 표준 콘센트다.** 이미 다른 시스템에 있는 능력을 다시 짜는 대신, 규격에 맞춰 연결한다. 단, 콘센트는 연결을 표준화할 뿐 안전을 주진 않는다.
- **커스텀 도구 vs MCP는 두 질문으로 갈린다.** 내 로직이고 되돌릴 수 있어야 하면 커스텀 도구, 이미 외부에 있고 읽기만 하면 MCP.
- **상태를 바꾸는 일은 내 도구로, 데이터를 가져오는 일은 외부 MCP로.** 외부 시스템은 `--readonly` + `allowed_tools`로 읽기만 허용해 되돌림의 구멍을 막는다.
- **에이전트는 두 손을 갖는다.** 내부 쓰기 통로와 외부 읽기 창구. 능력을 넓히면서도 되돌림을 지키는 분리다 — Part 2를 닫고 Part 3(앱으로 감싸기)로 간다.
