# 7.3 견고함과 안전 — 권한 정책 · 에러 · 재시도 · abort

## 이 챕터에서 배우는 것

- "절대 안 틀리게"가 아니라 *"틀려도 안전하게"*가 목표라는 것
- 권한을 안전장치로 — 2.1의 콜백을 운영 정책으로, 4.4가 약속한 식별자 화이트리스트
- 에러와 타임아웃을 가두는 법, 그리고 *무엇은 재시도하면 안 되는가*
- abort가 두 축의 정합을 깨지 않게 하는 법 (5.5의 트랜잭션이 받쳐준다)
- 신뢰는 "되는 것·명세·안전" 세 겹이라는 마무리

---

## 틀어질 때 어디로 떨어지나

7.1과 7.2에서 우리는 *잘 될 때* 잘 되는 걸 증명했다. 그런데 운영의 진짜 질문은 다른 데 있다 — **틀어질 때 어디로 떨어지나?** 네트워크가 끊기고, 도구가 멈추고, 사용자가 중간에 취소할 때.

목표는 "절대 안 틀림"이 아니다. 그건 불가능하다. 목표는 **틀려도 안전한 상태로 떨어지는 것** — 두 축이 여전히 맞물린, 일관된 트리로 착지하는 것이다.

## 인터록과 비상정지

팹 설비는 이걸 두 장치로 한다. **인터록(interlock)**은 위험한 조건이면 *애초에 안 돈다* — 챔버 문이 열려 있으면 공정이 시작되지 않는다. **비상정지(E-stop)**는 무슨 일이 생기면 *안전한 상태로* 모든 걸 멈춘다 — 아무 데나 멈추는 게 아니라 *안전*한 데로.

우리 안전장치도 둘을 닮았다. 권한은 인터록 — 허용 안 된 행동은 실행되지 않는다. 타임아웃·재시도·abort는 비상정지 계열 — 폭주를 끊되 *일관된* 상태로 멈춘다.

> 💡 **비유의 한계 — 우리는 멈추는 것만으론 부족하다**: E-stop은 일단 멈추면 된다. 우리는 더 까다롭다 — 멈추되 *두 축이 1:1로 맞은 채* 멈춰야 한다. 그냥 중단하면 반쪽 분기가 남을 수 있어서다. 멈춤보다 *어떻게 멈추느냐*가 어렵다.

## 권한을 안전장치로

2.1에서 `can_use_tool`을 "회색지대 판단"으로 소개했다. 운영에선 이게 마지막 인터록이 된다. 4.4에서 미뤘던 약속 — `payload`의 컬럼·식별자를 화이트리스트로 막는 일 — 을 여기서 갚는다.

```python
KNOWN_COLUMNS = {"lot_id", "wafer_id", "process_step", "yield"}

async def can_use_tool(tool_name: str, tool_input: dict, context) -> PermissionResult:
    if tool_name.endswith("merge_tables"):
        on = tool_input.get("on")
        if on not in KNOWN_COLUMNS:                      # 인터록: 모르는 키면 안 돈다
            return PermissionResultDeny(message=f"알 수 없는 머지 키: {on}")
    return PermissionResultAllow()
```

에이전트가 환각으로 없는 컬럼에 머지하려 들면, 인터록이 *실행 전에* 막는다. 권한은 단지 "위험한 도구 끄기"(2.1)를 넘어, 도구가 *나쁜 인자로* 불리는 것까지 막는 안전장치다. 단, 이 인터록이 *실제로 불리려면* 2.1의 두 배선이 전제다 — `merge_tables`를 `allowed_tools`에 넣지 말 것(넣으면 자동 승인돼 콜백을 건너뛴다), 그리고 `ClaudeSDKClient`로 구동할 것.

> ⚠️ **식별자는 절대 그냥 흘리지 마라.** `payload`의 컬럼·테이블 이름은 SQL에 들어간다(4.4). 화이트리스트로 막지 않으면 주입의 문이 열린다 — 외부 입력 검증의 기본이다.

## 에러·타임아웃·재시도

다음은 비상정지 계열이다. 멈춰야 할 때 멈추게 한다.

```python
try:
    async with asyncio.timeout(30):          # 멈춘 단계를 가둔다
        result = await run_step(prompt)
except TimeoutError:
    logger.warning("단계 타임아웃 — 안전 중단")
    raise
except TransientError:                        # 네트워크 같은 일시 오류만
    result = await retry_with_backoff(run_step, prompt, max_tries=3)
```

재시도에서 가장 중요한 건 *무엇을 재시도하면 안 되는가*다. 읽기(카탈로그 조회)는 몇 번을 해도 같으니 안전하다. 하지만 **머지 같은 상태 변경은 함부로 재시도하면 안 된다.** "머지가 됐는지 안 됐는지 모르는" 상태에서 다시 머지하면, 같은 머지가 두 번 들어가 데이터가 오염된다.

> ⚠️ **상태를 바꾸는 도구는 재시도 전에 "정말 안 됐나"를 확인한다.** 이벤트 로그(4.2)를 보면 그 머지 이벤트가 적혔는지 알 수 있다 — 적혔으면 성공한 것이니 재시도하지 않는다. append-only 로그가 멱등성(idempotency) 판단의 근거가 된다.

## abort는 정합을 깨지 않는다

마지막, 가장 까다로운 비상정지. 사용자가 분기 *도중에* 취소하면? fork는 됐는데 장부(노드·바인딩)가 아직 안 적힌 그 순간에 멈추면, 반쪽 분기가 남을 위험이 있다.

다행히 5.5에서 미리 막아뒀다. `branch`는 외부 작업(fork)을 먼저 하고 우리 장부를 *한 트랜잭션으로* 커밋한다. 그래서 중간에 취소돼도 트리는 "둘 다 또는 둘 다 아님"으로 떨어진다.

```python
try:
    node = await branch(store, B, "wafer_id로 머지", "wafer_id 가설")
except asyncio.CancelledError:
    # 5.5의 트랜잭션 덕에 반쪽 분기는 남지 않는다
    assert audit(store) == []        # 위험한 어긋남(세션 없는 노드)은 없다 — 안전한 착지
    raise
```

`audit`(5.5)이 빈 리스트를 준다는 건, 취소 뒤에도 *위험한* 어긋남(세션 없는 노드)이 없다는 뜻이다. 떠도는 고아 세션 정도는 남을 수 있고, 그건 GC가 청소한다(5.5). 비상정지가 *안전한* 상태로 떨어졌다. abort를 안전하게 만든 건 7.3의 새 코드가 아니라, 5.5에서 깔아둔 트랜잭션이다 — 안전은 한 곳에서 만들어지지 않고, 설계 전체에 분산돼 쌓인다.

이로써 Part 7이 닫힌다. 신뢰는 세 겹이었다. *되는 것*을 eval로 재고(7.1), *반드시 되는 것*을 명세로 못박고(7.2), *틀어질 때 안전한 것*을 안전장치로 받친다(7.3). 이제 이 믿을 만한 에이전트를 세상으로 내보낼 차례다.

> ⚠️ **부분 검증**: `can_use_tool` 인터록은 검증 레포에서 확인했다 — 막을 도구를 allowlist에서 빼고 `ClaudeSDKClient`로 구동하는 두 배선(2.1)이 전제다. 내장 도구(A5)뿐 아니라 **커스텀 MCP 도구 `merge_tables`도** allowed에서 빼면 `can_use_tool`이 받아 관장(Allow 시 실행)함을 실증했다(`probes/mcp_interlock_probe.py`). 단 `asyncio.timeout`·`retry_with_backoff`·`CancelledError`의 멱등성·취소 트랜잭션 경계는 설계 초안이며 이 책의 범위 밖이다 — 취소·재시도의 원자성은 단일 스레드 전제를 넘어 동시성 하드닝을 요구해, 다음 권으로 넘긴다.

## 핵심 정리

- **목표는 "안 틀림"이 아니라 "틀려도 안전".** 두 축이 맞물린 일관된 트리로 착지하는 것 — 팹의 인터록·비상정지처럼, 멈추되 안전한 데로 멈춘다.
- **권한은 마지막 인터록이다 — 제대로 배선했을 때.** `can_use_tool`로 도구를 끄는 것을 넘어 *나쁜 인자*(모르는 컬럼 머지)를 실행 전에 막는다(4.4의 식별자 화이트리스트). 단 막을 도구는 `allowed_tools`에서 빼고 `ClaudeSDKClient`로 구동해야 인터록이 산다(2.1).
- **상태 변경은 함부로 재시도하지 않는다.** 읽기는 안전하지만 머지는 이중 적용 위험이 있다 — 이벤트 로그로 "정말 안 됐나"를 확인하는 멱등성 판단이 먼저다.
- **abort의 안전은 5.5의 트랜잭션이 받친다.** 취소돼도 `audit`이 빈 리스트면 위험한 어긋남은 없다(고아 세션은 GC가 청소). 안전은 한 곳이 아니라 설계 전체에 쌓인다.
