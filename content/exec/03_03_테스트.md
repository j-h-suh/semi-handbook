# 3.3 테스트 — 검사가 아니라 안전망

## 이 챕터에서 배우는 것

- 자동화된 테스트가 *검사*가 아니라 *안전망*인 이유
- 단위 테스트·통합 테스트·E2E 테스트의 차이
- 왜 *변경의 자유*가 테스트에서 나오는가
- 임원이 *테스트 없음*의 비용을 인식해야 하는 이유

## 데모가 망한 날

리팩토링 회의 다음 달, 우리는 첫 잠재 고객사와의 데모를 잡았다. 작은 팹 회사였지만, 잘 되면 첫 매출이 될 수 있었다. 데모 일정은 화요일 오후 2시였다.

화요일 오전 11시. 진 팀장이 마지막 점검을 하던 중, INFER가 데이터를 받아들이지 못했다. 화면에 *Error: NoneType has no attribute 'columns'* 라는 메시지가 떴다.

진 팀장이 30분을 디버깅했다. 원인이 보였다 — 어제 서 상무가 모델 부분에 작은 변경을 했고, 그 변경이 *예상하지 못한 케이스*에서 데이터를 None으로 반환하고 있었다. 모델 자체는 잘 돌아갔다. 다만 그 한 가지 케이스에서.

12시 30분. 진 팀장이 임시로 패치를 만들었다. 1시 50분. 데모 환경에 배포 완료.

2시. 고객사가 줌에 들어왔다. INFER이 잘 돌아갔다. 다행히.

저녁에 회고 회의가 잡혔다.

## "내 모델은 검증 다 했어"

회고 회의는 5시에 시작됐다. 김 고문이 진행했다.

"오늘 11시 사건부터 정리해보죠. 진 팀장님, 무슨 일이었어요?"

진 팀장이 차분히 설명했다. 변경 → 데모 실패 → 1시간 디버깅 → 임시 패치 → 데모 직전 통과. 그가 사실관계만 짚었다.

서 상무가 끼어들었다. "내 모델은 검증 다 했어. 데이터 부분 문제잖아."

김 고문이 그를 봤다. "서 상무님, *검증* 하셨다는 게 무엇인가요?"

"내가 직접 데이터 넣어보고 결과 확인했지."

"몇 번이요?"

"...몇 번이라니. 한 번이면 되잖아."

김 고문이 짧게 침묵했다. 그리고 답했다.

"그건 *검증*이 아니라 *수동 확인*이에요. 단위 테스트와는 다른 일입니다."

"무슨 소리야?"

김 고문이 화이트보드 앞으로 갔다.

```
[수동 확인]                    [자동화된 단위 테스트]

한 번 실행, 한 번 확인          매 변경마다 자동 실행
사람이 안 보면 끝               기계가 본다, 24/7
케이스 1~2개                    케이스 수십~수백 개
변경 후 다시 확인 안 함         변경 후 자동으로 다시 확인
```

"서 상무님 모델 부분에 *자동화된 단위 테스트가 얼마나 있는지* 여쭤봐도 될까요?"

서 상무가 답을 하지 않았다.

진 팀장이 조용히 답했다. "...제가 알기로는 0개입니다."

회의실에 침묵이 흘렀다.

"오늘 11시에 일어난 일은, *서 상무님이 어제 변경한 게 데이터 파이프라인의 한 케이스를 깬* 거예요. 그 케이스에 대한 테스트가 있었으면 *어제 자동으로 알람이 갔을* 거고요. 테스트가 없어서, 오늘 데모 3시간 전에 발견됐어요. 운이 좋았어요."

지 대표가 그날 처음 입을 열었다. "...앞으로 어떻게 해?"

## 이 장면에서 떨어진 것

### 테스트는 *검사*가 아니라 *안전망*이다

테스트라는 단어를 들으면 임원은 *QA 부서가 다 만들어진 걸 검사하는 단계*를 떠올리기 쉽다. 그건 *수동 테스트* 또는 *최종 검수*에 가깝다. SW 엔지니어가 말하는 *자동화된 테스트*는 다른 일이다.

**자동화된 테스트가 하는 일**:

- 매 코드 변경 시 *자동으로* 실행됨 (사람이 시키지 않아도)
- 통과하지 못하면 *배포가 자동으로 막힘*
- 결과적으로 *변경이 기존 동작을 깼는지* 즉시 알려줌

이 자동화 안전망이 있으면 *변경의 두려움*이 사라진다. 코드를 자유롭게 바꿀 수 있다. 망가지면 즉시 알려주니까.

세미AI에서 서 상무의 모델 코드 영역은 이 안전망이 없었다. 그래서 *작은 변경 하나*가 *데모 3시간 전 사건*까지 발견되지 않았다.

### 단위·통합·E2E — 테스트 피라미드

자동화된 테스트는 세 층으로 구성된다.

```
       [E2E (적게)]            ← 사용자가 처음부터 끝까지 시나리오
    [Integration (중간)]       ← 모듈끼리 잘 붙는지
 [Unit Test (많이)]            ← 함수 하나가 잘 동작하는지
```

- **단위 테스트(Unit Test)**: 함수 하나, 작은 단위 하나. 빠름(밀리초). 가장 많이 있어야 함.
- **통합 테스트(Integration Test)**: 모듈 여러 개가 같이 동작. 좀 더 느림(초). 적당한 양.
- **E2E(End-to-End) 테스트**: 시스템 전체. 사용자 시나리오 흉내. 느림(수십 초~분). 적게.

이 *피라미드*가 무너지면 — 즉 *E2E만 많고 단위 테스트가 없으면* — 테스트가 느리고 불안정해진다. 그러면 *테스트가 신뢰되지 않고*, 결국 *테스트 자체를 안 짜게* 된다.

### *변경의 자유*가 테스트에서 나온다

자동화된 테스트가 잘 깔린 코드와 그렇지 않은 코드는, 변경 행동 자체가 다르다.

**테스트가 잘 깔린 코드**:

- 개발자가 *과감히 리팩토링한다* — 깨지면 자동으로 알려주니까
- 새 기능 추가가 빠르다 — 기존 동작을 깰까 걱정 안 해도 됨
- 신입이 *오래된 코드*를 만지는 데 두려움이 적다

**테스트 없는 코드**:

- 개발자가 *최소한만 건드린다* — 깨질까봐
- 새 기능 추가가 느리다 — 모든 변경을 수동으로 확인해야 함
- 신입은 *그 영역은 무서워서* 안 만진다

세미AI에서 서 상무의 코드가 *그 한 사람만 만질 수 있는* 상태가 된 이유 중 하나가 바로 이것이다. 테스트가 없으니까 다른 사람이 못 만진다. 코드의 *접근권*이 *읽기*에서 멈추고 *쓰기*로 나아가지 못한다.

### TDD — Test-Driven Development

**TDD(Test-Driven Development, 테스트 주도 개발)** 는 *테스트를 먼저 짜고, 그걸 통과시키는 코드를 짜는* 방식이다. 순서가 거꾸로다.

```
일반 개발:    코드를 짠다 → 잘 되는지 확인 → 테스트를 (가끔) 짠다
TDD:         테스트를 먼저 짠다 → 실패 확인 → 통과시키는 코드를 짠다
```

TDD를 하면 *모든 코드*가 *그것을 검증하는 테스트와 함께* 생긴다. 자연스럽게 100% 가까운 테스트 커버리지가 나온다. 다만 익숙해지는 데 시간이 들고, 모든 영역에 맞는 건 아니다.

> 💡 **HW 비유**: *인라인 검사(in-line inspection)* 와 매우 닮았다. 각 공정 단계 직후에 자동 검사 장비가 검수하고, 이상 시 *즉시 정지(안돈 코드)*. 사람이 *최종 단계에서 다 검사하는* 방식보다 *각 단계마다 자동으로 검사하는* 방식이 훨씬 빠르고 안전하다.

---

## 핵심 정리

- **테스트는 검사가 아니라 안전망**: 매 변경마다 자동으로 실행되어 *동작이 깨졌는지* 즉시 알려준다.
- **테스트 피라미드 — 단위가 많고 E2E는 적게**: 피라미드가 거꾸로 되면 테스트가 신뢰를 잃는다.
- **변경의 자유는 테스트에서 나온다**: 테스트 없는 영역은 결국 *한 사람만 만지는 영역*이 된다.
- **인라인 검사의 SW 버전**: 각 단계 자동 검사 → 즉시 정지가 *최종 단계 검사*보다 안전하고 빠르다.
