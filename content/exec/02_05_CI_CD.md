# 2.5 CI/CD — 매일 출하하는 공장

## 이 챕터에서 배우는 것

- CI/CD가 무엇이고 왜 그게 *매일 일어나야* 하는가
- *배포가 일상이 된* 세계의 의미
- DevOps — 운영이 다시 개발팀 안으로 들어왔다는 변화
- 임원이 CI/CD 성숙도로 SW 조직을 진단하는 법

---

## "오늘 10번째 배포입니다"

코드리뷰 사건 며칠 후, 진 팀장이 내 자리에 와서 *"이거 한 번 보세요"* 라고 했다. 그가 내 모니터에 어떤 화면을 띄웠다. 자동차 계기판 같은 대시보드였다.

화면에 *Deploys today: 10* 이라고 적혀 있었다.

"...오늘 10번이요?"

"네. 오늘 INFER 백엔드만 10번 배포됐어요."

"무슨 의미예요? 출시를 10번 했다는 거예요?"

진 팀장이 끄덕였다. "맞아요. 새 코드가 합쳐질 때마다 자동으로 테스트가 돌고, 통과하면 운영 환경에 배포됩니다. 사람이 *배포 버튼*을 누르지 않아요. 코드가 머지되면 그 즉시 자동으로."

내가 머리를 정리하는 데 시간이 좀 걸렸다. *양산 라인이 하루에 10번 새로운 제품으로 바뀐다*는 거잖아.

"...양산 라인을 하루에 10번 바꾼다고요? 그게 어떻게 가능해요?"

진 팀장이 웃었다. "그래서 *자동화*가 있는 거예요. 사람이 매번 검사하지 않고, 시스템이 자동으로 검증하고, 문제 있으면 자동으로 롤백합니다. 어제 한 번 롤백됐었는데, 정 이사님은 그게 일어났는지도 모르셨을 거예요."

"...어제 그런 일이 있었어요?"

"네. 30초 사이에 일어났습니다. 알람도 안 갔어요. 자동이 잡아서요."

## 김 고문의 한 마디

마침 김 고문이 우리 자리로 왔다. 그가 화면을 보더니 *"좋네요, 하루에 10번"* 이라고 했다.

내가 그를 봤다. "고문님, 이게... 좋은 거예요? 자주 바뀌면 더 위험한 거 아니에요?"

김 고문이 화이트보드 쪽으로 나를 데려갔다.

"정 이사님. 직관과 정반대일 수 있어요. 들어보세요."

그가 두 회사를 비교해 그렸다.

```
[회사 A — 분기에 한 번 배포]      [회사 B — 매일 10번 배포]

분기 배포 = 큰 변경 묶음            매번 배포 = 작은 변경 1개
   ↓                                  ↓
문제 생기면 어느 변경 때문인지 모름   문제 생기면 즉시 어느 변경인지 명확
   ↓                                  ↓
복구가 며칠 걸림                     30초에 자동 롤백
   ↓                                  ↓
다음 배포가 더 무서워짐              배포가 일상이 됨
```

"자주 배포할수록 *각각의 변경 크기가 작아져서* 위험이 줄어요. 그리고 *문제가 생겼을 때 빨리 잡아내는* 자동 시스템이 받쳐줍니다. 분기에 한 번 배포하는 회사가 *덜 위험할 것 같아 보이지만*, 실제로는 *변경 한 번에 사고가 날 확률*이 훨씬 높아요. 변경이 크니까요."

나는 그 그림을 한참 봤다.

"...그러면 *배포는 신중하게*가 SW에서는 틀린 말인 거예요?"

"네. *배포는 자주, 작게*가 맞습니다."

## 이 장면에서 떨어진 것

### CI/CD가 무엇인가

두 단어가 합쳐진 약어다.

- **CI (Continuous Integration, 지속적 통합)**: 개발자들이 짠 코드를 *매일 여러 번* 한 곳에 합친다. 합치는 순간 자동으로 테스트가 돈다. 누군가의 변경이 다른 사람 코드를 깨면 즉시 알려준다.

- **CD (Continuous Delivery/Deployment, 지속적 전달/배포)**: 합쳐진 코드가 *자동으로 운영 환경에 배포*된다. *Delivery* 는 *언제든 배포 가능한 상태로 유지*, *Deployment* 는 *자동으로 배포까지 실행*.

세미AI에서 *오늘 10번 배포*는 *Continuous Deployment* 다. 코드가 머지되면 사람이 손대지 않고 그대로 운영에 올라간다.

### *작게, 자주*가 왜 더 안전한가

직관과 반대로 보이지만 SW에서는 *작게 자주*가 위험을 줄인다.

**큰 변경 한 번의 위험**:

- 어느 부분이 문제인지 추적이 어려움 (변경이 100개면 100개 중 어디인지 모름)
- 문제 발생 시 복구가 어려움 (한꺼번에 되돌리면 *되살아나야 할 변경*도 같이 되돌아감)
- 큰 배포를 *언제 할지* 정치적으로 결정해야 함 (지연·취소 빈발)
- 배포 자체가 *드문 일*이라 절차가 익숙하지 않음 (실수 확률 증가)

**작은 변경 여러 번의 안전성**:

- 문제 발생 시 *바로 그 변경 하나*만 살펴보면 됨
- 자동 롤백이 30초~분 단위로 가능
- 배포가 *일상*이라 실수 확률이 낮음
- *문제가 작을 때 빨리 잡힘*

### DevOps — 운영이 다시 개발팀 안으로

CI/CD 이전에는 *개발팀*과 *운영팀*이 분리되어 있었다. 개발팀이 코드를 짜서 *던지면* 운영팀이 *받아서 깔았다*. 두 팀 사이에 *벽*이 있었고, 사고가 나면 서로 *너희 책임이다* 라고 했다.

**DevOps** 는 그 벽을 허무는 운동이다. 개발과 운영이 *같은 팀*으로 일한다. 코드를 짠 사람이 *그 코드의 배포·운영·인시던트 대응까지* 책임진다. *너희 책임이다* 라는 말이 자동으로 무의미해진다.

> 💡 **비유**: 양산 라인을 *기획한 엔지니어*가 *라인이 멈췄을 때 새벽에도 호출되어 같이 해결하는* 구조. 라인을 만든 사람이 *내가 만든 게 어떻게 돌아가는지*를 직접 안다. 책임과 학습이 한 사람에게 모인다.

### SRE — 운영을 SW 엔지니어링으로 풀기

**SRE (Site Reliability Engineering)** 는 구글에서 시작된 분야로, *운영을 사람이 손으로 하지 않고 SW 엔지니어링으로 푸는* 접근이다. 모니터링, 알람, 자동 복구, 용량 계획을 모두 *코드*로 다룬다.

세미AI는 아직 SRE 별도 팀이 없지만, DevOps 문화 안에서 그 일을 같이 한다. 진 팀장의 팀이 매일 *오늘 10번 배포* 가 가능한 이유는 *자동화된 운영 시스템*을 같이 짰기 때문이다.

### 박스 모델에서는 게임이 달라진다

> ⚠️ **온프레 박스 모델 (1.5 참고)**: *하루 10번 배포* 는 클라우드 SaaS에서 가능한 숫자다. 우리 같은 박스 모델은 다르다. 고객사 박스에 새 버전을 배포하려면 *고객사 보안 감사·운영팀 승인·테스트 환경 검증* 을 거쳐야 한다. 빠른 회사도 분기 1회, 보수적 고객사는 연 2회가 일반적.
>
> 그렇다고 CI/CD가 무의미해지는 건 아니다. 오히려 더 중요해진다. **우리 내부에서는 매일 통합·테스트하되, 고객사 배포는 분기 1회로 묶는** 구조가 된다. 내부 CI가 부실하면 분기 배포가 *대형 사고*가 된다. 박스 모델일수록 *고객사에 나가는 한 번의 배포*가 *지난 분기 누적 변경 모두*를 한꺼번에 들고 가기 때문이다.
>
> 박스 모델 회사의 CI/CD 성숙도 신호:
> - 내부 메인 브랜치는 *언제든 고객사 배포 가능 상태* 로 유지
> - 고객사 환경 시뮬레이터(*staging box*)에서 분기 전 검증
> - 고객사별 *피처 플래그* 로 같은 코드를 다르게 동작시킴
> - 롤백 절차가 *고객사 IT팀과 합의된* 형태로 문서화

### 임원이 CI/CD 성숙도로 SW 조직을 진단하는 법

DORA(DevOps Research and Assessment)가 발표한 4가지 핵심 지표가 있다.

| 지표 | Low (위태로움) | Elite (최상위) |
|---|---|---|
| 배포 빈도 | 한 달에 1번 미만 | 하루 여러 번 |
| 변경 리드 타임 | 1개월 이상 | 1시간 이내 |
| 변경 실패율 | 60% 이상 | 5% 미만 |
| 복구 시간 (MTTR) | 1개월 이상 | 1시간 이내 |

세미AI는 *Elite* 에는 못 미치지만 *High* 수준이다. 1년 전엔 *Low* 였다.

이 네 지표가 좋은 SW 조직과 그렇지 않은 조직을 가르는 가장 단순한 기준이다.

---

## 핵심 정리

- **CI/CD = 매일 여러 번 통합하고 배포하는 자동 시스템**: *작게, 자주*가 *크게, 가끔*보다 안전하다는 SW의 직관 반전.
- **DevOps = 운영이 개발팀 안으로 다시 들어왔다**: *던지고 받는* 구조가 *같이 책임지는* 구조로.
- **SRE = 운영을 SW 엔지니어링으로**: 모니터링·알람·복구를 코드로 다룬다.
- **DORA 4지표가 SW 조직 진단의 표준**: 배포 빈도, 리드 타임, 변경 실패율, 복구 시간.
