# 7.3 하이퍼파라미터 실험 — 크기·깊이·헤드 수 바꿔보기

## 이 챕터에서 배우는 것

- 6.1의 손잡이 네 개를 돌리는 실험 하네스 짜기
- 너비·깊이·헤드 수·문맥 길이가 각각 무엇을 바꾸나
- 더 크면 더 좋다, *그러나* 어디서 한계에 부딪히나 — 과적합과 비용
- 작은 데이터의 실험이 큰 스케일로 곧장 외삽되지 않는 이유

---

## 손잡이를 돌려본다

7.2로 안정적 학습을 갖췄으니, 이제 실험이다. 6.1에서 본 손잡이 — `n_embd`(너비), `n_layer`(깊이), `n_head`(헤드 수), `block_size`(문맥) — 를 바꿔가며 검증 perplexity를 비교한다. 믹싱 콘솔의 페이더를 하나씩 올려 소리가 어떻게 변하는지 듣는 것과 같다.

```python
from minigpt import MiniGPT              # 6.3
from training import train, estimate_loss  # 7.2

configs = {
    "tiny":   dict(n_embd=64,  n_head=4, n_layer=2, block_size=128),
    "small":  dict(n_embd=128, n_head=4, n_layer=4, block_size=128),
    "wider":  dict(n_embd=256, n_head=8, n_layer=4, block_size=128),
    "deeper": dict(n_embd=128, n_head=4, n_layer=8, block_size=128),
}

results = {}
for name, cfg in configs.items():
    model = MiniGPT(vocab_size, **cfg)
    train(model, max_steps=5000)              # 7.2 의 학습 루프
    results[name] = estimate_loss(model)["val"]   # 검증 손실 (→ perplexity)
```

한 번에 하나의 손잡이만 바꾸고 나머지는 고정하는 게 원칙이다. `small`을 기준으로, `wider`는 너비만, `deeper`는 깊이만 키웠다. 그래야 변화의 원인을 한 손잡이로 돌릴 수 있다.

## 각 손잡이가 바꾸는 것

실행은 검증 레포의 몫이지만, *어떤 경향이 나타날지*는 원리로 예측할 수 있다.

- **너비 `n_embd`**: 토큰당 표현 용량이다. 키우면 각 토큰이 더 풍부한 정보를 담아, 대개 perplexity가 내려간다. 단 데이터가 작으면 금세 과적합으로 돌아선다.
- **깊이 `n_layer`**: 잔차 스트림을 정제하는 단계 수다(5.6). 깊을수록 더 추상적인 패턴을 잡지만, *수확 체감*이 뚜렷하고 학습도 까다로워진다. 2층에서 4층은 크게 좋아져도, 8층에서 16층은 미미할 수 있다.
- **헤드 수 `n_head`**: 동시에 보는 시각의 수다(5.2). `n_embd`를 나눠 갖다 보니, 너무 많으면 헤드 하나가 너무 작아져 오히려 빈약해진다. 너비와 함께 균형을 맞춰야 한다.
- **문맥 `block_size`**: 한 번에 보는 토큰 수다. 길수록 먼 의존을 잡지만, 4.3에서 본 *제곱 비용*을 그대로 치른다 — 두 배 늘리면 Attention 계산·메모리가 네 배다.

> 💡 **더 크면 더 좋다 — 일정 지점까지**: 일반적 경향은 분명하다. 데이터가 충분하면, 모델을 키울수록 검증 perplexity가 내려간다. 4.2에서 본 "스케일이 성능을 정한다"가 우리의 장난감 모델에서도 작게나마 재현된다. 문제는 *어디까지*냐다.

## 어디서 한계에 부딪히나

키우기만 하면 되는 게 아니다. 두 벽이 있다.

첫째, **과적합**이다. 데이터는 작은데 모델만 키우면, 모델이 일반화 대신 암기로 빠진다. 학습 perplexity는 계속 내려가는데 검증 perplexity가 어느 순간 *고개를 든다*(7.2). 작은 셰익스피어 코퍼스에 큰 모델을 얹으면 이 갈림이 빨리 온다.

둘째, **비용**이다. 파라미터 수는 대략 깊이 × 너비²에 비례해 늘고, 계산량도 함께 커진다. 문맥을 늘리면 제곱으로 비싸진다. 무한정 키울 수는 없고, 주어진 데이터·계산 예산 안에서 *최적점*을 찾아야 한다.

> ⚠️ **작은 실험은 큰 스케일로 곧장 외삽되지 않는다**: 두 가지를 경계하자. 하나, 손잡이를 하나씩만 돌리면 손잡이 *사이의 상호작용*을 놓친다 — 너비와 깊이는 함께 키워야 균형이 맞는 경우가 많다. 둘, 작은 데이터·작은 모델에서 본 최적점은 큰 스케일에서 *크게 이동*한다. 우리의 실험은 경향을 *보여줄* 뿐, 거대 모델의 설계도를 주지는 않는다.

그렇다면 큰 스케일에서 "모델 크기와 데이터 양을 어떻게 맞춰야 하는가"에 *원리적인* 답이 있을까. 손잡이를 감으로 돌리는 대신, 법칙으로 정할 수 있을까. 그 질문에 답한 것이 다음 장의 스케일 법칙이다.

> ⚠️ **코드 부분 검증 — 하네스 미실행.** 실험이 쓰는 `MiniGPT`·`train`은 검증 레포에서 확인됐으나(probe_1·probe_2), 이 장의 *config 스윕 자체*는 시간 비용으로 실행하지 않았다. 본문의 경향(너비·깊이 효과)은 여전히 *예측*이다.

## 핵심 정리

- **실험은 손잡이를 하나씩 돌리는 것이다.** 기준 설정에서 너비만, 깊이만 바꿔 검증 perplexity를 비교한다 — 변화의 원인을 한 손잡이로 돌리기 위해.
- **네 손잡이는 각자 다른 걸 바꾼다.** 너비(토큰당 용량), 깊이(정제 단계, 수확 체감), 헤드 수(시각의 수, 균형 필요), 문맥(먼 의존, 제곱 비용).
- **더 크면 대개 더 좋다.** 데이터가 충분하면 키울수록 perplexity가 내려간다 — 스케일의 효과가 장난감 모델에서도 재현된다.
- **두 벽이 있다.** 작은 데이터에 큰 모델은 과적합하고, 키우는 데는 비용이 든다. 예산 안의 최적점을 찾아야 한다.
- **작은 실험은 외삽되지 않는다.** 손잡이 간 상호작용과 스케일에 따른 최적점 이동 때문에, 원리적 답이 필요하다 — 다음 장의 스케일 법칙이다.
