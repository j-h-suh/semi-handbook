# 5.3 원리가 프레임워크로 — 내가 만든 것 ↔ 실제 도구

## 이 챕터에서 배우는 것

- 손으로 만든 `MiniMemory`를 기능 계층으로 다시 보기
- 그 각 계층이 실제 프레임워크의 무엇에 대응하는가 — 원리 대조
- 대조표의 빈칸과 잉여 — 프레임워크가 빠뜨리는 것, 더 하는 것
- "직접 둘 것 vs 빌릴 것"의 경계, 그리고 Part 6의 평가 프레임

---

## 5.2에서 5.3으로

5.1과 5.2에서 메모리를 손으로 지었다. 두 동사로 걷는 골격을 세우고, 4장의 갱신·시간·망각을 살로 붙였다.

이제 그것을 실제 메모리 프레임워크 옆에 놓는다. 목적은 비교 우열이 아니라 *번역*이다 — 내가 만든 부품이 저들의 어떤 부품에 해당하는지를 짚어, 어떤 도구를 보든 그 속을 읽어내는 것.

## 로제타석 (비유)

서로 다른 메모리 프레임워크는 같은 원리를 *다른 이름*으로 부른다. 누구는 "ingest", 누구는 "add", 누구는 "write"라 하지만 다 저장이다. 누구는 "conflict resolution", 누구는 "reconciliation"이라 하지만 다 무효화다.

이건 **로제타석**과 같다. 같은 내용을 세 문자로 새긴 그 비석 덕에 고대 문자가 해독됐듯, *같은 원리를 내 코드와 여러 프레임워크가 어떻게 다르게 적는지*를 나란히 놓은 대조표를 쥐면, 처음 보는 도구도 읽힌다. 우리는 5.1·5.2에서 이미 한쪽 문자(내 코드)를 새겼다. 이제 대조표를 만든다.

> 💡 **비유의 한계**: 로제타석의 세 문자는 *같은 내용*의 완전한 번역이었다. 프레임워크는 다르다 — 내 원리를 다 옮기지 않은 것도, 내가 안 만든 걸 더 하는 것도 있다. 대조표에는 빈칸과 잉여가 생기고, 바로 그 빈칸과 잉여가 평가의 핵심이다.

## 내가 만든 것을 계층으로 다시 본다

먼저 `MiniMemory`를 기능 계층으로 분해한다. 코드를 다시 읽지 말고, *무엇을 하는 부품들이었나*로 본다.

1. **인터페이스** — `remember` / `recall` / `forget` (세 동사)
2. **표현** — 텍스트 + 임베딩 벡터
3. **저장** — `list[Item]` 하나 (단일)
4. **갱신** — `subject` 기반 무효화 (덮어쓰지 않음)
5. **시간** — bi-temporal (`valid_from` / `recorded_at`)
6. **망각** — 중요도로 식히기

이 여섯 계층은 사실 *모든* 메모리 시스템의 평가 축이다. 어떤 도구든 이 여섯 자리에 무엇을 놓았는지로 읽을 수 있다.

## 대조표를 그린다

이제 각 계층을 프레임워크가 부르는 *일반 이름*과 나란히 놓는다. 특정 제품이 아니라 범주다 — 어떤 도구든 이 좌표 위 어딘가에 있다.

| 내가 만든 부품 | 프레임워크에서 부르는 범주 |
|---|---|
| `remember` / `recall` | ingest / retrieve (또는 add / search) |
| 텍스트 + 벡터 | embedding 기반 표현 |
| `list[Item]` 하나 | vector DB, 흔히 graph·relational과 묶은 poly-store(2.3) |
| `subject` 무효화 | fact update, conflict resolution, memory reconciliation |
| bi-temporal | temporal·valid-time 모델 — *가진 도구가 드물다* |
| 중요도 식히기 | decay, consolidation, TTL |

이 표가 5.3의 핵심이다. 외울 것은 이름이 아니라 *좌표*다. 새 프레임워크를 만나면 "이건 위 여섯 자리에 무엇을 채웠나"를 물으면 된다. 사용법을 익히기 전에 원리 좌표부터 찍는 것이다.

## 빈칸과 잉여

대조표를 다 그리면 두 가지가 눈에 띈다.

**빈칸** — 내가 만든 것 중 프레임워크에 *없는* 것이다. 특히 bi-temporal이 그렇다. 많은 메모리 도구가 단일 timestamp만 갖거나, 갱신을 덮어쓰기로 처리한다. 일반 챗봇 기억엔 충분할지 몰라도, 분석 메모리엔 4.3에서 본 거짓말의 씨앗이다. lot_A 수율을 92%에서 89%로 정정하는 순간 옛값이 사라져, "5월 5일엔 왜 92%로 분석했나"에 더는 답하지 못하는 것이다. 이 빈칸을 그냥 빌리면, 내가 5.2에서 애써 박은 원리가 도로 사라진다.

**잉여** — 내가 안 만든 것 중 프레임워크가 *하는* 것이다. 수억 건 규모, 동시 접근, 프로세스가 죽어도 남는 영속성, 분산. 5.2의 단일 리스트 골격이 손도 못 댄 영역이다. 이건 직접 만들면 바퀴를 다시 깎는 일이고, 빌리는 게 현명하다.

그래서 프레임워크 평가는 두 방향으로 동시에 묻는다. *내 원리의 빈칸을 만들지 않는가*(갱신·시간·망각을 제대로 하는가), 그리고 *내 골격의 잉여를 메우는가*(규모·동시성·영속을 주는가).

## 그래서 — 직접 둘 것과 빌릴 것의 경계

여기서 경계가 또렷해진다.

**원리는 내가 통제한다.** 갱신을 무효화로 다룰지, 시간을 둘로 가질지, 어떻게 잊을지 — 이건 분석의 신뢰성을 좌우하므로, 프레임워크에 맡기더라도 *그것이 내 원리대로 하는지 확인하고* 빌려야 한다. 모르고 빌리면 분석이 조용히 거짓말한다.

**인프라는 빌린다.** 규모·동시성·영속성·분산은 잘 만들어진 도구가 푼 문제다. 직접 만들면 본질이 아닌 데 시간을 쏟는다.

그러니 좋은 프레임워크 선택은 "기능이 많은 것"이 아니다. *내 원리에 빈칸을 만들지 않으면서, 내 골격의 잉여를 메우는 것*이다. 이 대조표가 그 판단의 자다.

이제 이 자를 들고 Part 6으로 간다. 거기서 실제 프레임워크들의 지형을 — 사용법이 아니라 *이 여섯 좌표 위 어디에 있는지*로 — 분류하고 평가한다.

---

## 핵심 정리

- **`MiniMemory`는 여섯 계층으로 분해된다.** 인터페이스·표현·저장·갱신·시간·망각 — 이 여섯이 모든 메모리 시스템의 평가 축이다.
- **대조표는 사용법이 아니라 원리 좌표다.** 같은 원리를 다른 이름으로 부르는 프레임워크들을, 좌표 위 위치로 읽는다.
- **대조표엔 빈칸과 잉여가 있다.** 프레임워크가 빠뜨린 원리(특히 bi-temporal)와, 내가 못 만든 인프라(규모·동시성·영속).
- **원리는 통제하고 인프라는 빌린다.** 좋은 선택은 기능 수가 아니라, 내 원리에 빈칸을 안 만들면서 내 잉여를 메우는 도구다 — 이 자를 들고 Part 6으로 간다.
