# 7.1 네이티브 — Claude의 기억 수단

## 이 챕터에서 배우는 것

- Claude가 주는 두 네이티브 수단 — 장기와 단기, 두 시간 스케일
- memory tool은 저장 구현이 아니라 `remember`/`recall` *프로토콜*이다
- context editing은 1.1의 작업대를 자동으로 위생 관리하는 단기 수단이다
- 네이티브가 비워둔 칸 — 시간·망각은 여전히 내 몫이다

---

## 6.3에서 7.1로

6.3 끝에서 말했다. 남의 프레임워크를 얹기 전에, 플랫폼이 이미 주는 것을 보라고. 에이전트를 Claude 위에서 돌린다면, 기억 수단이 이미 손안에 있을 수 있다.

Claude의 네이티브 수단은 둘이다. 그리고 이 둘은 우연히도 1.1에서 그린 그림 — 장기(벽장)와 단기(작업대) — 에 정확히 한 칸씩 들어맞는다. 하나는 세션을 넘어 지속하는 장기 기억이고, 하나는 지금 이 컨텍스트를 정돈하는 단기 위생이다.

## memory tool — remember/recall의 프로토콜

장기 쪽이 **memory tool**(`memory_20250818`, 베타)이다. 모델에게 파일 기반 기억 인터페이스를 주는 도구로, 모델은 여섯 개 명령으로 기억을 다룬다 — `view`·`create`·`str_replace`·`insert`·`delete`·`rename`.

이 여섯을 보면 5.1이 떠오를 수밖에 없다. 우리가 손으로 만든 두 동사가 여기 표준 프로토콜로 들어와 있다.

```python
# Claude memory tool의 명령 ↔ 5.1 MiniMemory의 동사 (개념적 대응)
#   create / insert / str_replace   ≈  remember   (쓰기)
#   view                            ≈  recall     (읽기)
#   delete                          ≈  forget     (지우기)
#
# 모델은 '/memories' 디렉토리에 대고 이 명령들을 호출할 뿐이다.
def handle_memory_command(command: str, path: str, **kwargs) -> str:
    # 이 함수의 '속'을 개발자가 채운다 — 저장 백엔드는 전적으로 우리 몫
    ...
```

여기 결정적 사실이 있다. memory tool은 **완전히 클라이언트 사이드**다. 모델은 "이걸 기억해"·"그걸 꺼내"라고 명령할 뿐, *어디에 어떻게 저장하는지는 개발자가 구현*한다. `/memories` 경로에 파일을 두라는 관례만 있고, 그 파일을 로컬 디스크에 둘지 DB에 둘지, 어떤 구조로 쓸지는 전부 비어 있다.

즉 Anthropic은 "기억을 어떻게 부르고 모델이 어떤 명령을 내는가"라는 *프로토콜만 고정*하고, 저장 백엔드와 시간·망각 정책은 설계자에게 남겼다. 이 책이 줄곧 말한 "원리는 남고 구현은 갈아끼운다"가 플랫폼 설계로 박혀 있는 셈이다.

## context editing — 작업대 위생

단기 쪽이 **context editing**(`clear_tool_uses_20250919` 등)이다. 컨텍스트가 설정 임계를 넘으면, 가장 오래된 도구 결과부터 자동으로 비우고 그 자리에 "치웠음" 표시를 남긴다. `keep`(최근 몇 개는 보존)·`trigger`(언제 시작)·`exclude_tools`(면제할 도구) 같은 손잡이로 조절한다.

핵심은 이게 *영속 저장이 아니라는* 점이다. 비우기는 모델에 닿기 직전 서버 쪽에서 일어나고, 원본 대화 전체는 클라이언트가 그대로 들고 있다. 어디에도 새로 저장하지 않는다 — *지금 모델에게 보일 것만* 큐레이션한다.

그래서 context editing은 장기 기억이 아니다. 1.1의 작업대를 자동으로 정돈하는 단기 위생이고, 3.3에서 본 컨텍스트 예산의 네이티브 구현이다. 4.1의 망각과 헷갈리면 안 된다 — 망각은 벽장에서 *내보내는* 것이고, 이건 작업대에서 잠깐 *치우는* 것(원본은 남는다)이다.

## 운영체제의 메모리 관리 (비유)

두 수단을 한 그림으로 묶으면 **운영체제의 메모리 관리**가 된다.

OS는 두 층을 따로 다룬다. RAM이라는 작업 공간은 페이징으로 자동 관리해, 안 쓰는 페이지를 밀어내고 필요한 걸 올린다 — context editing이 하는 일이다. 디스크라는 영속 저장은 파일시스템으로 다룬다 — `view`·`create`로 파일을 읽고 쓰는 memory tool이 하는 일이다. 두 수단은 OS의 두 메모리 계층 관리에 정확히 대응한다.

> 💡 **비유의 한계**: OS는 페이징도 파일시스템도 *전부 구현해* 준다. 디스크에 실제로 비트를 쓰는 일까지 해낸다. Claude는 거기까지 가지 않는다 — *인터페이스*만 준다. 파일시스템으로 치면 `open`·`write` 같은 호출 규약만 정하고, 그 밑의 실제 디스크(저장 백엔드)와 조각 모음·만료(시간·망각 정책)는 우리가 붙여야 한다. 반쯤 만들어진 OS를 받은 셈이다.

## 네이티브가 비워둔 칸

그러니 네이티브 수단을 정확히 보자. memory tool은 `remember`/`recall` 프로토콜과 적시 인출의 사고방식을 준다. context editing은 단기 위생을 준다. 둘 다 유용하고, Claude 위라면 공짜로 깔린다.

그러나 5.2에서 손으로 박은 것들 — bi-temporal, 무효화, 망각 — 도, 4.4가 가리킨 파생 결론 재집계도, 이 프로토콜 *안에 없다*. `/memories`에 파일을 어떤 구조로 쓸지, lot_A 수율이 92%에서 89%로 정정될 때 옛값을 어떻게 보존할지는, 명령 여섯 개 어디에도 정해져 있지 않다. 그건 비워둔 칸이고, 분석 메모리라면 반드시 채워야 할 칸이다.

그래서 Claude 네이티브 위에 분석 메모리를 올리는 길은 분명하다 — memory tool을 *인터페이스*로 받아들이되, 그 백엔드에 5.2의 bi-temporal·무효화와 4.4의 재집계를 구현해 넣는다. 네이티브 프로토콜 + 내 원리. 플랫폼이 준 절반과 내가 채운 절반이 만나는 자리다.

그리고 그 "백엔드를 채우는 일"을 아예 자동 파이프라인으로 만든 것들이 있다. 모델이 명령을 내릴 때까지 기다리지 않고, 훅으로 기억을 자동 기록·주입하는 플러그인들 — 다음 챕터다.

## 핵심 정리

- **Claude의 네이티브 수단은 둘 — 장기 memory tool, 단기 context editing.** 1.1의 벽장과 작업대에 한 칸씩 대응한다.
- **memory tool은 저장이 아니라 프로토콜이다.** 여섯 명령(`view`·`create` 등)은 `remember`/`recall`에 대응하지만, 저장 백엔드와 시간·망각 정책은 전적으로 개발자 몫이다.
- **context editing은 단기 위생이지 망각이 아니다.** 컨텍스트에서 잠깐 치울 뿐 원본은 남으며, 영속 저장이 없다 — 3.3 컨텍스트 예산의 네이티브 구현이다.
- **네이티브가 비워둔 칸은 시간과 망각이다.** 분석 메모리라면 memory tool을 인터페이스로 받되, 그 백엔드에 5.2의 bi-temporal을 채워 넣어야 한다.
