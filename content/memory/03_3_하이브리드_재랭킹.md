# 3.3 하이브리드·재랭킹과 컨텍스트 예산

## 이 챕터에서 배우는 것

- 스케일이 다른 여러 축의 점수를 *순위*로 통일해 합치는 법
- 싸고 넓은 검색 뒤에 비싸고 정밀한 재랭킹을 두는 깔때기 구조
- 컨텍스트 예산 — 떠올린 걸 다 올릴 수 없다는 1.1의 귀환
- 미리 다 올리지 않고 필요할 때 필요한 만큼만 올리는 적시 인출

---

## 3.2에서 3.3으로

3.2 끝에서 우리는 막혔다. "최근에, lot A와 연결된, 수율 이상과 비슷한 기록"이라는 한 질문이 여러 축을 동시에 원하는데, 각 축은 *따로* 후보 목록을 내놓는다. 유사도는 수율 이상과 의미가 닮은 기록을, 시간은 최근 측정을, 관계는 lot A와 같은 장비를 거친 lot들을 올린다 — 세 뭉치가 제각기다.

이 뭉치들을 하나의 순위로 합쳐야 한다. 그리고 합친 뒤에도 문제가 남는다 — 1.1에서 봤듯 작업대(컨텍스트)는 유한하니, 합친 결과를 *다* 올릴 수는 없다. 이 챕터는 그 두 가지, 합치기와 추리기다.

## 채용 깔때기 (비유)

인출 파이프라인은 **채용 깔때기**를 닮았다.

지원자가 수백 명이다. 먼저 *서류 전형*으로 수십 명을 추린다 — 싸고 넓게, 놓치지 않는 게 목표다(유사도·다축 검색). 다음 *면접*으로 몇 명까지 좁힌다 — 비싸고 정밀하게, 진짜를 가리는 게 목표다(재랭킹). 마지막으로 *자리 수만큼만* 채용한다 — 아무리 좋은 지원자라도 자리가 셋이면 셋이다(컨텍스트 예산).

세 단계가 각각 다른 일을 한다. 넓게 건지기, 정밀하게 가리기, 자리에 맞추기. 인출도 똑같이 흐른다.

## 순위로 합치기

첫 과제는 스케일이 제각각인 점수를 합치는 것이다. 유사도는 0~1의 코사인 값이고, 시간은 순서이고, 관계는 다리 수다. 이 셋을 그냥 더할 수는 없다 — 단위가 다르다.

해법은 점수를 버리고 *순위*만 쓰는 것이다. **상호 순위 융합(Reciprocal Rank Fusion, RRF)**은 각 축에서의 등수를 역수로 바꿔 더한다. 1등은 큰 점수, 꼴등은 작은 점수를 받되, 원래 점수의 스케일은 사라진다.

```python
from collections import defaultdict

def rrf(rankings: list[list[str]], k: int = 60) -> list[str]:
    """여러 축의 순위 목록을 reciprocal rank로 융합한다."""
    score: dict[str, float] = defaultdict(float)
    for ranking in rankings:
        for rank, item in enumerate(ranking):
            score[item] += 1.0 / (k + rank)  # 등수만 쓴다 — 원점수 스케일 무시
    return sorted(score, key=lambda it: score[it], reverse=True)

fused = rrf([similar_hits, recent_hits, related_hits])  # 세 축을 하나로
```

RRF의 미덕은 *강건함*이다. 점수 정규화를 고민할 필요 없이 순위만 맞추면 되고, 한 축이 망가져도(예: 유사도가 엉뚱한 걸 1등으로 올려도) 다른 축들이 표를 분산시켜 완충한다. 여러 축에서 *고루* 상위에 오른 기록이 위로 떠오른다. lot A 수율 이상을 분석할 때, "최근에 equip_X를 거친 lot A의 수율 기록"처럼 세 축 모두에서 상위인 항목이 자연스럽게 1등으로 올라오는 것이다. (코드의 `k`는 상위 쏠림을 누르는 손잡이다 — 작을수록 각 축 1등이 압도하고, `60`은 원 논문이 쓴 관습값이니 도메인에 맞춰 조정한다.)

## 비싸게 다시 매기기

융합된 상위 목록은 아직 거칠다. 여기에 **재랭킹(reranking)** — 더 비싼 판단자로 상위 몇 개만 다시 순위 매기는 단계 — 를 얹는다.

1차 검색은 싸야 한다(수만 건을 훑으니까). 그래서 거칠다. 재랭킹은 그 반대다 — 후보가 수십 개로 줄었으니, 건당 비싼 모델(질의와 기록을 함께 읽고 관련도를 매기는 판단자)을 써도 된다. 면접이 서류보다 비싸지만 소수에게만 하니 감당되는 것과 같다. 분석 메모리에서는 "이 기록이 정말 질의에 답하는가"를 LLM에게 직접 물어 재순위하는 식이 흔하다.

깔때기의 핵심은 *비용을 단계에 맞게 배분*하는 것이다. 넓은 단계는 싸게, 좁은 단계는 비싸게.

## 자리 수만큼만 — 컨텍스트 예산

재랭킹까지 끝나면 잘 정렬된 목록이 남는다. 그런데 1.1을 기억하자 — 작업대는 유한하다. 이 목록을 다 컨텍스트에 올리면 작업대가 터지고, 매 턴 재조립 비용도 커진다.

그래서 **컨텍스트 예산(context budget)** — 이 질문에 쓸 토큰 상한 — 안에서 위에서부터 채운다.

```python
def fit_budget(items: list[str], max_tokens: int) -> list[str]:
    """순위 상위부터, 예산이 허락하는 만큼만 컨텍스트에 싣는다."""
    out, used = [], 0
    for it in items:
        t = estimate_tokens(it)
        if used + t > max_tokens:
            break
        out.append(it)
        used += t
    return out
```

이게 **적시 인출(just-in-time retrieval)**의 골격이다. 메모리를 통째로 컨텍스트에 상주시키지 않고, *그 질문이 들어온 순간* 필요한 만큼만 떠올려 올린다. 작업대는 매 턴 비워지니(1.1), 어차피 매번 새로 채워야 한다 — 그렇다면 *그때 필요한 것만* 채우는 게 맞다.

> 💡 **비유의 한계**: 채용은 한 번 뽑으면 한동안 간다. 인출은 매 턴 처음부터 다시 돈다 — 작업대가 매번 비워지니까. 게다가 "자리 수"가 고정이 아니다. 간단한 질문엔 두어 개, 복잡한 분석엔 수십 개로, *그 질문에 얼마를 쓸지*를 매번 정해야 한다. 채용 깔때기에서 가져올 것은 "단계별로 좁힌다"는 구조이지, "한 번 뽑고 끝"이라는 부분이 아니다.

## 그래서 — 인출은 검색이 아니라 파이프라인이다

Part 3을 닫자. 인출은 "벡터DB에 질의 한 방"이 아니다. 넓게 건지고(다축 검색), 순위로 합치고(RRF), 비싸게 거르고(재랭킹), 예산에 맞춘다(적시 인출). 이 파이프라인 전체의 목적은 하나다 — 유한한 작업대에 *딱 필요한 것만* 올리는 것.

그런데 여기까지는 줄곧 "쌓고 떠올리는" 이야기였다. 쌓기만 하고 *지우지 않으면* 어떻게 될까. 떠올릴 후보가 무한정 늘고, 그중엔 낡고 틀린 것이 섞이며(3.1에서 본 "낡은 값"), 깔때기가 아무리 정교해도 입구가 오염된다. 그래서 다음 Part는 메모리의 반대 방향이다 — 잊기와 갱신.

## 핵심 정리

- **스케일이 다른 신호는 순위로 합친다.** RRF는 점수 정규화 없이 등수만 융합하므로 강건하고, 한 축이 망가져도 완충된다.
- **인출은 비용을 단계에 배분하는 깔때기다.** 넓은 1차 검색은 싸게, 좁은 재랭킹은 비싸게 — 면접을 소수에게만 하듯.
- **컨텍스트 예산이 마지막 관문이다.** 잘 정렬해도 작업대는 유한하니, 예산 안에서 상위만 올린다.
- **적시 인출 — 상주가 아니라 그때그때.** 작업대는 매 턴 비워지므로, 질문이 든 순간 필요한 만큼만 떠올려 올리는 게 맞다.
