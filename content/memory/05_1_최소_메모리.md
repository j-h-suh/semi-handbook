# 5.1 최소 메모리 — 저장과 인출을 손으로

## 이 챕터에서 배우는 것

- 흩어진 저장·인출 조각을 하나의 메모리 인터페이스로 묶기
- `remember`와 `recall`, 두 동사로 된 최소 골격
- 가장 작게 시작하는 이유, 그리고 이 골격에 *빠진* 것
- 왜 프레임워크 대신 손으로 한 번 지어보는가

---

## 원리에서 손으로

Part 1부터 4까지는 원리였다. 기억의 유형(1), 담는 법(2), 떠올리는 법(3), 잊고 갱신하는 법(4). 이제 손을 움직인다.

Part 5의 방식은 *얹어 가기*다. 이 챕터에서 가장 작은 — 그러나 끝에서 끝까지 동작하는 — 메모리를 짓고, 5.2에서 거기에 4장의 망각·갱신·시간을 손으로 얹고, 5.3에서 그렇게 만든 것을 실제 프레임워크와 나란히 놓는다. 그러니 지금 짓는 것은 *완성품이 아니라 출발점*이다.

## 두 동사로 충분하다

메모리의 최소 인터페이스는 동사 둘이다 — `remember`(저장)와 `recall`(인출). 쓸 때 하나, 떠올릴 때 하나. 2장에서 본 저장도, 3장에서 본 인출도, 결국 이 두 동사 뒤에 숨는다.

가장 흔한 출발점을 고르자. 시맨틱 기억을 의미 유사로 떠올리는 것 — 즉 2.1의 vector store와 3.1의 유사도 검색이다. 이 둘을 한 클래스 뒤로 묶으면, 바깥에서는 그저 "기억하고, 떠올린다"가 된다.

## 걷는 해골 (비유)

이런 최소 구현을 소프트웨어에서는 **걷는 해골(walking skeleton)**이라 부른다 — 살은 없지만 머리부터 발끝까지 *관통해 걷는* 가장 얇은 뼈대다. 화면 한 줄, DB 한 줄, 그 사이를 잇는 한 줄이 일단 끝까지 통하게 만든 것. 기능은 빈약해도 *전 경로가 동작*한다는 게 핵심이다.

우리의 해골은 `remember → 저장 → recall`이 일단 관통하는 메모리다. 살(망각·시간·다중 저장)은 그다음에 붙인다.

```python
from dataclasses import dataclass
import numpy as np

def embed(text: str) -> np.ndarray: ...  # 임베딩 모델 호출 (추상화)

@dataclass
class Item:
    text: str
    vec: np.ndarray

class MiniMemory:
    """저장과 유사도 인출만 갖춘 최소 메모리 — Part 5의 출발점."""

    def __init__(self) -> None:
        self._items: list[Item] = []

    def remember(self, text: str) -> None:
        self._items.append(Item(text=text, vec=embed(text)))

    def recall(self, query: str, k: int = 3, min_sim: float = 0.6) -> list[str]:
        q = embed(query)
        scored = sorted(
            ((self._cos(q, it.vec), it.text) for it in self._items),
            key=lambda x: x[0], reverse=True,   # 점수로만 정렬 — 5.2에서 Item으로 키워도 안전
        )
        return [text for sim, text in scored[:k] if sim >= min_sim]  # 3.1의 컷오프

    @staticmethod
    def _cos(a: np.ndarray, b: np.ndarray) -> float:
        return float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))
```

전부다. `remember`는 텍스트를 임베딩해 쌓고(2.1), `recall`은 질의에 가까운 top-k를 임계 위에서만 돌려준다(3.1). 흩어져 있던 두 챕터의 조각이 한 클래스 뒤로 들어가, 바깥에서는 두 동사로 보인다.

## 동작시켜 본다

해골이 정말 걷는지 보자.

```python
mem = MiniMemory()
mem.remember("lot_A 수율 89%로 정정")
mem.remember("equip_X 3월 교정 완료")
mem.remember("lot_B 양품률 저하 관찰")

mem.recall("수율이 낮은 lot")
# → ["lot_A 수율 89%로 정정", "lot_B 양품률 저하 관찰"]
```

`equip_X` 기록이 빠진 것을 보자 — 글자는 안 겹쳐도 의미가 수율과 멀어 임계 아래로 떨어진 것이다(3.1). 끝에서 끝까지 걷는다. 작지만 진짜 메모리다.

## 골격엔 살이 없다

그런데 이 해골은 *걷기만* 한다. 일을 잘하지는 못한다. 4장과 2장이 경고한 것들이 통째로 빠져 있다.

- **갱신이 없다.** lot_A가 89%에서 다시 87%로 정정되면, `remember`는 새 기록을 *추가*만 한다. 옛 89%와 새 87%가 둘 다 남아, `recall`에 둘 다 떠오른다. 무엇이 현재인지 모른다(4.2).
- **시간이 없다.** "5월에 내가 알던 lot_A 수율은?"을 물을 수 없다. 모든 기록이 시점 없이 평평하게 누워 있다(4.3).
- **망각이 없다.** 무한정 쌓인다. 1년 뒤 수천 건이 되면 `recall`이 노이즈에 묻힌다(4.1).
- **유사도뿐이다.** "정확히 lot_A만", "lot_A·B의 공통 장비"를 못 한다. 의미 유사 하나로는 안 되는 질문들이다(2.2·2.3).

> 💡 **비유의 한계**: 걷는 해골은 "동작한다"는 자신감을 준다. 그러나 동작하는 것과 *쓸 만한* 것은 다르다. 이 메모리는 돌아가지만, 사실이 바뀌면 거짓말하고 무한정 부푼다. 골격이 걷는다고 일꾼이 된 건 아니다 — 살을 붙이기 전까지는.

## 왜 손으로 만드나

여기서 당연한 반문이 든다. 메모리 프레임워크를 가져다 쓰면 `remember`·`recall`이 한 줄인데, 왜 굳이 손으로 짓는가.

답은 Part 6을 위해서다. 남이 만든 `remember`가 안에서 무엇을 하는지 — 갱신을 어떻게 다루는지, 시간을 기록하는지, 언제 잊는지 — 를 *평가*하려면, 그 안을 한 번 지어본 사람이어야 한다. 골격을 직접 세워보지 않으면, 프레임워크의 화려한 기능 목록 앞에서 무엇이 중요한지 가릴 눈이 안 생긴다.

그래서 다음 챕터에서 이 해골에 살을 붙인다. 방금 빠졌다고 한 네 가지 중 4장이 다룬 셋 — 갱신·시간·망각 — 을 손으로 얹는다. 그 작업이 Part 6에서 프레임워크를 꿰뚫어 보는 눈이 된다.

## 핵심 정리

- **메모리의 최소 인터페이스는 두 동사다 — `remember`와 `recall`.** 2장의 저장과 3장의 인출이 이 둘 뒤로 숨고, 바깥에서는 기억하고 떠올리는 것만 보인다.
- **걷는 해골부터 짓는다.** 살은 없어도 전 경로가 관통해 동작하는 최소 뼈대 — 유사도 저장·인출만으로 진짜 메모리가 한 번 걷는다.
- **이 골격엔 갱신·시간·망각·정확조회가 없다.** 동작하는 것과 쓸 만한 것은 다르며, 빠진 것들이 곧 5.2에서 붙일 살이다.
- **손으로 짓는 이유는 평가의 눈을 얻기 위해서다.** 직접 한 번 지어본 사람만이 남의 프레임워크가 무엇을 하고 무엇을 빠뜨리는지 가려낼 수 있다(Part 6).
