# 7.2 플러그인 — claude-mem·claude-honcho

## 이 챕터에서 배우는 것

- 네이티브와 플러그인의 갈림 — 누가 기억을 트리거하나(모델 대 훅)
- 훅 기반 자동 기록·주입의 원리, always-on이라는 성격
- 두 플러그인을 가르는 축 — 저장소를 누가 소유하나(로컬 대 클라우드)
- 자동 편의가 분석 도메인에 남기는 빈칸

---

## 7.1에서 7.2로

7.1의 네이티브 수단에는 한 가지 전제가 있었다. memory tool은 *모델이 명령을 내려야* 작동한다. 모델이 "이걸 기억해", "그걸 꺼내"라고 도구를 호출해야 기억이 움직인다.

플러그인은 그 전제를 바꾼다. 모델의 명령을 기다리지 않고, **훅(hook)** — 세션 생애의 특정 시점에 자동으로 끼어드는 장치 — 이 기억을 대신 기록하고 주입한다. 사용자도 모델도 "기억해"라고 말할 필요가 없다.

## 블랙박스처럼 (비유)

이 차이는 **블랙박스(주행 기록계)**를 떠올리면 또렷하다.

운전자는 "지금부터 기록해"라고 말하지 않는다. 블랙박스는 시동이 걸리면 늘 돌아간다. 사고가 나거나 뭔가 확인할 일이 생겼을 때 꺼내 본다. 훅 기반 자동 기록이 정확히 이렇다 — always-on이고, 명령이 필요 없으며, 나중에 필요할 때 꺼내 쓴다.

> 💡 **비유의 한계**: 단순 블랙박스는 들어오는 영상을 그냥 다 녹화한다 — 무엇이 중요한지 모른다. 실제 플러그인은 그보다 똑똑해서, 기록을 의미 요약으로 압축해 둔다. 그러나 똑똑해진 건 *압축*이지 *판단*이 아니다. 무엇이 나중에 분석에서 결정적일지, 어떤 사실이 어떤 결론을 떠받치는지(4.4)까지 아는 건 아니다. 자동으로 다 담는 편함과, 무엇이 중요한지 아는 것은 다른 문제다.

## 훅이 트리거한다

플러그인의 작동 원리는 라이프사이클 훅에 걸린다. 세션이 시작될 때, 도구가 실행된 뒤, 세션이 끝날 때 같은 시점마다 훅이 자동으로 발동한다.

**claude-mem**을 보자. 세션이 도는 동안 도구 사용을 관찰 기록(observation)으로 자동 캡처하고, 그걸 의미 요약으로 압축해 둔다. 그리고 다음 세션이 시작될 때, 관련된 과거를 자동으로 컨텍스트에 주입한다. 흥미로운 건 인출 방식이다 — 압축된 인덱스를 먼저 보여주고, 필요한 것만 펼쳐 전체를 가져오는 점진적 공개(progressive disclosure)로 토큰을 아낀다. 3.3에서 본 컨텍스트 예산의 사고가 여기서도 돈다.

요점은 이 모든 게 *모델의 자율적 명령 없이* 훅으로 일어난다는 것이다. 7.1의 네이티브가 "모델이 트리거"였다면, 플러그인은 "훅이 트리거"다.

## 두 축으로 가른다

플러그인끼리도 갈린다. 가장 큰 축은 *저장소를 누가 소유하나*다.

claude-mem은 기억을 **로컬에 자기완결적으로** 둔다 — 키워드 검색용 색인과 의미 검색용 벡터 저장을 로컬에 두고 혼자 돈다(2.3의 poly-store를 작게 구현한 모습이다). 반면 claude-honcho는 외부 메모리 서비스에 **위임**한다 — 기록과 표상 추론을 클라우드 API에 맡기고, 그 결과를 받아 쓴다.

이 축은 단순한 취향이 아니다. 로컬 소유는 데이터를 내가 쥐고 오프라인에서도 돌지만, 규모와 크로스툴 연동은 직접 감당해야 한다. 클라우드 위임은 관리형 편의와 여러 도구 간 공유를 주지만, 데이터가 외부로 나간다. 분석 데이터가 민감하거나 대용량이라면, 이 축이 선택을 가른다.

6.1의 네 축으로 둘을 함께 보면 이렇다 — 둘 다 *대화·세션 관찰*을 기억하고, 저장은 벡터 계열이며, 관리는 자동(훅)이다. 그리고 시간 모델은 둘 다 약하다. 대화 개인화의 계보에서 나왔기에, bi-temporal이 1등 시민이 아니다.

## 자동이 분석에 남기는 빈칸

훅 기반 자동 기록은 코딩 세션의 회고나 개인화에는 훌륭하다. 손 안 대도 쌓이고, 다음 세션에 알아서 떠오른다. 그런데 분석 메모리의 눈으로 보면 빈칸이 보인다.

- **무엇을 기억할지를 훅이 정한다.** 1.3에서 본 저장 가치 판단을 도구에 넘기는 것이다. 분석에선 "이 관찰이 어느 결론을 떠받치나"가 중요한데, 범용 훅은 그걸 모른다.
- **시간성이 약하다.** lot 수율 정정 같은 사실 변화를 bi-temporal로 보존하는 건(4.3) 대화 개인화 도구의 관심사가 아니다.
- **파생 결론 재집계(4.4)는 아예 범위 밖이다.** 결론이 원천 변화로 낡는 문제를 훅이 풀어주지 않는다.

그래서 분석 에이전트라면 층을 나누는 게 현실적이다. 플러그인은 *세션 회고·개인화 층*으로 쓰되, 분석 결론의 bi-temporal 보존은 7.1처럼 따로 둔다 — memory tool 백엔드에 5.2의 원리를 박아서. 자동의 편의와 원리의 통제를 같은 통에 섞지 않고, 역할로 가른다.

Part 7을 닫자. 네이티브든 플러그인이든, Claude가 주는 것은 결국 *인터페이스와 자동화*다. 기억을 부르는 프로토콜(7.1), 기억을 자동으로 쌓는 훅(7.2). 둘 다 값지지만, 시간·망각·재집계라는 분석의 원리는 어느 쪽도 대신해주지 않는다. 그건 우리가 직접 엮어야 한다 — 그 엮는 일을 처음부터 끝까지 해보는 것이 마지막 Part 8이다.

## 핵심 정리

- **플러그인은 훅이 트리거한다.** 7.1의 네이티브가 모델 명령에 기대는 것과 달리, 라이프사이클 훅이 자동으로 기록·주입하는 always-on 방식이다.
- **편함은 판단의 외주다.** 자동 기록은 손이 편하지만, 무엇을 기억하고 무엇이 중요한지의 판단(1.3·4.4)을 훅에 넘긴다 — 블랙박스는 압축은 해도 판단은 못 한다.
- **저장소 소유가 둘을 가른다.** claude-mem은 로컬 자기완결, claude-honcho는 클라우드 위임 — 데이터 민감도와 규모가 이 축의 선택을 정한다.
- **분석엔 층을 나눈다.** 플러그인은 회고·개인화 층으로, 분석 결론의 시간 보존은 7.1 백엔드에 5.2 원리로 — 자동 편의와 원리 통제를 역할로 가른다.
