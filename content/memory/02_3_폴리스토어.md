# 2.3 relational·FTS와 섞기(poly-store) — 무엇이 무슨 유형에

## 이 챕터에서 배우는 것

- 만능 저장은 없다 — 사실 유형마다 맞는 저장이 따로다
- 관계형 저장과 전문 검색이 벡터·그래프의 빈틈을 어떻게 메우는가
- 무엇을 무슨 저장에 넣을지 — 유형↔저장 매핑
- 하나의 사실을 여러 저장에 쓰는 poly-store와 그 대가

---

## 2.2에서 2.3으로

지금까지 저장 둘을 봤다. 의미를 담는 vector store(2.1), 관계를 담는 그래프(2.2). 그리고 매번 "이건 못 한다"는 꼬리표가 붙었다 — 벡터는 정확 조회를 못 하고, 둘 다 집계나 키워드 매칭에 약하다.

이쯤이면 패턴이 보인다. *한 저장이 다 하는 일은 없다.* 그러니 마지막 저장 챕터의 결론은 정해져 있다 — 유형마다 맞는 저장을 고르고, 그것들을 *섞는다*.

## 만능 칼은 없다 (비유)

부엌을 떠올려 보자. 만능 칼 하나로 버티는 요리사는 없다. 빵은 빵칼로 썰고, 회는 사시미칼로 뜨고, 다지기는 식칼로 한다. 칼마다 *잘 드는 결*이 다르기 때문이다. 만능 칼을 고집하면 빵은 으스러지고 회는 뭉개진다.

저장도 똑같다. vector store는 의미에 잘 들고, 그래프는 관계에 잘 든다. 그런데 분석 기억에는 이 둘로 안 잘리는 것이 또 있다 — *정확한 값*과 *키워드*다. 칼을 두 자루 더 꺼낼 차례다.

## 빈틈을 메우는 두 칼

**관계형 저장(relational store)**은 구조화된 값과 정확 조회·집계를 맡는다. "lot A의 정확한 수율은?", "장비별 처리 lot 수는?", "수율 90% 미만 lot만" 같은 질문 말이다. 이건 의미 유사가 아니라 *정확히 일치하고 정확히 세는* 일이고, 표와 SQL이 수십 년간 다듬어 온 영역이다.

**전문 검색(full-text search, FTS)**은 키워드 매칭을 맡는다. "로그 메시지에 `overheat`가 든 기록"처럼, 의미가 아니라 *그 단어 자체*를 찾을 때다. 벡터의 의미 검색과 헷갈리기 쉬운데, 결이 다르다 — FTS는 글자가 일치하는 것을 찾아 빈도로 랭크하고, 벡터는 글자가 달라도 뜻이 통하면 찾는다. 에러 코드나 장비명처럼 *정확한 토큰*이 중요할 때는 의미 검색보다 FTS가 정직하다.

| 인출하려는 것 | 맞는 저장 |
|---|---|
| 의미가 비슷한 사실 (시맨틱) | vector store |
| 연결·공통 원인 (관계) | knowledge graph |
| 정확한 값·집계·필터 | relational store |
| 정확한 키워드·로그 | full-text search |
| 시간순 사건 (에피소딕) | relational(시각 정렬) 또는 graph(시점 엣지) |

이 표가 이 챕터의 절반이다. 1.2의 세 갈래(에피소딕·시맨틱·절차적)와 인출 패턴을 저장 기술에 *내려 꽂은* 것이다.

## 하나의 사실을 여러 저장에 — poly-store

저장이 넷이 됐으니, 사실 하나가 들어올 때 *어디에 쓸지*를 정해야 한다. 답은 종종 "여러 곳에 동시에"다. **다중 저장(poly-store)**은 여러 저장을 한 시스템에 묶고, 같은 사실을 그 측면에 따라 여러 저장에 색인하는 설계다.

```python
def remember(item: dict) -> None:
    """하나의 쓰기를, 사실의 측면에 따라 알맞은 저장들로 보낸다."""
    vector_store.add(item["text"], embed(item["text"]))  # 의미 인출용 — 항상
    fts.index(item["text"])                              # 키워드 검색용 — 항상
    if item.get("entities"):                             # 관계가 있으면
        graph.add_edges(item["entities"])               #   그래프에도
    if item.get("fields"):                               # 구조화 값이 있으면
        relational.insert(item["fields"])               #   표에도 (정확 조회·집계용)

remember({
    "text": "lot_A 수율 89%로 정정, 원인은 equip_X 과열",
    "entities": [("lot_A", "affected_by", "equip_X")],
    "fields": {"lot": "lot_A", "yield": 0.89, "cause": "overheat"},
})
```

한 줄짜리 분석 결론이 네 저장에 각각 다른 모습으로 들어갔다. 벡터엔 의미로, FTS엔 단어로, 그래프엔 관계로, 표엔 숫자로. 나중에 어떤 각도로 물어도 *적어도 한 저장은* 답을 갖고 있다. 이게 **이중 쓰기(dual-write)**의 발상이다 — 쓸 때 한 번 더 수고해서, 읽을 때 어떤 질문이든 받는다.

## 공짜가 아니다

poly-store의 대가는 *동기화*다. 같은 사실을 네 곳에 써 두면, 그 사실이 바뀔 때도 네 곳을 다 고쳐야 한다. 한 곳만 갱신하고 나머지를 놔두면, 저장마다 다른 답을 하는 메모리가 된다 — 벡터는 89%라는데 표는 92%인 식이다.

> 💡 **비유의 한계**: 칼은 서로 간섭하지 않는다. 빵칼을 갈아도 식칼은 그대로다. 저장은 다르다 — 같은 사실이 여러 저장에 *복제*돼 있어서, 하나를 갱신하면 나머지도 따라 바뀌어야 한다. "여러 칼"보다 "한 원본의 여러 사본"에 가깝고, 사본은 늘 동기화라는 빚을 진다. 이 빚을 어떻게 갚을지가 바로 갱신·무효화의 문제(Part 4)다.

## 그래서 — 인출에서 역산해 저장을 고른다

Part 2를 닫자. 핵심은 "어느 저장이 최고냐"가 아니다. *내 에이전트가 기억을 어떻게 떠올릴 것인가*에서 역산해 저장을 고르는 것이다.

- 의미로 떠올리면 → vector
- 관계로 타고 다니면 → graph
- 정확한 값과 집계가 필요하면 → relational
- 정확한 단어를 찾으면 → FTS
- 대개는 → 이 중 여러 개를 poly-store로

그러니 저장 설계는 사실 *인출 설계*가 먼저다. 무엇을 어떻게 떠올릴지를 정하면 저장은 거기서 따라 나온다. 그래서 다음 Part는 인출이다 — 떠올리는 법을 제대로 보고 나면, 방금 고른 저장들이 왜 그렇게 짝지어졌는지 분명해진다.

> ⚠️ **코드 미검증 — 검증 레포 실행 필요.** 위 스니펫은 poly-store의 라우팅 원리를 보이기 위한 골격으로, 각 저장 객체가 추상화되어 있다. 실행 가능한 형태는 Part 5에서 만든다.

## 핵심 정리

- **만능 저장은 없다.** vector·graph·relational·FTS는 각각 의미·관계·정확값·키워드라는 다른 결을 잘 자른다.
- **유형↔저장 매핑이 저장 설계의 뼈대다.** 1.2의 갈래와 인출 패턴을 저장 기술에 내려 꽂으면 무엇을 어디에 넣을지가 나온다.
- **poly-store는 하나의 사실을 여러 저장에 색인한다.** 쓸 때 한 번 더 수고해서, 읽을 때 어떤 각도의 질문이든 받는다.
- **그 대가는 동기화다.** 사본이 늘수록 갱신할 곳도 늘고, 한 곳만 고치면 저장마다 다른 답을 한다 — 이 빚이 Part 4의 무효화 문제로 이어진다.
