# 5.2 망각과 갱신을 얹기

## 이 챕터에서 배우는 것

- 5.1 골격에 4장의 갱신·시간·망각을 손으로 얹기
- 무효화로 `remember`를 바꾸기 — 덮어쓰지 않는 저장
- 레코드에 두 시간을 달고 `recall`로 "그때의 시야"를 묻기
- 중요도로 잊되, 현재 진실과 옛 기록을 구분해 식히기

---

## 5.1에서 5.2로

5.1의 해골은 걷는다. 그러나 갱신도, 시간도, 망각도 없다고 했다. 같은 lot의 수율이 두 번 정정되면 옛값과 새값이 나란히 떠오르고, "5월에 알던 값"은 물을 수 없으며, 기록은 무한정 쌓인다.

다행히 *무엇을 어떻게* 얹어야 하는지는 4장이 다 알려줬다. 무효화(4.2), 두 시간(4.3), 가지치기(4.1). 이제 그 원리를 골격에 손으로 박는다.

## 해골에 살을 붙인다 (비유)

방식은 **살 붙이기**다. 5.1의 뼈대 — `remember`와 `recall` 두 동사 — 를 헐지 않는다. 레코드를 늘리고, 두 동사의 *속을* 고치고, 동사 하나(`forget`)를 더한다. 골격이 정한 모양은 그대로 두고 그 위에 근육을 올린다.

> 💡 **비유의 한계**: 살을 다 붙여도 이건 여전히 *단일 리스트 위에 선* 메모리다. 사람 몸이 골격 위에 서듯, 이 메모리는 5.1의 `list[Item]` 위에 선다. 규모가 커지면(수십만 건), 동시에 여러 에이전트가 쓰면, 프로세스가 죽었다 살아나면 — 살로는 못 푸는 한계가 드러난다. 그건 골격을 바꾸는 일이고, 5.3에서 마주한다.

## 살 ① 덮어쓰지 않는 갱신

먼저 레코드를 늘린다. 5.1의 `Item`은 텍스트와 벡터뿐이었다. 4장이 요구한 것들을 단다.

```python
@dataclass
class Item:
    text: str
    vec: np.ndarray
    subject: str                       # 무엇에 관한 사실인가 — "lot_A.yield"
    valid_from: str                    # 사건 시간: 사실이 참인 때 (4.3)
    recorded_at: str                   # 기록 시간: 메모리에 적은 때 (4.3)
    recorded_until: str | None = None  # 무효화 시점 — None이면 현재 유효 (4.2)
    use_count: int = 0                 # 망각 점수용 (4.1)
```

`subject`가 열쇠다 — "이 기록이 무엇에 관한 것인가". 같은 `subject`에 새 사실이 들어오면, 옛 사실을 덮어쓰지 않고 무효화한다(4.2의 `update_fact` 그대로).

```python
def remember(self, text, subject, valid_from, at):
    # 4.2: 같은 subject의 현재 유효 기록에 '여기까지 유효'를 찍는다
    for it in self._items:
        if it.subject == subject and it.recorded_until is None:
            it.recorded_until = at
    # 옛 기록을 지우지 않고, 새 사실을 추가한다
    self._items.append(Item(text, embed(text), subject,
                            valid_from=valid_from, recorded_at=at))
```

덮어쓰기였다면 한 줄(`it.text = text`)로 끝났을 일을, 무효화 + 추가로 바꿨다. 옛 기록이 산다.

## 살 ② 두 개의 시간

레코드에 이미 `valid_from`(참인 때)과 `recorded_at`(안 때)을 달았다. 이제 `recall`이 *그 시점의 시야*를 자르게 한다.

```python
def recall(self, query, as_of, k=3, min_sim=0.6):
    q = embed(query)
    # 4.3: as_of 시점에 '알고 있던' 기록만 후보로 — 그때의 시야를 복원
    visible = [it for it in self._items
               if it.recorded_at <= as_of
               and (it.recorded_until is None or as_of < it.recorded_until)]
    scored = sorted(((self._cos(q, it.vec), it) for it in visible),
                    key=lambda x: x[0], reverse=True)
    hits = [it for sim, it in scored[:k] if sim >= min_sim]
    for it in hits:
        it.use_count += 1          # 쓰인 만큼 망각에서 멀어진다 (4.1)
    return [it.text for it in hits]
```

`as_of`로 거른 `visible` 한 줄이 4.3의 핵심이다 — "그때 기록됐고 그때 아직 유효하던" 것만 본다. 그리고 떠올린 기록의 `use_count`를 올려, 자주 쓰는 기억이 잊히지 않게 한다.

## 살 ③ 잊기

마지막은 가지치기다. 4.1에서 "지우기보다 식히기"라 했으니, 현재 유효한 기록은 건드리지 않고 *무효화된 옛 기록* 중 안 쓰인 것부터 정리한다.

```python
def forget(self, keep_invalid):
    # 4.1: 현재 진실은 모두 지키고, 무효화된 옛 기록만 use_count 낮은 순으로 솎는다
    active = [it for it in self._items if it.recorded_until is None]
    invalid = sorted((it for it in self._items if it.recorded_until is not None),
                     key=lambda it: it.use_count, reverse=True)
    self._items = active + invalid[:keep_invalid]
```

옛 기록을 *얼마나* 남길지(`keep_invalid`)가 정책 손잡이다. 0이면 현재만 남기는 공격적 망각, 크게 두면 이력을 길게 보존한다. 분석 메모리라면 후자로 기울 것이다 — 옛 결론을 변호하려면 옛 기록이 필요하니까(4.4).

## 다 붙인 메모리

이제 4.3의 시연을 코드로 재현해 보자. 같은 lot 수율이 정정되고, 같은 질의가 시점에 따라 다른 답을 한다.

```python
mem = MiniMemory()
mem.remember("lot_A 수율 92%", subject="lot_A.yield",
             valid_from="2026-03", at="2026-05-01")
mem.remember("lot_A 수율 89%로 정정", subject="lot_A.yield",
             valid_from="2026-03", at="2026-05-10")   # 덮어쓰지 않음

mem.recall("lot_A 수율", as_of="2026-05-05")  # → ["lot_A 수율 92%"]        (그때 알던 값)
mem.recall("lot_A 수율", as_of="2026-05-20")  # → ["lot_A 수율 89%로 정정"]  (현재 진실)
```

같은 질의, 다른 `as_of`, 다른 답. 5.1의 해골은 둘 다 떠올려 무엇이 맞는지 몰랐지만, 살을 붙인 지금은 "5월 5일의 앎"과 "지금의 진실"을 *둘 다* 정확히 답한다. 4.3이 말로 한 것을, 메모리가 코드로 한다.

## 그래서 — 이제 프레임워크를 볼 눈이 생겼다

해골에 4장의 살을 다 붙였다. 그 과정에서 우리는 *직접 손으로* 알게 됐다 — 갱신은 덮어쓰기가 아니라 무효화여야 하고, 시간은 하나가 아니라 둘이어야 하며, 망각은 삭제가 아니라 식히기여야 한다는 것을. 책으로 읽은 게 아니라 코드로 박았다.

이 눈이 결정적이다. 이제 실제 메모리 프레임워크를 펼치면, 그것이 갱신을 무효화로 다루는지, 두 시간을 가지는지, 어떻게 잊는지가 *대번에* 보인다. 화려한 기능 목록이 아니라 *원리의 유무*로 평가하게 된다.

동시에 한계도 안다. 우리가 만든 건 단일 리스트 위의 장난감이고, 규모·동시성·영속성은 손대지 않았다. 그러니 다음 질문은 자연스럽다 — *무엇을 직접 짓고 무엇을 프레임워크에 맡길 것인가.* 내가 만든 것과 실제 도구를 나란히 놓는 5.3으로 간다.

> ⚠️ **코드 미검증 — 검증 레포 실행 필요.** 위 코드는 4장 원리를 `MiniMemory`에 얹은 것으로, `embed()`가 추상화되어 그대로는 실행되지 않는다. Part 5의 모든 코드는 별도 검증 레포에서 실행·확인해야 한다.

## 핵심 정리

- **갱신을 무효화로 바꾼다.** `remember`가 덮어쓰는 대신, 같은 `subject`의 옛 기록에 `recorded_until`을 찍고 새 사실을 추가한다 — 옛 기록이 산다(4.2).
- **레코드에 두 시간을 달면 `recall`이 시점을 묻는다.** `as_of`로 "그때 기록됐고 그때 유효하던" 것만 보이게 잘라, 과거의 앎과 현재의 진실을 둘 다 답한다(4.3).
- **잊기는 현재를 지키고 옛 기록만 식힌다.** 무효화된 것 중 안 쓰인 순으로 솎되, 분석 메모리는 이력을 길게 두는 쪽이 맞다(4.1·4.4).
- **손으로 얹어본 원리가 프레임워크를 보는 눈이 된다.** 갱신·시간·망각의 유무로 도구를 평가하게 되며, 동시에 규모·동시성은 빌려야 할 영역임을 안다(5.3).
