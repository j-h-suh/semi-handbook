- 엣지에 시간을 달면 관계가 *언제* 성립했는지까지 담긴다

---

## 2.1에서 2.2로

2.1에서 vector store는 의미 유사를 잘 떠올리지만, "lot A와 같은 장비를 쓴 lot들" 같은 *연결을 따라가는* 질문은 못 한다고 했다. 유사도는 가까움만 알지 관계를 모르기 때문이다.

분석에서 이런 연결 질문은 흔하다 못해 핵심이다. 수율이 낮은 lot 몇 개가 *공통으로 거친* 장비가 있는가? 이건 의미가 비슷한 기록을 찾는 일이 아니라, 관계망을 *타고 다니는* 일이다. 그걸 담는 저장이 그래프다.

## 사실을 점과 선으로

**지식 그래프(knowledge graph)**는 사실을 *점과 선*으로 담는 구조다. 점은 **노드(node)** — lot, 장비, 공정 단계 같은 엔티티다. 선은 **엣지(edge)** — "lot A가 장비 X에서 처리됐다" 같은 관계다.

가장 단순한 형태는 관계 하나를 세 토막으로 적는 것이다. **트리플(triple)**은 `(주어, 관계, 목적어)`로 된 한 줄짜리 사실이다 — `(lot_A, processed_on, equip_X)`. 그래프 전체는 이런 트리플의 모음일 뿐이다.

비유하자면 형사의 **수사 보드**다. 사진(노드)을 핀으로 꽂고 실(엣지)로 잇는 그 코르크판 말이다. 형사는 한 단서에서 실을 따라 다음 단서로 건너가고, 여러 실이 한 사진으로 모이면 거기가 의심스러운 곳이다. 그래프 탐색이 정확히 그 일을 한다 — 실을 따라가고, 실이 모이는 곳을 찾는다.

## 그래프 탐색의 킬러 유스케이스

원리를 코드로 박아 보자. 핵심은 *실을 따라가는* 두 동작이다 — 한 노드의 이웃을 보는 것, 그리고 여러 노드의 이웃이 *겹치는* 곳을 찾는 것.

```python
from collections import defaultdict

# 그래프 = 트리플의 모음. (주어, 관계, 목적어)
edges: list[tuple[str, str, str]] = [
    ("lot_A", "processed_on", "equip_X"),
    ("lot_A", "processed_on", "equip_Y"),
    ("lot_B", "processed_on", "equip_X"),
    ("lot_C", "processed_on", "equip_Z"),
]

# 인접 인덱스: 빠른 탐색을 위해 양방향으로 펼쳐둔다
out: dict[str, set] = defaultdict(set)  # 주어 → {(관계, 목적어)}
inv: dict[str, set] = defaultdict(set)  # 목적어 → {(관계, 주어)}
for s, p, o in edges:
    out[s].add((p, o))
    inv[o].add((p, s))

def equipment_of(lot: str) -> set[str]:
    """lot이 거친 장비 — 정방향 1-hop 탐색."""
    return {o for p, o in out[lot] if p == "processed_on"}

def common_equipment(lots: list[str]) -> set[str]:
    """수율 낮은 lot들이 공통으로 거친 장비 — 이웃 교집합."""
    sets = [equipment_of(lot) for lot in lots]
    return set.intersection(*sets) if sets else set()

common_equipment(["lot_A", "lot_B"])  # → {"equip_X"}  ← 공통 원인 후보
```

마지막 줄이 그래프의 진가다. lot A와 lot B의 수율이 둘 다 낮을 때, 둘이 *공통으로* 거친 장비는 `equip_X` 하나다. 이건 강력한 원인 가설이다 — 그리고 vector store로는 *절대* 나오지 않는 답이다. 의미 유사가 아니라 관계망의 교집합이기 때문이다. `inv` 인덱스를 쓰면 거꾸로 "`equip_X`를 거친 모든 lot"도 한 번에 나온다.

## 엣지에 시간을 달면

지금까지의 엣지는 시점이 없다. 그런데 관계에는 거의 항상 *언제*가 따라붙는다. lot A가 장비 X를 거친 것은 3월의 일이다. 그 시점을 엣지에 속성으로 달면, 그래프는 관계뿐 아니라 *관계의 시간*까지 담는다.

```python
# 시점을 단 엣지 — 관계가 '언제' 성립했는지까지
("lot_A", "processed_on", "equip_X", "2026-03-12")
```

이렇게 해 두면 "3월에 equip_X를 거친 lot들"처럼 관계와 시간을 함께 묻는 질문에 답할 수 있다. 그리고 여기서 한 갈래가 갈라져 나온다 — *사실이 언제 참이었나*와 *우리가 언제 그걸 알았나*는 다르며, 이 둘을 엣지에 어떻게 담을지가 Part 4의 핵심 주제다. 지금은 "엣지에 시간을 달 수 있다"는 것만 짚어 둔다.

> 💡 **비유의 한계**: 수사 보드의 실은 형사가 *손으로* 잇는다. 그래프도 마찬가지로, 누군가 트리플을 *추출해 넣어야* 빛난다. 비정형 텍스트에서 `(주어, 관계, 목적어)`를 정확히 뽑아내는 일 자체가 비싸고 불완전하다. 깔끔히 정제된 위 예제와 달리, 실제 데이터에서 그래프를 *채우는* 비용이 그래프의 진짜 진입 장벽이다.

## 그래서 — 관계는 그래프, 의미는 벡터

그래프가 vector store보다 우월하다는 얘기가 아니다. 둘은 *다른 질문*에 답한다.

- "이것과 의미가 비슷한 기억은?" → vector store
- "이것과 연결된 것, 두 다리 건너 닿는 것은?" → 그래프
- "수율 낮은 lot들의 공통 장비는?" → 그래프 (유사도로는 불가능)

분석 에이전트의 기억은 보통 둘 다 필요하다. 사실을 의미로도 떠올리고(시맨틱), 사실들 사이를 관계로도 타고 다녀야(에피소딕·관계) 하기 때문이다. 그래서 내 메모리 설계의 다음 질문은 자연스럽게 이렇게 선다 — *의미용 저장과 관계용 저장을 어떻게 한 시스템에 섞을 것인가.* 거기에 정확 조회와 키워드까지 더하면 그림이 완성된다. 그 합치는 법이 다음 챕터다.

## 핵심 정리

- **그래프는 사실을 점과 선으로 담는다.** 노드(엔티티)와 엣지(관계), 가장 단순하게는 `(주어, 관계, 목적어)` 트리플의 모음이다.
- **킬러 유스케이스는 공통 원인 추적이다.** 수율 낮은 lot들의 이웃 교집합으로 공통 장비를 찾는 일은 유사도로는 불가능하고, 그래프 탐색에선 한 줄이다.
- **엣지에 시간을 달면 관계의 시점까지 담는다.** 그리고 "참이었던 때"와 "알게 된 때"를 가르는 문제가 여기서 싹트며, 그건 Part 4의 주제다.
- **그래프와 벡터는 경쟁이 아니라 분업이다.** 의미는 벡터, 관계는 그래프 — 분석 기억은 보통 둘 다 필요하고, 그래서 섞는 법이 다음 과제다.
