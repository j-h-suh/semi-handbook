## 사용자 경험에서 출발

Claude Code에 무언가를 물으면 응답이 졸졸 흘러나온다. 그동안 우리 컴퓨터는 놀고 있지 않다 — 디스크에서 파일을 읽고, 다른 도구를 준비하고, UI를 그린다. 하나가 진행되는 동안 다른 것들이 멈춰 있는 게 아니다.

이게 어떻게 가능한가? 답은 **비동기 프로그래밍(asynchronous programming)**. 그리고 그 핵심 빌딩 블록이 **코루틴(coroutine)** 이다.

근데 코루틴이 뭐냐고 물으면 보통 이렇게 답한다 — "async/await 쓰는 함수." 맞는 말이지만 이건 문법이지 본질이 아니다. 본질은 더 깊은 곳에 있다. 그리고 그 본질을 알면 `Promise`, `Task`, 이벤트 루프, `await`, `yield` 같은 흩어진 개념들이 전부 한 줄로 꿰어진다.

이 챕터에서 그 줄을 꿰어보자. Claude Code 의 핵심 루프(`query.ts`)가 처음부터 끝까지 이 패턴 위에 서 있기 때문이다.

## 코루틴 — 일시정지할 수 있는 함수

일반 함수의 약속은 단순하다. 호출하면 처음부터 끝까지 실행되고, 반환값을 돌려준다. 호출자는 함수가 끝날 때까지 기다린다.

```python
def add(a, b):
    return a + b

result = add(1, 2)   # 호출 → 끝까지 실행 → 3 반환
```

호출자와 함수 사이에 control flow의 거래는 단 두 번 — 호출 시 진입, 반환 시 복귀. 그 사이는 함수가 100% 통제한다.

**코루틴(coroutine)** 은 그 약속을 깬다. 코루틴은 중간에 멈출 수 있다. 그리고 나중에 그 자리에서 다시 시작할 수 있다. 호출자와 함수 사이에 control flow가 여러 번 왕래한다.

```python
async def fetch_user(user_id):
    response = await http.get(f"/users/{user_id}")  # 여기서 일시정지
    return response.json()
```

이 함수를 호출해도 본문은 진행되지 않는다. 코루틴 객체가 만들어질 뿐이다. 누군가가 그 객체를 **굴려야** (다음 `await` 까지 한 단계 진행시켜야) 비로소 본문이 시작된다. `await` 만나는 순간 함수는 자기 실행 상태를 통째로 들어올려 펜딩 상태로 둔다 — 지역 변수, 어디까지 진행했는지, 콜 스택 위치 모두 객체 안에 보존. 그리고 호출자에게 control을 돌려준다.

호출자(또는 그 위 누군가)는 그 사이에 다른 일을 한다. 다른 코루틴을 굴릴 수도 있고, I/O 결과를 기다릴 수도 있다. 마침내 `await` 가 기다리던 작업이 끝나면, 호출자가 다시 첫 코루틴을 재개한다. 코루틴은 자기가 멈췄던 자리에서, 멈춘 그 순간의 상태로 다시 진행한다.

이게 코루틴이다 — **실행 상태를 객체로 들고 있을 수 있는 함수**. 일시정지/재개라는 능력이 핵심.

JS/TS의 `async function` 도 정확히 같은 것이다. 호출하면 본문이 진행되지 않고 `Promise` 객체가 반환된다. `await` 마다 함수는 일시정지하고, 누군가가 굴려야 다시 진행된다. 이름만 다를 뿐 메커니즘은 동일.

> 💡 **왜 이런 걸 만들었나** — 다중 작업을 동시에 다루는 전통적 방법은 스레드였다. 스레드는 OS가 임의의 시점에 스위칭한다 (preemptive). 안전하게 쓰려면 lock, mutex가 필요하고 디버깅이 복잡해진다. 코루틴은 정반대 — 스위칭이 코드 안 명시적인 자리(`await`)에서만 일어난다. 모든 일시정지 지점이 코드에 보인다. 동시성 버그가 훨씬 줄어든다. 그래서 IO-bound 작업에는 거의 항상 코루틴을 쓴다.

## 이벤트 루프 — 누가 코루틴을 굴리는가

코루틴은 자기 혼자 못 굴러간다. 누군가 굴려야 한다. 그 누군가가 **이벤트 루프(event loop)** 다.

이벤트 루프는 단순하다 — 큐 하나와 무한 반복 하나.

```
무한 반복:
  1. 큐에서 깨어 있는 코루틴 하나 꺼냄
  2. 그 코루틴을 다음 await 까지 진행시킴
  3. await 가 기다리는 작업을 OS (또는 다른 코루틴) 에 위임
     → 코루틴은 "대기" 상태로 보류 (1번에서 큐 밖으로 나간 그대로)
  4. 위임된 작업이 끝나면 → 콜백을 통해 그 코루틴이 큐에 다시 들어감
  5. 처음으로
```

"왜 한 번에 끝까지 안 가고 굳이 큐에 넣었다 빼느냐?" 답은 단순하다 — `await` 가 기다리는 작업은 보통 다른 곳에서 진행되는 일(I/O 든, 다른 코루틴 이든) 이기 때문이다. 그 결과를 그 자리에서 기다리고만 있으면 이벤트 루프는 다른 일을 못 한다. 그래서 `await` 자리에서 코루틴을 한 번 빠뜨리고, 큐에서 다른 코루틴을 꺼내 굴린다.

I/O 작업(파일 읽기, 네트워크 요청)은 OS에 위임되어 백그라운드에서 진행된다. 이벤트 루프는 OS의 통지(epoll, kqueue 등) 를 받는 순간, 그 작업을 기다리던 코루틴을 큐에 다시 넣는다. 다음 루프 반복에서 그 코루틴이 꺼내져 다음 `await` 까지 진행된다.

핵심은 **single-threaded** 라는 것. 한 순간에 진행되는 코루틴은 단 하나. 진짜 병렬이 아니라 교대로 진행한다. 이게 cooperative scheduling — 코루틴이 스스로 양보(`await`) 하지 않으면 다음 코루틴이 진행을 못 한다.

JS와 Python은 모델이 같다. 다만 표현이 다르다.

| 항목 | JS / Node / Bun | Python asyncio |
|------|----------------|----------------|
| 이벤트 루프 | 자동, 항상 돌고 있음 | `asyncio.run()` 으로 명시적 실행 |
| top-level await | OK (ESM / Bun) | 안 됨 (`asyncio.run()` 안에서만) |
| 큐의 종류 | macrotask, microtask 두 가지 | 단일 큐 |

JS는 이벤트 루프가 암묵적이다. 모듈 최상위에서 `await` 가 그냥 동작한다. Python은 명시적이다 — 어딘가에서 `asyncio.run(main())` 을 호출해야 루프가 시작된다.

이 차이가 1.1 에서 본 `await import('...')` 같은 코드를 가능하게 한다. JS에서는 모듈 최상위에서 `await` 가 자연스러운 일이다. Python 의 진입점 코드가 `if __name__ == "__main__": asyncio.run(main())` 으로 끝나는 것과 대조된다.

> 💡 **왜 single-thread 인가** — 멀티스레드는 락 등 동기화가 필요해 복잡하고 느리다. I/O-bound 작업의 99% 시간은 기다리는 시간이다. 그 시간을 다른 일로 채울 수만 있다면 single-thread 로도 충분히 빠르다 (오히려 컨텍스트 스위칭 비용이 없어 더 빠를 수 있음). CPU-bound 작업에는 부적합. Claude Code 같은 I/O 중심 프로그램에는 완벽한 모델.

## 태스크와 Promise — 코루틴의 "예약권"

위에서 말했다 — "코루틴 호출은 본문을 진행시키지 않는다. 객체가 반환될 뿐." 그 객체가 **태스크(Task)** 또는 **프로미스(Promise)** 다. 이름은 다르지만 비슷한 역할 — "이 코루틴 굴려달라" 는 예약권.

JS의 Promise 는 세 가지 상태를 가진다 — `pending` (진행 중), `fulfilled` (성공으로 끝남), `rejected` (예외로 끝남). 코루틴 본문이 어디까지 갔든 상관없이, Promise 자체는 항상 이 세 상태 중 하나.

`await promise` 는 이런 의미 — "이 promise 가 fulfilled 될 때까지 내 코루틴 자리에서 멈춰라. 그동안 이벤트 루프는 다른 코루틴을 굴려도 좋다." 끝나면 promise 의 결과값이 `await` 표현식의 값이 된다.

그런데 Python `Task` 와 JS `Promise` 사이에 한 가지 미묘한 차이가 있다.

- **JS Promise** — 만들자마자 즉시 실행 시작. `new Promise(executor)` 의 executor 는 즉시 호출됨.
- **Python coroutine** — 만들기만 한 상태로 멈춰 있음. `asyncio.create_task(coro())` 로 Task 로 감싸야 그제서야 이벤트 루프에 등록되어 시작.

```python
async def fetch():
    print("fetching")
    return 42

c = fetch()              # 객체만 만들어짐. "fetching" 안 찍힘.
result = await c         # 여기서 비로소 진행. "fetching" 찍힘.
```

```typescript
async function fetch() {
  console.log("fetching")
  return 42
}

const p = fetch()        // 즉시 시작. "fetching" 바로 찍힘.
const result = await p   // 결과만 받음.
```

이 차이가 코드 패턴을 살짝 다르게 만든다. JS 에서는 "여러 작업 동시 시작" 이 자연스럽다 — 그냥 함수 호출 여러 번 하면 다 같이 시작.

```typescript
const [a, b, c] = await Promise.all([fetchA(), fetchB(), fetchC()])
```

세 함수가 호출되는 순간 세 작업이 다 시작된다.

Python 은 명시적으로 Task 로 감싸야 한다.

```python
results = await asyncio.gather(fetch_a(), fetch_b(), fetch_c())
# gather() 내부에서 각각 Task 로 감싼다
```

겉모양은 비슷하지만 메커니즘이 다르다. 본문에서 두 가지 패턴을 다 보게 될 것이고, 차이를 알면 코드가 읽힌다.

## 비동기 제너레이터 — 한 번이 아니라 여러 번

여기까지가 비동기. 이제 제너레이터를 얹는다.

코루틴은 끝나면 값 하나를 반환한다 (한 번의 return). 그런데 LLM 응답처럼 여러 값이 시간차로 도착하는 경우는 어떻게 모델링할까?

**제너레이터(generator)** 가 그 답이다. 제너레이터는 `yield` 로 값을 내보내고도 멈춰 있다. 다음 호출이 오면 멈춘 자리부터 진행해서 다음 `yield` 까지 간다. 사실상 코루틴인데 "끝까지 가서 한 번 반환" 대신 "중간에 여러 번 내보냄" 이 가능해진 것.

코루틴 + 제너레이터 = **비동기 제너레이터(async generator)**. `yield` 와 `await` 가 한 함수 안에 공존한다. 비동기 작업을 기다리면서 동시에 결과를 흘려보낼 수 있다.

```python
async def token_stream():
    async for chunk in api.stream():   # 비동기로 한 청크씩 받음
        yield chunk                     # 받자마자 흘려보냄
```

이 함수는 두 가지 일을 한다 — API 의 비동기 청크를 기다림(`await` / `async for`), 받은 청크를 흘려보냄(`yield`). 한 함수 안에서.

소비자는 `for await...of` (JS) 또는 `async for` (Python) 로 받는다.

```python
async for token in token_stream():
    print(token, end="", flush=True)
```

매 반복마다 "다음 yield 까지 진행 → 받은 값으로 본체 한 번 실행" 이 반복된다. 제너레이터가 끝나면(`return` 도달 또는 함수 끝에 도달) 루프도 끝난다.

이게 **스트리밍** 의 자연스러운 표현이다. 토큰이 도착할 때마다 흘려보내고, 받는 쪽은 도착할 때마다 그린다. 둘 사이에 큐, 콜백, 옵저버, 어떤 추가 인프라도 필요 없다. 그냥 비동기 제너레이터와 그것을 받는 루프뿐.

> 💡 **iterator 와 generator 의 관계**: 위에서 "generator" 라고 부른 것의 더 일반적인 이름은 **iterator(이터레이터)** — `next()` 호출하면 다음 값을 주는 인터페이스. iterator 는 클래스로도 만들 수 있고 (`__next__` 직접 구현), `yield` 로도 만들 수 있다. 후자가 generator. **모든 generator 는 iterator 지만, iterator 가 항상 generator 인 건 아니다** — `yield` 가 iterator 를 만드는 한 가지 쉬운 방법일 뿐. `for` 문 / `async for` 는 iterator 를 받는다 (비동기 평행 구조도 동일 — async iterator 인터페이스, async generator 는 그 한 형태).

## yield\* — 흐름의 합성

비동기 제너레이터의 또 한 가지 강력한 도구. `yield*` 는 다른 제너레이터를 그대로 흘려보낸다.

:::tabs

```typescript
async function* layered() {
  yield* serviceA()       // serviceA 의 모든 yield 를 흘려보냄
  yield* serviceB()       // 이어서 serviceB 의 모든 yield
  yield 'end'
}
```

```python
async def layered():
    async for x in service_a():    # service_a 의 모든 yield 를 흘려보냄
        yield x
    async for x in service_b():    # 이어서 service_b 의 모든 yield
        yield x
    yield 'end'
```

:::

> 💡 **`yield*` vs `async for ... yield`**: Python 의 async generator 에는 `yield from` 문법이 없다 (sync generator 에만 있다). 그래서 `async for ... yield` 로 한 줄씩 풀어 쓴다. 의미는 같다 — 하위 제너레이터의 모든 yield 를 흘려보낸다.

상위 함수는 하위 제너레이터의 내부를 알 필요 없다. 그냥 흘려보낼 뿐. 결과적으로 여러 제너레이터를 합성한 하나의 흐름이 된다.

이 패턴이 Claude Code 의 핵심 루프(`query.ts`)의 모양이다. 메시지 처리 / 도구 실행 / 컨텍스트 압축 같은 각 책임이 자기 비동기 제너레이터를 만들고, 최상위에서 `yield*` 로 묶인다. 소비자(터미널 UI)는 단 한 번의 `for await` 로 모든 이벤트를 차례대로 받는다.

> `query.ts` 의 진짜 본문은 2.1 에서 한 줄씩 본다.

## Claude Code 에서의 활용

전체 그림을 한 줄로 요약하면 — **에이전트 루프 전체를 단 하나의 비동기 제너레이터로 표현한다**.

```
Anthropic API stream  ─┐
도구 실행 결과         ─┼─→ query.ts (yield*) ─→ 터미널 UI (for await)
컨텍스트 압축 이벤트    ─┘
```

여러 비동기 흐름이 `query.ts` 안에서 `yield*` 로 합쳐지고, 소비자는 값의 흐름으로만 본다. UI 코드는 "이게 토큰인지, 도구 결과인지, 압축 이벤트인지" 만 보고 그린다. 언제 도착했는지, 어디서 왔는지는 신경 쓸 필요 없다.

비동기 제너레이터는 한 번만 돌릴 수 있다는 점도 기억해두자. 한 번 끝나면 다시 처음부터 보려면 함수를 다시 호출해서 새 객체를 만들어야 한다. 본문에서 암묵적 가정으로 자주 등장한다.

## 핵심 정리

- **코루틴은 일시정지/재개할 수 있는 함수.** 실행 상태를 객체로 들고 있어서 `await` 마다 멈췄다가 나중에 그 자리에서 다시 시작한다. JS의 `async function` = Python의 `async def coroutine` (이름만 다름).
- **이벤트 루프는 코루틴을 굴리는 single-threaded scheduler.** 모든 스위칭이 `await` 자리에서 명시적으로 일어남 — preemptive 스레드의 동기화 지옥에서 벗어나는 모델. JS는 암묵적(top-level await OK), Python은 명시적(`asyncio.run`).
- **Promise / Task 는 코루틴의 예약권.** JS Promise 는 즉시 실행, Python coroutine 은 Task 로 감싸야 시작 — 미묘한 차이지만 코드 패턴이 다르다.
- **비동기 제너레이터 = 코루틴 + 제너레이터.** `yield` 로 여러 번 내보내면서 `await` 로 기다릴 수 있음. LLM 토큰 스트리밍의 자연스러운 표현.
- **`yield*` 로 흐름을 합성한다.** 여러 비동기 제너레이터를 하나로 묶는 핵심 연산. Claude Code 의 `query.ts` 가 정확히 이 패턴 — 에이전트 루프 전체를 단 하나의 `for await` 로 소비할 수 있게 만든다.
