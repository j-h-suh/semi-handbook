5개 카테고리. 외울 만하다. 합치면 정확히 47개. 그 외 같은 잡종 카테고리는 없다 — 모든 필드가 다섯 자리 중 하나에 정확히 들어간다.

- **정체성**은 "이게 어떤 도구인가".
- **스키마**는 "어떤 입출력을 가지나".
- **실행**은 "무엇을 어떻게 하나".
- **권한/메타데이터**는 "이 도구를 호출해도 안전한가, 어떻게 처리해야 하나".
- **렌더링**은 "화면에 어떻게 그려지나" — 이게 가장 큼.

### 가장 큰 카테고리는 렌더링

15개. 47개의 1/3 가까이 된다. 왜 이렇게 많은가?

생각해보면 도구 결과는 여러 상태에서 여러 모양으로 그려져야 한다.

| 상황 | 메서드 |
|---|---|
| 도구 호출이 시작될 때 (입력 받자마자) | `renderToolUseMessage` |
| 도구가 실행 중일 때 (spinner + 진행 상황) | `renderToolUseProgressMessage` |
| 도구 결과가 나왔을 때 (성공) | `renderToolResultMessage` |
| 도구가 거부됐을 때 (사용자가 권한 거부) | `renderToolUseRejectedMessage` |
| 도구가 에러로 실패했을 때 | `renderToolUseErrorMessage` |
| 같은 도구가 여러 개 동시에 호출됐을 때 (그룹화) | `renderGroupedToolUse` |
| 사용자에게 표시되는 도구 이름 | `userFacingName` |
| 활동 설명 (예: "Reading `foo.ts`") | `getActivityDescription` |
| ... | ... |

각 상황마다 다른 함수가 있다. 왜냐하면 — 같은 도구라도 상황에 따라 다르게 그려야 하기 때문이다. `Read` 도구가 시작할 때는 "Reading file...", 결과일 때는 파일 내용 박스, 에러일 때는 빨간 박스. 한 메서드로 다 처리하기엔 케이스가 너무 다르다.

### 핵심 5개

47개가 다 필수는 아니다. **꼭 알아야 할 핵심은 5개**다 (그 중 4개는 진짜 mandatory, 1개는 default 가 있어 옵셔널).

| # | 메서드 | 책임 | mandatory? |
|---|---|---|---|
| 1 | `name` | 이 도구의 이름 (예: `"Read"`) | ✓ |
| 2 | `description()` | LLM에게 알려줄 언제 쓸지 설명 | ✓ |
| 3 | `inputSchema` | 입력의 모양 (Zod 스키마) | ✓ |
| 4 | `call()` | 진짜 실행 로직 | ✓ |
| 5 | `checkPermissions()` | 권한 확인 | ✗ (default `"allow"` — 사용자에게 안 묻고 자동 허용; 위험 도구는 `"ask"` 로 옵트인) |

이 4~5개만 채우면 최소한의 도구는 완성된다. 나머지 42개는 기본값으로 채워지거나 옵셔널 (다음 챕터 3.3의 `buildTool` 팩토리가 그 일을 한다).

> 💡 **Python 비유:** Python의 ABC(추상 클래스)와 비슷하다. **abstractmethod로 표시된 것**만 반드시 override 하면 되고, 나머지는 부모 클래스의 기본 구현을 그대로 쓰면 된다.
>
> Tool 인터페이스에서는 핵심 5개가 **abstractmethod**에 해당하고, 나머지 42개는 기본 구현이 있는 메서드에 해당한다고 보면 된다.

### 왜 이렇게 많은가 — 1급 시민의 대가

3.1에서 "도구는 시스템의 1급 시민"이라고 했다. 그 표현의 진짜 의미가 여기서 드러난다.

**시스템 곳곳이 도구에 적응한다는 게, 각 적응 지점이 메서드 하나가 된다는 뜻이다.**

- UI가 도구를 그려야 한다 → 렌더링 메서드 15개
- 권한 시스템이 도구별로 결정해야 한다 → 권한 메서드 ~10개
- LLM에게 도구를 전달해야 한다 → 정체성/스키마 메서드 ~8개
- 자동 모드 분류기가 도구를 판단해야 한다 → 분류기 메서드 ~3개
- ...

시스템에 새 영역이 추가될 때마다, 그 영역이 도구를 알아야 한다면, **Tool 인터페이스에 메서드가 하나 더 생긴다**. 그래서 47개다.

이건 나쁜 디자인인가? 그렇지 않다. 대안이 더 나쁘다. 만약 인터페이스가 작으면, 시스템 곳곳에 "이 도구가 X 종류인가?" 같은 if문이 산재하게 된다. 인터페이스가 크면 그 if문이 각 도구 정의 안에 캡슐화된다.

<details>
<summary>🔬 Deep Dive — 인터페이스 분리 원칙(ISP)을 어긴 거 아닌가?</summary>

> SOLID 원칙 중 ISP는 "클라이언트는 자기가 사용하지 않는 메서드에 의존하지 말아야 한다". 47개 필드짜리 인터페이스는 ISP 위반에 가까워 보인다. 도구를 만드는 사람이 렌더링 메서드 15개를 다 알아야 하는가?
>
> Claude Code의 답은 — "만드는 사람은 알 필요 없다. 시스템이 안다." `buildTool` 팩토리가 기본값을 채우고, 만드는 사람은 핵심 5개만 작성한다. 나머지 42개는 시스템이 호출하는 것이고, 도구 작성자는 **override하고 싶을 때만** 건드린다. **인터페이스는 크지만 사용은 작다.** 이게 의도적인 트레이드오프다.

</details>

### 그래서 47개를 다 외워야 하나?

아니다. 외워야 할 건 다음 정도다.

1. **5개 카테고리** (정체성/스키마/실행/권한/렌더링) — 어떤 카테고리가 있는지 정도만.
2. **핵심 5개 메서드** (`name`, `description`, `inputSchema`, `call`, `checkPermissions`) — 직접 작성할 것들.
3. **나머지는 기본값으로 충분하다는 사실** — 필요할 때 `Tool.ts` 가서 찾으면 된다.

이걸 알면 47개짜리 인터페이스 앞에서 더 이상 압도되지 않는다. 지도가 있으니까.

## Python으로 옮기면

3.1에서 만든 `ToolBase`를 좀 더 정확하게 5개 카테고리로 정리하면 이렇게 생겼다. 핵심 5개는 모두 `@abstractmethod` 로 강제 — `name`/`input_schema` 같은 속성은 `@property` 와 조합해야 강제 가능하다 (속성에 `@abstractmethod` 단독은 못 붙는다).

```python
from abc import ABC, abstractmethod
from typing import Generic, TypeVar
from pydantic import BaseModel

I = TypeVar("I", bound=BaseModel)

class ToolBase(ABC, Generic[I]):
    # ─── 1️⃣ 정체성 ──────────────────────────
    @property
    @abstractmethod
    def name(self) -> str:
        ...
    
    @abstractmethod
    def description(self) -> str:
        ...
    
    # ─── 2️⃣ 스키마 ──────────────────────────
    @property
    @abstractmethod
    def input_schema(self) -> type[I]:
        ...
    
    # ─── 3️⃣ 실행 ──────────────────────────
    @abstractmethod
    async def call(self, input: I) -> str:
        ...
    
    async def validate_input(self, input: I) -> None:
        return  # 기본은 통과
    
    def is_enabled(self) -> bool:
        return True  # 기본은 활성화 (input 없음 — 시스템 컨텍스트만 의존)
    
    # ─── 4️⃣ 권한 / 메타데이터 ──────────────────────────
    @abstractmethod
    async def check_permissions(self, input: I) -> bool:
        ...
    
    def is_read_only(self, input: I) -> bool:
        return False  # 기본은 보수적으로 (자식이 input 보고 override — 예: Bash 가 ls 면 True, rm 이면 False)
    
    def is_destructive(self, input: I) -> bool:
        return False
    
    def is_concurrency_safe(self, input: I) -> bool:
        return False
    
    # ─── 5️⃣ 렌더링 ──────────────────────────
    def render_progress(self, input: I) -> str:
        return f"{self.name}: {input}"  # 기본 렌더링
    
    def render_result(self, result: str) -> str:
        return result
    
    def render_error(self, error: Exception) -> str:
        return f"Error: {error}"
    
    def render_rejected(self, input: I) -> str:
        return f"User rejected: {self.name}"
    
    def user_facing_name(self) -> str:
        return self.name
```

`@abstractmethod`로 표시한 게 5개 핵심이다. 나머지는 **기본 구현이 있어서 override 안 해도 된다**. 이 패턴이 Claude Code의 `Tool` 인터페이스 + `buildTool` 팩토리와 정확히 같다.

> 💡 **팁:** 진짜 Tool 인터페이스에는 `renderToolUseProgressMessage`, `renderGroupedToolUse` 같은 훨씬 더 많은 렌더링 메서드가 있다. 위 Python 코드는 축약본이다. 핵심은 — 렌더링 메서드의 개수가 많다는 사실 자체가 카테고리 5번의 본질이라는 점.

## 핵심 정리

- `Tool` 인터페이스는 47개의 필드 (메서드 34 + 속성 13) 를 가진 거대한 타입이다. 처음 보면 압도적.
- **5개 카테고리**로 정확히 분류된다: 정체성 9 + 스키마 3 + 실행 9 + 권한/메타데이터 11 + 렌더링 15 = 47. 가장 큰 게 렌더링(15).
- **핵심 5개**만 직접 작성하면 도구가 완성된다: `name`, `description`, `inputSchema`, `call`, `checkPermissions`. 나머지 42개는 기본값.
- 왜 47개나 되는가 — **도구가 시스템의 1급 시민**이라서. 시스템의 각 영역이 도구에 적응한 결과가 각 적응 지점마다 메서드 하나다.
- ISP(인터페이스 분리 원칙) 관점에서는 위반에 가까워 보이지만, 인터페이스는 크고 사용은 작다는 의도적인 트레이드오프. 다음 챕터(3.3)에서 `buildTool` 팩토리가 그 작은 사용을 어떻게 가능하게 하는지 본다.
