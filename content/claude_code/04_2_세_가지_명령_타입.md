# 4.2 세 가지 명령 타입 — prompt / local / localJSX

---

## 이 챕터에서 배우는 것

- 슬래시 명령에 왜 세 가지 종류가 필요한가
- 각 타입이 언제 쓰이는지 — 진짜 코드 세 개로 비교
- 세 타입 모두가 공유하는 **lazy load 패턴** — 시작 시간을 줄이는 트릭
- 새 명령을 만들 때 어떤 타입을 골라야 하는지

---

## 사용자 경험에서 출발

세 가지를 차례로 쳐보자.

```
> /commit
   ⠋ creating commit  (스피너)
   git status, git diff 분석 중...
   "fix(api): 사용자 정보 반환 오류 수정" 으로 커밋함
```

```
> /cost
   Total cost: $0.42
```

```
> /config
   ┌─ Settings ─────────────────────┐
   │  > Theme: Dark                 │
   │    Model: claude-opus-4-6      │
   │    Notifications: On           │
   │  ────────────────────────────  │
   │   [↑↓ navigate, Enter select]  │
   └────────────────────────────────┘
```

세 명령 다 느낌이 다르다.

- `/commit`은 작업이 흐른다 — 시간이 걸리고, LLM이 일하고, 결과가 나온다.
- `/cost`는 즉시 답한다 — 한 줄. 끝.
- `/config`는 **대화형 UI가 뜬다** — 화살표 키로 항목을 고르고 엔터를 친다.

세 가지 다른 느낌은 우연이 아니다. **세 가지 타입의 명령**이라서 그렇다. 4.1에서 잠깐 본 그 셋 — `prompt`, `local`, `local-jsx`. 이 챕터에서 본격적으로 본다.

---

## 본문

### 타입 1: `prompt` — **프롬프트를 만들어 LLM에 보낸다**

가장 흔한 종류. `/commit`, `/init`, `/review`, `/security-review` 등이 다 이 타입이다. 4.1에서 본 `commit.ts`가 대표 예시.

```typescript
const command = {
  type: 'prompt',
  name: 'commit',
  allowedTools: ['Bash(git add:*)', 'Bash(git status:*)', 'Bash(git commit:*)'],
  progressMessage: 'creating commit',
  
  async getPromptForCommand(_args, context) {
    return [{ type: 'text', text: '<런타임에 만든 거대한 프롬프트>' }]
  },
} satisfies Command
```

특징 세 가지.

**(1) `getPromptForCommand` 함수가 진짜 일을 한다.** 호출 시점에 프롬프트를 만든다. 단순 문자열 리턴이 아니라 — git 명령을 직접 실행해서 결과를 박아 넣고, 시점에 따라 다른 프롬프트를 만든다 (4.1에서 본 `!\`git status\`` 패턴).

**(2) `allowedTools`로 도구 사용을 제한한다.** 이 명령이 도는 동안 LLM은 **세 가지 Bash 패턴만** 쓸 수 있다. `rm -rf`나 `git push`는 차단. 자세한 건 4.3에서.

**(3) `progressMessage`가 사용자에게 뭐 하고 있는지 보여준다.** 스피너 옆에 뜨는 "creating commit". 이게 없으면 사용자는 가만히 멈춘 화면을 본다.

### 타입 2: `local` — **LLM 없이 바로 답한다**

`/cost`. 진짜 코드는 어이없을 만큼 짧다 (`cost/cost.ts`, 23줄. 아래는 핵심만 골라낸 축약).

```typescript
// src/commands/cost/cost.ts (축약)
export const call: LocalCommandCall = async () => {
  if (isClaudeAISubscriber()) {
    return {
      type: 'text',
      value: 'You are currently using your subscription to power your Claude Code usage',
    }
  }
  return { type: 'text', value: formatTotalCost() }
}
```

함수 하나, 23줄. 토큰 카운터를 직접 읽어서 텍스트 한 줄로 돌려준다. (실제 코드에는 **overage 사용자** 분기와 **ANT 내부 사용자** 분기가 위에 추가로 있지만 본질은 같다.) **LLM은 호출되지 않는다**. 메시지 히스토리에 들어가지도 않는다. 사용자가 결과를 볼 뿐이다.

`/clear`도 같은 타입이다. 더 짧다.

```typescript
// src/commands/clear/clear.ts
export const call: LocalCommandCall = async (_, context) => {
  await clearConversation(context)
  return { type: 'text', value: '' }   // 빈 문자열도 OK
}
```

대화를 비우고, 빈 문자열을 돌려준다. **값보다 부수효과(side effect)가 본질**인 명령이다.

언제 `local`을 쓰는가? **두 가지 케이스**.

| 케이스 | 예시 |
|---|---|
| 결정적 계산 (LLM 추론 불필요) | `/cost`, `/insights`, `/version` |
| 부수효과만 필요 (LLM 응답 무의미) | `/clear`, `/exit`, `/logout`, `/compact` |

이 둘 다 — **LLM에 보내봤자 토큰 낭비**다. 클라이언트가 직접 처리하면 0 토큰, 즉시 응답.

### 타입 3: `local-jsx` — **대화형 UI를 띄운다**

`/config`. 진짜 코드는 6줄 — 그중 `call` 함수 본문은 한 줄이다.

```typescript
// src/commands/config/config.tsx
import { Settings } from '../../components/Settings/Settings.js'
import type { LocalJSXCommandCall } from '../../types/command.js'

export const call: LocalJSXCommandCall = async (onDone, context) => {
  return <Settings onClose={onDone} context={context} defaultTab="Config" />
}
```

JSX다. **React 컴포넌트**를 돌려준다. Claude Code가 그걸 받아서 터미널에 그린다. 5장(터미널 UI)에서 본격적으로 보는 그 **Ink + React** 패턴이 여기서 미리 등장한다.

핵심 차이는 — **`onDone` 콜백을 받는다는 사실**이다. 사용자가 언제 끝낼지 모르는 명령이다. `/cost`는 즉시 끝. `/config`는 **사용자가 화살표로 항목을 고르고, Enter로 선택하고, 'q'로 닫을 때**까지 화면에 떠 있다. 그 닫힘 이벤트가 `onDone`이다.

```
prompt:    호출 → 결과 → 끝
local:     호출 → 결과 → 끝
local-jsx: 호출 → UI 띄움 → 사용자 조작... → onDone() → 끝
```

언제 `local-jsx`를 쓰는가? **사용자와 대화가 필요할 때**. 설정 변경(`/config`), 권한 룰 편집(`/permissions`), 에이전트 관리(`/agents`), MCP 서버 추가(`/mcp`), 플러그인 마켓플레이스(`/plugin`). 다 멀티스텝, 멀티 키 입력이 필요한 작업이다.

> 💡 **`local-jsx`가 터미널에 React인 게 이상하면.** 터미널 UI에 React를 쓰는 라이브러리가 **Ink**다. React 컴포넌트를 돌려주면, Ink가 ANSI 문자열로 변환해서 그려준다. 5.1에서 **왜 굳이 React인가**를 본격적으로 본다. 지금은 "React 컴포넌트 = 터미널 위젯" 정도로 알고 가자.

### 세 타입이 공유하는 패턴: lazy load

세 타입 다 `index.ts`에 최소 메타데이터만 두고, 진짜 구현은 별도 파일에 둔다. `cost/index.ts`를 보자.

```typescript
// src/commands/cost/index.ts
const cost = {
  type: 'local',
  name: 'cost',
  description: 'Show the total cost and duration of the current session',
  supportsNonInteractive: true,
  load: () => import('./cost.js'),   // ← 핵심
} satisfies Command
```

`load: () => import('./cost.js')`. **동적 import**다. 명령을 실제로 호출하는 순간에야 `cost.ts`를 로드한다. 시작 시점에는 로드하지 않는다.

왜 이렇게 하는가? **시작 시간 때문**이다 (1.1에서 본 그 30ms 부트스트랩 기억나는가). 100개가 넘는 명령이 있는데 (실제 `commands/` 디렉토리 102개), 그 모든 구현 코드를 시작할 때 다 로드하면 — 첫 화면이 뜨는 데 100ms씩 더 걸린다. 매번. 사용자는 거의 모든 명령을 안 쓴다. 그래서 — 메타데이터만 미리 로드, 구현은 호출되는 그 순간에 로드.

> ⚙️ **추측이 아니라 코드의 docstring이 직접 말한다.** `cost/index.ts` 첫 줄 docstring (verbatim):
> "Cost command - minimal metadata only. Implementation is lazy-loaded from cost.ts to reduce startup time."
>
> 위 한 줄짜리 분석("메타데이터만 미리 로드, 구현은 호출되는 그 순간에 로드")이 코드 안에 명시적으로 박혀 있다. 단순한 관행이 아니라 문서화된 디자인 결정이다.

```typescript
// 호출 시점에야 진짜 코드를 가져옴
case 'local': {
  const module = await command.load()  // ← 여기서 import 발생
  const result = await module.call(args, ctx)
  break
}
```

"필요할 때만 로드"라는 단순한 규칙이 시작 시간을 몇 배 빠르게 만든다.

> 🔬 **Deep Dive — 왜 `prompt` 타입은 lazy load 안 하나?** 정확히는 **`getPromptForCommand`만** 미리 로드된다. `commit.ts`를 보면 — 거대한 `getPromptContent()` 헬퍼와 `executeShellCommandsInPrompt` 같은 무거운 의존성이 모듈 import에 다 들어와 있다. 왜 lazy load 안 했을까? 답: 프롬프트 명령은 자동완성 시점에 메타데이터만 보여야 한다. `description`, `argumentHint`가 로드되어 있어야 사용자가 `/`를 쳤을 때 목록에 뜬다. 그래서 메타데이터 + 프롬프트 함수는 미리 로드, 무거운 실행 함수만 lazy하게 분리하는 패턴이 일반적이다. `local`/`local-jsx`는 실행 함수가 본체라 통째로 lazy로 묶을 수 있다.

### 요약 표

| | `prompt` | `local` | `local-jsx` |
|---|---|---|---|
| LLM에 가나? | ✅ | ❌ | ❌ |
| 결과 형태 | 메시지 (LLM에 들어감) | `{type, value}` 객체 | React 노드 |
| 실행 시간 | 길다 (LLM 추론) | 즉시 | 사용자 조작 동안 (수 초~수 분) |
| 토큰 비용 | 든다 | 0 | 0 |
| `allowedTools` | 있음 | 없음 | 없음 |
| 대표 예시 | `/commit`, `/init`, `/review` | `/cost`, `/clear`, `/exit` | `/config`, `/permissions`, `/agents` |
| 결정 기준 | 추론이 필요한가? | 결정적 계산 + 부수효과 | **대화형 UI가 필요한가?** |

### 어떤 타입을 골라야 하나 — 결정 흐름

새 명령을 만들 때 어떤 타입을 골라야 하나? 세 질문을 순서대로.

```
질문 1: "사용자가 *여러 번 입력*해야 하나? (선택, 폼, 페이지 이동)"
   → YES → local-jsx
   → NO  ↓

질문 2: "LLM의 *추론*이 결과의 본질인가?"
   → YES → prompt
   → NO  ↓

질문 3: "결정적 계산이거나 부수효과만 필요한가?"
   → YES → local
```

세 질문이 다 **No**면 — 그 명령은 슬래시 명령으로 만들지 마라. 일반 채팅으로 충분하다는 뜻이다.

## Python으로 옮기면

세 타입을 Python으로 모델링하면 이렇게 생겼다.

```python
from __future__ import annotations
from dataclasses import dataclass
from typing import Awaitable, Callable, Literal, Any, Protocol


# ─── 결과 타입 ────────────────
@dataclass
class TextResult:
    type: Literal["text"] = "text"
    value: str = ""


# ─── 세 가지 명령 타입 ────────────────
@dataclass
class PromptCommand:
    type: Literal["prompt"] = "prompt"
    name: str = ""
    description: str = ""
    allowed_tools: list[str] | None = None
    progress_message: str = ""
    # 명령이 호출될 때 진짜 프롬프트를 만들어 돌려준다
    get_prompt: Callable[[str], Awaitable[str]] = None


@dataclass
class LocalCommand:
    type: Literal["local"] = "local"
    name: str = ""
    description: str = ""
    # lazy load: 실제 구현은 호출 시점에 import
    load: Callable[[], Awaitable[Any]] = None


@dataclass
class LocalJSXCommand:
    type: Literal["local-jsx"] = "local-jsx"
    name: str = ""
    description: str = ""
    load: Callable[[], Awaitable[Any]] = None


Command = PromptCommand | LocalCommand | LocalJSXCommand


# ─── 디스패처 ────────────────
async def dispatch_command(cmd: Command, args: str, ctx, messages, on_done):
    match cmd:
        case PromptCommand():
            content = await cmd.get_prompt(args)
            messages.append({"role": "user", "content": content})
            # → query.ts (에이전트 루프)로 흘러감
        
        case LocalCommand():
            module = await cmd.load()  # 여기서야 진짜 import
            result = await module.call(args, ctx)
            print(result.value)  # 직접 화면에
        
        case LocalJSXCommand():
            module = await cmd.load()
            # Textual의 Widget을 리턴 (Python 터미널 UI)
            widget = await module.call(on_done, ctx, args)
            await mount_widget(widget)  # 사용자 조작 대기
            # 사용자가 닫으면 on_done()이 호출되어 화면에서 사라짐
```

세 타입이 명확하게 구분된다. 디스패처는 `match`로 분기. 각 타입이 자기 시그니처를 가지고 자기 흐름을 탄다.

> 💡 **Python의 Textual이 Ink와 비슷.** Python에서 터미널에 대화형 UI를 만들 때 쓰는 라이브러리. Textual은 **Widget** 트리를 구성해서 ANSI로 그려준다. Claude Code의 `local-jsx`가 React 컴포넌트를 돌려주는 것과 본질이 같다. 5장에서 왜 굳이 컴포넌트 트리인가를 본다.

## 핵심 정리

- 슬래시 명령은 세 가지 타입: **`prompt`** (LLM에 보낼 프롬프트 생성), **`local`** (LLM 없이 직접 처리), **`local-jsx`** (대화형 React UI).
- 결정 기준: 사용자가 조작해야 하면 `local-jsx`, 추론이 본질이면 `prompt`, 계산/부수효과면 `local`.
- 세 타입 모두 **lazy load** 패턴을 쓴다 (`load: () => import('./X.js')`). 시작 시점엔 메타데이터만, 실제 구현은 호출되는 순간에 import. 1.1의 30ms 부트스트랩이 가능한 이유 중 하나.
- `local-jsx`가 React 컴포넌트를 돌려주는 게 이상해 보일 수 있는데 — Claude Code의 **터미널 UI 자체가 React+Ink**다. 5장에서 본격적으로.
- 다음 챕터(4.3): `prompt` 타입의 `allowedTools` — 명령이 도는 동안 도구 사용을 화이트리스트로 좁히는 안전 메커니즘.
