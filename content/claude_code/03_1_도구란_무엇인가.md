# 3.1 도구란 무엇인가 — 함수가 아니라 "1급 시민"

---

## 이 챕터에서 배우는 것

- 0.1과 2.1에서 계속 써왔던 "도구"라는 단어가 진짜로 무엇을 뜻하는지
- 도구가 **단순한 Python 함수와 어떻게 다른지**, 그리고 왜 다른지
- 도구가 함수가 아니라 마이크로서비스에 가까운 이유
- 그래서 다음 챕터(3.2)에서 만날 47개 필드짜리(메서드 34 + 속성 13) Tool 인터페이스가 왜 그렇게 큰지

---

## 사용자 경험에서 출발

지금까지 "도구"라는 단어를 계속 써왔다. "Claude가 도구를 호출한다", "Read 도구로 파일을 읽는다", "Bash 도구로 명령을 실행한다". 사용자 입장에서 이건 그냥 기능처럼 느껴진다. 파일을 읽을 수 있는 기능, 명령을 실행할 수 있는 기능.

근데 잠깐. 코드 관점에서 도구가 정확히 뭔가? 그냥 함수인가?

```python
def read(file_path: str) -> str:
    return open(file_path).read()
```

이게 도구인가? 틀린 건 아닌데, 한참 부족하다. 진짜 도구는 위 함수에 몇 가지가 더 붙어 있어야 한다. 그게 무엇이고 왜 필요한지가 이 챕터의 주제다.

---

## 본문

### 가장 단순한 정의

도구의 가장 단순한 정의는 이거다.

> **도구 = LLM이 호출할 수 있는 함수.**

그리고 이 정의는 본질적으로 맞다. 도구는 결국 호출되어 실행되고 결과를 돌려주는 무언가다. 함수의 본질이 그렇다.

근데 호출 가능한 게 끝이 아니다. **어떻게 호출할지를 LLM이 알아야** 한다. 그러려면 도구에 다음이 필요하다.

### 도구가 함수보다 더 가져야 하는 것들

도구가 보통의 함수와 다른 점을 카탈로그로 보자.

| # | 항목 | 왜 필요한가 |
|---|---|---|
| 1 | **이름 (`name`)** | LLM이 어떤 도구를 부를지 식별 |
| 2 | **설명 (`description`)** | LLM에게 언제 이걸 써야 하는지 자연어로 알림 |
| 3 | **입력 스키마 (`inputSchema`)** | LLM이 어떤 인자를 줘야 할지 JSON Schema로 알림 |
| 4 | **출력 형식** | Claude가 결과를 어떻게 해석할지 알 수 있어야 함 |
| 5 | **권한 체크 (`checkPermissions`)** | 위험한 작업이면 사용자에게 묻기 |
| 6 | **입력 검증 (`validateInput`)** | 권한 묻기 전에 말도 안 되는 인자 거르기 |
| 7 | **취소 가능성** | 사용자가 도중에 멈출 수 있어야 함 |
| 8 | **진행 상황 보고** | 오래 걸리는 작업은 **spinner와 진행률**을 표시 |
| 9 | **UI 렌더링** | 도구 결과를 어떻게 화면에 그릴지 (단순 텍스트? diff? 박스?) |
| 10 | **에러 처리** | 실패했을 때 어떻게 알릴지, 재시도 가능한지 |
| 11 | **메타데이터** | 읽기 전용인가? 동시 실행 가능한가? 파괴적인가? |
| 12 | **권한 룰 매칭** | `Bash(git *)` 같은 패턴에 매칭되어야 함 |

12개다. 진짜 `Tool` 인터페이스에는 더 있다(다음 챕터에서 본다). 한 도구가 이 모든 걸 다 들고 있어야 한다.

> 💡 **Python 비유:** 평범한 함수에 데코레이터로 위 12가지를 덧붙인다고 생각하면 안 된다. 그러기엔 너무 많다. 데코레이터 12개를 쌓는 거나, 함수를 클래스로 감싸는 거나 둘 중 하나다. **클래스가 더 자연스럽다**. 그래서 Claude Code의 도구도 클래스(또는 객체)다.

### 그래서 도구는 함수가 아니라 마이크로서비스에 가깝다

이렇게 생각해보자. 도구 하나는 작은 마이크로서비스다.

```
  ┌─────────────────────────────────────┐
  │  도구: Read                          │
  │                                     │
  │  ┌─ 입력 스키마 (Pydantic/Zod)      │
  │  ├─ 권한 체크 (validateInput)      │
  │  ├─ 권한 묻기 (checkPermissions)   │
  │  ├─ 실행 (call)                    │
  │  ├─ 진행 상황 보고 (onProgress)     │
  │  ├─ 결과 렌더링 (renderResult)     │
  │  ├─ 에러 렌더링 (renderError)      │
  │  └─ 메타데이터 (isReadOnly, ...)    │
  └─────────────────────────────────────┘
```

마이크로서비스에는 입력 검증, 인증, 권한, 비즈니스 로직, 응답 포맷, 에러 처리, 로깅, 모니터링이 다 있다. 도구도 똑같다. **단지 호출하는 주체가 사람이 아니라 LLM일 뿐.**

이 관점이 중요한 이유 — 도구를 만들 때 함수처럼 생각하면 빼먹는 게 너무 많다. 마이크로서비스처럼 생각해야 "권한은 어떻게 처리하지? UI는 어떻게 그리지? 취소되면 어떡하지?" 같은 질문이 자연스럽게 떠오른다.

### "1급 시민"이라는 표현의 의미

이 챕터 부제를 "함수가 아니라 1급 시민"이라고 붙였다. **1급 시민(first-class citizen)**이라는 표현은 보통 프로그래밍 언어 디자인에서 "변수에 담을 수 있고, 인자로 전달할 수 있고, 반환할 수 있는 것"을 가리킨다 (예: "함수는 1급 시민이다").

여기서 쓰는 의미는 살짝 다르다. 시스템 안에서 첫째 가는 시민이라는 뜻이다. 즉:

- **시스템이 도구를 알고 있다.** 도구 레지스트리가 있고, 권한 시스템이 도구별로 동작하고, UI가 도구별로 다른 렌더링을 한다.
- **시스템 곳곳이 도구에 적응한다.** 새 도구를 추가하면 자동으로 LLM 프롬프트에 들어가고, 자동으로 권한 룰의 대상이 되고, 자동으로 UI에 렌더링된다.
- **도구가 부수적인 것이 아니다.** "필요해서 더한 함수 모음" 같은 게 아니라, 시스템 디자인의 중심에 있다.

`Tool` 인터페이스가 47개 필드(34 메서드 + 13 속성)인 이유다. 부수적인 함수면 그렇게 많을 필요가 없다. **시스템의 1급 시민이라서** 그렇다.

> ⚠️ **함정:** "그럼 Python 함수에 데코레이터 몇 개 붙이면 되는 거 아냐?" — 안 된다는 건 아니다. 작은 도구는 그렇게 만들 수 있다. 근데 도구가 늘어나기 시작하면 데코레이터로는 한계에 부딪힌다. 권한 패턴 매칭, UI 렌더링 정책, 동시성 안전성 같은 **교차 관심사(cross-cutting concerns)**가 너무 많아진다. 이 시점에 클래스/인터페이스로 정형화 하는 게 거의 필연이다. Claude Code의 `Tool` 인터페이스는 그 정형화의 결과물이다.

## Python으로 옮기면

도구를 클래스로 모델링한 미니 버전을 보자.

```python
from abc import ABC, abstractmethod
from typing import Generic, TypeVar
from pydantic import BaseModel

I = TypeVar("I", bound=BaseModel)

class ToolBase(ABC, Generic[I]):
    name: str
    description: str
    input_schema: type[I]
    
    @abstractmethod
    async def call(self, input: I) -> str:
        """실제 실행."""
        ...
    
    async def validate_input(self, input: I) -> None:
        """기본은 통과. 도구별로 override."""
        return
    
    async def check_permission(self, input: I) -> bool:
        """기본은 허용. 도구별로 override."""
        return True
    
    def render_progress(self, input: I) -> str:
        return f"{self.name}: {input}"
    
    def render_result(self, result: str) -> str:
        return result
    
    @property
    def is_read_only(self) -> bool:
        return False  # 기본은 보수적으로


# 실제 도구 정의
class ReadInput(BaseModel):
    file_path: str

class ReadTool(ToolBase[ReadInput]):
    name = "Read"
    description = "Read a file from disk and return its contents"
    input_schema = ReadInput
    
    async def call(self, input: ReadInput) -> str:
        with open(input.file_path) as f:
            return f.read()
    
    def render_progress(self, input: ReadInput) -> str:
        return f"Reading {input.file_path}"
    
    @property
    def is_read_only(self) -> bool:
        return True
```

핵심:

1. **추상 클래스**로 도구가 무엇이어야 하는지 정의 (`ToolBase`).
2. **Pydantic 모델**로 입력 스키마 (`ReadInput`).
3. **각 도구**는 추상 클래스를 상속해서 자기 책임을 채운다 (`ReadTool`).
4. **기본값**이 있는 메서드는 `validate_input`, `check_permission`, `render_progress` 처럼 **override 안 하면 안전한 기본 동작**을 한다.

이 패턴이 Claude Code의 `Tool` 인터페이스 + `buildTool` 팩토리와 거의 같다. 다음 챕터(3.2)에서 진짜를 본다.

> 🔬 **Deep Dive — 함수형으로도 가능한가?** 가능하다. 추상 클래스 대신 **큰 dict**를 만들어서 거기에 모든 메서드를 함수로 넣을 수도 있다. TypeScript의 Claude Code는 사실 그쪽에 더 가깝다. `class` 키워드를 안 쓰고 `buildTool({...})` (`Tool.ts:783`) 로 객체 리터럴을 만든다. 그리고 `buildTool` 안에는 `TOOL_DEFAULTS`라는 7개 fail-closed 기본값 객체가 있어서 정의 안 한 메서드를 보수적으로 (e.g. `isReadOnly: false`, `isConcurrencySafe: false`) 채워 넣는다. 클래스든 객체든 본질은 같다 — "도구가 들고 있어야 할 47개 책임을 한 군데에 모으되, 안 쓴 자리는 안전한 기본값으로". 자세한 건 **3.3**에서.

## 핵심 정리

- 도구는 함수가 아니다. 함수보다 큰 것. 12개 이상의 책임을 한 군데에 모은 **객체** 또는 **인터페이스 구현체**다.
- 도구가 들고 있어야 할 책임 카탈로그: 이름, 설명, 입력 스키마, 권한 체크, 입력 검증, 취소 처리, 진행 보고, 결과 렌더링, 에러 처리, 메타데이터, 권한 룰 매칭, ... (Claude Code의 `Tool` type은 **47개 필드** — 34 메서드 + 13 속성)
- **도구는 마이크로서비스에 가깝다.** 입력 검증, 인증, 권한, 실행, 응답 포맷, 에러 처리가 다 있다. 단지 호출하는 주체가 사람이 아니라 LLM일 뿐.
- "1급 시민"이라는 건 — 시스템이 도구를 알고 있고, 도구별로 적응하고, 도구가 시스템 디자인의 중심에 있다는 뜻.
- Python으로 옮기면 추상 클래스(`ABC`) + Pydantic 모델로 자연스럽게 표현된다. 다음 챕터에서 진짜 `Tool` 인터페이스의 50개 메서드를 본다.
