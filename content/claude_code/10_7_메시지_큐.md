## 9.1 설계의 빠진 자리

9.1 ~ 9.5 의 mini_claude 는 *한 종류의 입력* 만 받는다. REPL 에서 사용자가 친 텍스트. 그게 끝.

```python
# src/mini_claude/main.py — 9.5 의 흐름 (단순화)
while True:
    user_input = await asyncio.to_thread(input, "> ")
    if not user_input.strip():
        continue
    async for chunk in query(user_input=user_input, ...):
        ...
```

이게 *최소한의 에이전트 골격* 으로는 충분했다. 하지만 *확장* 을 시작하면 곧장 빈 자리가 드러난다.

**4 가지 상황** — 진짜 코드의 큐가 처리하는 자리들.

| 상황 | 9.1~9.5 의 처리 | 큐 있으면 |
|---|---|---|
| 사용자가 도구 실행 중 새 입력 추가 | _next iteration 까지 못 받음_ — REPL 입력 자체가 막힘 | `now` 우선순위로 도구 abort 가능 |
| 백그라운드 task 완료 (e.g. `Bash(npm test &)` 가 끝남) | 완료 통지를 받을 *자리 자체가 없음* | `task_complete` push → 다음 LLM 호출에 attachment |
| 외부 트리거 (cron, webhook) | OUT — 트리거가 들어올 *경로 없음* | `proactive_tick` push → 모델이 자동으로 컨텍스트 인식 |
| 팀원 에이전트가 idle 됨 (10.8) | OUT — 팀 자체 없음 | 메일박스에 push → lead 가 *polling 없이* 알아챔 |

특히 *네 번째* 가 *10.8 에이전트 팀* 의 핵심 — 8.4 의 *polling 없는 fan-in* 이 큐의 한 인스턴스로 자연스럽게 표현된다.

> 💡 **빠진 자리의 정체**: queryLoop 의 *while 루프 매 반복마다* 확인하는 *모듈 싱글턴 채널*. 진짜 코드의 ``messageQueueManager.ts:53`` 가 그 자리. mini 가 이걸 *50 줄짜리 deque* 로 회수.

## 완성된 모습 먼저 보기

큐의 _전체 API_ 가 *세 함수* 다.

```python
from mini_claude import message_queue

# ── 아무 데서나 push (도구·외부 트리거·서브에이전트) ──
message_queue.push("npm test 완료: 42 passed, 0 failed", source="background_task")
message_queue.push("새 이메일 도착: 'PR review needed'", source="webhook")
```

push 된 항목은 *다음 LLM 호출 직전* 에 agent.py 가 자동으로 *drain* 해서 *tool_results 의 attachment* 로 합류시킨다. 모델은 그 항목을 *다음 턴의 컨텍스트* 로 본다.

```python
# ── agent.py 의 query() 안에서 자동 처리 ──
queued = message_queue.drain()
for item in queued:
    tool_results.append({
        "type": "text",
        "text": f"[queued/{item.source}] {item.content}",
    })
```

다음 LLM 호출에서 모델은 *도구 결과 + 큐 항목* 을 함께 본다.

```text
user role:
  [tool_result] ls 의 결과...
  [text] [queued/background_task] npm test 완료: 42 passed, 0 failed
  [text] [queued/webhook] 새 이메일 도착: 'PR review needed'

assistant role:
  "테스트가 모두 통과했으니 PR review 메일을 처리하겠습니다..."
```

모델이 *큐 항목을 자연스럽게 받아들임* — *시스템 메시지 추가* 없이, *도구 결과의 연속* 으로 보임.

> ⚙️ **왜 attachment 인가**: *별도 user 메시지* 로 추가하면 _alternating_ (user→assistant→user→...) 규칙이 깨질 수 있다. *tool_results 의 content 배열에 text block 한 줄 더하기* — Anthropic API 가 *user role 의 content* 로 *복합 블록* 을 허용한다는 사실의 정직한 활용.

## 4 입력자 — 큐가 받는 것

진짜 코드의 큐는 *네 입력자* 를 받는다 (2.2 Deep Dive).

### 1. 사용자 입력 — REPL 도중 들어오는 새 텍스트

도구 실행 중 사용자가 또 텍스트를 친 경우. 진짜 코드는 `now` 우선순위로 push 해서 *현재 도구를 abort 하고 즉시 처리*. mini 는 *REPL 입력 자체가 동기 블록* 이라 이 시나리오가 OUT — 9.5 의 `asyncio.to_thread(input, "> ")` 가 *턴 끝까지* 막혀 있다.

### 2. task 완료 통지

백그라운드 task (`Bash(npm test &)`, 서브에이전트, 원격 에이전트) 가 끝났을 때 push. mini 에서는 *9.5 의 서브에이전트가 동기 await* 라 이 자리도 OUT. 하지만 *향후 백그라운드 도구* 추가 시 _자연스러운 진입점_.

### 3. 프로액티브 — 크론·틱·webhook

진짜 코드는 *세션 timer* + *외부 webhook* + *MCP notifications/new_message* 로 push. mini 는 *외부 트리거 자리 자체가 없지만*, 큐 모듈을 import 한 *외부 스크립트* 가 push 하면 *동작은 한다*. 즉 _인프라는 있고 트리거만 OUT_.

### 4. 고아 퍼미션 응답

진짜 코드는 *원격 control 세션* 에서 권한 다이얼로그 응답이 *뒤늦게* 도착하는 경우를 큐로 받는다. mini 는 _interactive prompt_ 가 동기라 OUT.

**mini 의 실제 IN — 1.5 개 정도**: ②, ③ 의 *인프라만* 살아 있고, ①·④ 는 OUT. *그래도 충분하다* — 10.8 에서 ②·③ 의 응용으로 팀 알림이 만들어진다.

## 구현 — `message_queue.py` 한 파일 50 줄

```python
# src/mini_claude/message_queue.py
from __future__ import annotations
from collections import deque
from dataclasses import dataclass


@dataclass
class QueueItem:
    content: str
    source: str = "unknown"


# ── 모듈 싱글턴 — 진짜 코드의 messageQueueManager 와 같은 정신 ─────
_queue: deque[QueueItem] = deque()


def push(content: str, source: str = "unknown") -> None:
    """큐에 항목 추가. 모듈 어디서든 호출 가능."""
    _queue.append(QueueItem(content=content, source=source))


def drain() -> list[QueueItem]:
    """큐 전체를 한 번에 빼낸다. 다음 LLM 호출 직전 호출."""
    items = list(_queue)
    _queue.clear()
    return items


def size() -> int:
    return len(_queue)


def clear() -> None:
    _queue.clear()
```

*네 함수* + dataclass 한 개. 전부 *50 줄*. 우선순위 없음 — *순서 그대로*. abort 신호 없음 — *모두 next 로 처리*.

> 💡 **왜 deque 인가**: `list` 도 가능하지만 `collections.deque` 의 `append` / `popleft` 가 *O(1)*. 큐 항목이 많이 쌓이는 경우 (예: 활발한 webhook) 에도 *상수 시간*. Python 의 표준 도구로 *추가 의존성 없이* 큐를 만드는 가장 쉬운 방법.

> ⚠️ **모듈 싱글턴의 위험**: 한 프로세스에 *큐 인스턴스 하나*. 9.5 의 서브에이전트가 push 하면 *부모도 본다*. mini 의 _이번 챕터에서는_ OK — 부모/자식이 *같은 컨텍스트를 공유* 한다고 가정. 10.8 에서 *팀원별 격리된 메일박스* 를 만들 때 이 한계가 *해결되어야 할 자리* 로 드러난다.

## agent.py 의 통합 자리 — 한 자리

`query()` 의 while 루프 *끝* — `state.add_user(tool_results)` *직전*. 도구 결과가 *이미 모인 상태* 에서 큐 항목을 *합류*.

```python
# src/mini_claude/agent.py — tool_use 분기 끝
# ── 메시지 큐 (10.7) — 외부 push 된 항목을 다음 LLM 호출에 attachment ──
queued = message_queue.drain()
for item in queued:
    tool_results.append({
        "type": "text",
        "text": f"[queued/{item.source}] {item.content}",
    })

state.add_user(tool_results)
# while 루프의 다음 iteration → 다음 LLM 호출에 attachment 가 같이 보임
```

*세 줄 변경*. while 루프의 *매 iteration* 에서 큐를 비우고, *비워낸 항목들* 을 도구 결과 옆에 text block 으로 끼워 넣는다. 다음 LLM 호출에 *자연스럽게 포함*.

> 💡 **왜 매 iteration 인가**: 진짜 코드는 *도구 실행 사이 사이* 에 큐를 확인한다 — *최대한 빨리* 새 입력을 모델에 전달하려는 정신. mini 는 *도구 결과를 모은 직후* 한 번 확인 — *한 라운드 늦지만 단순*. 도구 실행 중간에 push 된 항목도 *그 iteration 끝* 에 처리.

> ⚙️ **`end_turn` 분기에서는 큐 처리 안 함**: stop_reason 이 `end_turn` 또는 `tool_use 아님` 이면 *while 루프가 끝나서* 큐 확인을 안 한다. 만약 그 시점에 큐에 항목이 있으면 *다음 사용자 입력 시점까지 대기*. 진짜 코드는 *턴 종료 시점에 `later` 우선순위 항목을 처리* 하지만 mini OUT — *항상 다음 LLM 호출에 합류* 가 정책.

## 진짜 코드에서는 — `messageQueueManager.ts` 의 구조

`src/utils/messageQueueManager.ts` + `src/query/queue.ts` 합쳐 *약 750 줄*. mini 의 *50 줄* 과 *15 배 차이*.

### 1. 우선순위 — `PRIORITY_ORDER`

진짜 코드의 우선순위 (`queue.ts:48`):

```typescript
const PRIORITY_ORDER = ['now', 'next', 'later'] as const
```

- **`now`**: *현재 도구를 abort 하고 즉시 처리*. e.g. 사용자가 도구 실행 중 새 입력
- **`next`**: *다음 LLM 호출 직전 처리*. 가장 흔한 자리 — 백그라운드 task 완료 등
- **`later`**: *현재 턴이 끝난 뒤 처리*. e.g. 프로액티브 알림 — 사용자 응답 마무리 끝나면

mini 는 셋 다 *next 로 통일*. abort 메커니즘이 없어서 `now` 가 의미 없고, `later` 도 mini 의 단순한 흐름에서는 *그냥 next 로 충분*.

### 2. 4 입력자 — 각자의 push 자리

| 입력자 | push 자리 (진짜 코드) | mini 대응 |
|---|---|---|
| 사용자 입력 | `REPL.tsx:2143` — keypress handler 안 | OUT (동기 input) |
| task 완료 | `bashTool.ts:567` — background task done | OUT (백그라운드 없음, 인프라만) |
| 프로액티브 | `proactiveTick.ts:89` — setInterval callback | OUT (트리거 없음, 인프라만) |
| 고아 퍼미션 | `remoteIO.ts:312` — control session response | OUT (interactive only) |

mini 는 *입력자가 비어 있는 인프라* — 큐는 동작하지만 *기본 상태에서는 항목이 안 들어옴*. 10.8 에서 *팀원 idle 알림* 이 첫 진짜 입력자가 된다.

### 3. abort 친화적 머지 — `queryLoop` 안의 흐름

진짜 코드의 queryLoop (`query.ts:204`) 는 *도구 실행 중에도* 큐를 본다. `now` 항목이 push 되면 `abortController.signal` 을 깨운다.

```typescript
// src/query/query.ts:412 — 압축 인용
for (const block of tool_uses) {
  const toolPromise = executeTool(block, abortController.signal)
  const queuePromise = queue.waitForNow()
  await Promise.race([toolPromise, queuePromise])
  if (queue.hasNow()) {
    abortController.abort()
    // 다음 iteration 에서 큐 항목 처리
    break
  }
}
```

`Promise.race` 로 *도구 실행 vs 큐 신호* 를 동시에 기다린다. mini 는 *순차 처리* — 도구 실행 끝나야 큐 확인. *abort 자체가 OUT* 이라 자연스러운 단순화.

### 4. attachment 변환 — `convertQueuedToAttachment`

진짜 코드는 큐 항목을 *5 가지 형태의 attachment* 로 변환 (`queue.ts:201`):

- `task_complete` → `<task_complete name="...">결과</task_complete>`
- `proactive` → `<proactive_message timestamp="...">내용</proactive_message>`
- `user_input` → user role 의 *별도 메시지* (alternating 깨는 경우 있음)
- `permission_response` → `<permission_response request_id="...">decision</permission_response>`
- `mcp_notification` → `<mcp_notification server="...">payload</mcp_notification>`

mini 는 *전부 `[queued/<source>] <content>` 한 형식*. XML 태그로 모델한테 *구조화된 신호* 를 주는 진짜 코드의 정신은 OUT — *단순 텍스트 prefix* 로 통일.

### 5. 압축 비율

| 진짜 코드 | mini | 비율 |
|---|---|---|
| `messageQueueManager.ts` 약 380 줄 | `message_queue.py` 50 줄 | **7.6 : 1** |
| `queue.ts` 약 370 줄 (변환·머지) | (agent.py 의 3 줄) | **123 : 1** |
| 3 우선순위 | 0 (모두 next) | — |
| abort 친화적 머지 | 순차 처리 | — |
| 5 attachment 형식 | 1 형식 (`[queued/<source>]`) | — |

**핵심 (모듈 싱글턴 큐, push/drain API, attachment 합류) 은 살아 있고**, 엔터프라이즈 기능 (우선순위·abort·구조화 attachment) 은 OUT.

## 진짜로 활용해 보기

세 시나리오. 첫째는 *직접 push*, 둘째·셋째는 *외부 트리거*.

### 시나리오 1: 직접 push (대화 도중 외부 알림 주입)

mini_claude REPL 안에서 *다른 터미널* 에서 push 가능. Python REPL 을 하나 더 띄우고:

```python
# 다른 터미널의 python 또는 IPython
import sys
sys.path.insert(0, "/path/to/mini_claude/src")
from mini_claude import message_queue

message_queue.push("긴급: 배포 실패. CI 로그 확인 필요", source="cron_check")
```

mini_claude 의 *다음 LLM 호출* 에서 이 메시지가 attachment 로 들어간다. 모델이 *자동으로* 인지하고 응답:

```text
> ls

[Bash] {'command': 'ls'}
README.md  main.py  tests/

(다음 턴에서:)
긴급 알림이 들어왔습니다. CI 로그를 확인하겠습니다 — Bash(cat logs/ci.log) ...
```

대화 흐름의 *중간에* 자연스럽게 합류. *시스템 메시지 없이* 텍스트 attachment 만으로 가능.

### 시나리오 2: 백그라운드 task 시뮬레이션

`Bash` 도구가 *백그라운드 모드* 를 지원한다고 가정하면 (현재 mini 는 OUT). 도구 호출 시 *별도 thread* 에서 push:

```python
# src/mini_claude/tools/bash.py — 가상의 백그라운드 모드 추가 예시
import threading

async def call(self, args, context):
    if args.get("background", False):
        def run():
            result = subprocess.run(args["command"], capture_output=True)
            message_queue.push(
                f"task complete: {result.stdout.decode()[:200]}",
                source="background_task",
            )
        threading.Thread(target=run, daemon=True).start()
        return "(백그라운드 실행 시작)"
    # 기본 동작 ...
```

모델이 `Bash(npm test &, background=true)` 같은 호출을 하면, *즉시 "(백그라운드 실행 시작)"* 응답 받고 *다음 도구* 로. 그 동안 thread 가 끝나서 큐에 push. *몇 턴 뒤* attachment 로 들어와서 모델이 *결과를 인지*. 큐가 없으면 *완전히 불가능* 한 흐름.

### 시나리오 3: 외부 webhook 트리거

FastAPI 같은 간단한 웹훅 서버를 *별도로 띄우고*, 그 서버가 `message_queue.push` 호출:

```python
# webhook_server.py — 별도 프로세스로 띄움
from fastapi import FastAPI
from mini_claude import message_queue

app = FastAPI()

@app.post("/notify")
def notify(content: str, source: str = "webhook"):
    message_queue.push(content, source=source)
    return {"ok": True}
```

근데 *별도 프로세스* 면 *큐 모듈 싱글턴이 분리* — 안 통한다. 진짜 webhook 통합은 *같은 프로세스 내 thread/asyncio task* 거나 *외부 메시지 브로커 (Redis 등)* 가 필요. mini 의 *모듈 싱글턴 한계* 가 여기서 드러난다.

> 💡 **모듈 싱글턴의 경계**: *같은 Python 프로세스* 안에서만 동작. *교차 프로세스 trigger* 는 별도 메커니즘 필요 — Redis pub/sub, 파일 watching, OS signal 등. mini 의 *이 챕터 범위는* "한 프로세스 안의 다양한 source" 까지. *프로세스 경계* 는 향후 확장 (10.x?) 의 자리.

## 핵심 정리

- **9.1 의 빠진 자리** — queryLoop 가 매 반복마다 확인하는 *외부 입력 채널* 이 mini 에는 없었다. 메시지 큐가 *그 자리* 를 채운다.
- **모듈 싱글턴 + deque + 50 줄** — push / drain / size / clear 네 함수 + QueueItem dataclass 한 개. 진짜 코드의 750 줄 인프라가 *기하학적으로 압축*.
- **agent.py 의 한 자리** — `state.add_user(tool_results)` 직전. *세 줄 변경* 으로 매 iteration 에서 큐 drain → attachment 합류.
- **4 입력자, mini 는 1.5** — 사용자/task 완료/프로액티브/고아 퍼미션 중 *task 완료·프로액티브 인프라만* 살아 있다. 트리거가 없을 뿐 *기반은 있다*.
- **이 큐가 10.8 의 토대** — *팀원의 idle 알림* 이 큐의 한 인스턴스 (메일박스). *polling 없는 fan-in* 이 큐의 자연스러운 응용.
- **OUT 정리** — 3 우선순위 (`now`/`next`/`later`), abort 친화적 머지, 5 attachment 형식, 프로세스 경계 통신. 모두 *학습용 단순화*.
