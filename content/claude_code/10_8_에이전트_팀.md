# 10.8 에이전트 팀 — in-process 메일박스로 협력하는 동등한 팀원들

## 이 챕터에서 배우는 것

- *왜* 10.3 (Hook), 10.6 (사용자 정의 에이전트), 10.7 (메시지 큐) _세 토대 위에야_ 에이전트 팀이 자연스럽게 얹히는지
- Node 의 `AsyncLocalStorage` 와 Python 의 `contextvars` 가 _같은 디자인_ 임 — 같은 프로세스 안의 N 팀원이 _async 호출 트리를 따라 자동 격리_
- 10.7 의 _모듈 싱글턴 큐_ 가 _팀원별 인스턴스_ 로 진화해 *격리된 메일박스* 가 되는 자리
- 10.3 의 Stop 훅이 _기다리던 진짜 활용처_ — 팀원의 turn 끝이 lead 에게 자동 알림
- `asyncio.create_task` + `asyncio.Queue` + `asyncio.Event` _셋만으로_ polling 없는 fan-in 이 가능한 이유
- 진짜 8.4 가 _1100 줄_ 인 자리를 mini 가 _400 줄_ 로 압축할 때 무엇이 빠지는지

## 8.4 가 푸는 자리, 10.7 의 한계

Part 8 의 끝, **8.4 에이전트 팀** 은 _peer 협업 모델_ 을 다뤘다. 8.1 (`AgentTool` 재귀) + 8.2 (`createSubagentContext` 격리) 의 공통 기반 위에, 두 가지 디자인 시도가 있었다:

- **8.3 코디네이터 모드** — 위계 (lead → 자식). 시스템 프롬프트로 역할 전환. _외부 미출시_.
- **8.4 에이전트 팀** — peer (동등한 팀원들). in-process 격리 + 공유 메모리. *2026-02 외부 experimental*, *2026-03 Claude Code Review 프로덕션* 채택.

10.8 은 8.4 의 _peer 모델_ 을 mini_claude 로 가져온다. 그런데 _혼자서는 작동 안 한다_ — 세 토대가 필요하다.

### 9.5 의 격리는 _한 단계_, 8.4 의 격리는 _N 명_

9.5 (`AgentTool`) 는 부모가 자식 하나를 *동기* 로 await — 한 번에 한 명, 끝까지 기다린다. 격리는 한 줄로 충분:

```python
child_state = ConversationState()  # 새 그릇 — 부모와 분리
```

8.4 는 _다르다_. 같은 프로세스 안에서 **N 명이 동시에** 일한다. `messages=[]` 한 줄로는 부족 — *호출 트리* 가 분기되면서 각자가 _자기 신원_ 을 들고 다녀야 한다. 어느 한 함수가 `current_agent_name()` 같은 걸 물었을 때, _누구의 컨텍스트에서 호출됐는지_ 따라 답이 달라야 한다.

> 💡 **모듈 변수는 race condition**: 만약 `_current_name: str = ""` 같은 전역 변수에 _매번_ 쓰고 읽으면, 두 팀원이 동시에 일할 때 *서로의 신원을 덮어쓴다*. _thread-local_ 도 안 된다 — async 는 같은 스레드에서 여러 task 가 돈다.

Node 가 푸는 답이 `AsyncLocalStorage` — _async 호출 트리를 따라 자동 격리되는 변수_. Python 의 `contextvars` (PEP 567, 2018) 가 _같은 디자인_. 8.4 본문이 이미 등가를 명시했다 ([§4](#contextvars--node-asynclocalstorage-의-python-등가) 에서 본격적으로 다룬다).

### 10.7 의 모듈 싱글턴이 팀에서는 *깨진다*

10.7 메시지 큐는 _모듈 싱글턴_ 한 벌이다:

```python
# mini_claude/message_queue.py
_queue: deque[QueueItem] = deque()
```

10.7 본문이 이 한계를 _명시적으로 적었다_:

> ⚠️ **모듈 싱글턴의 위험**: 한 프로세스에 *큐 인스턴스 하나*. 9.5 의 서브에이전트가 push 하면 *부모도 본다*. mini 의 _이번 챕터에서는_ OK — 부모/자식이 *같은 컨텍스트를 공유* 한다고 가정. 10.8 에서 *팀원별 격리된 메일박스* 를 만들 때 이 한계가 *해결되어야 할 자리* 로 드러난다.

10.8 의 답: **팀원별 `asyncio.Queue` 인스턴스의 dict**. agent_id 가 키, queue 가 값. 디자인은 10.7 과 똑같다 — 다만 *N 개의 인스턴스* 가 있을 뿐.

### 10.3 의 Stop 훅이 _기다리던 진짜 활용처_

10.3 Hook 시스템에서 다섯 이벤트 중 **Stop** 이 있었다. 본문에서는 _턴 끝 정리_ 정도로 다뤘지만, 8.4 본문은 Stop 의 _진짜 쓰임_ 을 보여준다:

> 6장의 훅 메커니즘을 통신 인프라로 재사용. Stop 훅은 _원래_ 세션 종료시 임의 동작 실행을 위한 훅이지만, 여기서는 _팀원의 work-cycle 끝을 lead 한테 알리는 신호_ 가 된다.

10.8 의 mini 회수에서는 _Hook 시스템 외부에 별도 진입점_ 을 두지 않는다 — `agent.py` 의 query() 가 _자기 stop 자리에서 직접_ `teams.get_identity()` 로 자기가 팀원인지 확인하고, lead 메일박스에 idle 알림을 push 한다. 효과는 동일하지만, mini 단순화 차원에서 Hook 등록 + 디스패치 한 층을 뺀 형태.

> ⚙️ **세 토대 한 줄 정리**: 10.3 가 _Stop 자리_ 를 만들어줬고, 10.6 가 _팀원 정의_ 의 그릇 (`.claude/agents/<name>/AGENT.md`) 을 만들어줬고, 10.7 이 _큐 인프라_ 의 패턴을 잡아줬다. 10.8 은 _세 자리 위에 contextvars + asyncio.create_task 두 줄을 얹어_ 팀 협업을 만든다.

### ③ 동시 spawn → polling 없는 fan-in → 결과 합치기

`TeamTool.call()` 안에서 _세 가지_ 가 일어난다 (전체 코드는 [§7](#agentpy--toolsagentpy-에-연결--두-자리) 에서).

1. **각 팀원마다 `asyncio.create_task` + `TeammateIdentity` 설정** — contextvars 가 task 트리를 따라 자동 격리. 세 명이 _동시에_ 일한다.
2. **`coordinator.wait_all_idle()`** — 한 줄. 세 명이 모두 idle 될 때까지 polling 없이 대기. `asyncio.Event` 가 _마지막 팀원의 mark_idle 콜백_ 에서 set 됨.
3. **결과 합치기** — `await task` 로 각 팀원의 마지막 텍스트 회수 + lead 메일박스 drain 으로 idle 알림 순서 확인.

## contextvars — Node `AsyncLocalStorage` 의 Python 등가

### 같은 프로세스 안에서 _N 개의 그릇_

```python
# mini_claude/teams/identity.py
from contextvars import ContextVar
from dataclasses import dataclass


@dataclass(frozen=True)
class TeammateIdentity:
    agent_id: str         # "researcher@doc-team"
    agent_name: str       # "researcher"
    team_name: str        # "doc-team"
    is_lead: bool = False


_identity: ContextVar[TeammateIdentity | None] = ContextVar(
    "teammate_identity", default=None,
)


def get_identity() -> TeammateIdentity | None:
    return _identity.get()


def set_identity(identity: TeammateIdentity) -> object:
    return _identity.set(identity)


def reset_identity(token: object) -> None:
    _identity.reset(token)  # type: ignore[arg-type]
```

핵심은 `ContextVar` 의 _작동 모델_ 이다.

### `_identity.get()` 이 호출자마다 다른 값을 돌려준다

```python
async def teammate_work(identity: TeammateIdentity) -> str:
    token = set_identity(identity)
    try:
        # 여기서 시작하는 *모든 함수 호출 트리* 에서 get_identity() 가
        # 이 identity 를 돌려준다. 다른 task 와 섞이지 않는다.
        return await deep_call_chain()  # 5 단계 깊이로 들어가도 OK
    finally:
        reset_identity(token)


async def deep_call_chain() -> str:
    return await level_2()

async def level_2() -> str:
    return await level_3()

async def level_3() -> str:
    me = get_identity()
    return f"hello from {me.agent_name}"  # ⭐ 트리를 따라 자동 격리


# 두 task 가 동시에 일해도 서로 섞이지 않음
alice = TeammateIdentity("alice@team", "alice", "team")
bob = TeammateIdentity("bob@team", "bob", "team")

await asyncio.gather(
    asyncio.create_task(teammate_work(alice)),  # "hello from alice"
    asyncio.create_task(teammate_work(bob)),    # "hello from bob"
)
```

`asyncio.create_task` 가 _부모 컨텍스트의 copy_ 를 자식 task 에 전달한다. 자식이 `set()` 해도 _자식 트리에만_ 보인다 — 부모의 컨텍스트는 영향 없음.

> 💡 **모듈은 한 벌, 컨텍스트는 N 벌**: `_identity` 모듈 변수는 _하나_ 다. 하지만 _그 변수가 든 값_ 은 task 마다 다르다. ContextVar 가 _내부적으로_ 각 컨텍스트의 mapping 을 들고 있고, `.get()` 이 *호출자의 컨텍스트* 를 보고 답한다.

### Node 의 `AsyncLocalStorage` 와의 1:1 대응

8.4 본문이 명시한 등가:

| Node (TypeScript) | Python |
|---|---|
| `new AsyncLocalStorage<T>()` | `ContextVar[T]("name", default=...)` |
| `store.run(value, fn)` | `set_identity(value)` + `try/finally reset` |
| `store.getStore()` | `get_identity()` |
| 자식 `new Promise(...)` 가 컨텍스트 상속 | `asyncio.create_task(...)` 가 컨텍스트 copy |

디자인이 _같다_. Python 의 `contextvars` 는 2018 (PEP 567) — Node 의 `AsyncLocalStorage` 보다 약간 일찍 표준화됐다 (Node 가 stable 로 표시한 건 2021). 두 언어 다 _async 시대의 thread-local 부재_ 라는 같은 문제를 같은 답으로 풀었다.

### 9.5 의 _재귀 한 단계_ 격리와의 차이

| 9.5 (AgentTool) | 10.8 (Team) |
|---|---|
| 부모가 자식 _하나_ 를 동기 await | 부모가 N 명 동시 spawn |
| 격리 = `ConversationState()` 새 그릇 | 격리 = `ConversationState()` + `ContextVar` 두 줄 |
| 한 번에 한 명 — race 없음 | N 명 동시 — race 처리 (등록 시점 isIdle 재체크) 필요 |
| 자식 끝나면 마지막 텍스트 회수 | 모두 끝나면 `asyncio.gather(*tasks)` 로 회수 |
| 부모의 _턴 한 자리_ 를 자식이 차지 | 부모의 _한 턴 안에서_ N 자식이 평행 일 |

9.5 는 _재귀 한 단계_ — 자식이 끝나야 부모가 다음. 10.8 은 _평행 N 인스턴스_ — 모두가 끝나야 부모가 다음. **9.5 의 격리는 _데이터만_, 10.8 의 격리는 _데이터 + 신원_**.

> 🔬 **Deep Dive — contextvars 의 trap**:
> 
> <details>
> <summary>`set()` 후 `reset()` 안 하면 _현재 컨텍스트_ 에 남는다</summary>
> 
> > 보통 `asyncio.create_task` 안에서 `set()` 을 부르면 _그 task 의 contextvars copy 에만_ 설정되어 자동 격리된다. 하지만 _같은 task 안에서_ `set()` 만 부르고 `reset()` 안 하면 _현재 컨텍스트_ 에 남아서 _이후 호출_ 에 영향. 그래서 `set_identity()` 가 토큰을 반환하고, `try/finally` 로 `reset_identity(token)` 호출하는 패턴이 정석.
> > 
> > mini 의 `TeamTool._run_member()` 는 task 안에서 `set_identity` 를 부르므로 _task 격리_ 가 자동으로 일어나지만, finally 의 `reset_identity()` 가 _명시적 정리_ 를 보장한다 — 같은 task 가 _이후 다시 사용_ 될 가능성 (asyncio 의 task 풀링은 안 하지만, _안전망_) 에 대비.
> 
> </details>

## Mailbox — 10.7 의 _격리된 응용_

10.7 메시지 큐는 _프로세스 안에 한 벌_ 의 `deque`. 9.5 서브에이전트가 push 하면 부모도 본다. 10.7 본문이 _이 한계를 명시_ 했다.

10.8 의 답: **팀원별 `asyncio.Queue` 인스턴스의 dict**. agent_id 가 키, queue 가 값. 디자인은 똑같다 — *N 개의 인스턴스* 가 있을 뿐.

> ⚙️ **mailbox 와 10.7 큐의 _공존_**: 10.7 의 `message_queue` 모듈 싱글턴은 _그대로 살아있다_ — 사용자 입력 / 백그라운드 task 완료 등 _전역 트래픽_ 을 받는 _하나의 채널_. 10.8 의 mailbox 는 그 _옆_ 에 새로 추가되는 _팀원별 격리 채널_. _대체 관계가 아니라 다른 일을 하는 별도 모듈_ — `mini_claude/message_queue.py` 와 `mini_claude/teams/mailbox.py` 가 _공존_. 팀원 task 안에서도 `message_queue.push()` 를 부르면 _부모와 공유_ (10.7 의 _부모/자식 공유_ 가정이 _팀 컨텍스트에서도 그대로_ 유효), mailbox 는 _그 옆에서_ idle 알림 / peer DM 같은 _팀 전용 트래픽_ 만 격리. 두 채널이 _각자의 일_ 에 집중하는 디자인 — _전역 vs 팀별_ 이라는 _서로 다른 격리 단위_.

### 데이터 모델

```python
# mini_claude/teams/mailbox.py
@dataclass
class MailboxMessage:
    sender: str       # 보낸 팀원의 agent_name
    text: str         # 본문
    kind: str = "dm"  # "idle" (turn 끝 알림) | "dm" (peer-to-peer 메시지)
```

`kind` 가 두 가지를 구분한다:
- `"idle"` — 팀원이 turn 을 끝냈다는 _시스템 신호_. lead 가 wait_all_idle 후 drain.
- `"dm"` — 팀원 → 팀원 (또는 → lead) _명시적 메시지_. mini 의 핵심 시나리오 OUT — 향후 확장 자리.

### `asyncio.Queue` — `put` 은 즉시 깨움, `await get()` 은 polling 없음

```python
_mailboxes: dict[str, _MailboxState] = {}


@dataclass
class _MailboxState:
    queue: asyncio.Queue[MailboxMessage] | None = None
    history: list[MailboxMessage] = field(default_factory=list)

    def ensure_queue(self) -> asyncio.Queue[MailboxMessage]:
        if self.queue is None:
            self.queue = asyncio.Queue()
        return self.queue


async def deliver(recipient_id: str, message: MailboxMessage) -> None:
    state = _mailboxes.setdefault(recipient_id, _MailboxState())
    queue = state.ensure_queue()
    state.history.append(message)
    await queue.put(message)


async def receive(recipient_id: str) -> MailboxMessage:
    state = _mailboxes.setdefault(recipient_id, _MailboxState())
    queue = state.ensure_queue()
    return await queue.get()  # ⭐ put 시 자동 깨움 — polling 없음


def drain(recipient_id: str) -> list[MailboxMessage]:
    state = _mailboxes.get(recipient_id)
    if state is None or state.queue is None:
        return []
    items: list[MailboxMessage] = []
    while not state.queue.empty():
        try:
            items.append(state.queue.get_nowait())
        except asyncio.QueueEmpty:
            break
    return items
```

핵심 두 가지:

1. **`asyncio.Queue.put()` 은 _즉시_ 받는 쪽을 깨운다** — 받는 쪽이 `await get()` 하고 있으면 _다음 이벤트 루프 tick_ 에서 깨어남. _polling 안 함_.
2. **lazy queue 생성** — `asyncio.Queue` 는 _이벤트 루프가 있을 때만_ 만들 수 있다. 모듈 import 시점에 만들면 _이벤트 루프 없음_ 으로 에러. `ensure_queue()` 가 lazy 초기화.

### `drain()` vs `receive()` — 두 모드

- **`receive(recipient_id)`** — *blocking* — 한 항목 도착할 때까지 기다림. lead 가 _다음 알림_ 을 기다리는 자리.
- **`drain(recipient_id)`** — *non-blocking* — 지금 쌓인 모두를 한 번에 꺼냄. lead 가 `wait_all_idle` 후 _전체 검토_ 하는 자리.

mini 의 `TeamTool.call()` 은 _drain 패턴_ 만 쓴다 — `wait_all_idle` 로 모두 idle 까지 기다린 후, `drain(lead_id)` 로 도착한 알림들 한꺼번에 검토. _receive 패턴_ (lead 가 실시간으로 알림을 받음) 은 _향후 확장_ — 진짜 8.4 에서는 LLM 사이클이 _도착하는 알림마다_ 메시지에 attachment 로 붙인다.

### 8.4 의 디스크 jsonl mailbox vs mini 의 in-memory

진짜 8.4 의 mailbox 는 _디스크 jsonl_ — `~/.claude/teams/<team>/<name>.jsonl` 에 append-only:

```typescript
// utils/teammateMailbox.ts (8.4)
await writeToMailbox({
  recipient: "lead",
  team: "doc-team",
  message: { from: "researcher", text: "...", timestamp: "..." }
});
```

_왜 디스크?_ 8.4 는 _in-process 팀원_ 과 _out-of-process 팀원_ (별도 터미널에서 실행되는 팀원) 이 _같은 매체_ 로 통신할 수 있어야 한다. 디스크 jsonl 은 _공통 기반_.

mini 는 *in-process 만* 다룬다 — `asyncio.Queue` 로 충분하고, _훨씬 빠르다_ (디스크 I/O 없음, watcher 없음).

| 진짜 8.4 | mini 10.8 |
|---|---|
| `~/.claude/teams/<team>/<name>.jsonl` (디스크 append-only) | `dict[agent_id, asyncio.Queue]` (메모리) |
| inotify/FSEvents watcher 로 변경 감지 | `asyncio.Queue.get()` 자동 깨움 |
| Cross-process 통신 가능 | Same-process 만 |
| 영속성 (재시작 후 메시지 보존) | 휘발성 (재시작 시 사라짐) |

> ⚙️ **언제 진짜 디스크 mailbox 가 필요한가**: 팀원이 _다른 터미널_ 에서 별도 mini-claude 인스턴스로 실행되는 경우, 또는 _재시작 후에도 idle 알림이 남아 있어야_ 하는 경우. mini 의 _이번 챕터 범위는_ "한 프로세스 안의 N 팀원" 까지 — _프로세스 경계_ 는 향후 확장 (10.x?) 의 자리.

### ③ `coordinator.py` — polling 없는 fan-in

핵심은 `wait_all_idle()`. 8.4 본문의 `waitForTeammatesToBecomeIdle()` 의 mini 등가.

```python
@dataclass
class TeammateTaskState:
    identity: TeammateIdentity
    task: asyncio.Task | None = None
    is_idle: bool = False
    on_idle_callbacks: list[Callable[[], None]] = field(default_factory=list)
    result: str | None = None


class TeamCoordinator:
    def __init__(self) -> None:
        self.tasks: dict[str, TeammateTaskState] = {}

    def register(self, identity: TeammateIdentity, task: asyncio.Task) -> None:
        self.tasks[identity.agent_id] = TeammateTaskState(
            identity=identity, task=task,
        )

    def mark_idle(self, agent_id: str, result: str | None = None) -> None:
        state = self.tasks.get(agent_id)
        if not state or state.is_idle:
            return
        state.is_idle = True
        if result is not None:
            state.result = result
        for cb in state.on_idle_callbacks:
            cb()
        state.on_idle_callbacks.clear()

    async def wait_all_idle(self, agent_ids: list[str] | None = None) -> None:
        if agent_ids is None:
            agent_ids = list(self.tasks.keys())

        working = [
            self.tasks[a] for a in agent_ids
            if a in self.tasks and not self.tasks[a].is_idle
        ]
        if not working:
            return  # 모두 이미 idle

        event = asyncio.Event()
        remaining = len(working)

        def on_idle() -> None:
            nonlocal remaining
            remaining -= 1
            if remaining == 0:
                event.set()

        for state in working:
            if state.is_idle:
                # race: 콜백 등록 직전에 이미 idle 됐다면 즉시 호출
                on_idle()
            else:
                state.on_idle_callbacks.append(on_idle)

        await event.wait()


_coordinator: TeamCoordinator = TeamCoordinator()


def get_coordinator() -> TeamCoordinator:
    return _coordinator
```

여기서 **race 처리** 가 8.4 본문의 핵심 디테일이었다 — `on_idle_callbacks.append(on_idle)` 하기 _직전_ 에 _이미 idle_ 이 됐을 수 있다 (다른 코루틴이 그 사이에 `mark_idle` 호출). 그러면 _콜백이 영원히 안 불려서 deadlock_. 그래서 _등록 직전 isIdle 재체크_ 가 들어있다.

> 🔬 **Deep Dive — race 가 정말 발생하나**:
> 
> <details>
> <summary>같은 이벤트 루프, 한 스레드 — race 가 정말 가능한지</summary>
> 
> > Python asyncio 는 단일 스레드 + 협력적 스케줄링 — _명시적 await 지점_ 에서만 컨텍스트 전환이 일어난다. `wait_all_idle()` 의 for 루프는 _명시적 await 없음_, 그래서 _이론적으로는_ for 루프 도중에 다른 코루틴이 끼어들 수 없어 보인다.
> > 
> > 하지만 _더 일반적 케이스_ 가 있다: **`wait_all_idle` 이 호출되기 _전에_ 이미 mark_idle 이 일어난 경우**. 예: 첫 두 팀원이 매우 빠르게 끝났는데 lead 가 그제서야 `wait_all_idle` 을 호출. for 루프 시작 시점에 _이미 is_idle=True_ 인 팀원들은 `working` 리스트에서 제외되어 자연 처리. _세 번째 팀원이 working 인 채로 들어왔는데, append 직전에 (이론상 같은 코루틴 안에서는 불가능하지만) idle 이 됐다면_ — 그 경우를 위한 안전망.
> > 
> > 진짜 8.4 의 Node 코드는 _진짜로_ 이 race 가 가능하다 — Node 의 microtask queue 가 더 적극적으로 컨텍스트 전환을 한다. Python 은 _덜 적극적_ 이지만 _안전망_ 으로 두는 게 정석.
> 
> </details>

```python
async def _notify_lead_on_idle(state: ConversationState, stop_reason: str) -> None:
    identity = teams.get_identity()
    if identity is None or identity.is_lead:
        return  # 팀 밖 또는 lead 본인 — 알림 불필요

    summary = _last_assistant_text(state)
    coordinator = teams.get_coordinator()
    # ① fan-in 콜백 트리거 — lead 의 wait_all_idle() 깨움
    coordinator.mark_idle(identity.agent_id, result=summary or None)
    # ② lead 메일박스에 idle 메시지 push — wait_all_idle 후 drain 으로 검토
    lead_id = f"lead@{identity.team_name}"
    await teams.deliver(
        lead_id,
        teams.MailboxMessage(
            sender=identity.agent_name,
            text=summary or f"(no text; stop_reason={stop_reason})",
            kind="idle",
        ),
    )


def _last_assistant_text(state: ConversationState) -> str:
    """대화 끝에서 가장 가까운 assistant 텍스트 블록을 합쳐 돌려준다.

    AgentTool / TeamTool 의 마지막 텍스트 회수 로직과 같은 fallback.
    """
    for msg in reversed(state.messages):
        if msg.get("role") != "assistant":
            continue
        blocks = msg.get("content", [])
        texts = [
            b.get("text", "")
            for b in blocks
            if isinstance(b, dict) and b.get("type") == "text"
        ]
        if texts:
            return "\n".join(texts)
    return ""
```

세 가지 디테일:

- **`identity is None` 이면 no-op** — 단독 실행 (lead 의 메인 루프) 또는 9.5 의 일반 서브에이전트. 팀 밖에서는 _아무 일도 안 일어남_.
- **`identity.is_lead` 면 no-op** — lead 가 _자기 자신_ 에게는 알림 안 보냄 (`agent@team` 패턴에서 lead 가 자기 idle 알림을 받으면 _자기를 기다리는_ deadlock 위험).
- **`coordinator.mark_idle` 이 _콜백 트리거_, `deliver` 가 _기록_** — 두 가지가 _분리_ 되어 있다. mark_idle 만으로 fan-in 동작; deliver 는 lead 가 _순서를 보고 싶을 때_ drain 으로 검토.

`call()` 본문 (스폰 루프):

```python
async def call(self, args: dict[str, Any], context: ToolContext) -> str:
    team_name = args["team_name"]
    assignments: dict[str, str] = args["assignments"]

    lead_id = f"{self.lead_name}@{team_name}"
    ensure_mailbox(lead_id)

    coordinator = get_coordinator()
    coordinator.clear()  # 이 호출 한정 — 이전 팀의 잔여 상태 정리

    agent_ids: list[str] = []
    task_handles: list[tuple[str, asyncio.Task]] = []

    for member_name, prompt in assignments.items():
        spec = self._find_spec(member_name)
        identity = TeammateIdentity(
            agent_id=f"{member_name}@{team_name}",
            agent_name=member_name,
            team_name=team_name,
            is_lead=False,
        )
        ensure_mailbox(identity.agent_id)
        child_tools = self._filter_tools(spec)

        task = asyncio.create_task(
            self._run_member(identity, spec, prompt, child_tools, context.cwd),
            name=f"team:{identity.agent_id}",
        )
        coordinator.register(identity, task)
        agent_ids.append(identity.agent_id)
        task_handles.append((identity.agent_id, task))

    # ⭐ polling 없는 fan-in
    await coordinator.wait_all_idle(agent_ids)

    # 결과 회수 + lead 메일박스 drain
    sections: list[str] = []
    for agent_id, task in task_handles:
        try:
            result = await task
        except Exception as e:
            result = f"(error: {type(e).__name__}: {e})"
        sections.append(f"=== {agent_id} ===\n{result}")

    from ..teams import drain_mailbox
    lead_box = drain_mailbox(lead_id)
    if lead_box:
        notes = "\n".join(
            f"- [{m.kind}] {m.sender}: {m.text[:80]}"
            for m in lead_box
        )
        sections.append(f"=== mailbox (lead) ===\n{notes}")

    return "\n\n".join(sections)
```

세 단계 정확히:

1. **spawn**: 각 팀원마다 `asyncio.create_task` + `coordinator.register`.
2. **wait**: `coordinator.wait_all_idle(agent_ids)` — 한 줄.
3. **collect**: `await task` 로 결과 회수 + `drain_mailbox(lead_id)` 로 idle 알림 순서 검토.

## 핵심 디테일

### lead 는 _수신 허브_ 이지 _합성 책임자_ 가 아니다

8.4 본문의 한 줄: _명시적 팀 lead 는 통신 허브이지 코디네이터처럼 강한 역할 분리는 아님_. 차이가 하나뿐 — _자기 자신한테 idle 알림 안 보낸다_.

mini 의 디자인은 더 단순하다 — _lead 의 메인 루프는 identity 가 None_. 즉:

| | Identity | is_lead | idle 알림 보냄 |
|---|---|---|---|
| 단독 실행 (mini-claude 본체) | `None` | `False` (None 이라) | 안 보냄 (no-op) |
| Team 팀원 | `name@team`, is_lead=False | `False` | _lead 메일박스에 보냄_ |
| (가상의) Team lead | `lead@team`, is_lead=True | `True` | 안 보냄 (자기 자신) |

mini 는 _세 번째 경우 (lead identity)_ 를 _사용하지 않는다_. lead 가 _Team 도구를 호출_ 한다는 사실 자체가 _lead 라는 정체성을 표현_ — 별도 identity 가 필요 없다. 진짜 8.4 는 lead 도 _명시적 identity_ 를 갖지만, 그건 _peer DM 대상_ 으로 등장하기 위해서다 (팀원이 lead 한테 DM 보낼 때 lead 의 agent_id 가 수신자).

### peer DM 의 자리는 _이미 깔려 있다_

mini 는 peer DM 시나리오를 _기본 사용 흐름_ 에서 보여주지 않지만, _기반은 갖춰져 있다_:

```python
# 가상의 peer DM 시나리오
async def writer_asks_researcher() -> str:
    me = get_identity()  # writer@doc-team
    # researcher 에게 자료 요청
    await deliver(
        f"researcher@{me.team_name}",
        MailboxMessage(sender=me.agent_name, text="EUV 마일스톤 좀 다시 정리해줄 수 있어?", kind="dm"),
    )
    # 답 기다림
    reply = await receive(me.agent_id)  # ⭐ writer 의 메일박스 받기
    return reply.text
```

데이터 모델 (`MailboxMessage.kind = "dm"`) 과 함수 (`deliver` / `receive`) 가 _이미 그대로_. 다만 _모델이 이 패턴을 알고 호출_ 하려면 _별도 peer-dm 도구_ 가 필요 (`PeerDmTool`), 또는 _Bash 같은 임의 도구를 통해 mailbox 라이브러리를 직접 부르는_ 방식. mini 의 _이번 챕터 범위 OUT_ — _향후 확장_.

> ⚙️ **시간 축으로 본 peer DM 의 어려움**: writer 가 researcher 에게 자료 요청을 보냈을 때 _researcher 가 이미 끝났을 수 있다_ (writer 보다 먼저 시작하지 않은 한, 또는 빨리 끝났을 경우). 그럼 _요청이 도착해도 받을 사람이 없다_. 진짜 8.4 는 _researcher 의 Stop 훅이 메일박스 watcher 를 유지_ 해서 _세션이 끝나도 응답 가능_ 한 디자인. mini 는 _task 가 끝나면 contextvar 도 사라짐_ — peer DM 이 _실시간_ 으로만 가능한 한계.

### `asyncio.Queue` 의 자동 깨움 — _polling 없는_ 의 진짜 의미

`coordinator.wait_all_idle()` 이 한 줄 `await event.wait()` 으로 끝난다. _얼마나 기다리는지 모름_. 하지만 _CPU 를 안 쓴다_.

이게 _진짜로_ polling 없다는 의미다:

- **나쁜 패턴 (polling)**: 0.1 초마다 모든 팀원의 `is_idle` 체크. CPU 가 _주기적으로_ 깨어남.
  ```python
  while not all(t.is_idle for t in tasks):
      await asyncio.sleep(0.1)  # ❌ polling
  ```
- **좋은 패턴 (event 기반)**: 마지막 팀원의 `mark_idle` 콜백 안에서 `event.set()`. CPU 가 _그 순간만_ 깨어남.
  ```python
  await event.wait()  # ✅ 이벤트 루프가 알아서 깨움
  ```

`asyncio.Event` 는 내부에 _Future_ 를 들고 있다. `event.wait()` 호출자는 _그 Future 가 done 될 때까지_ 이벤트 루프에 의해 _대기 상태로 잠재워진다_. `event.set()` 이 Future 를 _done_ 으로 표시하면 _그 대기자 모두_ 가 _다음 tick_ 에 깨어난다.

> 💡 **N 팀원이 1000 명이어도 비용 일정**: polling 이면 1000 명 × 100Hz = 100k 체크/초 가 _아무 일 없어도_ 흐른다. event 기반은 _깨어남이 N 번_ — 팀원이 끝나는 횟수만큼만. 8.4 의 _OOM 사례_ (`TEAMMATE_MESSAGES_UI_CAP = 50`, 292 에이전트 36.8GB) 가 _메모리_ 문제였지 _CPU_ 가 아니었던 이유다.

### `context_token` 의 reset — _try/finally 의 진짜 이유_

`set_identity` 가 _토큰_ 을 돌려준다. 그 토큰을 `reset_identity` 에 들이밀면 _이전 값 복원_. 보통은 `asyncio.create_task` 안에서 호출되므로 _task contextvars copy_ 가 자동 격리하지만, _명시적 reset_ 의 의미는:

- task 가 _재사용_ 되는 환경 (asyncio 의 task pooling — 표준 라이브러리는 안 함; 일부 라이브러리가 함)
- _같은 task 안에서_ 여러 번 `set_identity` 가 불릴 가능성 (mini 의 디자인은 그렇지 않지만 _안전망_)
- 예외 전파 시 _컨텍스트 누수_ 방지

```python
token = set_identity(identity)
try:
    return await teammate_work(...)
finally:
    reset_identity(token)  # ⭐ 예외든 정상이든 _반드시_ 호출
```

mini 의 `_run_member` 가 정확히 이 패턴. _8.4 본문의 `run_with_teammate_context()`_ 가 같은 디자인.

## 진짜 코드에서는 — 8.4 vs mini

mini 의 ~400 줄 (`teams/` + `tools/team.py` + `agent.py` 5 줄 추가) 이 진짜 8.4 의 ~1500 줄 (모듈 클러스터 합산) 을 어떻게 압축했는지.

| 차원 | 진짜 8.4 (TS) | mini 10.8 (Python) | 압축 |
|---|---|---|---|
| **격리** | 13 개 컨텍스트 슬라이더 + AsyncLocalStorage | `ConversationState()` + ContextVar | ~95% |
| **게이트** | 3 단계 (ant always / 외부 opt-in / GrowthBook killswitch) | 항상 활성 | OUT |
| **정체성** | `agent@team` + 우선순위 사다리 + color + plan_mode | `TeammateIdentity` dataclass | ~80% |
| **mailbox** | 디스크 jsonl + watcher (inotify/FSEvents) | `asyncio.Queue` dict | ~60% |
| **Stop 훅** | `register_teammate_stop_hook()` + Hook 시스템 등록 | `agent.py` Stop 자리 인라인 | ~70% |
| **fan-in** | `waitForTeammatesToBecomeIdle()` + race 처리 + abort chaining | 같은 패턴, 라인은 그대로 | ~10% |
| **공유 메모리** | team memory.md + secret guard + DCE | OUT | OUT |
| **OOM 캡** | `TEAMMATE_MESSAGES_UI_CAP = 50` 등 다수 캡 | 없음 | OUT |
| **peer DM** | 메일박스 watcher 가 실시간 수신 | 데이터 모델은 IN, 도구는 OUT | ~80% |
| **계측/디버깅** | `getLastPeerDmSummary`, `idle_reason` 6 종 등 | text + kind 두 필드 | ~85% |

전체 압축률 약 **70%** (400 / 1500 ≈ 27%, 즉 73% 압축).

### mini 가 의도적으로 _빼지 않은_ 자리

압축 결과 mini 가 _가져온 것_:

- **`ContextVar` 격리** — 8.4 의 핵심. PEP 567 의 정확한 1:1 대응.
- **`asyncio.create_task` 평행 spawn** — 8.4 의 _N 명 동시_ 의 본질.
- **`wait_all_idle` 의 race 처리** — _등록 직전 isIdle 재체크_ 의 한 줄. 안 빼는 게 정수.
- **mailbox 데이터 모델** — `MailboxMessage(sender, text, kind)` — 진짜와 _필드명까지_ 일치.
- **lead 가 자기 자신에게 알림 안 보냄** — `is_lead` 분기.

### mini 가 _뺀_ 자리 (이유와 함께)

- **3 단계 게이트** — mini 는 _프로덕션 rollout_ 인프라가 없음. 항상 활성.
- **공유 팀 메모리 + secret guard** — _격리 정책_ 과 정면 충돌. 별도 챕터급 작업.
- **디스크 jsonl mailbox** — _in-process 만_ 다루므로 in-memory 로 충분. _cross-process_ 통신 (out-of-process 팀원) 은 향후 확장.
- **13 컨텍스트 격리 슬라이더** — 9.5 의 `ConversationState()` 한 줄로 mini 단계에서 이미 충분.
- **abort chaining** — lead 가 abort 하면 자식들이 자동 abort. mini 는 _명시적 abort 도구_ 가 아직 없으므로 OUT.
- **OOM 캡** — 8.4 의 _실패담_ (292 에이전트 36.8GB) 이 mini 의 _경고_ 로 남음 (§"진짜로 팀을 구성해 보기" 의 ⚠️). 캡 자체는 OUT.

> 🔬 **Deep Dive — 빼고도 작동하는 자리, 빼면 부서지는 자리**:
> 
> <details>
> <summary>mini 가 _빼고도 작동_ 하는 이유는 무엇이 받쳐주는가</summary>
> 
> > **3 단계 게이트** 는 _Anthropic 의 점진 출시_ 를 위한 것 — mini 는 _개념 증명_ 이므로 _아무도 활성화 안 됨_ 이라는 시나리오가 없다.
> > 
> > **공유 메모리** 는 _peer 협업의 강점_ 이지만 _격리 정책_ 과 정면 충돌. mini 는 _격리 우선_ 디자인 — 메모리 공유는 _명시적 도구로 외부에서_ 일어나야 함 (Write/Read 로 같은 파일 접근). 그래서 _공유 메모리 OUT_ 이 _격리 정책의 자연스러운 귀결_.
> > 
> > **디스크 mailbox** 는 _cross-process 통신_ 의 매체. mini 는 _한 프로세스 안_ 만 다루므로 in-memory 로 충분. _만약 cross-process 가 필요해지면_ — 그 자리에 디스크 mailbox 가 들어가야 한다 (또는 Redis pub/sub, 또는 OS signal).
> > 
> > **OOM 캡** 은 _N 이 커질 때_ 만 의미. mini 의 시연 시나리오는 _3~5 명_ 수준 — _캡 없이도_ 안전. _만약 N=100 으로 늘리면_ — 그 순간 OOM 캡 도입이 필요해진다.
> > 
> > _빼면 부서지는 자리_ 는 **ContextVar 격리** 와 **race 처리** 뿐. ContextVar 없으면 _서로의 신원을 덮어쓰는_ race condition; race 처리 없으면 _이미 끝난 팀원_ 에 콜백 등록되어 deadlock. 이 둘은 _어떤 단순화에도_ 살아남아야 한다.

### ③ 시나리오의 의도적 _약한_ 자리

위 시나리오는 _직렬 의존성_ 이 자연스러운데도 _평행 spawn_ 으로 처리한다 — triager 는 scanner 의 결과를 _봐야_ 정확히 분류할 수 있지만, mini 의 디자인은 _세 명이 동시에 시작_ 한다. 어떻게 작동하는가:

- scanner 가 _금방 끝남_ (grep 몇 번) — 10초 이내
- triager 와 fixer-planner 는 _자기 prompt 만 보고 시작_ 하지만, _작업이 길어서_ 한 30초 후 scanner 의 결과를 _스스로 다시 grep_ 할 수 있음
- 또는 _LLM 이 의존성을 느끼지 못하고 일반론적_ 으로 답할 수 있음 (이건 _진짜 한계_)

진짜 시나리오에서는 _lead 가 Team 도구를 두 번 호출_ 하는 게 더 깔끔:
1. 첫 호출: `scanner` 만 spawn (또는 AgentTool 로 1 명)
2. 두 번째 호출: `triager` + `fixer-planner` 만 spawn, scanner 의 결과를 prompt 에 _명시적으로_ 전달

> ⚠️ **mini 의 한계 정리**: _직렬 의존성_ 시나리오는 *Team 도구 한 번 호출* 보다 *Agent 도구 직렬 호출* 또는 *Team 도구 여러 번 호출* 이 더 깔끔. 10.8 의 Team 은 _완전 평행_ 이 자연스러운 시나리오 (각자 다른 측면을 동시에 검토) 에 최적. _직렬 chain_ 을 표현하려면 _peer DM_ (mini OUT) 또는 _명시적 호출 분할_ 필요.

## 핵심 정리

- **세 토대 위에 얹은 완성** — 10.3 (Stop 자리), 10.6 (`.claude/agents/<name>/AGENT.md` 의 그릇), 10.7 (큐 패턴) 셋이 _혼자서는 작은 챕터_ 였지만, 10.8 에서 _합쳐져_ 팀 협업이 된다. _각 토대 챕터가 미해결로 남긴 자리_ 가 10.8 의 자리.
- **격리는 `ContextVar` 한 객체로 충분** — Node 의 `AsyncLocalStorage` 와 1:1. _async 호출 트리를 따라 자동 격리_ 가 핵심 — 모듈 변수는 한 벌, 컨텍스트는 N 벌. `asyncio.create_task` 가 부모 컨텍스트 copy 를 자식에 전달.
- **메일박스는 10.7 의 _격리된 응용_** — 모듈 싱글턴 큐가 _agent_id 키의 dict_ 가 되면 자연스러운 mailbox. `asyncio.Queue` 의 `put`/`get` 이 *polling 없는 자동 깨움*.
- **`wait_all_idle` 의 race 처리는 _안 빼는 게 정수_** — _등록 직전 isIdle 재체크_ 한 줄. 8.4 본문에 길게 적힌 디테일이 mini 의 ~5 줄로 살아남음. 빼면 _이미 끝난 팀원_ 에 콜백 등록되어 deadlock.
- **mini 가 _뺀_ 자리는 _프로덕션 인프라_** — 3 단계 게이트, 디스크 mailbox, 공유 메모리, secret guard, OOM 캡. 빼고도 _개념 증명_ 은 작동 — 다만 _프로덕션_ 으로 가려면 각각이 _진짜 자리_ 로 돌아와야 한다.
- **AI 엔지니어에게 이것이 중요한 이유** — 멀티 에이전트 시스템은 _하나의 정답_ 이 아니라 _협업 구조의 선택_. 위계 vs peer, 격리 vs 공유, 직렬 chain vs 평행 fan-out. mini 가 _Team 도구 한 개_ 로 평행 fan-out 만 다뤘다는 사실이 _다른 모든 구조_ 를 부정하지 않는다 — _자기 문제에 맞는 협업 구조를 직접 선택_ 해야 한다. mini 의 ~400 줄이 _세 토대 위에서_ peer 모델을 _실제로 작동_ 시킨다는 증명만으로도 — _당신의 코드에서_ 어떤 구조든 만들 수 있다는 _자신감_ 의 근거가 된다.
- **Part 10 끝** — 슬래시 명령 (10.1), 스킬 (10.2), MCP (10.4) 가 _사용자 정의 콘텐츠_ 의 확장이었다면, 10.3~10.8 은 _도구 실행 흐름_ 의 확장. 일곱 챕터가 모여 mini_claude 가 _진짜 Claude Code 의 압축판_ 으로 완성된다. _혼자 만들 수 없을 것 같던 멀티 에이전트 시스템_ 이 _세 토대 위 ~400 줄_ 로 작동한다는 증명 — 이제 _이 위에 무엇을 더 얹을지_ 는 당신의 문제 영역에 달렸다.
