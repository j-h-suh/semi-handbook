이 챕터의 그림은 책 전체에서 계속 돌아온다. 머릿속에 단단히 박아두자.

## 사용자 경험에서 출발

Claude Code 켜고 다음과 같이 친다.

> `src/utils/parser.py 좀 읽어줘`

엔터 치는 순간부터 화면에 결과가 나오기까지, 짧으면 1초도 안 걸린다. 그 사이에 무슨 일이 일어났는지 차근차근 풀어보자.

직관적으로는 이렇게 생각할 수 있다.

> "Claude가 알아서 파일을 읽고 보여줬겠지."

근데 이 문장에는 작은 함정이 숨어 있다. **Claude는 파일을 직접 못 읽는다.** Claude는 그저 문자열을 입력으로 받고 문자열을 출력하는 LLM이다. 파일 시스템에 접근할 수 없다. 네트워크에도 접근할 수 없다. Claude가 할 수 있는 건 오로지 "텍스트 받고, 텍스트 뱉기"뿐이다.

그럼 어떻게 파일이 읽혔을까?

## 본문 — Claude Code의 한 줄 요약

답은 한 줄로 정리된다.

> **Claude Code = "도구를 쓸 줄 아는 챗봇"**

진짜로 이게 전부다. 풀어보면 이렇다.

1. 사용자 입력을 Claude에게 보낸다 — "`src/utils/parser.py` 좀 읽어줘"
2. 사용자 메시지와 함께 **사용 가능한 도구 목록**도 같이 보낸다 — "너 이런 도구 쓸 수 있어: Read, Write, Bash, Edit, Glob, Grep, ..."
3. Claude가 응답을 보낸다. 응답은 두 가지 중 하나다.
    - **A. 그냥 텍스트** — "안녕" 같은 거. 화면에 표시하고 끝.
    - **B. 도구 호출 요청** — "Read 도구를 써. file_path는 '/Users/.../parser.py'야."
4. **B의 경우**, 시스템이 진짜로 Read 도구를 실행한다. 파일을 디스크에서 읽는다.
5. 읽은 결과를 다시 Claude에게 보낸다 — "여기, Read 결과야: [파일 내용]"
6. Claude가 결과를 보고 다음 행동을 결정한다. 다시 3번으로 돌아간다.

이 루프가 Claude의 응답이 "그냥 텍스트"가 될 때까지 반복된다. 그러면 사용자에게 답이 보이고 한 턴이 끝난다.

그림으로 그리면 이렇게 생겼다.

```
    ┌──────────────────┐
    │    사용자 입력      │
    └────────┬─────────┘
             ↓
    ┌──────────────────┐
    │  Claude API 호출  │ ← 매 호출마다
    │  (메시지 + 도구)   │   메시지 누적해서 보냄
    └────────┬─────────┘
             ↓
        Claude의 응답
             │
       ┌─────┴─────┐
       ↓           ↓
   [그냥 텍스트]  [도구 호출 요청]
       ↓           ↓
    [화면 표시]   [도구 실행]
       ↓           ↓
      [끝]   [결과를 메시지에 추가]
                   ↓
                  ┌┘ (위의 "Claude API 호출"로)
                  ↓
```

이 루프를 **에이전트 루프(agent loop)** 또는 **도구 사용 루프(tool-use loop)** 라고 부른다. 학술 논문에 나오는 ReAct, Plan-and-Execute 같은 패턴들의 가장 단순한 형태이기도 하다.

여기서 짚고 넘어갈 포인트가 세 가지 있다.

**첫째, 결정권은 Claude한테 있다.** 어떤 도구를 쓸지, 인자는 뭘로 줄지, 도구를 또 부를지 말지 — 다 Claude가 결정한다. 시스템은 그저 Claude가 시키는 대로 도구를 실행하고 결과를 돌려주는 "집사" 역할만 한다. 이게 처음 보면 좀 이상하게 느껴질 수 있다. "내가 짠 프로그램인데 흐름 제어를 LLM한테 맡긴다고?" 그렇다. 바로 이 지점이 전통적인 프로그램과 에이전트의 가장 큰 차이다.

**둘째, 메시지는 누적된다.** 매번 API 호출에 보내는 메시지 리스트에는 처음 사용자 입력부터 지금까지의 모든 대화 + 도구 호출 + 도구 결과가 다 들어 있다. Claude는 stateless하기 때문에 (서버가 이전 호출을 기억하지 않는다) 매번 전체 컨텍스트를 다시 보내야 한다. 대화가 길어지면 이 리스트도 같이 커지고, 그래서 나중에 컨텍스트 압축 같은 게 필요해진다.

**셋째, 도구 결과는 사용자 메시지처럼 보인다.** Anthropic API 입장에서 도구 결과는 `role: "user"`의 특수한 메시지로 들어간다. Claude의 입장에서는 "방금 내가 부른 도구가 결과를 돌려줬구나" 하고 인식하는 셈이다. 사람이 답한 게 아니라 시스템이 자동으로 채워준 user 메시지다.

## Python으로 옮기면

위 루프를 Python 의사코드로 옮기면 이렇게 생겼다. (진짜 동작하는 코드는 Part 9에서 만들 거다. 지금은 골격만 보자.)

```python
from anthropic import Anthropic

client = Anthropic()

TOOLS = [
    {
        "name": "Read",
        "description": "Read a file from disk",
        "input_schema": {
            "type": "object",
            "properties": {"file_path": {"type": "string"}},
            "required": ["file_path"],
        },
    },
    # Write, Bash, Edit, ... 도구가 더 들어간다
]

def execute_tool(name: str, args: dict) -> str:
    if name == "Read":
        return open(args["file_path"]).read()
    # Write, Bash, Edit, ...
    raise ValueError(f"Unknown tool: {name}")

def claude_code(user_input: str) -> None:
    messages = [{"role": "user", "content": user_input}]

    while True:
        response = client.messages.create(
            model="claude-sonnet-4-20250514",
            messages=messages,
            tools=TOOLS,
            max_tokens=4096,
        )

        # A: Claude가 텍스트로 답하고 끝낸 경우
        if response.stop_reason == "end_turn":
            for block in response.content:
                if block.type == "text":
                    print(block.text)
            return

        # B: Claude가 도구를 호출한 경우
        if response.stop_reason == "tool_use":
            # Claude의 응답(도구 호출 포함)을 메시지에 추가
            messages.append({"role": "assistant", "content": response.content})

            # 도구를 진짜로 실행
            tool_results = []
            for block in response.content:
                if block.type == "tool_use":
                    result = execute_tool(block.name, block.input)
                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": result,
                    })

            # 도구 결과를 user 메시지로 추가
            messages.append({"role": "user", "content": tool_results})
            # 다시 while 위로 → Claude가 결과 보고 다음 결정
```

50줄 안 된다. 그리고 진짜 동작한다 (Anthropic API 키만 있으면).

이게 Claude Code의 **본질의 가장 작은 형태**다. Part 9에서 여기에 권한 체크, 스트리밍, Pydantic 스키마, 서브 에이전트를 붙여서 진짜 미니 Claude Code로 키울 거다. 하지만 **골격은 위 50줄에서 한 줄도 변하지 않는다.**

> 💡 **팁:** 이 코드를 직접 돌려보고 싶으면 `pip install anthropic`만 하면 된다. `ANTHROPIC_API_KEY` 환경변수 설정하고 `claude_code("hello")`를 호출. Claude는 도구를 안 부르고 그냥 인사하고 끝낸다. `claude_code("/tmp/test.txt 읽어줘")` 같은 걸 시켜보면 도구 호출 분기가 발동한다.

## LLM은 CPU다

여기서 한 발 물러나자. 50줄 루프가 본질이면, 52만 줄은 대체 뭐냐? "부수적인 것"이라고 치부하기엔 뭔가 찝찝하다. 52만 줄을 "살"이라고 불렀는데, 살 없는 골격은 걸어다니지 못한다.

비유를 하나 가져와 보자. 여러분이 잘 아는 것으로.

**CPU는 혼자서 컴퓨터가 아니다.**

CPU가 하는 일은 명확하다 — 명령어를 fetch하고, decode하고, execute한다. 그게 전부다. 오직 그 일만 한다. 하지만 CPU만 갖고는 아무것도 할 수 없다. 파일을 저장할 수 없고, 화면에 뭘 띄울 수 없고, 네트워크로 뭘 보낼 수도 없다.

CPU가 "컴퓨터"가 되려면 **운영체제(OS)**가 필요하다. OS가 파일 시스템을 관리하고, 프로세스를 스케줄링하고, I/O를 중재하고, 메모리를 할당하고, 권한을 검사한다. CPU가 할 줄 아는 단 하나의 일 — "명령어 실행" — 을 유의미한 시스템으로 만드는 건 OS의 역할이다.

이제 대입해보자.

| 컴퓨터 | Claude Code |
|--------|-------------|
| CPU | Claude (LLM) |
| CPU의 유일한 일 | 텍스트 받고 텍스트 뱉기 |
| OS | 하네스 (52만 줄 TypeScript) |
| OS의 역할 | LLM의 출력을 유의미한 시스템으로 만들기 |

Claude(LLM)는 텍스트를 받으면 텍스트를 뱉는다. 그게 전부다. 파일을 못 읽고, 명령을 못 실행하고, 화면에 뭘 못 그린다. CPU가 fetch-decode-execute만 하듯, LLM은 predict-next-token만 한다.

이 LLM을 "코딩 에이전트"로 만드는 건 **하네스(harness)** — 우리가 방금 50줄로 본 그 루프를 포함해서, 그 루프가 제대로 돌아가게 만드는 모든 것 — 의 역할이다. 하네스가 없는 LLM은 CPU가 없는 컴퓨터만큼이나 무력하고, LLM이 없는 하네스는 OS만 있고 CPU가 없는 것만큼이나 무의미하다.

## 하네스는 마이크로커널이다

OS에도 종류가 있다. 여기서 두 번째 비유의 층위를 열어보자.

**모놀리식 커널(monolithic kernel)** 은 모든 서비스 — 파일 시스템, 네트워크 스택, 디바이스 드라이버, 스케줄러 — 를 커널 공간 안에 넣는다. Linux가 대표적이다. 빠르지만 덩어리가 크다.

**마이크로커널(microkernel)** 은 반대 전략을 택한다. 커널에는 IPC(프로세스 간 통신)와 스케줄링만 남기고, 나머지는 전부 **user-space 서비스**로 뺀다. Mach, QNX, MINIX 3이 대표적이다. 커널 자체는 극도로 작다 — 수천 줄. 파일 시스템도, 네트워크도, 디바이스 드라이버도 커널 밖에 있다. 커널은 그것들 사이의 메시지 전달만 책임진다.

Claude Code의 하네스는 마이크로커널 스타일이다.

- **커널**: `query.ts`의 `while(true)` 루프. 하는 일은 딱 하나 — LLM에게 메시지를 보내고, 응답이 도구 호출이면 실행하고, 결과를 메시지에 추가해서 다시 보낸다. 우리가 50줄 Python으로 본 바로 그것.
- **user-space 서비스**: 그 루프가 제대로 돌아가기 위해 필요한 나머지 모든 것.

그 "나머지 모든 것"이 52만 줄이다. 그리고 이것은 명확한 레이어 구조를 갖고 있다.

```
+-----------------------------------------------------------+
|                    사용자 (터미널 / IDE)                     |
+-----------------------------------------------------------+
|                                                           |
|  +--------------+  +---------------+  +----------------+  |
|  | 입력 처리     |  | 응답 처리      |  | 확장 시스템     |  |
|  |              |  |               |  |                |  |
|  | - 슬래시 명령 |  | - 스트리밍     |  | - MCP 클라이언트|  |
|  | - 시스템 프롬 |  | - 파싱        |  | - 멀티 에이전트 |  |
|  |   프트 조립   |  | - UI 렌더링   |  | - IDE 브릿지   |  |
|  | - 컨텍스트    |  |               |  | - 스킬         |  |
|  |   주입       |  |               |  |                |  |
|  +------+-------+  +-------+-------+  +-------+--------+  |
|         |                  |                   |           |
|  +------+------------------+-------------------+--------+  |
|  |              도구 실행 + 권한 시스템                    |  |
|  |                                                      |  |
|  |  - 40+ 도구 (Read, Write, Bash, Edit, Glob, ...)     |  |
|  |  - 5가지 권한 모드 / Hook 시스템 / 보안 검사 23개      |  |
|  +---------------------------+--------------------------+  |
|                              |                             |
|  +---------------------------+--------------------------+  |
|  |           메모리 + 컨텍스트 관리                       |  |
|  |                                                      |  |
|  |  - 자동 압축 / 세션 저장 / CLAUDE.md 로딩             |  |
|  +---------------------------+--------------------------+  |
|                              |                             |
|  +===========================+==========================+  |
|  ||       마이크로커널: query.ts while(true)            ||  |
|  ||                                                    ||  |
|  ||  메시지 전송 -> 응답 수신 -> 도구 호출 분기 -> 반복   ||  |
|  +===========================+==========================+  |
|                              |                             |
+------------------------------+-----------------------------+
|              Claude API (LLM = CPU)                        |
+-----------------------------------------------------------+
```

아래에서 위로 읽어보자.

1. **맨 아래 — Claude API**: CPU에 해당한다. 텍스트를 받으면 텍스트를 내뱉는다. 그게 전부다.
2. **마이크로커널**: `query.ts`의 `while(true)` 루프. CPU 위에 직접 올라앉아서, API 호출과 도구 실행의 메시지 전달만 책임진다. 50줄.
3. **메모리 + 컨텍스트 관리**: 메시지가 무한히 쌓이면 터진다. 자동 압축(`autoCompact`), 세션 저장, 마이크로컴팩트 등이 이 층에서 작동한다.
4. **도구 실행 + 권한 시스템**: "Claude가 Bash를 쓰겠다고 했는데, 진짜로 실행해도 되나?" — 권한 검사, Hook 실행, 보안 검증이 이 층에서 일어난다. 도구 40여 개의 구현체도 여기.
5. **입력 처리 / 응답 처리 / 확장 시스템**: 사용자가 치는 슬래시 명령을 파싱하고, Claude의 스트리밍 응답을 터미널에 그리고, MCP 서버에서 외부 도구를 가져오고, 서브 에이전트를 재귀 호출하는 것들. 가장 바깥 레이어.

**이 책의 나머지가 하는 일은, 이 다이어그램의 각 레이어를 한 겹씩 벗겨보는 것이다.**

## 왜 이 구조가 중요한가

"비유는 재밌는데, 그래서 뭐?" 이 구조를 아는 게 실무에 뭘 바꿔주는지 구체적으로 짚자.

**첫째, 문제가 생겼을 때 어디를 봐야 하는지 안다.** "Claude가 파일을 못 읽어요" → 도구 실행 + 권한 레이어. "응답이 잘리네요" → 메모리 + 컨텍스트 레이어. "MCP 도구가 안 보여요" → 확장 시스템 레이어. 레이어를 알면 52만 줄 전체를 뒤지지 않아도 된다.

**둘째, 확장할 때 어디에 끼워넣으면 되는지 안다.** Hook을 추가하고 싶다면 도구 실행 레이어에. 새 슬래시 명령을 만들고 싶다면 입력 처리 레이어에. MCP 서버를 연결하고 싶다면 확장 시스템 레이어에. 마이크로커널 자체는 건드릴 필요가 없다.

**셋째, Part 9에서 직접 만들 수 있다.** 마이크로커널이 작으니까 복제할 수 있다. 50줄로 시작해서 레이어를 한 겹씩 직접 쌓아보면, 52만 줄이 왜 그렇게 생겼는지 체감하게 된다.

## 핵심 정리

- **Claude Code = LLM(CPU) + 하네스(OS).** LLM은 텍스트를 받으면 텍스트를 뱉는다. 하네스는 그 출력을 파일 편집, 명령 실행, 코드 리뷰 같은 유의미한 행동으로 바꾼다.
- **하네스의 커널은 50줄짜리 `while(true)` 루프다.** 메시지 전송 → 응답 수신 → 도구 호출이면 실행 → 결과를 메시지에 추가 → 반복. 이것이 에이전트 루프이고, Claude Code의 마이크로커널이다.
- **52만 줄은 이 커널 위에 쌓인 user-space 서비스다.** 도구 실행, 권한, 스트리밍, 압축, MCP, 멀티 에이전트, UI — 모두 마이크로커널 바깥에서, 명확한 레이어 구조로 조직되어 있다.
- **결정권은 Claude(LLM)한테 있다.** 하네스는 도구를 실행하고 결과를 돌려주는 집사다. 흐름 제어는 LLM이 쥐고 있다. 이것이 전통적 프로그램과 에이전트의 가장 큰 차이다.
- **Part 9에서 마이크로커널을 직접 만들고, 나머지 Part에서 레이어를 한 겹씩 분석한다.** 이것이 이 책의 여정이다.
