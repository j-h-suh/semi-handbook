# 2.1 에이전트 루프 한 장 — Claude Code의 본질을 한 그림으로

---

## 이 챕터에서 배우는 것

- 0.1에서 그렸던 단순한 에이전트 루프를, 진짜 Claude Code에 더 가까운 모양으로 업그레이드
- "한 턴(turn)"이 무엇이고, 그 안에서 LLM API가 몇 번이나 호출되는가
- `query.ts`와 `QueryEngine.ts`의 역할 차이 — 외부 라이프사이클과 내부 루프
- 그리고 이 그림이 **Part 2 전체의 지도**가 된다는 사실

---

## 사용자 경험에서 출발

`/commit` 비슷한 작업을 시켜보자.

```
> 이 프로젝트의 변경사항 보고 커밋 메시지 작성해줘
```

엔터를 누르면 일어나는 일을 눈에 보이는 대로 적어보면 이렇다.

```
1. "확인해볼게요" 같은 짧은 텍스트가 토큰 단위로 흐름
2. spinner: "Bash: git status"
3. 결과 박스가 나타남 (변경된 파일 목록)
4. spinner: "Bash: git diff --stat"
5. 결과 박스
6. spinner: "Read: src/foo.py"
7. 결과 박스 (파일 내용)
8. "변경 사항을 정리하면..." 같은 더 긴 텍스트가 토큰 단위로 흐름
9. 추천 커밋 메시지
10. 응답 종료
```

이 전체가 **한 턴(turn)**이다. 사용자가 한 번 엔터를 친 것에 대한 응답이 끝날 때까지가 한 턴.

여기서 슬슬 의문이 생긴다.

> "잠깐. 0.1에서 그린 그림에서는 'Claude API 호출' 박스가 하나였잖아. 근데 위 흐름에선 도구가 3번 호출됐고, 텍스트도 두 번에 나눠서 흘러나왔는데, 그럼 API는 몇 번 호출된 거지?"

좋은 질문이다. 답은 **여러 번**. 그리고 그 여러 번을 정확히 그리는 게 이 챕터의 목표다.

## 본문

### 0.1의 그림 — 단순한 버전

먼저 0.1에서 그렸던 그림을 다시 가져와보자.

```
사용자 입력
   ↓
Claude API 호출
   ↓
[텍스트] or [도구 호출]
   ↓
도구 호출이면 → 실행 → 결과를 메시지에 추가 → 위로 다시
텍스트면 → 화면에 출력 → 끝
```

이 그림은 틀린 건 아니다. 본질은 정확히 이거다. **다만 한 가지 추상화가 숨어 있다**: "Claude API 호출"이 한 박스로 그려진 것.

진짜 Claude Code에서는 이 박스를 열어봐야 한다.

### 진짜 그림 — 두 개의 루프가 겹쳐 있다

진짜 Claude Code의 에이전트 루프는 **두 계층**으로 되어 있다.

![두 계층의 에이전트 루프](/content/claude_code/images/02_1/two_layer_loop.svg)

여기에 한 가지 더가 있다. 내부 루프 중간에 **복구 경로**가 끼어 있을 수 있다.

```
내부 루프 안에서:
  → API 호출 시 429 (rate limit) → 잠시 대기 후 재시도
  → 토큰 한도 초과 → 자동 압축(autocompact) 트리거
  → 스트리밍 도중 연결 끊김 → 부분 결과로 폴백
  → 도구 결과가 너무 큼 → 디스크에 저장하고 요약본만 LLM에
```

이 모든 게 내부 루프 한 번 안에서 일어날 수 있다. 그래서 진짜 코드의 내부 루프는 단순한 `while True`가 아니라 **상태 머신**에 가깝다.

### query.ts와 QueryEngine.ts의 역할 차이

위 두 계층이 코드에서는 두 파일로 나뉜다.

| 파일 | 역할 |
|---|---|
| **`QueryEngine.ts`** (1,297줄) | **외부 라이프사이클 매니저**. 한 conversation(대화) 동안 살아 있는 객체 — `submitMessage()` 호출 한 번이 한 턴을 시작하고, 그 턴이 끝나도 객체 자체는 다음 턴을 위해 유지된다. 메시지 히스토리, file cache, usage, 권한 모드, MCP 클라이언트 같은 **세션 수준 상태**(턴 사이에 살아남는 상태) 를 들고 있다. |
| **`query.ts`** (1,730줄) | **내부 루프**. 한 턴 안에서 메시지 정규화 → API 호출 → 도구 디스패치 → 결과 수집 → 반복을 돈다. 복구 경로(autocompact, 재시도, 폴백)가 다 여기 들어 있다. |

여기서 **conversation(대화)** 는 사용자가 인식하는 한 세션 — `claude` 실행부터 `/clear` 또는 REPL 종료까지. `/resume` 으로 이전 대화의 메시지 히스토리를 복원해 같은 conversation 으로 이어갈 수도 있다.

위 표는 추측이 아니다 — `QueryEngine.ts:175-183` 의 클래스 주석이 거의 같은 말을 한다.

> "QueryEngine **owns the query lifecycle and session state for a conversation**. ... **One QueryEngine per conversation**. Each `submitMessage()` call **starts a new turn** within the same conversation. State (messages, file cache, usage, etc.) **persists across turns**."

> 한글 번역: "QueryEngine 은 한 **대화(conversation)** 의 query 라이프사이클과 **세션 상태**를 소유한다. ... 대화 하나당 QueryEngine 하나. 같은 대화 안에서 `submitMessage()` 호출 한 번이 **한 턴을 시작**한다. 상태(메시지, 파일 캐시, 사용량 등) 는 **턴 사이에 유지**된다."

대략 다음과 같은 호출 관계다.

```
사용자 입력
   ↓
QueryEngine.submitMessage(input)        ← 외부 진입점 (async generator!)
   ↓
   메시지 히스토리에 추가
   시스템 프롬프트 빌드
   ↓
   query(params: QueryParams)           ← 얇은 wrapper. lifecycle tracking 만 추가
      ↓
      queryLoop(params, ...)            ← 진짜 내부 루프 (while + 상태 머신)
         ↓
         while True:
            API 호출 (스트리밍)
            도구 호출 있으면 → 실행 → 메시지에 추가 → continue
            없으면 → break
   ↓
   호출자(REPL)가 yield 받은 이벤트를 UI 에 반영
   ↓
턴 종료
```

> ⚙️ **세 계층이다, 사실은**: `query.ts` 안에는 진입점이 둘이다. `query()`가 외부에서 부르는 **얇은 wrapper** (`query.ts:219`), `queryLoop()`가 진짜 `while` 루프를 도는 내부 함수 (`query.ts:241`).
>
> - `query()` 의 일 (**명령 lifecycle 추적**): `queryLoop` 가 정상 종료된 후에만 모은 명령 UUID 들에 `'completed'` 신호를 보낸다. throw 시에는 안 보냄 — 외부가 "시작-만-된" 명령을 감지할 수 있는 비대칭 신호.
> - `queryLoop` 의 일 (**상태 머신 운영**): `query.ts:204` 의 `type State` 가 머신의 정의 (`autoCompactTracking`, `maxOutputTokensRecoveryCount`, `turnCount`, `transition` 등). 매 반복이 이 상태를 읽고 다음 행동(API 호출 / 도구 실행 / 재시도 / 압축 등) 을 결정 → 새 상태로 전이. 단순 `while True` 가 아니라 반복 사이에 누적되는 mutable 상태가 다음 행동을 결정.
>
> "두 계층"이라고 했지만 실제는 `submitMessage` → `query` → `queryLoop`의 세 계층.

<summary>🔬 Deep Dive — wrapper 와 상태 머신, 더 깊이</summary>

> 콜아웃의 세 키워드(`throw`, "lifecycle 신호", "mutable 상태") 를 코드 레벨로 풀어둔다.
>
> **1. `throw 시 안 보냄` 의 의미** — `query()` 의 `yield* queryLoop(...)` 는 throw 를 잡지 않고 통과시킨다. queryLoop 안에서 예외가 발생하면 그 다음 줄(`for (const uuid of ...) notifyCommandLifecycle(uuid, 'completed')`) 자체가 실행되지 않는다. 그래서 외부에서 "시작은 받았는데 completed 통지가 안 온 명령" 을 비정상 종료로 감지할 수 있다.
>
> **2. 이 신호는 누가 듣는가** — `setCommandLifecycleListener` 의 유일한 사용처는 `cli/remoteIO.ts:159`. 원격 control 세션의 클라이언트(`ccrClient`) 에 `started → 'processing'`, `completed → 'processed'` 로 매핑되어 보고된다. 즉 외부에서 명령을 보낸 채널 용 — IDE 통합, headless SDK 사용자(REPL 화면 없이 스크립트·subprocess·라이브러리 임베드로 Claude Code 를 굴리는 쪽 — Anthropic 의 공식 **Claude Agent SDK** 같은 곳), 웹 UI 등. REPL 자체는 화면에 직접 그려서 안다 보니 이 신호를 안 쓴다.
>
> **3. `mutable 상태` 가 정확히 무엇인가** — `queryLoop` 안의 `let state: State = { ... }` 가 핵심. `let` 선언이라 재할당 가능, 매 반복 끝에 `state = { ... }` 로 새 객체로 갱신된다. 일반 함수의 지역 변수는 함수 종료 시 사라지지만, 여기서는 while 루프 반복 사이에 살아남아 한 반복의 결과가 다음 반복의 입력이 된다. 0.5 의 클로저가 함수 호출 사이에 변수가 살아남는다면, 여기서는 루프 반복 사이에 변수가 살아남는다.

</details>

> 💡 **`params: QueryParams`**: `query()`는 13개 필드의 객체로 인자를 받는다 — `messages`, `systemPrompt`, `canUseTool`(권한 함수), `toolUseContext`(tools가 여기 안에 묻혀 있음), `maxTurns`, `taskBudget`, ... 의존성 주입 패턴이다. "messages와 tools만 받는다"는 단순화는 큰 그림용.

> 💡 **Python 비유:** `QueryEngine.submitMessage()`는 FastAPI의 라우트 핸들러처럼 한 요청을 받는 진입점이고, `query()`는 그 안에서 도는 비즈니스 로직 함수다. 외부와 내부의 책임을 명확히 나눠둔 거다. 단, 둘 다 **async generator**라는 게 핵심 — 이벤트가 외부에서 내부로, 그리고 다시 호출자(REPL)까지 한 줄로 흐른다. **2.2**에서 본격적으로 본다.

### 한 턴 안에 LLM API가 몇 번 호출되는가

위 흐름을 따라 다시 세보자. 아까 사용자 경험 예시(`/commit` 작업)에서 일어난 일을 LLM API 호출 단위로 풀면 이렇다.

```
[API 호출 1]
  사용자: "이 프로젝트의 변경사항 보고 커밋 메시지 작성해줘"
  Claude 응답: "확인해볼게요" + tool_use(Bash, "git status")
  → "git status" 실행
  → 결과를 메시지에 추가

[API 호출 2]
  ... (위 메시지들 누적)
  Claude 응답: tool_use(Bash, "git diff --stat")
  → 실행 → 결과 추가

[API 호출 3]
  Claude 응답: tool_use(Read, "src/foo.py")
  → 실행 → 결과 추가

[API 호출 4]
  Claude 응답: "변경 사항을 정리하면..." + 추천 커밋 메시지
  stop_reason = "end_turn"
  → 내부 루프 종료
  → 한 턴 끝
```

**한 사용자 입력에 대해 LLM API 호출이 4번** 일어났다. 매번 전체 메시지 히스토리 + 도구 결과들을 같이 보낸다. 그래서 대화가 길어지면 한 턴당 토큰 비용이 기하급수적으로 늘어날 수 있다. (이 문제를 푸는 게 컨텍스트 압축 — Part 7에서 본다.)

> ⚠️ **함정:** "그럼 사용자가 한 메시지 보낼 때마다 API 호출 한 번이 아니구나" — 정확히 그렇다. 도구를 쓰는 작업은 거의 항상 여러 번 호출된다. Anthropic 계정의 사용량이 생각보다 빨리 차는 이유 중 하나다.

### 이 그림이 Part 2 전체의 지도다

이 챕터에서 그린 두 계층 + 복구 경로 그림을, 다음 챕터들이 하나씩 분해한다.

- **2.2 비동기 제너레이터 파이프라인** — "내부 루프가 어떻게 코드로 표현되어 있는가". TypeScript의 `AsyncIterator`로 만들어져 있는데, 그게 Python의 `async for`와 어떻게 비슷한지.
- **2.3 스트리밍과 재시도** — "내부 루프 안의 복구 경로 10가지". 토큰 단위 스트리밍, 429 재시도, 자동 압축, max_output_tokens 폴백, ...

여기서 큰 그림만 단단히 박아두면 다음 챕터들이 세부 디테일로 들린다. 큰 그림이 없으면 세부가 **수많은 if문의 모음**으로 들린다. 큰 그림이 먼저다.

## Python으로 옮기면

0.1의 단순 루프를 두 계층으로 쪼개보자.

```python
class QueryEngine:
    """외부 라이프사이클 매니저."""
    
    def __init__(self):
        self.messages: list[dict] = []
        self.tools = AVAILABLE_TOOLS
        self.permission_context = PermissionContext()
    
    async def submit_message(self, user_input: str):
        """한 턴 시작. 자체도 async generator — 호출자에게 이벤트를 yield 로 흘려보냄."""
        self.messages.append({"role": "user", "content": user_input})
        system_prompt = build_system_prompt(self.permission_context)
        
        # 내부 루프의 이벤트들을 그대로 호출자(REPL)에게 forward
        async for event in query(self.messages, self.tools, system_prompt, self.permission_context):
            yield event  # ← 호출자가 한 이벤트씩 받아볼 수 있음
        # 내부 루프가 끝나면 한 턴 종료


async def query(messages, tools, system_prompt, permission_context):
    """내부 루프. 한 턴 안에서 도는 함수.

    실제 query.ts 에서는 13개 필드의 QueryParams 객체로 인자를 받고,
    query() 자체는 얇은 wrapper, 진짜 while 루프는 내부의 queryLoop() 에 있다."""
    while True:
        try:
            # API 호출 (스트리밍)
            response = await call_anthropic_api(messages, tools, system_prompt)
        except RateLimitError:
            await asyncio.sleep(backoff())
            continue  # 재시도
        except ContextLengthExceededError:
            messages = await autocompact(messages)
            continue  # 압축 후 재시도
        
        # 응답 처리
        if response.stop_reason == "end_turn":
            yield response  # 마지막 텍스트
            return  # 내부 루프 종료
        
        if response.stop_reason == "tool_use":
            messages.append({"role": "assistant", "content": response.content})
            
            tool_results = []
            for block in response.content:
                if block.type == "tool_use":
                    result = await execute_tool(block.name, block.input)
                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": result,
                    })
                    yield ToolUseEvent(block, result)  # UI에 도구 결과 알림
            
            messages.append({"role": "user", "content": tool_results})
            # 다시 while 위로 → 같은 내부 루프 한 바퀴 더
```

핵심이 다 들어 있다.

- **외부**: `QueryEngine.submit_message`가 한 사용자 입력에 대한 한 턴을 시작. **자체도 generator**라서 내부 이벤트를 호출자(REPL)까지 그대로 흘려보낸다.
- **내부**: `query()`가 그 안에서 `while True` 루프를 돌며 API 호출 + 도구 디스패치를 반복.
- **복구 경로**: `try/except`로 rate limit과 context length 초과 처리.
- **이벤트 yield**: 내부에서 발생하는 일들을 외부에 알리기 위해 generator로 만들었음. 외부 → 내부 → 호출자가 한 줄의 generator 체인.

이 의사코드가 **`query.ts`의 1,730줄과 거의 같은 골격**이다. 진짜 코드는 더 많은 복구 경로, 더 정교한 스트리밍 처리, 더 많은 권한 체크가 들어 있을 뿐이다. 그리고 위에서 본 것처럼 `query()` 자체는 얇은 wrapper고, 진짜 루프는 `queryLoop()`에 있다. 그것들이 2.2와 2.3의 주제다.

## 핵심 정리

- 0.1에서 그린 단순 루프는 본질이 정확하지만, 진짜 Claude Code는 **두 계층**으로 되어 있다: 외부 라이프사이클(`QueryEngine.ts`, 1,297줄) + 내부 루프(`query.ts`, 1,730줄). 더 정확히는 `submitMessage` → `query` → `queryLoop`의 **세 계층**.
- **한 턴(turn)** = 한 사용자 입력에 대한 응답이 끝날 때까지. 한 턴 안에서 **LLM API 호출이 여러 번** 일어난다 (도구를 부를 때마다 결과를 다시 LLM에 보내야 하니까).
- 외부와 내부 모두 **`async generator`**다 (`async function*`). 내부 루프 → 외부 → 호출자(REPL)가 한 줄의 generator 체인으로 연결되어 이벤트가 흐른다. **2.2**의 주제.
- 내부 루프는 단순한 `while True`가 아니라 **상태 머신**에 가깝다. `query.ts:204-217`의 `type State`가 그걸 직접 증명한다 — `autoCompactTracking`, `maxOutputTokensRecoveryCount`, `hasAttemptedReactiveCompact`, `turnCount`, `transition` 같은 필드가 한 턴 동안 변한다. rate limit 재시도, 자동 압축, 스트리밍 폴백, 토큰 한도 폴백 등 복구 경로가 끼어 있다.
- 이 두/세 계층 + 복구 경로의 그림이 **Part 2 전체의 지도**다. 2.2에서 비동기 제너레이터로 어떻게 코드화되었는지, 2.3에서 복구 경로 10가지의 디테일을 본다.
- "한 메시지 = 한 API 호출"이 아니라 **"한 턴 = 여러 API 호출"**이라는 사실 하나만 기억해도 큰 그림은 잡힌다.
