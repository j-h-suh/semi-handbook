# 2.3 스트리밍과 재시도 — 네트워크 불안정을 견디는 10가지 복구 경로

---

## 이 챕터에서 배우는 것

- 2.1에서 그렸던 내부 루프가 진짜로는 단순한 `while True`가 아니라 **상태 머신**에 가깝다는 사실
- 그 상태 머신이 처리하는 **10가지 복구 경로**의 카탈로그
- 스트리밍 모드와 비스트리밍 모드의 분기
- "사용자가 거의 못 느낀다"가 어떻게 만들어지는가
- Python의 `tenacity` 같은 라이브러리와 비교

---

## 사용자 경험에서 출발

지하철, 카페, 비행기 안에서 Claude Code를 써본 적이 있으면 한 번쯤 이런 경험을 했을 거다.

- 응답이 평소보다 살짝 느린데, 어쨌든 결국엔 도착한다.
- spinner가 잠깐 깜빡이거나 한두 번 다시 시작되는 게 보인다.
- 가끔 "네트워크가 불안정합니다" 같은 작은 안내가 뜨고 사라진다.
- 그런데 "에러로 죽었다"는 거의 없다.

근데 사실은 네트워크가 그렇게 자주 안정적이지 않다. Anthropic API 서버도 가끔 과부하 상태(529)다. 토큰 한도에 부딪힐 때도 있다. 스트리밍 연결이 중간에 끊길 때도 있다. 이 모든 게 내부에서 일어나는데, 사용자에게는 거의 안 보인다.

그 안 보이는 곳에 무엇이 들어 있는지가 이 챕터의 주제다.

## 본문

### 첫 번째 분기: 스트리밍 모드 vs 비스트리밍 모드

`query.ts`에는 두 가지 API 호출 모드가 있다.

:::tabs

```typescript
// 두 가지 호출 함수가 있다
queryModelWithStreaming(...)    // 기본
queryModelWithoutStreaming(...) // 폴백
```

```python
# Python 등가 — Anthropic SDK의 두 가지 호출 모드
response = await client.messages.create(...)         # 비스트리밍 (한 번에)

async with client.messages.stream(...) as stream:    # 스트리밍 (토큰 단위)
    async for event in stream:
        yield event
```

:::

> 💡 **잠깐 — 스트리밍의 정체 (SSE):** 일반 HTTP 는 한 요청에 응답 하나로 끝난다. 그런데 LLM 응답은 다르다 — 토큰 수백 개가 한 응답 안에서 흘러나온다. 다 만들어질 때까지 기다리지 말고 도착하는 대로 받고 싶다. 이걸 받쳐주는 게 **Server-Sent Events(SSE)** — HTTP 연결을 끊지 않고 서버가 데이터를 계속 밀어 넣는 방식이다.
>
> 응답 헤더로 구분된다. 일반 HTTP 는 `Content-Type: application/json`, SSE 는 `Content-Type: text/event-stream`.
>
> WebSocket 도 서버 푸시가 가능한데 SSE 와 어떻게 다른가? SSE 는 **서버 → 클라이언트 단방향**이고 HTTP 위에 그대로 올라간다. WebSocket 은 별도 프로토콜 업그레이드가 필요하고, 일부 기업/네트워크 환경에서 차단된다. LLM 응답은 클라이언트가 보낼 게 없어서 단방향으로 충분 — SSE 가 자연스러운 선택이다.

**스트리밍 모드**가 기본이다. 토큰이 도착하는 즉시 yield해서 사용자가 흘러나오는 응답을 본다.

**비스트리밍 모드**는 응답이 다 도착할 때까지 기다렸다가 한 번에 받는다. 다음 같은 경우에 쓴다.

- 스트리밍 모드가 실패해서 폴백할 때
- 어차피 한 번에 처리해도 되는 짧은 작업 (예: 자동 압축의 요약 LLM 호출)
- SSE 를 지원하지 않는 환경

흥미로운 건 스트리밍이 실패하면 비스트리밍으로 자동 폴백된다는 점이다. 같은 내용을 다시 요청하되, 이번에는 스트리밍 없이. 사용자 입장에서는 "응답이 한꺼번에 나왔네" 정도로 보이고 끝.

### 복구 경로 10가지 카탈로그

`query.ts`의 1,730줄 + 함께 작동하는 `services/api/withRetry.ts` 의 823줄 안에는 10가지가 넘는 복구 경로가 흩어져 있다. 각각이 어떤 상황에서 무엇을 다르게 하는지 표로 정리해보자.

> ⚙️ **3계층 구조** — 이 경로들이 한 함수 안에 있는 게 아니다. **세 계층에 흩어져 있다.**
>
> | 계층 | 파일 | 처리하는 에러 |
> |---|---|---|
> | HTTP 재시도 | `services/api/withRetry.ts` (823줄, 55+ 군데) | 429, 529, 5xx, network |
> | 모드 폴백 | `services/api/claude.ts` (`queryModel`) | 스트리밍 → 비스트리밍 |
> | 의미적 복구 | `query.ts` (`queryLoop`) | prompt_too_long, max_output_tokens, image_error, reactive_compact, ... |
>
> 아래 표는 그 셋을 한 화면에 평탄화한 것. 진짜는 한 함수도, 한 파일도 아니다.

| # | 트리거 | 대응 | 처리 계층 |
|---|---|---|---|
| 1 | **429 (rate limit)** | 백오프 후 재시도. retry-after 헤더 따름 | `withRetry.ts` |
| 2 | **529 (server overloaded)** | 더 긴 백오프 + 재시도 | `withRetry.ts` |
| 3 | **5xx 일반 에러** | 지수 백오프 + 최대 N회 재시도 | `withRetry.ts` |
| 4 | **네트워크 끊김 (스트리밍 중)** | 부분 결과 보존 + 재연결 | `withRetry.ts` + `queryModel` |
| 5 | **스트리밍 자체 실패** | 비스트리밍 모드로 폴백 | `queryModel` (`claude.ts`) |
| 6 | **`max_output_tokens` 도달** | 출력 한도 늘리거나 응답 분할 후 재시도 | `queryLoop` (`query.ts`) |
| 7 | **`prompt_too_long`** | **autocompact** 트리거 → 메시지 요약 → 재시도 | `queryLoop` |
| 8 | **context length exceeded** | 마찬가지로 autocompact 후 재시도 | `queryLoop` |
| 9 | **잘못된 도구 호출 형식** | 도구에게 에러 메시지를 결과로 돌려보내고 다시 LLM 호출 | tool dispatch |
| 10 | **모델 응답이 비어 있음** | 재시도 (모델의 일시적 hiccup) | `withRetry.ts` |
| (+) | **모델 자체 폴백** | 환경에 따라 더 작은 모델로 폴백 가능 | `queryModel` |

이 모든 경로가 한 사용자 입력에 대한 응답이 끝날 때까지 안에서 일어난다. 사용자가 재시도해주세요 같은 걸 누르는 게 아니라, **시스템이 알아서 처리한다.**

> 💡 **표는 단순화 — 진짜는 17가지 이상.** `query.ts` 의 `queryLoop` 가 사용하는 **transition reason** 값들을 본문 곳곳의 `return { reason: ... }` 에서 다 세보면 17가지다 — `image_error`, `model_error`, `aborted_streaming`, `collapse_drain_retry`, `reactive_compact_retry`, `prompt_too_long`, `max_output_tokens_escalate`, `max_output_tokens_recovery`, `blocking_limit`, `completed`, `stop_hook_prevented`, `stop_hook_blocking`, `token_budget_continuation`, `aborted_tools`, `hook_stopped`, `max_turns`, `next_turn`.
>
> 이 중 절반 이상이 복구 관련 (위 10가지 중 일부 + `image_error`, `aborted_streaming`, `collapse_drain_retry`, `reactive_compact_retry`, `blocking_limit` 같은 덜 알려진 경로들).
>
> 그리고 이 `transition` 필드 (`query.ts:216`) 의 주석은 의미심장하다 (`query.ts:214-215`):
>
> > "Why the previous iteration continued. Undefined on first iteration. **Lets tests assert recovery paths fired without inspecting message contents.**"
> >
> > → "이전 iteration 이 왜 이어졌는지. 첫 iteration 에서는 undefined. **테스트가 메시지 내용을 들여다보지 않고도 어떤 복구 경로가 발화했는지 단언할 수 있게 해준다.**"
>
> 그리고 한 가지 더 — `reason` 은 라벨이 아니라 **루프의 분기 키**다. queryLoop 의 `while(true)` 안에서 한 iteration 은 두 가지로 마무리된다:
>
> - **종료**: `return { reason: 'completed' | 'max_turns' | 'blocking_limit' | ... }` — 루프 빠져나감
> - **다음 iteration 으로 넘기기**: state 에 `transition: { reason: 'reactive_compact_retry' | 'collapse_drain_retry' | 'max_output_tokens_recovery' | ... }` 를 기록하고 `continue`
>
> 즉 다음 iteration 이 시작될 때 `transition.reason` 만 보면 "직전이 왜 끝났는지" 를 바로 알 수 있다. 이 필드가 없었다면 메시지 배열을 뒤져서 직전 turn 의 도구 결과나 에러 페이로드를 보고 추론해야 했을 것 — 위 영문 주석의 "without inspecting message contents" 가 정확히 이 얘기다.

### 그래서 `query.ts` 내부 루프는 어떻게 생겼나

2.1에서 그렸던 단순한 `while True`를 더 정확하게 그리면 이렇다.

```
while True:
  try:
    response = await callAPI(messages, tools)   ← 스트리밍 시도
  except RateLimitError(429):
    await sleep(retry_after)
    continue                                    ← 경로 1
  except ServerOverloadedError(529):
    await sleep(longer_backoff)
    continue                                    ← 경로 2
  except StreamingFailedError:
    response = await callAPINonStreaming(...)   ← 경로 5 (모드 폴백)
  except PromptTooLongError:
    messages = await autocompact(messages)      ← 경로 7
    continue
  except ContextLengthExceededError:
    messages = await autocompact(messages)      ← 경로 8
    continue
  except NetworkError:
    if can_resume_stream():
      response = await reconnectStream(...)     ← 경로 4
    else:
      continue                                  ← 다시 시도
  
  # 응답 처리
  if response.stop_reason == "max_tokens":
    if can_increase_budget():
      max_output_tokens *= 2                    ← 경로 6
      continue
    else:
      # 응답을 지금까지로 자르고 사용자에게 알림
      break
  
  if response.content is empty:
    if retry_count < N:
      retry_count += 1
      continue                                  ← 경로 10
  
  if response.stop_reason == "end_turn":
    yield final_text
    return
  
  if response.stop_reason == "tool_use":
    for tool_use in tool_uses:
      try:
        result = await execute_tool(tool_use)
      except ToolFormatError:
        result = error_result(...)              ← 경로 9
      messages.append(tool_result(result))
    continue
```

진짜 코드는 더 길고, 각 경로마다 **어떤 조건에서 재시도 가능한지**, **몇 번까지 재시도할지**, **백오프를 얼마나 줄지**, **사용자에게 알릴지 말지** 같은 세부 정책이 더 있다. 하지만 골격은 위와 같다.

> ⚠️ **`except` 와 `transition.reason` 은 다른 자리다.** 위 pseudocode 는 `except → continue` 로 끝나는 것처럼 보이지만, 실제 queryLoop 은 `continue` 직전에 `state.transition = { reason: 'prompt_too_long' | ... }` 를 한 줄 더 쓴다. **except 는 한 iteration 안의 트리거, transition.reason 은 다음 iteration 에 직전이 왜 끝났는지 알리는 기록.** 한 복구 경로 안에서 둘이 함께 일한다.
>
> 그리고 위 `except` 들이 모두 queryLoop 안에 있는 것도 아니다 — 429/529/5xx 는 `withRetry.ts` 가 아래 레이어에서 묵묵히 처리해서 queryLoop 까지 안 올라온다 (위 ⚙️ 3계층 콜아웃). queryLoop 의 진짜 `try/except` 에 등장하는 건 의미적 복구 경로 (`prompt_too_long`, `max_output_tokens`, `image_error` 등) 뿐.

> 💡 **Python 비유:** 이 패턴을 Python에서 라이브러리로 잡으면 [`tenacity`](https://tenacity.readthedocs.io/)를 쓴다.
>
> ```python
> from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type
>
> @retry(
>     retry=retry_if_exception_type(RateLimitError),
>     wait=wait_exponential(multiplier=1, min=4, max=60),
>     stop=stop_after_attempt(5),
> )
> async def call_api(...):
>     ...
> ```
>
> 단순한 재시도면 데코레이터로 충분하다. 근데 Claude Code의 복구 경로는 각 에러마다 다른 행동을 해야 해서, 데코레이터 하나로는 부족하다. 그래서 `query.ts`는 직접 `try/except` 분기를 다 손으로 쓴다.

### autocompact — 가장 정교한 복구 경로

10가지 중에서 가장 흥미로운 게 **autocompact**다 (경로 7, 8).

대화가 길어져서 메시지 히스토리가 토큰 한도(예: 200K)를 넘기 직전이 되면, Claude Code가 알아서 다음을 한다.

1. 메시지 히스토리에서 오래된 메시지들을 골라낸다.
2. 그 메시지들을 **별도의 LLM 호출**로 요약한다 (보통 더 작은 모델로).
3. 요약본을 새 시스템 메시지로 만들고, 원본을 대체한다.
4. 압축된 메시지 리스트로 원래 진행하던 호출을 재시도한다.

```
원본 메시지 (200K 토큰)
   ↓
[autocompact 트리거]
   ↓
[요약 LLM 호출] (별도 turn)
   ↓
요약본 + 최근 메시지 (50K 토큰)
   ↓
[원래 호출 재시도]
   ↓
정상 응답
```

사용자 입장에서는 "잠깐 spinner가 좀 길었네" 정도다. 자기 대화가 내부적으로 압축됐다는 걸 거의 못 느낀다.

> 🔬 **Deep Dive — autocompact 의 한계:** autocompact는 메시지를 잃지 않는다고 약속하지 않는다. 요약은 lossy하다. 대화의 디테일은 사라지고 요지만 남는다. 그래서 "30분 전에 했던 그 코드 블록 다시 보여줘" 같은 요청은 압축 후에는 동작하지 않을 수 있다. Part 7.4에서 더 자세히 본다.

> ⚙️ **사실은 두 종류의 compact 가 있다.** `query.ts:11-16` 을 보면:
>
> ```typescript
> import { ... } from './services/compact/autoCompact.js'
>
> const reactiveCompact = feature('REACTIVE_COMPACT')
>   ? require('./services/compact/reactiveCompact.js') as ...
>   : ...
> ```
>
> - **`autoCompact`** (**proactive**): 토큰 한도에 접근 하면 미리 압축. 위에서 설명한 흐름.
> - **`reactiveCompact`** (**reactive**): 에러 (`prompt_too_long`, `media_size_error`) 가 발생한 후 압축. feature flag 뒤에 있음. transition reason `reactive_compact_retry` (`query.ts:1162`) 가 이걸 가리킴.
>
> 두 전략의 차이는 언제 트리거되느냐. 둘 다 메시지를 요약해서 토큰을 줄인다는 본질은 같다. proactive 가 우선, 실패하거나 못 잡아낸 경우 reactive 가 받아낸다.

### 왜 이게 다 필요한가

"근데 이렇게까지 해야 해?"라고 물을 수 있다. 답은 — 그렇다. 이유는 단순하다.

**LLM API는 신뢰할 수 없다.** 네트워크는 항상 끊긴다. Anthropic 서버는 가끔 과부하다. 토큰 한도는 항상 부딪힌다. 모델 응답은 가끔 비어 있다. 도구 호출 형식도 가끔 잘못된다.

이 모든 불완전함을 위에서 처리하지 않으면, 사용자가 처리해야 한다. 그러면 사용자 경험이 깨진다. "잠시 후 다시 시도해주세요" 같은 걸 매번 보면 누가 쓰고 싶겠나.

Claude Code가 매끄럽게 느껴지는 가장 큰 이유 중 하나가 **이 10가지 복구 경로가 잘 동작한다는 것**이다. 사용자는 거의 못 느낀다. 그게 핵심이다.

## Python으로 옮기면

`tenacity`를 써서 일부 경로를 잡아보면 이렇게 생겼다.

```python
import asyncio
from tenacity import (
    retry,
    stop_after_attempt,
    wait_exponential,
    retry_if_exception_type,
)
from anthropic import Anthropic, RateLimitError, APIStatusError

class PromptTooLongError(Exception): pass
class StreamingFailedError(Exception): pass

@retry(
    retry=retry_if_exception_type((RateLimitError, APIStatusError)),
    wait=wait_exponential(multiplier=1, min=4, max=60),
    stop=stop_after_attempt(5),
)
async def call_with_retries(client, messages, tools):
    """경로 1, 2, 3 — rate limit과 5xx만 자동 재시도."""
    return await client.messages.create(
        model="claude-opus-4-6",
        messages=messages,
        tools=tools,
        max_tokens=4096,
    )

async def query_with_recovery(messages, tools):
    """더 복잡한 복구 경로를 손으로 처리."""
    while True:
        try:
            try:
                response = await call_with_retries(client, messages, tools)
            except StreamingFailedError:
                # 경로 5 — 비스트리밍으로 폴백
                response = await call_non_streaming(messages, tools)
        except PromptTooLongError:
            # 경로 7 — autocompact 후 재시도
            messages = await autocompact(messages)
            continue
        
        if response.stop_reason == "max_tokens":
            # 경로 6 — 출력 한도 늘려서 재시도
            ...
            continue
        
        if response.stop_reason == "end_turn":
            return response
        
        if response.stop_reason == "tool_use":
            tool_results = await dispatch_tools(response)
            messages.append({"role": "user", "content": tool_results})
            continue
```

핵심 두 가지가 보인다.

1. **`tenacity`로 잡을 수 있는 단순 재시도** (rate limit, 5xx)는 데코레이터로 깔끔하게.
2. **상태가 복잡한 복구 경로**(autocompact, max_tokens 조정 등)는 명시적인 `try/except` + `while True` + `continue`로.

`query.ts`는 **거의 전부 후자**다. 데코레이터로 잡기에는 각 경로마다 행동이 너무 다르다.

> ⚠️ **함정:** "그럼 모든 에러를 다 잡고 재시도하면 되잖아?" — 안 된다. 어떤 에러는 재시도하면 안 되는 것이다 (예: 인증 실패, 잘못된 모델 이름). 어떤 에러는 몇 번까지만 재시도해야 하는 것이다 (무한 재시도는 사용자가 비용만 더 내고 결과는 못 받는 최악). 어떤 에러는 재시도하기 전에 무언가를 바꿔야 하는 것이다 (autocompact). 복구 경로마다 정책이 다르다는 게 핵심이다.

## 핵심 정리

- 2.1에서 본 내부 루프는 단순한 `while True`가 아니라 **상태 머신**이다. 그 안에 **17가지+ transition reason** 이 들어 있고, 그 중 절반 이상이 복구 관련.
- 복구 경로는 **3 계층에 흩어져** 있다:
  - **HTTP 재시도** (`withRetry.ts`, 823줄): 429, 529, 5xx, network — 단순 재시도
  - **모드 폴백** (`claude.ts queryModel`): 스트리밍 실패 → 비스트리밍
  - **의미적 복구** (`query.ts queryLoop`): prompt_too_long → autocompact, max_output_tokens, image_error, reactive_compact, ...
- **autocompact 는 사실 두 종류**: `autoCompact` (proactive, 한도 접근 시 미리) + `reactiveCompact` (reactive, 에러 후). 둘 다 메시지 요약으로 토큰을 줄인다.
- `query.ts:216` 의 `transition` 필드는 "테스트가 어떤 복구 경로가 발화했는지 검증할 수 있도록" 일부러 노출된 자리. 복구 경로가 코드 안에서 1급 시민.
- "사용자가 거의 못 느낀다"가 핵심 가치다. 이 10+ 복구 경로가 잘 동작하는 것이 Claude Code의 매끄러운 사용 경험을 만든다.
- Python으로 옮기면 `tenacity`로 단순한 부분만 잡고, 복잡한 상태 변경 경로는 직접 `try/except + continue`로 작성한다. **`query.ts`는 거의 전부 후자다.**
