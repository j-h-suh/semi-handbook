# 11. 에필로그 — 책을 닫으며

---

## 끝까지 읽어주셔서 감사합니다

먼저 끝까지 따라와 주신 것에 감사 인사를 드립니다. 39개 챕터, 11개 Part, 52만 줄짜리 코드베이스의 지도를 같이 그려본 셈입니다. 분량이 적지 않았고, 중간에 "이게 왜 이렇게 복잡하지?" 싶은 자리도 여러 번 있었을 거라고 생각합니다.

이 챕터는 책의 닫는 인사입니다. 새로운 내용은 없습니다. 대신 — 처음에 한 약속이 어떻게 지켜졌는지, 그리고 책을 덮고 무엇을 할 수 있게 되었는지를 짧게 정리합니다. 0.0에서 시작했던 톤 그대로, 존댓말로 마무리합니다.

---

## 0.0의 두 가지 약속을 다시 봅니다

책의 첫 챕터에서 두 가지를 약속드렸습니다.

> **1. `claude` 명령을 칠 때 일어나는 일을 머릿속에서 전부 그릴 수 있습니다.**
>
> **2. Python으로 미니 Claude Code를 직접 만들 수 있습니다.**

지금 이 페이지에 도착하신 분이라면 — 두 약속 모두 지켜졌습니다.

**첫 약속**. 사용자가 터미널에 `claude`를 치는 순간부터 — Part 1의 부트스트랩 30ms의 병렬 prefetch, Part 2의 에이전트 루프와 비동기 제너레이터 파이프라인, Part 3의 도구 시스템과 BashTool의 셸 인젝션 방어, Part 4의 슬래시 명령 디스패치, Part 5의 Ink + React가 그려내는 터미널 UI, Part 6의 권한 모드 4가지와 와일드카드 매칭, Part 7의 MCP 클라이언트와 컨텍스트 압축, Part 8의 AgentTool 재귀와 fork-join Coordinator — 책의 어느 챕터를 펼쳐도 그 자리가 전체 그림 안의 어디인지 보입니다. 한 장의 큰 그림이 머릿속에 있습니다. 마지막 비트까지는 아니어도, **"여기서 무슨 일이 일어나는가"라는 질문 앞에서 더는 멈추지 않습니다**.

**두 번째 약속**. Part 9에서 우리는 ~500줄짜리 mini-claude를 만들었습니다. 9.1의 80줄짜리 스캐폴드에서 시작해서 — 9.2의 핵심 루프, 9.3의 도구 시스템, 9.4의 권한 게이트, 9.5의 스트리밍과 서브 에이전트까지. 동작하는 미니 에이전트가 손에 있습니다. 그리고 Part 10에서 — 진짜 Claude Code에 사용자 정의 슬래시 명령, **`SKILL.md`**, **Python MCP 서버**를 추가하는 방법도 봤습니다. **내일 켜는 Claude Code**가 **어제 켜던 Claude Code**와 다른 도구가 됩니다.

## `asyncio.run(main())`의 회수

0.0에서 한 비유를 기억하시나요. `asyncio.run(main())` 한 줄을 써본 사람은 많지만, 이벤트 루프가 어떻게 도는지 한 번이라도 그려본 사람만이 — `await`를 빼먹은 코드가 왜 코루틴 객체를 출력하는지, 동기 라이브러리가 왜 전체 서버를 멈추는지, `gather` 안의 예외가 왜 다른 태스크를 안 멈추는지 디버깅할 수 있는 능력을 갖는다는 비유였습니다.

이 책은 **Claude Code의 이벤트 루프 — 즉 에이전트 루프 — 를 머릿속에 그려주는** 것을 목표로 했습니다. 지금 당신은 그 그림을 가지고 있습니다.

- "방금 내가 시킨 작업이 왜 거부됐지?" 앞에서 — 6.4의 8 출처 평탄화 + 와일드카드 매처를 떠올리고 어디부터 봐야 할지 압니다.
- "왜 이 도구 호출이 실패했지?" 앞에서 — 3.5의 BashTool 셸 인젝션 방어와 9.4의 권한 게이트를 떠올리고 어느 단계에서 막혔는지 압니다.
- "이 긴 대화가 왜 갑자기 짧아졌지?" 앞에서 — 7.4의 9-섹션 강제 컨텍스트 압축과 **autocompact**를 떠올립니다.
- "내가 시킨 작업이 왜 서브 에이전트로 넘어갔지?" 앞에서 — 8.1의 AgentTool 재귀와 8.2의 createSubagentContext를 떠올립니다.

어떤 디버깅 자리에서도 이제 멈추지 않습니다. **그게 0.0에서 약속드린 능력**입니다.

## Part 9와 Part 10 — 두 길이 한 점에 모입니다

이 책의 후반부는 두 갈래였습니다.

- **Part 9**: 이해를 위해서 mini-claude를 만들었습니다. 진짜 코드의 기하학적 압축. 52만 줄을 ~500줄로 줄이면서, 그 압축의 자리마다 왜 진짜는 더 큰지를 같이 봤습니다.
- **Part 10**: 매일 쓰기 위해서 진짜 Claude Code를 확장했습니다. `.claude/commands/`, `.claude/skills/SKILL.md`, MCP 서버. 내가 만든 도구가 모델의 손에 들어가는 자리.

이 둘은 사실 같은 통찰 위에 서 있습니다.

10.4의 마지막 자리에서 본 것 — **9.3의 Python 클래스 도구와 10.4의 MCP 서버 함수가 같은 일을 완전히 다른 형식으로 한다**. 9.3은 같은 프로세스 안의 클래스, 10.4은 **외부 프로세스의 stdio JSON-RPC**. 그런데 모델 입장에서는 완전히 같은 것입니다. 7.2의 변환층이 경계를 지웁니다.

10.2의 충격도 같은 통찰의 다른 표현이었습니다 — **"slash command = skill"**이 진짜 코드의 시스템 프롬프트에 박혀 있다는 발견. 디렉토리 이름이 다르고 형식이 다르지만 — 모델 입장에서는 같은 것. **언어 형식의 차이가 기능의 차이가 아닙니다**.

이 통찰이 실제로 무슨 의미냐면 — 당신이 **9.3에서 만든 ReadTool**의 사고방식 (입력 검증, 권한 분류, 에러 처리)을 그대로 10.4의 MCP 서버 함수로 옮길 수 있다는 뜻입니다. 같은 사고방식, 같은 검증, 같은 권한 모델, 같은 스키마 정의. 형식만 바꾸면 — **어떤 LLM 클라이언트에서든** 쓸 수 있는 재사용 가능한 도구가 됩니다.

**Part 9의 이해와 Part 10의 확장이 한 점에 모이는 자리**입니다. 미니를 만들면서 얻은 직관이 진짜를 확장하는 손에 그대로 들어옵니다.

이 _확장의 범위_ 자체도 책 후반에 한 번 더 자랐습니다. **10.3~10.8** 은 _도구 실행 흐름_ 의 확장 — 10.3 Hook 으로 _도구 실행 자리에 외부 코드를 끼우고_, 10.6 사용자 정의 에이전트로 _AGENT.md 한 파일이 새 에이전트가 되며_, 10.7 메시지 큐가 _4 입력자 인프라_ 의 토대를 깔고, 10.8 에이전트 팀이 _contextvars 격리 + polling 없는 fan-in_ 으로 peer 협업을 완성합니다. **10.5** 은 _백엔드 추상화_ — 같은 `client.messages.stream(...)` 호출이 Vertex 든 vLLM 이든 어디서나 작동하게 만드는 자리. _구조적 타이핑 한 줄_ 의 힘.

미니가 작아서 _대신_ 작아 보이지만, 9.1 시작 시점부터 10.5 까지 누적으로 따라 만들어보면 — _당신 손에서_ 같은 인터페이스 위에 백엔드도 바뀌고, 도구도 확장되고, 팀도 만들어지는 자리가 다 작동합니다. _진짜 Claude Code_ 가 _52 만 줄로_ 하는 일을 mini 의 _수천 줄_ 이 _개념의 정수_ 만으로 보여줍니다.

## 책에서 다루지 않은 것들

정직하게 말씀드리면, 이 책은 **Claude Code의 모든 것**을 다루지 않았습니다. 0.0에서 미리 약속드린 대로 — 핵심 패턴 위주로만 봤습니다.

다루지 않은 것 중 흥미로운 자리들:

- **Bun의 빌드 트릭** — `feature()` 함수로 dead code elimination 하는 부분. 6장에서 잠깐 언급만 하고 넘어갔습니다.
- **OpenTelemetry + gRPC 텔레메트리** — `~700KB`짜리 의존성을 lazy import로 처리하는 자리.
- **GrowthBook 피처 플래그** — 모든 승부처 챕터의 분기에 박혀 있던 그 게이트.
- **Plugin 시스템 디테일** — Part 7에서 한 단락만 봤습니다. `src/plugins/bundled/` 아래의 진짜 플러그인들은 들여다보지 못했습니다.
- **Coordinator Mode의 5가지 실제 시나리오** — 8.3에서 그림만 그리고, 진짜 fork-join 시나리오의 디테일은 안 봤습니다.
- **Voice Mode** — `src/voice/` 디렉토리 전체. 음성 입력과 STT 스트리밍.

이 자리들은 — 지금 당신이 가진 그림 위에서 직접 들여다보면 됩니다. 책에서 본 읽는 법 (`exploration-guide.md`, 키 함수 찾기, 5단계 상태 머신 알아보기)이 그대로 적용됩니다.

## 책을 덮고 무엇을 할 수 있을까요

이 챕터를 닫으면서 — 다음 한 가지만 권해드립니다.

**오늘 안에 `SKILL.md` 한 개를 만들어 보세요.** 

어떤 거든 좋습니다. "오늘 한 git 작업 요약", "PR 제목 한국어로 다듬기", "테스트 실패 로그 정리". 5줄짜리 마크다운 한 파일이면 됩니다. `.claude/skills/today/SKILL.md` 같은 자리에 박아두고, `claude`를 다시 켜고, 자연어로 한 번 부르거나 `/today`로 직접 부릅니다. 동작하는 걸 보는 그 한 번이 — 책을 한 번 더 읽는 것보다 큽니다.

그게 잘 되면 — **Python MCP 서버 한 개**를 만들어 보세요. 30줄짜리 파일 한 개. 사내 시스템 한 가지를 노출하면 — 다음 주부터 매일 쓰는 도구가 됩니다. 10.4의 코드를 그대로 출발점으로 쓰셔도 됩니다.

그게 잘 되면 — **진짜 mini-claude**를 자기 손으로 한 번 더 다시 짜 보세요. 책의 코드를 보지 않고요. 9.1~9.5의 이 챕터에서 배우는 것만 보고 처음부터. 400줄 안에서 동작하는 걸 직접 만들어 본 사람만이 진짜 클로드 코드의 52만 줄을 두려워하지 않게 됩니다.

## 마지막 한 마디

이 책의 톤은 "옆자리 선배가 후배에게 알려주는" 느낌이었습니다. 본문은 반말이었고, 도입과 이 마지막만 존댓말이었습니다. 그게 의도였습니다 — 처음과 끝은 정중하게, 가운데는 옆자리 선배의 직설적인 친근함으로.

52만 줄짜리 코드베이스 앞에서 멈췄던 사람을, 그 코드의 손님이 아니라 일부가 되도록 데려오는 게 이 책의 목표였습니다. 지금 이 자리에 도착하셨다면 — 그 목표가 적어도 한 명의 독자에게는 이루어진 셈입니다. 그것만으로 책을 쓰는 데 들인 시간이 충분히 가치 있었다고 생각합니다.

마지막으로 — Claude Code가 앞으로도 계속 바뀔 것이라는 점을 짚어드립니다. 이 책을 쓴 시점의 코드는 2026년 3월 31일에 본 버전입니다. 디렉토리 구조도, 함수 이름도, 시스템 프롬프트도 — 다음 버전에서는 다를 수 있습니다. 그건 자연스럽습니다.

하지만 큰 그림은 잘 안 바뀝니다. 에이전트 루프, 도구 시스템, 권한 슬롯, MCP의 양방향 프로토콜, 비동기 제너레이터로 흐르는 스트리밍 — 이 패턴들은 프레임워크가 바뀌어도 같습니다. 다음 버전의 Claude Code를 열어볼 때, 세부 함수 이름은 달라져 있어도 큰 그림은 그대로 있을 것입니다. 그때 어디가 어디에 해당하는지 짚어내는 능력 — 그게 이 책이 남긴 진짜 결과물입니다.
