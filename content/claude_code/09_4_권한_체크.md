# 9.4 권한 체크 — fail-closed 기본값과 와일드카드 매칭

---

## 이 챕터에서 배우는 것

- 권한 시스템이 왜 9.3의 미니를 안 위험하게 만드는지 — 한 가지 게이트의 힘
- **`deny > allow > ask`** 정렬의 의미 — 6.3의 5가지 모드를 3가지 결정으로 압축
- **Fail-closed 기본값** — 모르는 도구는 물어본다, 알려진 안전한 도구만 자동 허용
- 6.4의 **7단계 와일드카드 → regex 변환**을 Python `fnmatch` 한 줄로 교체
- 세션 동안 기억하기 — 한 번 허용한 패턴은 그 세션 동안 다시 안 묻기
- 9.4 끝의 결과물: `rm -rf ~` 같은 위험한 명령에 반드시 사용자한테 물어보는 mini-claude

## 본문

### `deny > allow > ask` — 결정 모델

6.3에서 본 5가지 권한 모드 (`default`/`acceptEdits`/`bypassPermissions`/`plan`/`dontAsk`)는 과하다. 6.4의 8개 출처 평탄화 (`userSettings` / `projectSettings` / `localSettings` / `flagSettings` / `policySettings` / `cliArg` / `command` / `session`)도 OUT. 수명과 권한이 모두 다른 출처들이 결정 시점에 한 리스트로 평탄화되는 무게를 — 우리는 3가지 결정과 2개 규칙 집합만으로 압축한다.

```
PermissionEngine:
  deny_rules:  set[str]   # ["Bash:rm *", "Bash:sudo *"]
  allow_rules: set[str]   # ["Read", "Bash:git *", "Bash:ls"]

check(tool, args) -> "allow" | "deny" | "ask":
  ① deny_rules 중 매칭이 있으면 → "deny"
  ② allow_rules 중 매칭이 있으면 → "allow"
  ③ tool.is_read_only() == True 이면 → "allow"  (휴리스틱)
  ④ 그 외 → "ask"
```

**우선순위가 결정적**이다. `deny > allow > ask`. 같은 도구에 대해 **deny가 먼저 돌아간다** — **deny가 이긴다**. 6.4에서 본 진짜 Claude Code의 정신과 같다. 보안 결정에서 **deny는 항상 우선**. 그래야 "이건 무조건 막아야 해"가 "보통 허용"에 우선한다.

`is_read_only`가 휴리스틱 자동 허용인 게 흥미롭다. ReadTool, GlobTool 같은 읽기만 하는 도구는 물어볼 가치가 없다. 사용자가 매번 "파일 읽기 허용?"에 답하면 피로만 쌓인다. 그래서 9.3의 `is_read_only()` 메서드가 이 자리에서 회수된다.

**Fail-closed 기본값**: 모르는 새 도구가 들어오면 — `is_read_only`의 기본값이 `False`(9.3에서 본 **fail-safe**) — 그러므로 자동 허용 안 됨 → `ask`. **새 도구는 위험하다고 가정**한다. 이건 3.3의 `buildTool` 팩토리에서 본 **fail-closed defaults**의 직접 회수.

> ⚙️ **9.3의 `is_destructive`는 이 챕터에서 직접 호출되지 않는다.** 9.3의 표가 "9.4 권한 휴리스틱"이라고 적었지만, 미니의 `check()`는 `is_read_only`만으로 충분하다 — 읽기 전용이면 자동 허용, 그 외엔 ask. `is_destructive`는 플래그로 보존되었지만 **결정 트리의 향후 가지**. 예: 진짜 deny 휴리스틱 (`if tool.is_destructive() and not allow_match: 항상 ask 강화`)을 추가하고 싶을 때 이미 자리가 있다. **fail-safe 메서드는 지금 당장 안 써도 정의해 두는 가치**가 있다 — 8.2의 fail-safe defaults 정신과 같다.

### Rule 포맷과 와일드카드 매칭

규칙은 문자열 한 개다.

```
"Read"              ← Read 도구의 *모든* 호출
"Bash"              ← Bash 도구의 *모든* 호출
"Bash:git *"        ← git으로 시작하는 Bash 명령
"Bash:ls"           ← ls 정확히 일치
"Write:/tmp/*"      ← /tmp 아래로 쓰기만
```

콜론(`:`)으로 도구 이름과 입력 패턴을 가른다. 콜론이 없으면 모든 입력에 매칭. 패턴은 **fnmatch** 형식 — 셸 와일드카드 (`*`, `?`, `[abc]`).

매칭 함수 한 개.

```python
import fnmatch

def matches_rule(rule: str, tool_name: str, summary: str) -> bool:
    if ":" not in rule:
        return rule == tool_name
    tool_part, _, pattern = rule.partition(":")
    if tool_part != tool_name:
        return False
    return fnmatch.fnmatchcase(summary, pattern)
```

**10줄**. 6.4의 **7단계 와일드카드 → regex 변환** — null-byte sentinel, 트레일링 옵셔널화, unescaped star count 가드 — **전부 OUT**. 우리는 Python 표준 라이브러리의 `fnmatch` 한 줄에 맡긴다. 진짜 Claude Code 에서 _권한 매처(6.4)_ 와 _Hook matcher(6.5)_ 가 **같은 fnmatch 정신을 공유**한다 — 미니는 Hook OUT이지만, 한 매칭 인프라가 두 시스템을 동시에 떠받친다는 디자인은 기억해둘 만하다.

뺀 것의 비용: `Bash:git *`으로 매칭이 **`git status`에는 되는데 `git`(인자 없음)에는 안 된다** — 6.4의 트레일링 옵셔널화가 해결한 케이스. 미니에서는 그 정도 정밀도는 포기. 사용자가 `Bash:git*`라고 쓰면 (공백 빼고) 둘 다 매칭. 간소함의 대가.

> 💡 **`fnmatch.fnmatchcase` vs `fnmatch.fnmatch`.** `fnmatch.fnmatch`는 **대소문자를 OS 기본**에 따른다 — Linux/macOS는 case-sensitive, Windows는 case-insensitive. 우리는 **항상 case-sensitive**가 필요 — `Bash:Git *`과 `Bash:git *`이 다르다는 사실을 보존해야 한다. 그래서 `fnmatchcase`. 작은 차이가 보안을 망친다.

### 도구의 권한 요약

매칭 대상이 될 문자열을 어디서 가져오나? 도구 입력은 dict (`{"file_path": "...", "content": "..."}`). 여기서 어느 필드가 권한 결정에 의미 있는지는 도구마다 다르다.

답: **도구 자신이 알려준다**. Tool Protocol에 한 메서드 추가.

```python
class Tool(Protocol):
    # ... 9.3 의 5개 ...
    
    def permission_summary(self, args: dict[str, Any]) -> str:
        """*권한 매칭에 쓸 한 줄 문자열*. 비어 있으면 도구 이름만 매칭."""
        ...
```

각 도구가 자기에 맞는 필드를 노출.

```python
class ReadTool:
    # ...
    def permission_summary(self, args: dict[str, Any]) -> str:
        return args.get("file_path", "")

class WriteTool:
    # ...
    def permission_summary(self, args: dict[str, Any]) -> str:
        return args.get("file_path", "")

class EditTool:
    # ...
    def permission_summary(self, args: dict[str, Any]) -> str:
        return args.get("file_path", "")

class BashTool:
    # ...
    def permission_summary(self, args: dict[str, Any]) -> str:
        return args.get("command", "")
```

ReadTool/WriteTool/EditTool은 경로, BashTool은 명령어. **각 도구가 자기 위험의 가시성을 어떤 필드로 표현할지를 자기가 안다**. EditTool은 WriteTool과 같은 `file_path`를 노출 — 진짜 Claude Code에서도 `FileEditTool`의 `preparePermissionMatcher`가 `checkWritePermissionForTool`을 호출한다. 쓰기와 편집은 같은 권한 축이다. 3.2 / 3.5에서 본 진짜 Claude Code의 `getPath` (FileRead/FileWrite/Glob/Grep/LSP의 메서드), `preparePermissionMatcher` (BashTool 등 8 파일에서 권한 매처를 미리 빌드) 같은 메서드들의 **Python 미니 버전**.

### 사용자한테 묻기

`ask` 결정이 떨어지면 — 사용자한테 물어본다. 4가지 선택.

```
[a] allow once               ← 이번 한 번만
[A] always allow this exact  ← 정확히 이 입력만 (세션 동안)
[t] always allow this tool   ← 이 도구는 *모든 입력* 자동 허용 (세션 동안)
[d] deny once                ← 거부
```

선택하면 — `A`와 `t`는 **allow_rule을 추가**. 이번 세션 동안 다시 안 묻는다. 다음 세션은 처음부터. (영구 저장은 미니에서 OUT — Part 10에서 추가할 자리.)

비동기 안 깨기 위해 `asyncio.to_thread`로 감싼 `input()`.

```python
async def prompt_user(tool: Tool, args: dict[str, Any]) -> tuple[bool, str | None]:
    """사용자한테 묻고 (allowed, new_persistent_rule) 반환."""
    summary = tool.permission_summary(args)
    print(f"\n[Permission] Tool: {tool.name}")
    print(f"             Input: {summary or args}")
    print("  [a] allow once")
    print("  [A] always allow this exact input")
    print("  [t] always allow this tool (any input)")
    print("  [d] deny")
    
    choice = (await asyncio.to_thread(input, "> ")).strip()
    
    if choice == "a":
        return True, None
    if choice == "A":
        return True, f"{tool.name}:{summary}" if summary else tool.name
    if choice == "t":
        return True, tool.name
    return False, None
```

### `agent.py`에 게이트 끼워 넣기

한 자리만 바뀐다. `tool.call()` 직전.

```python
# 9.3 에서:
result = await tool.call(block["input"], context)

# 9.4 에서:
decision = permissions.check(tool, block["input"])

if decision == "deny":
    result = "Permission denied by deny rule."
elif decision == "ask":
    allowed, new_rule = await prompt_user(tool, block["input"])
    if new_rule:
        permissions.add_allow(new_rule)
    if allowed:
        result = await tool.call(block["input"], context)
    else:
        result = "Permission denied by user."
else:  # "allow"
    result = await tool.call(block["input"], context)
```

**골격이 정확한 자리에 살을 받는다**. 9.2/9.3의 어떤 다른 코드도 안 바뀐다. `messages.py`, `tools/*.py` 모두 그대로. **계층화의 힘**.

## Python으로 옮기면

```python
# src/mini_claude/permissions.py
from __future__ import annotations
import asyncio
import fnmatch
from dataclasses import dataclass, field
from typing import Any, Literal
from .tools.base import Tool


PermissionDecision = Literal["allow", "deny", "ask"]


def matches_rule(rule: str, tool_name: str, summary: str) -> bool:
    """*규칙 매칭*. 6.4의 7단계 변환을 fnmatch 한 줄로."""
    if ":" not in rule:
        return rule == tool_name
    tool_part, _, pattern = rule.partition(":")
    if tool_part != tool_name:
        return False
    return fnmatch.fnmatchcase(summary, pattern)


@dataclass
class PermissionEngine:
    """*deny > allow > ask* 의 결정 엔진. 6.3의 5가지 모드를 3가지로 압축."""
    
    allow_rules: set[str] = field(default_factory=set)
    deny_rules: set[str] = field(default_factory=set)
    
    def check(self, tool: Tool, args: dict[str, Any]) -> PermissionDecision:
        summary = tool.permission_summary(args)
        
        # ① deny first — 보안 결정에서 deny는 항상 우선
        for rule in self.deny_rules:
            if matches_rule(rule, tool.name, summary):
                return "deny"
        
        # ② allow next — 명시적 허용 규칙
        for rule in self.allow_rules:
            if matches_rule(rule, tool.name, summary):
                return "allow"
        
        # ③ Read-only 휴리스틱 자동 허용
        if tool.is_read_only():
            return "allow"
        
        # ④ Fail-closed 기본값 — 모르는 건 물어본다
        return "ask"
    
    def add_allow(self, rule: str) -> None:
        self.allow_rules.add(rule)
    
    def add_deny(self, rule: str) -> None:
        self.deny_rules.add(rule)


async def prompt_user(
    tool: Tool, args: dict[str, Any]
) -> tuple[bool, str | None]:
    """사용자한테 묻고 (allowed, new_persistent_rule) 반환."""
    summary = tool.permission_summary(args)
    
    print(f"\n[Permission] Tool: {tool.name}")
    print(f"             Input: {summary or args}")
    print("  [a] allow once")
    print("  [A] always allow this exact input")
    print("  [t] always allow this tool (any input)")
    print("  [d] deny")
    
    choice = (await asyncio.to_thread(input, "> ")).strip()
    
    if choice == "a":
        return True, None
    if choice == "A":
        return True, f"{tool.name}:{summary}" if summary else tool.name
    if choice == "t":
        return True, tool.name
    return False, None
```

```python
# src/mini_claude/agent.py — 도구 실행 부분만 교체
from .permissions import PermissionEngine, prompt_user

async def query(
    *,
    user_input: str,
    tools: list[Tool],
    permissions: PermissionEngine,  # ← 새 파라미터
    cwd: str,
    state: ConversationState,
    system_prompt: str = "You are a helpful coding assistant.",
    client: AsyncAnthropicVertex | None = None,
) -> None:
    # … 이전 코드 그대로, 단 context 생성 한 줄만 *permissions 합류* …
    context = ToolContext(cwd=cwd, permissions=permissions)
    
    # tool_use 분기 안에서:
    if response.stop_reason == "tool_use":
        tool_results: list[dict] = []
        for block in content_blocks:
            if block["type"] != "tool_use":
                continue
            
            tool = find_tool(tools, block["name"])
            print(f"[{tool.name}] {block['input']}")
            
            # ── 권한 게이트 ──────────────────────
            decision = permissions.check(tool, block["input"])
            
            if decision == "deny":
                result_text = "Permission denied by deny rule."
                is_error = True
            elif decision == "ask":
                allowed, new_rule = await prompt_user(tool, block["input"])
                if new_rule:
                    permissions.add_allow(new_rule)
                if allowed:
                    try:
                        result_text = await tool.call(block["input"], context)
                        is_error = False
                    except Exception as e:
                        result_text = f"Error: {e}"
                        is_error = True
                else:
                    result_text = "Permission denied by user."
                    is_error = True
            else:  # "allow"
                try:
                    result_text = await tool.call(block["input"], context)
                    is_error = False
                except Exception as e:
                    result_text = f"Error: {e}"
                    is_error = True
            
            tool_results.append({
                "type": "tool_result",
                "tool_use_id": block["id"],
                "content": result_text,
                **({"is_error": True} if is_error else {}),
            })
        
        state.add_user(tool_results)
        continue
```

## 핵심 정리

- **`deny > allow > ask` 정렬**이 권한 시스템의 본질. **deny가 항상 우선** — "이건 무조건 막아야 해"가 "보통 허용"에 이긴다. 6.3의 5가지 모드를 3가지 결정으로 압축하면서도 정신은 보존.
- **Fail-closed 기본값**: 모르는 도구는 물어본다. `is_read_only`가 `False` (모름)이면 자동 허용 안 됨. **3.3의 `buildTool` 팩토리 fail-closed 정신의 직접 회수**.
- **Rule 포맷 한 줄**: `Tool` 또는 `Tool:fnmatch_pattern`. `fnmatch.fnmatchcase` 한 줄이 6.4의 **7단계 와일드카드 → regex 변환**을 대체. 정밀도는 조금 잃지만(트레일링 옵셔널화 OUT 등) — 80% 케이스에 충분.
- **`fnmatch`가 아니라 `fnmatchcase`** — 대소문자 보존은 보안이다. OS에 따라 흔들리면 안 됨.
- **`permission_summary` 메서드**가 각 도구의 위험한 필드를 노출. ReadTool/WriteTool/EditTool은 `file_path`, BashTool은 `command`. EditTool과 WriteTool은 같은 권한 축(쓰기 권한)을 공유 — 진짜 Claude Code에서도 `FileEditTool`은 `checkWritePermissionForTool`을 호출.
- **사용자 prompt의 4가지 선택**: `a`(이번만), `A`(이 정확한 입력 항상), `t`(이 도구 항상), `d`(거부). `A`와 `t`는 **allow_rule을 동적 추가** — 세션 동안 기억. 영구 저장은 Part 10에서.
- **`agent.py`의 한 자리에만 게이트 추가**. `tool.call()` 직전. 9.2/9.3의 다른 코드는 한 줄도 안 바뀜. **계층화의 힘**.
- 비동기 안 깨기: `await asyncio.to_thread(input, "> ")`로 blocking input을 비동기 컨텍스트에서 안전하게.
- **이 챕터의 결과물**: `rm -rf ~` 같은 위험한 명령은 **deny rule이 자동 차단**, 새로운 명령은 반드시 사용자한테 물어봄, 한 번 허용한 패턴은 세션 동안 다시 안 묻음. **위험한 미니가 안전한 미니가 되었다**. 9.5가 마지막 살 — 스트리밍 + 서브 에이전트 — 을 붙이면 Part 9 완성.
