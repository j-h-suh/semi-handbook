# 5.3 메시지 렌더링과 가상 스크롤 — 1만 개 메시지를 100줄로 그리기

---

## 이 챕터에서 배우는 것

- 긴 대화에서 수만 개의 메시지가 있어도 왜 안 느려지는지
- **가상 스크롤(virtual scroll)** — 실제로 그리는 건 보이는 부분만
- 보이지 않는 부분을 어떻게 공간만 차지하게 만드는가 — 스페이서(spacer) 트릭
- 높이를 모르는 항목을 처리하는 두 가지 트릭: 추정값과 과대 마운트
- 휠 한 번에 5개씩 오는 이벤트를 스크롤 양자화로 처리하는 영리함

---

## 사용자 경험에서 출발

긴 세션을 몇 시간 했다고 하자. 메시지가 수천 개 쌓였다. 위로 마구 스크롤한다.

```
↑ ↑ ↑ ↑ ↑ ↑ ...
```

부드럽게 올라간다. 끊김이 없다. CPU 팬도 안 돈다. 메모리도 안 폭발한다.

근데 잠깐. 5.1에서 **모든 메시지가 React 컴포넌트**라는 걸 봤다. 그러면 27,000개 메시지면 — 27,000개의 컴포넌트 인스턴스가 메모리에 떠 있어야 하는 거 아닌가? 각 컴포넌트가 약 250KB라고 치면 — **250KB × 27,000 = 6.75GB**. 터미널 앱 하나가 7GB? 말이 안 된다.

말이 안 되니까 — 그렇게 하지 않는다. 진짜로 메모리에 떠 있는 건 겨우 30~300개다. 나머지는 없다. 그런데 사용자는 전부 다 있는 것처럼 본다. 이 마법이 가상 스크롤이다. 이 챕터의 주제.

---

## 본문

### 문제: 모든 메시지를 mount하면 기가바이트가 든다

`useVirtualScroll.ts` 124줄에 진짜 코멘트가 있다.

> **"At ~250 KB RSS per MessageRow, a 1000-message session costs ~250 MB of grow-only memory (Ink screen buffer, WASM linear memory, JSC page retention all grow-only)."**

번역하면 — **"MessageRow 하나당 250KB. 1000개면 250MB. 게다가 grow-only"**. **grow-only**가 핵심이다. 한 번 할당하면 반환되지 않는다. Ink의 셀 버퍼, Yoga가 쓰는 WASM linear memory, JavaScriptCore의 페이지 retention — 셋 다 늘어나기만 한다. 1만 개면 **2.5GB**. 사용자가 좀 더 일하면 **5GB**. 터미널이 죽는다.

해결 방법은 단순하다 — **그냥 만들지 마라**. 사용자가 지금 보고 있는 것만 만든다. 안 보이는 건 없는 셈 친다. 

### 해결: 보이는 부분만 mount

```
            ┌─────────────────────────┐ scrollTop = 0
            │                         │
            │   메시지 1               │
            │   메시지 2               │
            │   ...                   │
            │   메시지 14000          │
            │   ━━━━━━━━━━━━━ ↑ 안 보임 │
            │   (top spacer)          │
            │   ━━━━━━━━━━━━━ ↓ 보임  │
   viewport│   메시지 14001          │
   ↑       │   메시지 14002          │  ← 진짜 mount된 것
   │       │   ...                   │
   80 rows │   메시지 14060          │
   │       │   ━━━━━━━━━━━━━ ↑ 보임  │
   ↓       │   ━━━━━━━━━━━━━ ↓ 안 보임│
            │   (bottom spacer)       │
            │   ━━━━━━━━━━━━━━━━━━━━━│
            │   메시지 14061          │
            │   ...                   │
            │   메시지 27000          │
            │                         │ scrollTop = max
            └─────────────────────────┘
```

화면에 보이는 **60줄짜리 viewport**를 중심으로, 위아래로 **overscan 80줄씩** 더 mount한다 (총 약 200~300개). **나머지 26,700개는 mount하지 않는다.** 대신 그 자리에 — 동일한 높이의 빈 공간을 둔다. 위쪽은 `topSpacer`, 아래쪽은 `bottomSpacer`. 두 개의 큰 빈 박스가 없는 메시지들의 자리를 차지한다.

사용자 입장에서는 — 27,000개 메시지가 다 있는 것처럼 보인다. 스크롤 막대도 전체 길이에 맞게 그려진다. 위로 올리면 위에 있는 메시지가 나온다. 단지 그 메시지가 지금 막 **mount된다**는 사실을 사용자는 모른다.

### `useVirtualScroll.ts` — 핵심 상수들

진짜 코드의 첫 60줄에 모든 트레이드오프가 상수로 박혀 있다.

```typescript
const DEFAULT_ESTIMATE = 3        // 안 잰 항목의 추정 높이 (rows)
const OVERSCAN_ROWS = 80          // viewport 위/아래 여분
const COLD_START_COUNT = 30       // 첫 mount 개수
const SCROLL_QUANTUM = OVERSCAN_ROWS >> 1  // = 40
const PESSIMISTIC_HEIGHT = 1      // 안 잰 항목의 최악(=가장 작음) 가정
const MAX_MOUNTED_ITEMS = 300     // mount 상한
const SLIDE_STEP = 25             // 한 commit에 새로 mount할 최대 개수
```

이 7개 상수가 전체 동작을 결정한다. 각각이 왜 그 값인지 코멘트에 적혀 있다 — 실제로 측정해서 정한 것들이다. 직관이 아니다.

### 추정값과 측정된 값

처음에는 모든 항목의 높이가 모른다. `DEFAULT_ESTIMATE = 3`줄로 가정한다. 항목이 한 번 mount되면 — Yoga가 진짜 높이를 계산하고, 그 결과가 `heightCache`라는 Map에 저장된다.

```typescript
const heightCache = useRef(new Map<string, number>())
```

키는 `itemKey` (메시지 ID), 값은 **측정된 row 수**. 한 번 측정한 항목은 **다음번 mount 안 해도** 그 높이를 안다. 그래서 총 스크롤 높이를 계산할 때:

```typescript
arr[i + 1] = arr[i]! + (heightCache.current.get(itemKeys[i]!) ?? DEFAULT_ESTIMATE)
```

잰 적 있으면 진짜 높이, 없으면 추정값. 이 누적합이 `offsets[]` 배열 — **각 항목의 y 좌표**다. 마지막 값(`offsets[n]`)이 전체 스크롤 높이. 이걸 spacer 박스의 크기로 쓴다.

### 추정값이 틀려도 돌아가는 트릭 — overscan

문제: 추정값이 진짜 높이와 다르면? 예를 들어 3줄로 추정했는데 실제는 50줄이라면, 내가 mount해야 한다고 계산한 항목이 **viewport를 못 채운다**. 빈 공간이 보인다.

해결: **overscan**. viewport 위아래로 80줄씩 더 항상 mount한다. 추정 오차가 80줄 안이면 — 빈 공간이 안 생긴다. 사용자는 모른다.

추가로 한 가지 더 영리한 트릭. 안 잰 항목의 **coverage 계산**에서는 `DEFAULT_ESTIMATE = 3`이 아니라 `PESSIMISTIC_HEIGHT = 1`을 쓴다.

```typescript
// useVirtualScroll.ts:39-43 코멘트 (verbatim):
// "Worst-case height assumed for unmeasured items when computing coverage.
//  A MessageRow can be as small as 1 row (single-line tool call). Using 1
//  here guarantees the mounted span physically reaches the viewport bottom
//  regardless of how small items actually are — at the cost of over-mounting
//  when items are larger (which is fine, overscan absorbs it)."
```

번역: **"MessageRow가 1줄 (single-line tool call) 까지 작아질 수 있다. 그래서 worst-case로 1을 쓴다. 그러면 어떤 항목이든 viewport 바닥까지 닿는 게 보장된다. 더 큰 항목이라면 과대 mount가 되지만 — overscan이 흡수해준다."**

**과대 mount가 좋은 트레이드오프다**. 적게 mount해서 빈 공간이 보이는 것보다, 약간 **더 mount**해서 **항상 viewport가 채워지는** 게 낫다. 왜 1? 라는 답이 경험 (single-line tool call) 에서 나왔다는 점이 흥미롭다 — 직관이 아니라 측정.

### 스크롤 양자화 — CPU 폭발 방지

휠을 한 번 굴리면 — 보통 **3~5개의 scroll 이벤트**가 발생한다. 트랙패드의 관성 스크롤은 수십 개다. 매 이벤트마다 React가 다시 commit하면 — Yoga 레이아웃 + Ink diff까지 다 돈다. **CPU 100%**. 화면이 멈춘다.

코멘트가 친절하다.

> **"every wheel tick (3-5 per notch) triggers a full React commit + Yoga calculateLayout() + Ink diff cycle — the CPU spike."**

해결책 — **`SCROLL_QUANTUM = 40`**.

```typescript
useSyncExternalStore(subscribe, () => {
  const s = scrollRef.current
  if (!s) return NaN
  // Snapshot is scrollTop QUANTIZED to SCROLL_QUANTUM bins
  return Math.floor(s.scrollTop / SCROLL_QUANTUM)
})
```

스크롤 위치를 40줄 단위로 양자화해서 React에 보고한다. 사용자가 5줄, 10줄, 20줄을 스크롤해도 — **같은 bin**. `useSyncExternalStore`의 selector가 같은 값을 본다 → React 리렌더 안 일어남. 40줄을 넘어가는 순간에야 새 bin → 리렌더.

근데 시각적 스크롤은 어떻게 되나? — **Ink가 직접 처리한다**. ScrollBox의 `forceRender`가 매 휠 이벤트마다 발화하고, Ink는 **React 상태와 무관하게** 화면을 다시 그린다. **시각은 매끄럽고, React commit은 드물고**. 두 마리 토끼를 잡는다.

> 🔬 **Deep Dive — React와 ScrollBox의 분리된 관심사.** 위의 트릭이 가능한 이유는 시각적 스크롤과 **React mount 범위**가 다른 일이기 때문이다. ScrollBox는 **순수 Ink 컴포넌트**로 매 휠 이벤트마다 자기 viewport 위치를 갱신하고 cell 출력을 다시 paint한다. React는 그 위치를 양자화해서 듬성듬성 보고받고, 보고받을 때만 **mount할 항목 범위를 조정**한다. 두 시스템이 느슨하게 연결되어서 — 한쪽이 빠르고 한쪽이 느려도 충돌이 없다. **"Visual scroll stays smooth regardless"**라는 코멘트가 정확히 이 분리를 가리킨다.

### 죽음의 나선 방지 — `SLIDE_STEP`

빠른 스크롤 (휠을 마구 굴림)로 한 번에 200줄을 점프하면? 그 200줄 안의 항목들이 **전부 처음 mount**된다. 각 메시지의 첫 mount는 마크다운 파싱, 신택스 하이라이팅 등 **3ms 정도**. 200개면 — **600ms**. 0.6초 짜리 동기 블록. 그동안 입력을 또 받으면, 다음 commit은 더 큰 점프 → 더 큰 블록 → 죽음의 나선.

해결: **`SLIDE_STEP = 25`**. **한 commit에 새로 mount할 항목 수를 25개로 제한**한다. 200줄 점프를 **25개씩 8 commit**로 나눠서 처리한다. 매 commit은 **25 × 3ms = 75ms** — 사용자가 못 느끼는 수준. 8 commit 동안 viewport는 **catch-up 중**임을 표시한다 (`scrollClampMin/Max`로 마운트된 끝에 viewport를 고정).

이게 반응성과 완성도의 트레이드오프다. 완벽한 한 번보다 불완전한 여러 번이 사용자 경험은 더 좋다.

### 두 층의 가상화

진짜 코멘트의 마지막 영리함 (`useVirtualScroll.ts:122-127` docstring):

> **"The ScrollBox already does Ink-output-level viewport culling (render-node-to-output.ts:617 skips children outside the visible window), but all React fibers + Yoga nodes are still allocated."**

(코드 주석의 **line 617** 은 outdated 인 듯 — 현재 `render-node-to-output.ts` 에서는 viewport culling 이 **line 1371+** `Render children of a scroll container with viewport culling` 부근으로 옮겨져 있다. 코멘트는 갱신을 못 따라간 듯 하지만, 두 층 가상화 의 본질은 그대로다.)

번역: **"ScrollBox는 이미 Ink 출력 단계에서 viewport 밖 자식을 안 그린다. 그런데 React fiber와 Yoga 노드는 여전히 할당된다."**

즉 가상화가 두 층에 있다.

| 층 | 무엇을 안 하는가 | 절약되는 것 |
|---|---|---|
| **Ink 출력 층** (`render-node-to-output.ts`) | viewport 밖 셀을 그리지 않음 | CPU (paint 시간) |
| **React fiber 층** (`useVirtualScroll.ts`) | viewport 밖 fiber를 만들지 않음 | 메모리 (250KB×N) |

Ink 단계 가상화만으로는 — **paint**는 빠른데 메모리는 안 줄어든다. fiber와 Yoga 노드는 다 할당된 채. React 단계 가상화가 더해져야 진짜로 메모리가 안 늘어난다. **두 층 모두 필요하다.**

## Python으로 옮기면

가상 스크롤의 핵심 아이디어를 Python으로 옮기면 이렇게 생겼다.

```python
from __future__ import annotations
from dataclasses import dataclass


# ─── 상수 ────────────────
DEFAULT_ESTIMATE = 3
OVERSCAN_ROWS = 80
PESSIMISTIC_HEIGHT = 1
MAX_MOUNTED = 300


@dataclass
class VirtualScrollResult:
    range_: tuple[int, int]   # [start, end) — 마운트할 인덱스
    top_spacer: int           # 위쪽 빈 공간 높이
    bottom_spacer: int        # 아래쪽 빈 공간 높이


class VirtualScroller:
    def __init__(self):
        self.height_cache: dict[str, int] = {}  # itemKey → 측정 높이
    
    def compute(
        self,
        item_keys: list[str],
        scroll_top: int,
        viewport_h: int,
    ) -> VirtualScrollResult:
        n = len(item_keys)
        
        # 1. 누적 오프셋 계산 (캐시된 높이 + 추정값)
        offsets = [0] * (n + 1)
        for i in range(n):
            h = self.height_cache.get(item_keys[i], DEFAULT_ESTIMATE)
            offsets[i + 1] = offsets[i] + h
        total_height = offsets[n]
        
        # 2. start: scrollTop - overscan 위치 찾기 (binary search)
        target_lo = max(0, scroll_top - OVERSCAN_ROWS)
        l, r = 0, n
        while l < r:
            m = (l + r) // 2
            if offsets[m + 1] <= target_lo:
                l = m + 1
            else:
                r = m
        start = l
        
        # 3. end: viewport + overscan을 채울 때까지 PESSIMISTIC=1로 확장
        # (안 잰 항목은 1줄로 가정 → 항상 viewport를 충분히 덮는다)
        budget = viewport_h + 2 * OVERSCAN_ROWS
        end = start
        covered = 0
        while end < n and covered < budget and (end - start) < MAX_MOUNTED:
            h = self.height_cache.get(item_keys[end], PESSIMISTIC_HEIGHT)
            covered += h
            end += 1
        
        # 4. spacer 크기 = mount 안 한 부분의 누적 높이
        top_spacer = offsets[start]
        bottom_spacer = total_height - offsets[end]
        
        return VirtualScrollResult(
            range_=(start, end),
            top_spacer=top_spacer,
            bottom_spacer=bottom_spacer,
        )
    
    def measure(self, item_key: str, real_height: int) -> None:
        """렌더링 후 실제 높이를 캐시에 저장."""
        self.height_cache[item_key] = real_height


# ─── 사용 ────────────────
scroller = VirtualScroller()
keys = [f"msg_{i}" for i in range(27_000)]

# 사용자가 14000번째 메시지 부근을 보고 있다면
result = scroller.compute(keys, scroll_top=42_000, viewport_h=60)
print(result.range_)         # (13970, 14080) 정도 — 100개만 mount
print(result.top_spacer)     # 41920 — "위쪽에 14000개가 있는 척"
print(result.bottom_spacer)  # 38880 — "아래쪽에 12920개가 있는 척"

# mount 후 실제 높이 측정
for i in range(*result.range_):
    real_h = render_message(keys[i])  # 가상의 렌더 함수
    scroller.measure(keys[i], real_h)

# 다음 compute는 *측정된 높이*로 더 정확한 결과
```

핵심 셋이 다 있다.

1. **`height_cache`** — 측정된 높이를 누적하는 dict. 한 번 잰 건 다시 안 잰다.
2. **PESSIMISTIC_HEIGHT로 end 확장** — 항상 viewport+overscan을 덮을 만큼 mount.
3. **두 개의 spacer** — mount 안 한 부분의 자리를 공간만으로 표시.

> 💡 **Python의 Textual도 같은 패턴을 쓴다.** Textual의 `DataTable`, `RichLog` 같은 위젯은 내부적으로 수만 행을 효율적으로 다룬다. 같은 **viewport + overscan + spacer** 패턴이다. 큰 데이터를 작은 화면에 그리는 모든 시스템이 이 패턴을 쓴다 — 웹 React의 `react-window`, `react-virtuoso`도 정확히 같은 알고리즘.

## 핵심 정리

- 27,000개 메시지를 모두 mount하면 **그로우온리 메모리만 6GB+**. 그래서 **mount하지 않는다**.
- **가상 스크롤**: viewport 위/아래 `OVERSCAN_ROWS = 80` 만 mount, 나머지는 **두 개의 큰 spacer 박스**로 공간만 표시. mount는 30~300개로 묶임.
- **height cache** — Yoga가 한 번 잰 높이를 Map에 저장. 안 잰 항목은 `DEFAULT_ESTIMATE = 3`으로 누적합 계산. 측정 오차는 **overscan이 흡수**.
- 안 잰 항목의 coverage는 `PESSIMISTIC_HEIGHT = 1`로 — **과대 mount가 빈 공간보다 낫다**.
- **스크롤 양자화** (`SCROLL_QUANTUM = 40`): 매 휠 이벤트마다 React가 commit하면 CPU가 폭발. 40줄 단위 bin으로 양자화 → React는 듬성듬성, **시각은 Ink가 직접 매끄럽게**. **분리된 관심사**.
- **`SLIDE_STEP = 25`**: 한 commit에 새로 mount할 항목 수 제한 → 죽음의 나선 방지. 큰 점프를 여러 commit으로 나눠 처리.
- **두 층 가상화**가 다 필요: Ink 출력 단계는 **paint 시간**만 줄이고, React fiber 단계는 메모리도 줄인다. 둘 다 있어야 진짜로 안 늘어난다.
