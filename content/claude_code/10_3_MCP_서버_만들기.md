# 10.3 MCP 서버를 Python으로 만들어 도구 추가하기 — `mcp` SDK + Claude Code 연결

---

## 이 챕터에서 배우는 것

- 7.2에서 마법처럼 발견되던 도구를 — 이번엔 내가 직접 만들어 들여보낸다
- MCP 서버는 외부 프로세스 — Claude Code와 **JSON-RPC로 통신**하는 별도 Python 프로세스
- **가장 단순한 MCP 서버**는 **30줄짜리 Python 파일** 한 개
- `tools/list`와 `tools/call` 두 메서드가 전부
- ⚠️ 가장 큰 함정: stdout은 JSON-RPC 채널 — `print`하면 프로토콜 깨짐
- `claude mcp add` 한 줄로 등록 → 다음 세션부터 `mcp__myserver__mytool`이 모델 도구 목록에 등장
- 7.2의 `fetchToolsForClient`가 내 도구를 받아가는 진짜 코드 — 양방향의 회수
- 9.3의 **Python 클래스 도구** ↔ 10.3의 **MCP 서버 도구** — 같은 일을 완전히 다른 형식으로

## 사용자 경험에서 출발

7.2의 마지막을 다시 떠올려보자:

이번 챕터에서는 — 내가 만든 적이 있는 도구가 그 자리에 들어간다.

당신이 자주 쓰는 내부 시스템이 있다고 하자. 예를 들어:

- 사내 Linear API를 호출해서 내가 담당한 이슈 목록 가져오기

**Claude Code가 이걸 직접 할 수는 없다.** 내장 도구에 사내 시스템 도구가 있을 리 없으니까. **하지만 내가 Python 30줄로 그 도구를 노출하는 MCP 서버를 만들면**:

```bash
$ claude mcp add my-internal -- python /path/to/my_server.py
```

다음 번 `claude`를 켜면:

```bash

(...모델이 도구 목록에서 mcp__my-internal__list_my_issues 발견)
(...mcp__my-internal__list_my_issues 호출)

내가 담당한 미해결 이슈 3개야:
1. PROJ-123: 사용자 인증 버그
2. PROJ-145: 대시보드 로딩 속도
3. PROJ-167: README 업데이트
```

**내가 만든 도구가 진짜로 모델 손에 들어간다**. 내가 직접 짠 Python 함수가 — 모델이 자기 도구처럼 부른다. 7.2의 그림이 반대 방향으로 동작한다.

이 챕터에서 — 그 30줄이 어떻게 생겼는지, 그리고 그게 **Claude Code 안으로 어떻게 들어가는지** 본다. 진짜 클로드 코드 안에 **MCP 서버 구현 사례**가 박혀 있어서 — 양면을 같이 본다.

## 본문

### MCP가 양방향 프로토콜이라는 사실

7.2에서 우리는 MCP의 클라이언트 측만 봤다. 외부 서버를 발견하고 도구를 가져오는 자리. 이번엔 반대편 — 서버 측.

```
       Client (Claude Code)            Server (내 Python 프로세스)
              │                                  │
              │ ──── tools/list ───────────────→ │
              │ ←─── { tools: [...] } ─────────  │
              │                                  │
       (...모델이 도구 호출 결정...)               │
              │                                  │
              │ ──── tools/call ───────────────→ │
              │      { name, arguments }         │
              │ ←─── { content: [...] } ──────── │
              │                                  │
```

**JSON-RPC 두 메서드**가 **MCP의 전부**. `tools/list`는 "네가 가진 도구 목록을 알려줘", `tools/call`은 "이 이름의 도구를 이 인자로 호출해줘". 그게 전부.

7.2에서 본 8가지 전송 (stdio/HTTP/SSE/WebSocket/...)은 전송 계층. 그 위에 흐르는 메시지는 항상 같다. **나는 서버를 만들 때 전송 한 가지만 골라도 된다** — 가장 흔한 건 stdio.

### 가장 단순한 Python MCP 서버 — 30줄

```python
# my_server.py
from mcp.server.fastmcp import FastMCP

server = FastMCP("my-internal")


@server.tool()
async def list_my_issues(status: str = "open") -> str:
    """Linear 에서 내가 담당한 이슈 목록을 가져온다.

    Args:
        status: 이슈 상태 — "open", "in_progress", "done", "all"
    """
    # 실제 Linear API 호출 (간략화)
    issues = await fetch_linear_issues(assignee="me", status=status)

    if not issues:
        return f"미해결 이슈가 없어요. (status={status})"

    lines = [f"내가 담당한 {status} 이슈 {len(issues)}개:"]
    for issue in issues:
        lines.append(f"- {issue['identifier']}: {issue['title']}")

    return "\n".join(lines)


if __name__ == "__main__":
    server.run()  # ← stdio 시작
```

**30줄. 그 중 함수 본체는 8줄, 뼈대는 4줄**.

`FastMCP`의 `@server.tool()` 데코레이터가 마법을 한다:

1. 함수 시그니처를 읽어서 JSON Schema 생성 (`status: str = "open"` → `properties.status.type = "string"`)
2. **docstring**을 description으로 박음
3. 함수 자체를 `tools/call` 핸들러에 등록

**9.3에서 본 Pydantic의 마법의 친척**. 함수 시그니처 → JSON Schema 자동 변환. 데코레이터 한 줄에 50줄짜리 도구 정의가 압축.

> 💡 **`mcp` SDK 설치.** Python `mcp` 패키지는 `uv add mcp`로 설치. **공식 SDK**. `FastMCP`는 그 안의 데코레이터 기반 헬퍼 — 표준 `mcp.Server`를 직접 쓰면 더 verbose하지만 유연. 처음 만들 때는 FastMCP가 훨씬 짧다.

### 진짜 클로드 코드의 MCP 서버 — **24줄짜리 stdio 진입점**

진짜 클로드 코드 안에 **MCP 서버 구현**이 박혀 있다. `claude-code-main/mcp-server/` — **Claude Code 자체의 소스를 탐색하는** MCP 서버. **자기 회귀**. Claude Code가 자기 자신을 탐색하는 도구를 MCP로 노출한 거다.

진입점 (`mcp-server/src/index.ts`) — 통째로 24줄:

```typescript
#!/usr/bin/env node
/**
 * STDIO entrypoint — for local use with Claude Desktop, Claude Code, etc.
 *
 * Usage:
 *   node dist/index.js
 *   CLAUDE_CODE_SRC_ROOT=/path/to/src node dist/index.js
 */

import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { createServer, validateSrcRoot, SRC_ROOT } from "./server.js";

async function main() {
  await validateSrcRoot();
  const server = createServer();
  const transport = new StdioServerTransport();
  await server.connect(transport);
  console.error(`Claude Code Explorer MCP (stdio) started — src: ${SRC_ROOT}`);
}

main().catch((err) => {
  console.error("Fatal error:", err);
  process.exit(1);
});
```

**주석 + import + main wrapper 빼면 4줄**:

```typescript
const server = createServer();
const transport = new StdioServerTransport();
await server.connect(transport);
console.error(`...started`);
```

진짜 코드도 **위 Python 30줄**과 완전히 같은 골격. 언어가 다를 뿐.

### ⚠️ 가장 큰 함정 — `print`하면 죽는다

진짜 코드의 마지막 줄을 다시 보자.

```typescript
console.error(`Claude Code Explorer MCP (stdio) started — src: ${SRC_ROOT}`);
```

**`console.log`가 아니다**. **`console.error`**. 일부러.

왜? **stdout은 JSON-RPC 채널**이다. MCP 클라이언트 (Claude Code)가 **서버의 stdout을 읽어서** JSON 메시지로 파싱한다. 거기에 임의의 텍스트 한 줄이 섞이면 — **클라이언트가 "이게 뭔 JSON이냐" 하고 reject**. 프로토콜 깨짐.

**Python에서도 똑같다**:

```python
# ❌ 안 됨 — stdout 을 오염시킴
print("서버 시작됨")

# ✅ OK — stderr 사용
import sys
print("서버 시작됨", file=sys.stderr)

# ✅ OK — logging 모듈은 *기본이 stderr*
import logging
logging.info("서버 시작됨")
```

**가장 흔한 처음 만드는 사람의 실수**. **디버깅 중 print 한 줄 박았다가** 클라이언트가 조용히 연결 실패하고 — 왜 안 되는지 모르고 한 시간을 잃는다.

> 🔴 **MCP 서버에서는 어떤 라이브러리도 `print` 또는 `console.log`를 호출하면 안 된다.** 모든 출력은 **stderr**로 가야 한다. 어떤 의존성이 stdout에 뭔가 찍는지 모를 때는 — 시작 시점에 `sys.stdout = sys.stderr` 같은 **극단적인 redirect**도 가능하다.

진짜 클로드 코드의 클라이언트 측에서도 이걸 방어한다. 7.2에서 본 stdio transport 옵션:

```typescript
// services/mcp/client.ts (7.2 에서 본 자리)
transport = new StdioClientTransport({
  command: finalCommand,
  args: finalArgs,
  env: { ...subprocessEnv(), ...serverRef.env },
  stderr: 'pipe',  // ← 서버의 stderr 를 가로채서 별도 처리
})
```

`stderr: 'pipe'` — **서버가 stderr에 뭘 찍든 터미널 UI로 새지 않는다**. **양쪽이 같은 약속을 안다** — **stdout은 프로토콜, stderr는 디버그/로그**.

### `tools/list`와 `tools/call` — 진짜 코드의 두 핸들러

진짜 클로드 코드의 `mcp-server/src/server.ts:257-377`을 보면 `ListToolsRequestSchema` 핸들러가 순수한 데이터 구조로 8개 도구를 정의한다.

```typescript
// mcp-server/src/server.ts:257
server.setRequestHandler(ListToolsRequestSchema, async () => ({
  tools: [
    {
      name: "list_tools",
      description:
        "List all Claude Code agent tools (BashTool, FileReadTool, etc.) ...",
      inputSchema: { type: "object" as const, properties: {} },
    },
    {
      name: "search_source",
      description:
        "Search for a regex pattern across the Claude Code source. ...",
      inputSchema: {
        type: "object" as const,
        properties: {
          pattern:     { type: "string", description: "Search pattern (regex)." },
          filePattern: { type: "string", description: "File extension filter, e.g. '.ts'" },
          maxResults:  { type: "number", description: "Max matches (default: 50)." },
        },
        required: ["pattern"],
      },
    },
    // ... 6 개 더
  ],
}));
```

**MCP 도구의 최소 필수 형태**: `{ name, description, inputSchema }`. `inputSchema`는 **JSON Schema** — 9.3에서 본 **Pydantic의 `model_json_schema()`가 만들어주는 것과 완전히 같은 형식**. **Python에서 Pydantic으로 만든 모델이 그대로 MCP inputSchema가 된다**. 9.3 회수.

`CallToolRequestSchema` 핸들러는 **큰 switch 문**. 도구 이름으로 분기. `search_source`의 케이스 (`server.ts:531-582`):

```typescript
case "search_source": {
  const pattern = args?.pattern as string;
  if (!pattern) throw new Error("pattern is required");
  // ... 정규식 컴파일 + 파일 walk + 매칭 ...

  return {
    content: [
      {
        type: "text" as const,
        text: matches.length > 0
          ? `Found ${matches.length} match(es):\n\n${matches.join("\n")}`
          : "No matches found.",
      },
    ],
  };
}
```

**MCP 도구 응답의 표준 형식**:

```
{ content: [{ type: "text", text: "..." }] }
```

`content`는 배열 — 여러 블록을 동시에 돌려줄 수 있다 (`type: "image"`, `type: "resource"`도 있음). 텍스트 도구는 블록 한 개. **Python에서 옮길 때도 정확히 같은 dict 형식**. 프로토콜이 같으니까.

### `claude mcp add` — 등록 한 줄

서버를 만들었다. 어떻게 **Claude Code가 알게** 하나?

```bash
$ claude mcp add my-internal -- python /path/to/my_server.py
```

이 한 줄이 기본적으로 `~/.claude.json` 안의 `projects.<현재 경로>.mcpServers`에 **서버 entry**를 추가한다 (`addCommand.ts:48-52` — 기본 scope가 `local`). `--scope user`면 `~/.claude.json`의 최상위 `mcpServers`, `--scope project`면 `<프로젝트 루트>/.mcp.json`. 어느 자리든 형식은 같다:

```json
{
  "mcpServers": {
    "my-internal": {
      "type": "stdio",
      "command": "python",
      "args": ["/path/to/my_server.py"]
    }
  }
}
```

> 💡 **`~/.claude.json` vs `~/.claude/`**. 글로벌 Claude 설정은 디렉토리 (`~/.claude/`)가 아니라 한 파일 (`~/.claude.json`). MCP 서버 entry도 그 한 파일 안에 살고, scope (local/user)는 키 위치로 구분 — `projects.<path>.mcpServers` (local) 또는 최상위 `mcpServers` (user). 프로젝트 단위 공유 (팀이 같이 쓰는 서버)만 별도 파일 `<프로젝트 루트>/.mcp.json`으로 빠진다.

**다음 세션부터** — Claude Code가 시작 시점에 이 파일을 읽고, 각 서버에 연결을 시도. 7.2의 `connectToServer`가 stdio transport로 **내 Python 프로세스를 spawn**하고, **tools/list를 부른다**. 응답으로 받은 도구 목록이 내장 도구 풀에 합쳐진다.

### 7.2의 `fetchToolsForClient`가 내 도구를 받아가는 자리

7.2에서 본 그 함수가 내 서버를 어떻게 처리하는지 — 그대로 회수:

```typescript
// services/mcp/client.ts:1766 — fetchToolsForClient 의 핵심
// (축약 — 전체 ~90 줄, MCPTool 의 모든 콜백 spread; skipPrefix 분기 단순화)
return toolsToProcess.map((tool): Tool => {
  const fullyQualifiedName = buildMcpToolName(client.name, tool.name)
  return {
    ...MCPTool,                                  // ← fail-closed 기본값 spread
    name: skipPrefix ? tool.name : fullyQualifiedName,  // mcp__my-internal__list_my_issues
    mcpInfo: { serverName: client.name, toolName: tool.name },
    isMcp: true,
    inputJSONSchema: tool.inputSchema,           // ← 내 서버가 보낸 그대로
    async description() { return tool.description ?? '' },
    isReadOnly() { return tool.annotations?.readOnlyHint ?? false },
    isDestructive() { return tool.annotations?.destructiveHint ?? false },
    isOpenWorld() { return tool.annotations?.openWorldHint ?? false },
    // ... searchHint / alwaysLoad / prompt() / isConcurrencySafe() /
    //     toAutoClassifierInput() / isSearchOrReadCommand() / checkPermissions() 등 생략
    async call(args, context, ...) {
      // → callMCPTool() → JSON-RPC tools/call → 내 Python 프로세스
    },
  }
})
```

내가 보낸 `name: "list_my_issues"`가 → `mcp__my-internal__list_my_issues`로 접두사가 붙는다. `description`은 그대로 흘러간다. `inputSchema` (Pydantic이 만든 거)도 그대로. **내가 만든 도구가 3.2의 47 필드 Tool 객체로 변신** — 호출자 코드는 차이를 모른다.

### `client.callTool()` — 추상화의 완성

모델이 `mcp__my-internal__list_my_issues`를 호출하기로 결정한다. 그 호출이 **어떻게 내 Python 프로세스에 도달**하느냐? `client.ts:3091-3097`:

```typescript
// services/mcp/client.ts:3091-3097 (축약 — onprogress 핸들러 ~13 줄 생략)
const result = await Promise.race([
  client.callTool(
    {
      name: tool,         // ← "list_my_issues" (접두사 제거된 원본)
      arguments: args,    // ← 모델이 만든 dict
      _meta: meta,
    },
    CallToolResultSchema,
    { signal, timeout: timeoutMs, onprogress: ... },
  ),
  timeoutPromise,
])
```

**`client.callTool()` 한 메서드 호출**. 그게 전부 보이는 것. **MCP SDK가 알아서**:

1. JSON-RPC `tools/call` 메시지로 직렬화
2. **내 Python 프로세스의 stdin**으로 전송
3. 응답 (stdout으로 도착) 받아서 `CallToolResultSchema`로 검증
4. 결과 객체로 변환

**추상화의 완성**. 8가지 전송 (stdio/HTTP/SSE/...) 중 어떤 거든 호출자는 같은 한 줄. 7.2의 **"호출자 코드는 차이를 모른다"**가 진짜로 같은 한 줄로 압축된다.

> 🔬 **Deep Dive — production timeout 디테일.** 위 코드의 `Promise.race`가 흥미롭다. 코드 라인 3068-3069의 주석: **"Use Promise.race with our own timeout to handle cases where SDK's internal timeout doesn't work (e.g., SSE stream breaks mid-request)"**. **SDK의 내부 timeout이 SSE stream 깨질 때 동작 안 하는 production 버그**를 발견하고, 외부에서 한 번 더 timeout을 건다. **추상화에 의존하되 그 한계도 안다** — production 코드의 자세. 그리고 30초마다 progress 로깅 (라인 3055-3066)으로 **조용한 hang**도 감지. 작은 디테일이지만 오래 도는 도구 호출의 진단 가치가 크다.

### 권한 — `mcp__my-internal__*` 와일드카드

내가 만든 도구도 6.4의 권한 시스템을 그대로 통과한다. 7.2에서 본 풀 네임 매칭이 내 도구에도 동작:

```yaml
# 사용자의 settings.json
permissions:
  allow:
    - "mcp__my-internal__list_my_issues"      # 정확한 한 도구만
    - "mcp__my-internal__*"                    # 내 서버의 모든 도구
    - "mcp__*__list_*"                         # 어느 서버든 list_* 는 자동 허용
```

`mcp__my-internal__*` 한 줄이 내 서버의 모든 도구를 자동 허용한다. 언제 추가하는 도구도 자동으로 통과. **6.4의 7단계 와일드카드 변환 + 4.3의 권한 슬롯**이 내가 만든 도구에도 그대로 적용 — 아무 추가 코드 없이.

**fail-closed 기본값**: 처음 호출되는 도구는 기본적으로 사용자에게 묻는다. `readOnlyHint: true` 같은 어노테이션을 내 서버가 응답에 박아두면 읽기 전용으로 분류되어 자동 허용 가능. 7.2에서 본 그 패턴.

## Python으로 옮기면

진짜로 동작하는 Python MCP 서버. 위의 30줄짜리를 좀 더 풍부하게 만든 실제로 돌릴 수 있는 버전.

```python
# my_server.py
"""사내 시스템을 Claude Code 에 노출하는 MCP 서버.

실행:
    python my_server.py

등록:
    claude mcp add my-internal -- python /absolute/path/to/my_server.py
"""
from __future__ import annotations
import asyncio
import sys
import logging

from mcp.server.fastmcp import FastMCP


# ⚠️ 가장 중요한 한 줄 — *모든 출력은 stderr 로*.
# 의존성 라이브러리가 우연히 print 하면 stdout 채널이 깨진다.
# 명시적으로 sys.stderr 를 지정해서 로깅 셋업.
logging.basicConfig(
    stream=sys.stderr,
    level=logging.INFO,
    format="%(asctime)s | %(name)s | %(levelname)s | %(message)s",
)
logger = logging.getLogger(__name__)


server = FastMCP("my-internal")


@server.tool()
async def list_my_issues(status: str = "open") -> str:
    """Linear 에서 내가 담당한 이슈 목록을 가져온다.

    Args:
        status: 이슈 상태 — "open", "in_progress", "done", "all"

    Returns:
        이슈 목록을 *사람이 읽을 수 있는* 한국어 텍스트로.
    """
    logger.info(f"list_my_issues 호출: status={status}")  # ← stderr 로 감

    issues = await fetch_linear_issues(assignee="me", status=status)

    if not issues:
        return f"미해결 이슈가 없어요. (status={status})"

    lines = [f"내가 담당한 {status} 이슈 {len(issues)}개:"]
    for issue in issues:
        lines.append(f"- {issue['identifier']}: {issue['title']}")

    return "\n".join(lines)


@server.tool()
async def get_service_status(service_name: str) -> str:
    """사내 모니터링 시스템에서 서비스 상태를 가져온다.

    Args:
        service_name: 서비스 이름 — "api", "web", "worker" 등
    """
    logger.info(f"get_service_status 호출: service={service_name}")

    status = await fetch_monitoring_status(service_name)
    return f"{service_name}: {status['health']} ({status['uptime']} 가동)"


# ── 가짜 구현 (실제로는 외부 API 호출) ──────────────
async def fetch_linear_issues(assignee: str, status: str) -> list[dict]:
    """*가짜 구현*. 진짜는 Linear API 호출."""
    await asyncio.sleep(0.1)  # API call 시뮬레이션
    return [
        {"identifier": "PROJ-123", "title": "사용자 인증 버그"},
        {"identifier": "PROJ-145", "title": "대시보드 로딩 속도"},
    ]


async def fetch_monitoring_status(service: str) -> dict:
    return {"health": "healthy", "uptime": "14d 3h"}


if __name__ == "__main__":
    logger.info("MCP server starting (stdio)")
    server.run()  # ← FastMCP 가 stdio 채널 시작
```

**한 자리만 본다**:

1. `logging.basicConfig(stream=sys.stderr, ...)` — **stdout 오염 방지**의 첫 줄
2. `@server.tool()` 데코레이터 — 함수 시그니처 + **docstring**만으로 도구 정의 완성
3. `server.run()` — 모든 것을 시작

진짜 클로드 코드의 24줄짜리 stdio 진입점 + ListTools/CallTool 핸들러 + 각 도구 구현이 — **FastMCP 데코레이터 한 줄로 압축**. **Python SDK의 친절함**.

### 9.3의 Python 도구 ↔ 10.3의 MCP 도구

마지막으로 — 이 챕터의 **Part 9와의 연결**. 9.3에서 우리는 미니 에이전트의 도구를 **Python 클래스**로 만들었다:

```python
# 9.3
class ReadTool:
    name = "Read"
    input_model = ReadInput

    async def call(self, args, context):
        return Path(args["file_path"]).read_text()
```

10.3에서는 같은 일을 **MCP 서버 + 외부 프로세스**로 한다:

```python
# 10.3
@server.tool()
async def read_file(file_path: str) -> str:
    return Path(file_path).read_text()
```

**같은 일. 완전히 다른 형식**.

| | 9.3 미니 도구 | 10.3 MCP 도구 |
|---|---|---|
| 형식 | Python 클래스 (Tool Protocol) | Python 함수 (`@server.tool()`) |
| 위치 | `agent.py`에 **직접 import** | 외부 프로세스가 stdio로 노출 |
| 프로세스 | 같은 프로세스 안 | 다른 프로세스 (JSON-RPC 통신) |
| 사용처 | 9.3에서 내 미니 에이전트만 쓸 수 있음 | **어떤 MCP 클라이언트든** 쓸 수 있음 |
| 인터페이스 | Tool Protocol 5 구성 (3 속성 + 3 메서드) | tools/list + tools/call 두 메서드 |

**그런데 모델 입장에서는 같은 것** — 둘 다 도구 목록의 한 줄, 같은 호출 형식, 같은 응답 형식. 7.2의 변환층이 경계를 지운다. **언어 형식의 차이가 기능의 차이가 아니다** (10.2의 마지막 메시지 회수).

10.3의 진짜 의미: 9.3에서 만든 **Python 도구의 노하우**가 — 10.3에서 **MCP 서버의 함수**로 **그대로 옮겨간다**. 같은 사고방식, 같은 검증, 같은 권한, 같은 스키마. 형식만 바꾸면 — **어떤 LLM 클라이언트에서든** 쓸 수 있는 재사용 가능한 도구가 된다.

## 핵심 정리

- **MCP는 양방향 프로토콜**: 7.2에서 본 클라이언트 측 (외부 도구를 받아오는 자리)의 반대편 — 서버 측 (내가 도구를 노출하는 자리). 핵심 메서드는 두 개: `tools/list`와 `tools/call`. 그게 전부.
- **가장 단순한 Python MCP 서버는 30줄**: `FastMCP` + `@server.tool()` 데코레이터 + `server.run()`. 함수 시그니처 → JSON Schema 자동 변환, docstring → description 자동 추출. **9.3의 Pydantic 마법의 친척**.
- **진짜 클로드 코드의 stdio 진입점은 24줄** (`mcp-server/src/index.ts`). `createServer()` + `StdioServerTransport` + `connect` + `console.error` 4줄이 본질. Python 등가물도 비슷한 분량.
- ⚠️ **가장 큰 함정 — `print`하면 죽는다**: stdout은 JSON-RPC 채널. 어떤 라이브러리든 stdout에 뭘 찍으면 프로토콜 깨짐. 진짜 코드도 **명시적으로 `console.error`** 사용. Python에서는 `logging.basicConfig(stream=sys.stderr, ...)`가 시작 첫 줄.
- **`claude mcp add` 한 줄로 등록** → 기본은 `~/.claude.json` 안의 `projects.<현재 경로>.mcpServers` (local scope), `--scope user`면 `~/.claude.json`의 최상위 `mcpServers`, `--scope project`면 `<프로젝트 루트>/.mcp.json` → **다음 세션부터 자동 spawn 및 연결**. **`~/.claude/`** 디렉토리가 아니라 **`~/.claude.json`** 한 파일.
- **7.2의 `fetchToolsForClient`가 내 도구를 받아간다**: 내가 보낸 `name`, `description`, `inputSchema`가 → `mcp__myserver__myname` 풀 네임 + Tool 객체로 변환. 호출자는 차이를 모른다. 양방향의 회수.
- **`client.callTool()` 한 메서드 호출이 추상화의 완성**: MCP SDK가 알아서 JSON-RPC 직렬화 + stdio 전송 + 응답 검증. 8가지 전송이 같은 한 줄로 압축. production 디테일로 **Promise.race timeout** (SDK 내부 timeout의 SSE 버그 우회) + **30초 progress 로깅** (조용한 hang 감지).
- **권한은 7.2의 패턴 그대로**: `mcp__my-internal__*` 같은 와일드카드로 서버 단위 자동 허용. `readOnlyHint` 어노테이션을 응답에 박으면 **fail-closed 기본값을 피해** 자동 허용 가능.
- **9.3의 Python 도구 ↔ 10.3의 MCP 도구**: 같은 일을 완전히 다른 형식으로. 9.3은 같은 프로세스 안의 클래스, 10.3은 다른 프로세스의 함수. 모델 입장에서는 같은 것 — 언어 형식의 차이가 기능의 차이가 아니다. 9.3에서 만든 도구의 노하우가 **그대로 MCP 서버의 함수로 옮겨간다**.
