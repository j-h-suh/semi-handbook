# 6.3 권한 모드 5가지 — default / acceptEdits / plan / bypassPermissions / (+ ant-only auto)

---

## 이 챕터에서 배우는 것

- Shift+Tab으로 순환하는 5가지 외부 모드 (+ ant-only `auto`) 의 정확한 의미
- 각 모드가 권한 결정에 어떻게 영향을 주는지
- 놀라움 — **plan 모드는 권한 코드가 아니라 프롬프트 주입으로 구현된다**
- 가장 위험한 모드 `bypassPermissions`에 **원격 killswitch**가 달려 있는 이유
- ant-only `auto` 모드 — **transcript classifier**가 권한을 결정하는 방식
- 6.2의 `toolPermissionContext.mode` 필드 한 줄이 **전체 권한 정책 regime**을 바꾸는 자리

---

## 사용자 경험에서 출발

Claude Code 입력창에서 `Shift+Tab`을 누른다. 푸터에 모드 이름이 순환한다.

```
Default     → ⏵⏵ Accept edits  → ⏸ Plan Mode  → ⏵⏵ Bypass Permissions  → Default
```

각 모드마다 동작이 다르다. **Default** 에서는 위험한 명령마다 다이얼로그가 뜬다. **Accept edits** 에서는 파일 편집이 조용히 통과한다. **Plan Mode** 에서는 LLM이 아무것도 수정하지 않는다. **Bypass Permissions** 에서는 모든 다이얼로그가 사라진다.

같은 도구, 같은 명령, 같은 입력. **`mode` 한 글자**가 바뀌었을 뿐인데 — 전혀 다른 시스템처럼 동작한다. 이 챕터에서 그 한 글자가 어디에 들어 있고, 어떻게 동작을 바꾸는지를 본다.

---

### 1️⃣ `default` — 매번 묻는다

기본값. 권한 룰에 매칭되지 않은 도구 호출은 전부 사용자 다이얼로그를 띄운다. 사용자가 **Yes / No / Always**를 결정한다. **Always**를 누르면 — 그 패턴이 `alwaysAllowRules`의 `session` 슬롯에 추가되어, 이 세션 동안 다시 안 묻는다.

```
LLM: Bash(rm temp.txt)
   ┌─ Permission required ─────────────┐
   │  Bash: rm temp.txt                │
   │   [Y]es  [N]o  [A]lways           │
   └───────────────────────────────────┘
```

가장 보수적이고 가장 번거롭다. 처음 쓰는 디렉토리, 처음 쓰는 도구에서는 안전하다. 익숙해지면 답답하다. 그래서 다른 모드로 옮긴다.

### 2️⃣ `acceptEdits` — 파일 편집은 그냥 통과

쓰기 작업 중 덜 위험한 것들을 자동 허용. `BashTool/modeValidation.ts`에 명시적 화이트리스트가 있다.

```typescript
const ACCEPT_EDITS_ALLOWED_COMMANDS = [
  'mkdir', 'touch', 'rm', 'rmdir', 'mv', 'cp', 'sed',
] as const
```

이 7개 + `Edit`/`Write` 도구가 조용히 통과한다. 다이얼로그 안 뜸. 그 외의 명령(`git push`, `curl`, `npm install` 등)은 여전히 다이얼로그.

**범위가 의도적으로 좁다**. 파일 시스템 작업만. 네트워크나 패키지 설치 같은 바깥 세상에 영향을 주는 것은 안 통과시킨다. 익숙한 디렉토리에서 반복적인 편집 작업을 할 때 이 모드를 켠다.

### 3️⃣ `plan` — 놀라움: 권한 코드가 아니라 프롬프트 주입

여기가 이 챕터의 진짜 보석이다. Plan 모드는 권한 시스템에서 구현된 게 아니다. **시스템 리마인더 메시지**로 구현된다.

`src/utils/messages.ts:3227`을 보자. (같은 텍스트가 line 3331, 3407 에도 거의 그대로 박혀 있다 — 다른 시나리오용 분기들. plan 모드의 말로 부탁 메커니즘이 세 곳에서 따로 살아 있다.)

```typescript
const content = `Plan mode is active. The user indicated that they do not want you to execute yet -- you MUST NOT make any edits (with the exception of the plan file mentioned below), run any non-readonly tools (including changing configs or making commits), or otherwise make any changes to the system. This supercedes any other instructions you have received.

## Plan File Info:
...
`
```

권한 검사 코드에서 "plan 모드면 거부"라는 식의 분기가 거의 없다. 대신 — **LLM에게 말로 부탁한다**. **"Plan 모드 켜져 있으니 아무것도 바꾸지 마라. 다른 지시보다 이게 우선이다."**

**왜 이렇게 했나?** 두 가지 이유가 있다고 본다.

**(1) Plan 모드의 목적은 의도 이해다.** 사용자는 "먼저 계획만 세워줘, 실행은 내가 결정"을 원한다. LLM이 왜 그 결정인지 이해하고 읽기 작업만 하면서 계획을 세우는 게 핵심이다. 권한 코드로 강제로 차단하면 — LLM이 왜 차단됐는지 모르고 같은 것을 다른 방식으로 시도한다. 의도가 안 닿는다. 프롬프트로 부탁하면 — LLM이 맥락을 이해한다. 자기가 왜 그렇게 동작해야 하는지를 안다.

**(2) 더 부드럽다.** 권한 다이얼로그가 안 뜬다. LLM이 알아서 읽기 도구만 쓴다. 사용자는 다이얼로그 클릭의 지옥에 빠지지 않는다. 

물론 — 완벽하지는 않다. 모델이 지시를 어길 가능성이 있다. 그래서 plan 모드에는 추가 안전망이 있다. `bypassPermissions`와 합쳐졌을 때만 일부 검사를 우회한다. **plan 모드 + 실제 쓰기 시도**가 일어나면 — 에이전트 루프가 그 메시지를 잡아내고 `ExitPlanModeTool`로 모드를 빠져나가게 강제한다 (8.3에서 본격적으로).

> 💡 **모델에게 말로 부탁하는 것도 권한 시스템이다.** 권한이라고 하면 코드 분기만 떠올리기 쉽다. 근데 LLM 시대에는 — 프롬프트로 명시한 제약도 권한이다. 모델이 지시를 따른다는 가정 위에 시스템이 돌아간다. 이게 불완전하지만 — 완벽한 차단보다 유연한 협력이 더 좋은 사용자 경험을 만들 수 있다. **Claude Code는 두 방식을 섞어서 쓴다**. 위험도가 낮은 모드는 프롬프트, 높은 것은 코드.

### 4️⃣ `bypassPermissions` — 모든 다이얼로그를 끈다

가장 위험한 모드. `permissions.ts:1268` 를 보면 바로 분기가 있다.

:::tabs

```typescript
const shouldBypassPermissions =
  appState.toolPermissionContext.mode === 'bypassPermissions' ||
  (appState.toolPermissionContext.mode === 'plan' &&
    appState.toolPermissionContext.isBypassPermissionsModeAvailable)
if (shouldBypassPermissions) {
  return { behavior: 'allow', ... }
}
```

```python
# Python 등가 — bypass 모드 체크
def check_permission(tool, args, mode: PermissionMode) -> str:
    if mode == PermissionMode.BYPASS:
        return "allow"  # 아무것도 안 묻는다

    if mode == PermissionMode.ACCEPT_EDITS:
        if tool.is_read_only() or tool.name in ("Edit", "Write"):
            return "allow"

    # default 모드: 룰 매칭 → 없으면 "ask"
    return match_rules(tool, args) or "ask"
```

:::

아무 검사도 안 한다. 그냥 통과. `rm -rf`, `git push --force`, `curl | bash` 다 통과. **사용자가 책임지는 모드**다.

이 모드에는 세 겹의 안전장치가 있다.

**(1) 옵트인 강제** — `isBypassPermissionsModeAvailable` 플래그가 **true**여야만 진입할 수 있다. 사용자가 명시적으로 활성화한 경우만.

**(2) 원격 killswitch** — `bypassPermissionsKillswitch.ts`에 **Statsig gate 체크**가 있다. **"이 사용자의 bypass 모드를 원격으로 끌 수 있어야 한다"**는 보안 요구. 만약 발견된 위험이 있어서 **모든 사용자의 bypass 모드를 즉시 무력화**해야 하면 — Anthropic이 gate를 끄고, 다음 세션부터는 bypass 모드가 자동으로 비활성된다. **0-day 대응**용 안전장치.

**(3) 시각 경고** — 푸터에 빨간색 ⏵⏵ 아이콘이 항상 떠 있다. `mode.color = 'error'`. "지금 위험한 모드"가 시각적으로 절대로 안 잊혀짐.

**bypass 모드는 명시적인 위험 인수다.** 사용자가 알고 켰고, 알고 쓴다. 자동으로는 절대 켜지지 않는다.

> ⚙️ **`auto` 모드도 같은 killswitch 안에 산다.** `bypassPermissionsKillswitch.ts` 는 이름과 달리 두 위험 모드를 같이 다룬다. line 19-47 에 `checkAndDisableBypassPermissionsIfNeeded`, line 74-117 에 `checkAndDisableAutoModeIfNeeded`. **두 모드 모두 원격 gate 로 무력화 가능**하다는 사실이 한 파일에 같이 쓰여 있다. 개발자가 위험 모드는 같이 관리해야 한다고 명시적으로 결정한 흔적 — 두 모드 다 기본 권한 플로우 밖에서 조용히 비활성화 될 수 있어야 한다.

권한 결정을 LLM에게 위임한다. 보조 모델이 **현재 transcript 전체**와 시도되는 도구 호출을 보고 — "이게 사용자의 의도와 맞나, 안전한가"를 판단한다. 예측되는 위험이면 **block**, 합리적이면 **allow**. 사용자에게 다이얼로그 안 띄운다.

**bypass 모드와 다른 점**: bypass는 아무것도 검사 안 함, auto는 **별도 LLM 호출**(`sideQuery`)로 검사. 덜 빠르지만 더 똑똑하다. 분류기가 거부를 너무 많이 누적하면 — **모드는 `auto` 그대로 두되 그 호출만 사용자 다이얼로그로 폴백**한다(모드 전환 아님). 임계값은 `denialTracking.ts:12-15` 에 못 박혀 있다 — `maxConsecutive: 3` (연속 3회 거부) 또는 `maxTotal: 20` (누적 20회 거부) 시 발동. **fail-safe 메커니즘**.

> 🔬 **Deep Dive — 모드 cycle은 Shift+Tab에서 일어난다.** `getNextPermissionMode.ts:34-79`의 switch가 그 cycle을 정의한다. 외부 사용자: `default → acceptEdits → plan → (bypass 가능하면) bypassPermissions → default`. ant 사용자: `default → (bypass 가능하면) bypass → (auto 가능하면) auto → default` — `acceptEdits` 와 `plan` 을 건너뛴다. 코드 자체가 직접 설명한다 (`getNextPermissionMode.ts:40` verbatim): **"Ants skip acceptEdits and plan — auto mode replaces them"**. 외부와 내부의 진입 가능 모드가 다르다. 같은 코드가 빌드 분기에 따라 다른 사용자 경험을 제공한다. **feature gate**로 제어. dead code elimination으로 외부 빌드에서는 auto 관련 코드가 통째로 제거된다. `dontAsk` 모드도 cycle 에 안 들어감 (line 70-72: **"Not exposed in UI cycle yet"**) — 헤드리스/SDK 에서만 쓰인다.

### 5개 모드 비교

| 모드 | 다이얼로그 | 자동 허용 범위 | 구현 자리 | 위험도 |
|---|---|---|---|---|
| `default` | 매번 | 알림 룰만 | 권한 코드 | 🟢 낮음 |
| `acceptEdits` | 가끔 | 파일 편집 + 7개 명령 | 권한 코드 (mode validation) | 🟡 중간 |
| `plan` | 안 뜸 | (이론상) 읽기만 | **프롬프트 주입** | 🟢 낮음 |
| `bypassPermissions` | 절대 안 뜸 | 전부 | 권한 코드 (early return) | 🔴 높음 |
| `auto` | 안 뜸 | classifier 결정 | 권한 코드 + LLM | 🟡 중간 |

각 모드가 완전히 다른 메커니즘을 쓴다. 하나는 코드 분기, 하나는 프롬프트, 하나는 LLM 호출. **`mode` 한 글자가 5개의 다른 시스템을 트리거한다.**

## Python으로 옮기면

같은 패턴을 Python으로 모델링하면 이렇게 생겼다.

```python
from __future__ import annotations
from dataclasses import dataclass, field
from enum import Enum
from typing import Awaitable, Callable


class PermissionMode(str, Enum):
    DEFAULT = "default"
    ACCEPT_EDITS = "acceptEdits"
    PLAN = "plan"
    BYPASS = "bypassPermissions"
    AUTO = "auto"


@dataclass
class PermissionContext:
    mode: PermissionMode = PermissionMode.DEFAULT
    always_allow_rules: dict[str, list[str]] = field(default_factory=dict)
    is_bypass_available: bool = False
    is_auto_available: bool = False


# ─── 모드별 정책 함수 ────────────────
async def check_permission(
    tool_name: str,
    input_str: str,
    ctx: PermissionContext,
    classifier: Callable[[str, str], Awaitable[bool]] | None = None,
) -> str:  # "allow" | "ask" | "deny"
    
    # 1) bypassPermissions — 가장 먼저, *모든 검사 우회*
    if ctx.mode == PermissionMode.BYPASS:
        return "allow"
    
    # 2) auto — classifier에 위임
    if ctx.mode == PermissionMode.AUTO and classifier:
        is_safe = await classifier(tool_name, input_str)
        return "allow" if is_safe else "ask"
    
    # 3) acceptEdits — 파일 편집 화이트리스트
    if ctx.mode == PermissionMode.ACCEPT_EDITS:
        if tool_name in ("Edit", "Write") or any(
            input_str.startswith(cmd) for cmd in ["mkdir", "touch", "rm", "mv", "cp"]
        ):
            return "allow"
        # 화이트리스트에 없으면 default로 폴백
    
    # 4) plan — 코드에서는 거의 안 거름. 실제 차단은 프롬프트 주입에 의존
    # (plan 모드면 시스템 리마인더가 메시지에 들어감 → LLM이 알아서 안 함)
    
    # 5) default + plan 폴백 — 룰 매칭 + 다이얼로그
    for pattern in ctx.always_allow_rules.get(tool_name, []):
        if input_str.startswith(pattern):
            return "allow"
    return "ask"


# ─── plan 모드는 프롬프트 주입으로 구현 ────────────────
PLAN_MODE_REMINDER = (
    "Plan mode is active. The user indicated that they do not want you "
    "to execute yet — you MUST NOT make any edits, run any non-readonly "
    "tools, or otherwise make any changes to the system. This supercedes "
    "any other instructions you have received."
)


def inject_mode_reminder(messages: list[dict], mode: PermissionMode) -> list[dict]:
    """Plan 모드면 시스템 리마인더를 메시지 앞에 끼워 넣는다."""
    if mode == PermissionMode.PLAN:
        return [
            {
                "role": "user",
                "content": f"<system-reminder>\n{PLAN_MODE_REMINDER}\n</system-reminder>",
                "is_meta": True,
            },
            *messages,
        ]
    return messages


# ─── 사용 ────────────────
ctx = PermissionContext(mode=PermissionMode.PLAN)

# 권한 코드는 거의 아무 일도 안 함 — passthrough
result = await check_permission("Edit", "foo.py", ctx)
# → "ask" 로 떨어짐 — 코드는 별다른 처리 안 함

# 진짜 차단은 메시지에 끼워넣은 리마인더로
messages = [{"role": "user", "content": "foo.py 좀 수정해줘"}]
final = inject_mode_reminder(messages, ctx.mode)
# → final[0] = "Plan mode is active. ... MUST NOT make any edits ..."
# → LLM은 이 리마인더를 보고 Edit 도구를 시도하지도 않음
```

핵심 셋이 다 있다.

1. **`mode` 필드 한 글자**가 5개의 다른 분기를 트리거.
2. **bypass는 가장 먼저** — 다른 검사 다 우회.
3. **plan은 프롬프트 주입** — 코드는 거의 손대지 않음, LLM에게 말로 부탁.

> 💡 **이 패턴이 왜 LLM 시대에 가능한가.** 옛날 시스템은 코드만이 강제였다. 사용자에게 부탁해도 안 따라줬다 (사용자는 자기 의도가 있으니까). LLM 시대에는 모델에게 부탁하면 대체로 따른다. 100%는 아니지만 — 그 불완전한 협력이 완벽한 차단보다 **더 자연스러운 UX**를 만든다. Plan 모드가 권한 코드가 아니라 프롬프트 주입으로 구현된 게 그 증거다.

> 💡 **Python: `Literal` vs `Enum` — 같아 보이지만 결정적으로 다르다.**
>
> 위 코드의 `PermissionMode`를 `Enum` 대신 `Literal`로 쓸 수도 있다.
>
> ```python
> from typing import Literal
>
> PermissionMode = Literal[
>     "default", "acceptEdits", "plan", "bypassPermissions", "auto"
> ]
>
> def check_permission(mode: PermissionMode) -> str:
>     if mode == "default":  # 그냥 문자열 비교
>         ...
> ```
>
> 둘 다 "정해진 문자열 중 하나"를 표현하는데, 차이는 깊다.
>
> | | `Literal[...]` | `Enum` |
> |---|---|---|
> | **런타임 비용** | 0 — 타입 체커에만 전달 | 클래스 + 인스턴스 객체가 메모리 상주 |
> | **값의 정체** | 그냥 `str` (`"default"`) | enum 인스턴스 (`PermissionMode.DEFAULT`) |
> | **타입 체크** | mypy/pyright가 정의된 값만 허용 | 같음 + IDE 자동완성 더 강함 (`PermissionMode.` 누르면 5개 뜸) |
> | **런타임 검증** | 없음 — 잘못된 값 할당해도 통과 | 같음(변수 할당) — 단 `PermissionMode("invalid")` 변환 시 `ValueError` |
> | **Pydantic** | `field: PermissionMode` — JSON에 `"default"` 그대로 | 같음, 단 직렬화 모드 옵션(`.value` vs 인스턴스) |
> | **부가 데이터** | 불가 (문자열일 뿐) | 메서드/속성을 enum 안에 묶을 수 있음 |
>
> **언제 어느 쪽?**
>
> - **`Literal`** — 값 자체가 본질이고 부가 정보가 필요 없을 때. JSON 호환(외부 API/DB 직렬화)에 자연스럽고 런타임 0 비용. TypeScript의 `as const` 배열과 의미상 가장 닮은 표현.
> - **`Enum`** — 값에 의미 있는 메서드/속성을 묶고 싶을 때, 또는 IDE 자동완성을 강하게 받고 싶을 때. `PermissionMode.DEFAULT` 같은 명시적 표현이 코드 가독성에 도움.
>
> 실제 Claude Code의 TypeScript `EXTERNAL_PERMISSION_MODES = [...] as const`는 의미상 **`Literal`에 더 가깝다** (런타임 객체 없이 타입만 좁힘). 위 본문이 `Enum`을 쓴 이유는 Python에서 enum 멤버가 더 명시적으로 읽히기 때문 — 첫 등장 시 `PermissionMode.DEFAULT`처럼 클래스명이 같이 나와서 "이게 어디 정의된 것인지" 한눈에 보임.

## 핵심 정리

- 권한 모드는 `appState.toolPermissionContext.mode` 한 필드에 산다. **이 한 글자가 5개의 다른 권한 정책 regime을 트리거**한다.
- **`default`** — 매번 다이얼로그. 가장 보수적, 가장 번거로움.
- **`acceptEdits`** — 파일 편집 + 7개 명령(`mkdir`/`rm`/`mv`/...) 자동 허용. 코드 분기로 구현.
- **`plan` (놀라움)** — 권한 코드가 아니라 **프롬프트 주입**으로 구현. **"You MUST NOT make any edits"**라는 시스템 리마인더가 메시지에 끼워 들어감. LLM에게 말로 부탁.
- **`bypassPermissions`** — 모든 검사 우회. 세 겹 안전장치: (a) 옵트인 강제, (b) 원격 killswitch (Statsig gate), (c) 빨간 시각 경고.
- **`auto` (ant-only)** — **transcript classifier** 보조 LLM이 도구 호출의 안전성을 판단. 분류기가 실수하면 연속 거부 카운터로 자동 비활성.
- 5개 모드의 구현 자리가 다 다르다 — 코드 분기, 프롬프트 주입, LLM 호출. **권한 시스템이 단일 메커니즘이 아니라 여러 메커니즘의 조합**임을 보여줌.
- 프롬프트로 부탁하는 것도 권한이다 — LLM 시대에는 완벽한 차단보다 유연한 협력이 더 좋은 UX를 만들 수 있다. Plan 모드가 그 증거.
- 다음 챕터(6.4): 각 모드가 다 의존하는 룰 매칭 — `Bash(git *)` 같은 와일드카드는 어떻게 작동하나. 그리고 룰이 어디서 오는지 — `PermissionRuleSource` 8개 출처 (`userSettings, projectSettings, localSettings, flagSettings, policySettings, cliArg, command, session`) 가 한 평탄화된 룩업으로 합쳐진다.
