# 10.4 MCP 서버 만들기 — 외부 도구를 붙이고, 도구를 내보내기

---

## 이 챕터에서 배우는 것

- 9.3의 도구는 **같은 프로세스 안에 산다**. MCP는 **외부 프로세스의 도구**를 JSON-RPC로 가져온다
- 미니 클로드를 **MCP 클라이언트**로 만드는 전체 구현 — 서버 spawn + tools/list + 도구 풀 합류
- **MCP 서버**를 Python 30줄로 만들어서 미니 클로드에 연결 — 양방향의 완성
- `tools/list`와 `tools/call` — 두 메서드가 MCP의 전부
- ⚠️ **stdout은 JSON-RPC 채널** — `print`하면 프로토콜이 깨진다
- **비동기 RPC 의 표준 패턴** — reader task + `Queue` map 으로 응답 dispatch. DB 드라이버/WebSocket/gRPC 에서 반복되는 모양
- 7.2의 `fetchToolsForClient`가 Python 100줄로 압축되는 과정

---

## 왜 MCP인가

9.3~10.2까지 미니 클로드의 도구는 두 종류다:

1. **Python 클래스** (Read, Write, Bash, Edit, Agent) — 같은 프로세스 안
2. **마크다운 스킬** (SkillTool) — 같은 프로세스 안에서 텍스트를 로드

둘 다 **같은 프로세스 안에** 산다. 문제:

- 사내 Linear API를 호출하는 도구를 만들고 싶다 → 미니 클로드 코드에 직접 박아야 한다
- 동료가 만든 모니터링 도구를 가져다 쓰고 싶다 → 소스를 복사해야 한다
- 다른 LLM 클라이언트에서도 쓸 수 있는 재사용 가능한 도구를 만들고 싶다 → 방법이 없다

MCP가 이 세 가지를 푼다. **도구를 별도 프로세스로 분리**하고, **표준 프로토콜로 통신**한다. 미니 클로드 입장에서는 — 외부 프로세스의 도구가 **내장 도구와 같은 풀에 합류**한다. 모델은 차이를 모른다.

이 챕터에서 양방향을 다 구현한다:
- **클라이언트**: 미니 클로드가 외부 MCP 서버에 연결해서 도구를 가져온다
- **서버**: Python으로 MCP 서버를 만들어서 미니 클로드에 붙여본다

---

## Part 1: 미니 클로드를 MCP 클라이언트로

### MCP 프로토콜의 본질 — 두 메서드

```
   Client (mini_claude)           Server (외부 Python 프로세스)
          │                                │
          │ ── tools/list ──────────────→  │
          │ ←── { tools: [...] } ────────  │
          │                                │
    (...모델이 도구 호출 결정...)             │
          │                                │
          │ ── tools/call ──────────────→  │
          │    { name, arguments }         │
          │ ←── { content: [...] } ─────── │
```

`tools/list`는 "네가 가진 도구 목록을 알려줘", `tools/call`은 "이 도구를 이 인자로 호출해줘". **그게 전부**.

전송 계층은 여러 가지가 있지만 (stdio, HTTP, SSE, WebSocket) 가장 흔한 건 **stdio** — 서버 프로세스의 stdin/stdout을 JSON-RPC 채널로 쓴다.

### MCP 클라이언트 구현 — 100줄

```python
# src/mini_claude/mcp/client.py
from __future__ import annotations
import asyncio
import json
import logging
from dataclasses import dataclass, field
from typing import Any

logger = logging.getLogger(__name__)


@dataclass
class MCPServerConfig:
    """MCP 서버 설정. mcp_config.json의 한 entry."""
    name: str
    command: str
    args: list[str] = field(default_factory=list)
    env: dict[str, str] = field(default_factory=dict)


@dataclass
class MCPToolDef:
    """MCP 서버가 노출한 도구 한 개의 정의."""
    name: str
    description: str
    input_schema: dict[str, Any]
    server_name: str


@dataclass
class MCPConnection:
    """활성 MCP 서버 연결. 백그라운드 reader task 가 응답을 dispatch."""
    config: MCPServerConfig
    process: asyncio.subprocess.Process
    tools: list[MCPToolDef] = field(default_factory=list)
    _request_id: int = 0
    # ⭐ id → Queue. send_request 가 등록 → `await queue.get()`,
    #    _read_loop 가 응답을 `put`. 한 응답 = 한 put.
    _pending: dict[int, asyncio.Queue] = field(default_factory=dict)
    _reader_task: asyncio.Task | None = None

    async def _read_loop(self) -> None:
        """stdout 을 무한 흡수 → id 로 dispatch.

        진짜 SDK 의 핵심 패턴 — 비동기 RPC 의 표준 모양.
        """
        while True:
            line = await self.process.stdout.readline()
            if not line:
                # ⭐ 연결 종료 — 남은 queue 에 sentinel error put (영원히 await 방지)
                err_msg = f"MCP server {self.config.name} closed"
                for queue in self._pending.values():
                    await queue.put((err_msg, None))
                return

            msg = json.loads(line)
            if "id" in msg:
                # 응답 — 해당 queue 에 (error, result) put
                queue = self._pending.pop(msg["id"], None)
                if queue:
                    error = (
                        msg["error"].get("message", "unknown")
                        if "error" in msg else None
                    )
                    await queue.put((error, msg.get("result")))
            else:
                # notification — 학습용으로는 로그만 (실무는 handler dispatch)
                logger.debug(f"notification: {msg.get('method')}")

    async def send_request(self, method: str, params: dict | None = None) -> Any:
        """JSON-RPC 요청 → queue 만들고 reader task 가 put 해주길 기다림."""
        self._request_id += 1
        req_id = self._request_id
        queue: asyncio.Queue = asyncio.Queue(maxsize=1)
        self._pending[req_id] = queue

        request = {
            "jsonrpc": "2.0",
            "id": req_id,
            "method": method,
            "params": params or {},
        }
        line = json.dumps(request) + "\n"
        self.process.stdin.write(line.encode())
        await self.process.stdin.drain()

        # ← readline 직접 안 함. _read_loop 가 queue 에 put.
        error, result = await queue.get()
        if error:
            raise RuntimeError(f"MCP error: {error}")
        return result


async def connect_to_server(config: MCPServerConfig) -> MCPConnection:
    """MCP 서버 프로세스를 spawn하고 초기화한다.

    진짜 코드의 connectToServer (client.ts:595)의 정수.
    """
    process = await asyncio.create_subprocess_exec(
        config.command,
        *config.args,
        stdin=asyncio.subprocess.PIPE,
        stdout=asyncio.subprocess.PIPE,
        stderr=asyncio.subprocess.PIPE,  # ⭐ stdout 과 분리된 채널 — 서버 로그용
    )

    conn = MCPConnection(config=config, process=process)
    # ⭐ reader task 먼저 시작 — initialize 응답도 이걸로 받음
    conn._reader_task = asyncio.create_task(conn._read_loop())

    # ① 초기화 핸드셰이크
    await conn.send_request("initialize", {
        "protocolVersion": "2024-11-05",
        "capabilities": {},
        "clientInfo": {"name": "mini-claude", "version": "0.1.0"},
    })

    # ② 초기화 완료 알림 (notification — 응답 안 옴)
    notify = {"jsonrpc": "2.0", "method": "notifications/initialized"}
    conn.process.stdin.write((json.dumps(notify) + "\n").encode())
    await conn.process.stdin.drain()

    return conn


async def fetch_tools(conn: MCPConnection) -> list[MCPToolDef]:
    """tools/list를 호출해서 서버의 도구 목록을 가져온다.

    진짜 코드의 fetchToolsForClient (client.ts:1743)의 정수.
    """
    result = await conn.send_request("tools/list")
    tools = []

    for tool_data in result.get("tools", []):
        tools.append(MCPToolDef(
            name=tool_data["name"],
            description=tool_data.get("description", ""),
            input_schema=tool_data.get("inputSchema", {}),
            server_name=conn.config.name,
        ))

    conn.tools = tools
    return tools


async def call_tool(conn: MCPConnection, tool_name: str, args: dict) -> str:
    """tools/call을 호출해서 도구를 실행한다."""
    result = await conn.send_request("tools/call", {
        "name": tool_name,
        "arguments": args,
    })

    # MCP 응답 형식: { content: [{ type: "text", text: "..." }] }
    content_blocks = result.get("content", [])
    texts = [b["text"] for b in content_blocks if b.get("type") == "text"]
    return "\n".join(texts) if texts else "(no output)"
```

**핵심 4단계**:
1. `connect_to_server()` — 프로세스 spawn + **reader task 시작** + initialize 핸드셰이크
2. `_read_loop()` — stdout 무한 흡수 → `id` 로 `Future` resolve, notification 분리
3. `fetch_tools()` — `tools/list`로 도구 목록 가져오기
4. `call_tool()` — `tools/call`로 도구 실행

진짜 코드의 `connectToServer` (595줄) + `fetchToolsForClient` (1743줄)가 이 100줄로 압축된다. 빠진 것: OAuth 인증, SSE/HTTP/WebSocket 전송, timeout 관리, retry, notification handler 등록, 캐시. **남은 것은 stdio JSON-RPC + 비동기 RPC 의 표준 모양**.

> 💡 **왜 reader task 가 필요한가**. `send_request` 가 직접 `readline()` 해서 _첫 줄_ 을 응답으로 가정하면 — 서버가 _요청 없이 보내는_ notification (`notifications/progress`, `notifications/message`) 이 먼저 오면 그걸 응답으로 오해한다. 동시에 두 요청을 보내면 어느 응답이 어느 요청 것인지도 모른다. **별도 reader task** 가 stdout 을 무한 흡수하면서 `id` 별로 등록된 `asyncio.Queue` 에 _put_ 하는 — 이게 비동기 RPC 의 _표준 모양_ 이다. DB 드라이버, WebSocket 클라이언트, gRPC — 다 같은 패턴 (그쪽들은 보통 `Future` 를 쓰는데, 미니에서는 _put 하면 get 이 받는다_ 라는 흐름이 더 명확한 Queue 로 시연).

### MCP 도구를 9.3 도구 풀에 합류시키기

외부 서버에서 가져온 `MCPToolDef`를 — 9.3의 Tool Protocol을 따르는 도구 객체로 변환해야 한다. 진짜 코드의 `fetchToolsForClient`가 하는 핵심 작업.

```python
# src/mini_claude/mcp/bridge.py
from __future__ import annotations
from typing import Any
from pydantic import BaseModel, Field

from ..tools.base import Tool, ToolContext
from .client import MCPConnection, MCPToolDef, call_tool


def create_mcp_tool(conn: MCPConnection, tool_def: MCPToolDef) -> Tool:
    """MCPToolDef를 9.3의 Tool Protocol 도구로 변환한다.

    진짜 코드의 fetchToolsForClient (client.ts:1766)에서
    MCPTool spread + 각 콜백 생성하는 부분의 정수.
    """
    # MCP의 inputSchema → Pydantic 모델로 동적 생성
    # (간략화 — 진짜 코드는 inputJSONSchema를 그대로 넘김)
    _input_model = _schema_to_pydantic(tool_def)
    _full_name = f"mcp__{tool_def.server_name}__{tool_def.name}"
    _desc = tool_def.description
    _server = tool_def.server_name
    _tname = tool_def.name

    # ⚠️ alias (_full_name, _desc, _input_model) 로 받는 이유는 아래 콜아웃 참조.
    class MCPToolWrapper:
        name = _full_name
        description = _desc
        input_model = _input_model

        def is_read_only(self) -> bool:
            return False  # fail-closed — 외부 서버가 뭘 할지 모름

        def is_destructive(self) -> bool:
            return False

        def permission_summary(self, args: dict[str, Any]) -> str:
            return f"{_server}/{_tname}"

        async def call(self, args: dict[str, Any], context: ToolContext) -> str:
            # ⭐ JSON-RPC tools/call → 외부 프로세스
            return await call_tool(conn, _tname, args)

    return MCPToolWrapper()


def _schema_to_pydantic(tool_def: MCPToolDef) -> type[BaseModel]:
    """JSON Schema → Pydantic 모델 동적 생성 (간략화).

    진짜 코드는 inputJSONSchema를 직접 LLM에 넘기므로
    이 변환이 필요 없다. 미니에서는 Pydantic이 필수이므로 변환.
    """
    properties = tool_def.input_schema.get("properties", {})
    required = set(tool_def.input_schema.get("required", []))

    fields: dict[str, Any] = {}
    for prop_name, prop_schema in properties.items():
        desc = prop_schema.get("description", "")
        default = ... if prop_name in required else prop_schema.get("default")
        fields[prop_name] = (str, Field(default=default, description=desc))

    model = type(
        f"MCPInput_{tool_def.server_name}_{tool_def.name}",
        (BaseModel,),
        {"__annotations__": {k: v[0] for k, v in fields.items()},
         **{k: v[1] for k, v in fields.items()}},
    )
    return model
```

> ⚠️ **alias 로 받는 이유 — class body 의 scope 함정**. `class Foo: x = x` (또는 `@dataclass` 의 `x: int = x`) 처럼 _좌변과 우변이 같은 이름_ 이면 _import 즉시 `NameError`_ 로 깨진다. 두 규칙이 겹쳐서 일어나는 함정 — (1) _class body 는 enclosing function 의 local 을 못 본다_ (LEGB 의 `E` 가 _class body 안에서는 건너뛰는_ 고전 함정), (2) _좌변 binding 이 있는 statement_ 의 우변에서 _같은 이름_ 을 참조하면 Python 컴파일러가 _그 이름을 class body local 로 marking_ 한다 → 아직 bound 안 된 local 을 참조 → `NameError`. 회피: `_x = x` 처럼 _다른 이름_ 으로 alias. 우리 코드는 `_full_name`, `_desc`, `_input_model` 모두 alias 라서 class body 에서 _다른 이름_ 으로 안전히 참조한다. _일반 `class`_ 인 건 부수적 — method 가 많아서 `@dataclass` 의 자동 `__init__` / `__repr__` 이득이 적기 때문이고, alias 만 적용하면 `@dataclass` 로도 똑같이 동작한다.

**`create_mcp_tool()`가 하는 일**: 외부 서버의 도구 정의를 → 9.3의 Tool Protocol을 따르는 객체로 감싼다. 그 결과는 `parent_tools`에 들어갈 수 있고, 9.4의 권한 게이트도 그대로 통과한다. **모델 입장에서는 내장 도구와 MCP 도구의 차이가 없다**.

### main.py에 MCP 클라이언트 연결

```python
# src/mini_claude/main.py — 10.3 위의 add-up

import json    # ← *10.4 에서 추가* (이전엔 main.py 에 없었음)

# 9.5 / 10.1 / 10.2 / 10.3 의 기존 import 들...
from .mcp.client import MCPServerConfig, connect_to_server, fetch_tools   # ← *10.4 에서 추가*
from .mcp.bridge import create_mcp_tool                                    # ← *10.4 에서 추가*


async def main_async() -> None:
    parser = argparse.ArgumentParser(prog="mini-claude")
    parser.add_argument("--cwd", type=Path, default=Path.cwd())
    # ⭐ 추가 ①: --mcp-config 인자. default 는 프로젝트 루트의 mcp_config.json
    #   main.py 는 src/mini_claude/ 안 → parents[2] 가 프로젝트 루트
    #   (10.3 의 hooks/__init__.py 는 한 단계 더 깊어서 parents[3] 이었음)
    parser.add_argument(
        "--mcp-config",
        type=Path,
        default=Path(__file__).resolve().parents[2] / "mcp_config.json",
    )
    args = parser.parse_args()

    # ... 9.5 / 10.1 / 10.2 / 10.3 의 초기화 (AWS_BEARER_TOKEN_BEDROCK 검사 / state / permissions /
    #     parent_tools / SkillTool / AgentTool / md_commands /
    #     hooks / hooks.session_start) ...

    # ⭐ 추가 ②: MCP 서버 연결 — parent_tools 풀에 합류
    if args.mcp_config.exists():
        mcp_configs = load_mcp_config(args.mcp_config)
        for config in mcp_configs:
            print(f"Connecting to MCP server: {config.name}...")
            conn = await connect_to_server(config)
            tools = await fetch_tools(conn)
            print(f"  ✓ {len(tools)} tools loaded: "
                  f"{', '.join(t.name for t in tools)}")
            for tool_def in tools:
                mcp_tool = create_mcp_tool(conn, tool_def)
                parent_tools.append(mcp_tool)

    print("mini-claude 시작 (Ctrl+D로 종료)")
    # ... 나머지 루프는 동일 — 모델은 MCP 도구를 그냥 부른다 ...


# ⭐ 추가 ③: mcp_config.json 로더 (main 함수 위)
def load_mcp_config(config_file: Path) -> list[MCPServerConfig]:
    """mcp_config.json → MCPServerConfig 리스트."""
    data = json.loads(config_file.read_text(encoding="utf-8"))
    configs = []
    for name, server in data.items():
        configs.append(MCPServerConfig(
            name=name,
            command=server["command"],
            args=server.get("args", []),
            env=server.get("env", {}),
        ))
    return configs
```

**세 자리 변경의 그림**:

| 자리 | 무엇 | 어디 |
|---|---|---|
| ① argparse `--mcp-config` | default 가 _프로젝트 루트의 mcp_config.json_ — 파일이 있으면 _인자 없이도 자동 사용_ (10.3 의 hooks.json 패턴) | parser 정의 직후 |
| ② MCP 연결 블록 | 파일이 있으면 서버 spawn + `tools/list` + `create_mcp_tool` 로 풀 합류 | `hooks.session_start` 다음, `print("mini-claude 시작 ...")` 직전 |
| ③ `load_mcp_config` 함수 | JSON → `MCPServerConfig` 리스트 | `main_async` 밖, `main` 함수 위 |

**while 루프 안은 한 줄도 안 바뀝니다** — `create_mcp_tool` 의 wrapper 가 Tool Protocol 을 따르므로, 모델이 `mcp__my-internal__list_my_issues` 를 부르면 _9.4 의 권한 게이트 통과 → `MCPToolWrapper.call()` → JSON-RPC_ 가 _기존 도구 호출 흐름과 완전히 동일_. 이게 MCP 도구 풀 합류 패턴의 진짜 가치.

## Part 2: MCP 서버 만들기

### 가장 단순한 Python MCP 서버 — 30줄

```python
# mcp_servers/my_server.py
"""사내 시스템을 mini_claude에 노출하는 MCP 서버.

실행: python mcp_servers/my_server.py
"""
from __future__ import annotations
import asyncio
import sys
import logging

# ⚠️ FastMCP 는 ``mcp`` 패키지에 들어 있다 — 별도 의존성.
# uv add 'mcp[cli]'   # CLI 도구 포함 (또는 그냥 'mcp' 만)
from mcp.server.fastmcp import FastMCP

# ⚠️ 모든 출력은 stderr로. stdout은 JSON-RPC 채널.
logging.basicConfig(
    stream=sys.stderr,
    level=logging.INFO,
    format="%(asctime)s | %(name)s | %(levelname)s | %(message)s",
)
logger = logging.getLogger(__name__)

server = FastMCP("my-internal")


@server.tool()
async def list_my_issues(status: str = "open") -> str:
    """Linear에서 내가 담당한 이슈 목록을 가져온다.

    Args:
        status: 이슈 상태 — "open", "in_progress", "done", "all"
    """
    logger.info(f"list_my_issues 호출: status={status}")
    issues = await fetch_linear_issues(assignee="me", status=status)

    if not issues:
        return f"미해결 이슈가 없어요. (status={status})"

    lines = [f"내가 담당한 {status} 이슈 {len(issues)}개:"]
    for issue in issues:
        lines.append(f"- {issue['identifier']}: {issue['title']}")
    return "\n".join(lines)


@server.tool()
async def get_service_status(service_name: str) -> str:
    """사내 모니터링 시스템에서 서비스 상태를 가져온다.

    Args:
        service_name: 서비스 이름 — "api", "web", "worker" 등
    """
    logger.info(f"get_service_status 호출: service={service_name}")
    return f"{service_name}: healthy (14d 3h 가동)"


# ── 가짜 구현 (실제로는 외부 API 호출) ──
async def fetch_linear_issues(assignee: str, status: str) -> list[dict]:
    await asyncio.sleep(0.1)
    return [
        {"identifier": "PROJ-123", "title": "사용자 인증 버그"},
        {"identifier": "PROJ-145", "title": "대시보드 로딩 속도"},
    ]


if __name__ == "__main__":
    logger.info("MCP server starting (stdio)")
    server.run()
```

`FastMCP`의 `@server.tool()` 데코레이터가 마법을 한다:
1. 함수 시그니처 → JSON Schema 자동 생성
2. docstring → description 추출
3. 함수를 `tools/call` 핸들러에 등록

**9.3에서 본 Pydantic의 마법과 같은 계통**. 함수 하나 정의하면 도구가 된다.

### ⚠️ 가장 큰 함정 — stdout은 JSON-RPC 채널

```python
# ❌ 프로토콜 깨짐 — 클라이언트가 "이게 뭔 JSON이냐" 하고 reject
print("서버 시작됨")

# ✅ OK — stderr 사용
print("서버 시작됨", file=sys.stderr)

# ✅ OK — logging은 기본이 stderr
logging.info("서버 시작됨")
```

**가장 흔한 처음 만드는 사람의 실수**. 디버깅 중 print 한 줄 박았다가 — 클라이언트가 조용히 연결 실패. 왜 안 되는지 모르고 한 시간을 잃는다.

진짜 코드도 **명시적으로 `console.error`** 사용 (`mcp-server/src/index.ts:24`). 클라이언트 측에서 `stderr: 'pipe'`로 서버의 stderr를 별도 처리한다. **stdout은 프로토콜, stderr는 디버그/로그** — 양쪽이 같은 약속을 안다.

## 9.3의 도구 ↔ MCP 도구 — 같은 일, 다른 형식

| | 9.3 미니 도구 | MCP 도구 |
|---|---|---|
| 형식 | Python 클래스 (Tool Protocol) | Python 함수 (`@server.tool()`) |
| 위치 | 같은 프로세스 안에 import | 외부 프로세스 (JSON-RPC 통신) |
| 등록 | `parent_tools.append(tool)` | 설정 파일 + 시작 시 자동 연결 |
| 사용처 | 미니 클로드만 | **어떤 MCP 클라이언트든** |
| 인터페이스 | Tool Protocol (name/description/call) | tools/list + tools/call |

**그런데 모델 입장에서는 같은 것** — 둘 다 도구 목록의 한 줄, 같은 호출 형식, 같은 응답 형식. `create_mcp_tool()`의 변환층이 경계를 지운다.

이게 MCP의 진짜 의미: 9.3에서 만든 **도구 설계의 노하우**가 그대로 **MCP 서버의 함수로 옮겨간다**. 같은 사고방식, 같은 검증, 같은 스키마. 형식만 바꾸면 — **어떤 LLM 클라이언트에서든** 쓸 수 있는 재사용 가능한 도구가 된다.

## 진짜 코드에서는 — production 디테일

<details><summary>🔬 Deep Dive — 진짜 MCP 클라이언트의 복잡성</summary>

우리의 70줄짜리 클라이언트와 진짜 `client.ts`의 차이:

| 관심사 | 미니 클로드 | 진짜 코드 |
|---|---|---|
| 전송 | stdio만 | stdio, SSE, HTTP, WebSocket |
| 인증 | 없음 | OAuth 2.0 + session ingress JWT |
| 캐시 | 없음 | `memoizeWithLRU` (연결 + 도구 목록) |
| timeout | 없음 | `Promise.race` + 30초 progress 로깅 |
| 에러 | 기본 | retry + graceful disconnect + reconnect |
| 도구 변환 | `create_mcp_tool()` | `MCPTool` spread (47필드) |

**`client.callTool()` 한 메서드 호출이 추상화의 완성** (`client.ts:3091`):

:::tabs

```typescript
const result = await Promise.race([
  client.callTool(
    { name: tool, arguments: args, _meta: meta },
    CallToolResultSchema,
    { signal, timeout: timeoutMs, onprogress: ... },
  ),
  timeoutPromise,
])
```

```python
# Python 등가 — asyncio.wait_for로 외부 timeout (SDK 내부 timeout 백업)
import asyncio

result = await asyncio.wait_for(
    client.call_tool(
        {"name": tool, "arguments": args, "_meta": meta},
        timeout=timeout_ms / 1000,
        on_progress=...,
    ),
    timeout=timeout_ms / 1000 + 1,  # 외부 timeout이 살짝 더 길게
)
# SSE stream이 깨질 때 SDK 내부 timeout이 안 걸리는 버그 — 외부에서 한 번 더
```

:::

SDK의 내부 timeout이 SSE stream 깨질 때 동작 안 하는 production 버그를 발견해서, 외부에서 `Promise.race`로 한 번 더 timeout을 건다. **추상화에 의존하되 그 한계도 안다**.

**풀 네임 규칙**: `buildMcpToolName(client.name, tool.name)` → `mcp__my-internal__list_my_issues`. 언더스코어 두 개(`__`)가 서버명과 도구명의 구분자. 권한 규칙에서 `mcp__my-internal__*` 와일드카드로 서버 단위 허용이 가능하다.

**`readOnlyHint` 어노테이션**: MCP 서버가 `annotations: { readOnlyHint: true }`를 보내면 — 클라이언트가 해당 도구를 읽기 전용으로 분류해서 권한 자동 허용 가능. 우리의 `is_read_only() → False` (fail-closed)를 서버가 override할 수 있는 메커니즘.

## 핵심 정리

- **MCP는 두 메서드**: `tools/list` (도구 목록 요청)와 `tools/call` (도구 실행). 전송(stdio/HTTP/SSE)은 그 위의 계층. 미니 클로드는 stdio — 가장 단순하고 가장 흔한 형식.
- **MCP 클라이언트 구현 핵심 4단계**: ① 프로세스 spawn + reader task 시작 + initialize 핸드셰이크, ② `_read_loop` 가 stdout 흡수 → `id` 별 `Queue` 에 `put`, ③ `tools/list`로 목록 가져오기, ④ `tools/call`로 실행. 진짜 코드의 수천 줄이 Python 100줄로 압축된다.
- **비동기 RPC 의 표준 패턴**: reader task + `Queue` map + `id` dispatch. notification 이 응답보다 먼저 와도 안 밀리고, 동시에 여러 요청 in-flight 가능. _DB 드라이버, WebSocket 클라이언트, gRPC_ 에서 반복적으로 나오는 모양 — MCP 가 한 번 더 보여준 자리.
- **`create_mcp_tool()`이 경계를 지운다**: 외부 서버의 도구 정의를 9.3 Tool Protocol 객체로 감싼다. `parent_tools.append(mcp_tool)` 한 줄로 풀에 합류. **모델은 내장 도구와 MCP 도구의 차이를 모른다**.
- ⚠️ **stdout은 JSON-RPC 채널**: MCP 서버에서 `print()`하면 프로토콜이 깨진다. 모든 출력은 stderr로. `logging.basicConfig(stream=sys.stderr, ...)`가 서버 코드의 첫 줄이어야 한다.
- **FastMCP 데코레이터**: `@server.tool()` + 함수 시그니처 + docstring = 도구 정의 완성. 9.3의 Pydantic 마법과 같은 계통 — 함수 하나 정의하면 도구가 된다.
- **9.3의 도구 설계 노하우가 MCP로 그대로 옮겨간다**: 같은 사고방식(입력 검증, 에러 메시지, 읽기 전용 분류), 같은 스키마(JSON Schema). 형식만 바꾸면 어떤 LLM 클라이언트에서든 쓸 수 있는 재사용 가능한 도구.
- **설정 파일 한 줄로 도구 추가**: 미니 클로드 코드를 고치지 않고 외부 스크립트만으로 확장. 이것이 MCP의 진짜 가치 — **도구 생태계의 분리와 재사용**.
