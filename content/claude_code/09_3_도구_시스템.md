- **Pydantic 모델** 한 클래스가 **입력 검증 + JSONSchema + 타입 힌트**를 모두 한 번에 주는 마법

## 본문

### Pydantic의 마법

진짜 Claude Code는 TypeScript의 `zod`로 도구 입력을 정의한다 (3.3의 `buildTool` 팩토리). 우리는 Python의 `pydantic`으로 같은 일을 한다 — 게다가 훨씬 적은 줄로.

```python
from pydantic import BaseModel, Field


class ReadInput(BaseModel):
    file_path: str = Field(
        ...,
        description="The absolute or relative path to the file to read.",
    )


# 마법: 한 줄로 JSONSchema 생성
print(ReadInput.model_json_schema())
# {
#   'properties': {
#     'file_path': {
#       'description': 'The absolute or relative path to the file to read.',
#       'title': 'File Path',
#       'type': 'string'
#     }
#   },
#   'required': ['file_path'],
#   'title': 'ReadInput',
#   'type': 'object'
# }
```

**`model_json_schema()` 한 메서드**가 **Anthropic API가 받는 정확한 형식**을 만들어낸다. 우리가 직접 dict를 손으로 짤 일이 없다.

게다가 공짜로 입력 검증까지 따라온다.

```python
ReadInput.model_validate({"file_path": "/etc/passwd"})  # ✅ OK
ReadInput.model_validate({"file_path": 42})              # ❌ ValidationError: int은 str 아님
ReadInput.model_validate({})                             # ❌ ValidationError: file_path required
```

진짜 Claude Code의 `validateInput` 메서드(3.4에서 본 것)가 **Pydantic 한 줄**로 끝난다. **이게 KISS의 정신** — 언어 생태계가 이미 잘 푼 문제는 그 위에 올라간다. 새로 짜지 않는다.

> 💡 **`Field(...)`의 첫 인자.** Ellipsis(`...`)는 **required**라는 뜻. 기본값을 안 주는 필드. `Field(default=None, ...)`처럼 기본값을 주면 **optional**이 된다. `Field(description=...)`의 description은 모델한테 보이는 자연어 힌트 — Anthropic API가 도구 호출을 결정할 때 이걸 읽는다. 그래서 좋은 description이 좋은 도구 사용으로 이어진다.

### Tool Protocol 정식화

9.1/9.2의 stub Tool Protocol을 살을 붙여 정식화한다. 3.2에서 본 47개 필드를 5개로 압축.

```python
# src/mini_claude/tools/base.py
from __future__ import annotations
from dataclasses import dataclass
from typing import Any, Protocol, runtime_checkable
from pydantic import BaseModel


@dataclass
class ToolContext:
    """도구 실행 시 주변 컨텍스트. 8.2의 ToolUseContext의 극단적 미니."""
    cwd: str
    # 9.4에서 permissions 추가


@runtime_checkable
class Tool(Protocol):
    """5개로 압축된 Tool 인터페이스. 3.2의 47개를 정신적으로 회수."""
    
    # ── 정적 메타 ────────────────
    name: str               # 도구 이름 (Anthropic API한테 보이는)
    description: str        # 모델한테 보이는 자연어 설명
    input_model: type[BaseModel]  # Pydantic 모델 = 스키마 + 검증
    
    # ── 메서드 ────────────────
    async def call(self, args: dict[str, Any], context: ToolContext) -> str:
        """실제 동작. 결과는 문자열 (Anthropic API가 받는 형식)."""
        ...
    
    def is_read_only(self) -> bool:
        """Fail-safe 기본값: 모르면 False (위험하다고 가정).
        
        9.4의 권한 시스템과 9.5의 병렬 실행 결정에 사용.
        """
        ...
    
    def is_destructive(self) -> bool:
        """파일을 지우거나 덮어쓸 수 있는가? 모르면 True."""
        ...


def find_tool(tools: list[Tool], name: str) -> Tool:
    """이름으로 도구 찾기."""
    for t in tools:
        if t.name == name:
            return t
    raise ValueError(f"Unknown tool: {name}")


def tool_to_anthropic_schema(tool: Tool) -> dict[str, Any]:
    """Pydantic → Anthropic API 도구 스키마 변환."""
    return {
        "name": tool.name,
        "description": tool.description,
        "input_schema": tool.input_model.model_json_schema(),
    }
```

3.2의 47개 필드와 비교해 어떤 것을 남기고 어떤 것을 뺐는지 보자.

| 3.2의 필드 | 9.3에서 | 이유 |
|---|---|---|
| `name`, `description` | ✅ 남김 | 본질 |
| `inputJSONSchema` | ✅ `input_model`로 대체 | Pydantic이 공짜로 만듦 |
| `call` | ✅ 남김 | 본질 |
| `validateInput` | ✅ Pydantic이 대체 | `model_validate` 한 줄 |
| `checkPermissions` | 🔁 9.4 분리 | 권한은 별도 챕터 |
| `isConcurrencySafe`, `isReadOnly` | ✅ `is_read_only` 한 개로 합침 | 9.5에서 사용 |
| `isDestructive` | ✅ 남김 | 9.4 권한 휴리스틱 |
| `isOpenWorld`, `searchHint`, `alwaysLoad` | ❌ OUT | 미니에서 의미 없음 |
| `prompt`, `userFacingName`, `renderToolUseMessage`, `renderToolResultMessage`, … | ❌ OUT | UI 없음 (5장 OUT) |
| `toAutoClassifierInput` | ❌ OUT | 자동 분류기 없음 |
| `mcpInfo`, `isMcp` | ❌ OUT | MCP 없음 (7.2 OUT) |
| `getPath`, `isReadOnlyByInput` | ❌ OUT | 동적 결정 없음 |

**5개로 압축**(name, description, input_model, call, is_read_only/is_destructive). 47 → 5. 90%가 살이고 10%가 본질. 우리가 만드는 건 그 10%.

### ReadTool — 한 페이지로 끝

가장 단순한 도구. 3.4에서 본 진짜 FileReadTool은 수백 줄이지만 — 핵심은 세 단계다 (3.4의 보석): **검증 → 권한 → 실행**. 미니에서는 권한 단계가 9.4에서 별도라 2단계.

```python
# src/mini_claude/tools/read.py
from __future__ import annotations
from pathlib import Path
from typing import Any
from pydantic import BaseModel, Field
from .base import ToolContext


class ReadInput(BaseModel):
    file_path: str = Field(
        ...,
        description="The absolute or relative path to the file to read.",
    )


class ReadTool:
    name = "Read"
    description = (
        "Read the contents of a file from disk. Returns the full text. "
        "Use this when you need to see the actual content of a file."
    )
    input_model = ReadInput
    
    def is_read_only(self) -> bool:
        return True
    
    def is_destructive(self) -> bool:
        return False
    
    async def call(self, args: dict[str, Any], context: ToolContext) -> str:
        # ① 검증 — Pydantic이 한다
        validated = ReadInput.model_validate(args)
        
        # ② 경로 해석 — 상대 경로면 cwd 기준
        path = Path(validated.file_path)
        if not path.is_absolute():
            path = Path(context.cwd) / path
        path = path.resolve()
        
        # ③ 존재 확인
        if not path.exists():
            return f"Error: File not found: {path}"
        if not path.is_file():
            return f"Error: Not a file: {path}"
        
        # ④ 읽기
        try:
            return path.read_text(encoding="utf-8")
        except UnicodeDecodeError:
            return f"Error: File is not UTF-8: {path}"
```

40줄 안 된다. **이게 진짜 동작하는 ReadTool**. 진짜 Claude Code의 보석 몇 가지는 일부러 생략했다.

| 진짜 FileReadTool | 미니 | 이유 |
|---|---|---|
| UNC NTLM 자격 증명 누수 차단 | ❌ | Windows 전용 + 보안 깊이 — KISS |
| 부분 view 추적 (`isPartialView`) | ❌ | Edit 도구 없음 — 필요 없음 |
| 큰 파일 청킹 (`offset`, `limit`) | ❌ | 컨텍스트 압축 없음 — 그냥 다 읽음 |
| 이미지/PDF/Jupyter 처리 | ❌ | 멀티모달 없음 |
| `readFileState` 캐싱 | ❌ | 캐시 없음 — 매번 디스크 |

뺀 것마다 보석을 잃는다. 그러나 이 미니가 80%의 시나리오를 동작시킨다는 사실은 변하지 않는다. 나머지 20%는 당신이 직접 추가할 자리 — Part 10에서 본격적으로 다룬다.

### WriteTool — 부모 디렉토리 보장

```python
# src/mini_claude/tools/write.py
from __future__ import annotations
from pathlib import Path
from typing import Any
from pydantic import BaseModel, Field
from .base import ToolContext


class WriteInput(BaseModel):
    file_path: str = Field(
        ...,
        description="The absolute or relative path to write to.",
    )
    content: str = Field(
        ...,
        description="The full text content to write. Overwrites existing files.",
    )


class WriteTool:
    name = "Write"
    description = (
        "Write text content to a file, creating it if necessary. "
        "Overwrites existing files. Creates parent directories if needed."
    )
    input_model = WriteInput
    
    def is_read_only(self) -> bool:
        return False
    
    def is_destructive(self) -> bool:
        return True  # 덮어쓰기 가능
    
    async def call(self, args: dict[str, Any], context: ToolContext) -> str:
        validated = WriteInput.model_validate(args)
        
        path = Path(validated.file_path)
        if not path.is_absolute():
            path = Path(context.cwd) / path
        path = path.resolve()
        
        # 부모 디렉토리 보장 — 없으면 생성
        path.parent.mkdir(parents=True, exist_ok=True)
        
        # 쓰기
        try:
            path.write_text(validated.content, encoding="utf-8")
        except OSError as e:
            return f"Error: Failed to write {path}: {e}"
        
        line_count = validated.content.count("\n") + 1
        return f"Wrote {len(validated.content)} chars ({line_count} lines) to {path}"
```

**ReadTool보다 한 단계** 더 위험하다. `is_destructive() → True`. 9.4에서 권한 시스템이 이걸 **기본 deny**로 처리할 것이다 — 사용자한테 물어본 후에만 실행.

진짜 Claude Code의 `Write`는 훨씬 더 많은 안전 장치를 갖는다.
- **Read 전에는 Write 못함** (사용자가 의도치 않게 덮어쓰는 사고 방지) — 미니에서 OUT
- 디스크 변경 감지 — 외부 편집을 덮어쓰면 경고 — 미니에서 OUT
- 백업 만들기 — 미니에서 OUT
- 디렉토리 분리 권한 — 미니에서 OUT

**미니의 Write는 위험하다**. 9.4의 권한 시스템이 그래서 필요한 것이다.

### BashTool — 가장 복잡

3.5의 BashTool은 1,144줄. 우리는 60줄.

```python
# src/mini_claude/tools/bash.py
from __future__ import annotations
import asyncio
from typing import Any
from pydantic import BaseModel, Field
from .base import ToolContext


# 기본 타임아웃 — 진짜 Claude Code는 2분, 우리도 같음
DEFAULT_TIMEOUT_SEC = 120
MAX_OUTPUT_BYTES = 64 * 1024  # 64KB로 자름


class BashInput(BaseModel):
    command: str = Field(
        ...,
        description="The shell command to execute.",
    )
    timeout_sec: int | None = Field(
        default=None,
        description=f"Timeout in seconds (default: {DEFAULT_TIMEOUT_SEC}).",
    )


class BashTool:
    name = "Bash"
    description = (
        "Execute a shell command. Returns combined stdout/stderr. "
        f"Default timeout {DEFAULT_TIMEOUT_SEC}s, output capped at {MAX_OUTPUT_BYTES // 1024}KB."
    )
    input_model = BashInput
    
    def is_read_only(self) -> bool:
        # Fail-safe: 명령어 분석 안 함, 그냥 위험하다고 가정
        return False
    
    def is_destructive(self) -> bool:
        return True
    
    async def call(self, args: dict[str, Any], context: ToolContext) -> str:
        validated = BashInput.model_validate(args)
        timeout = validated.timeout_sec or DEFAULT_TIMEOUT_SEC
        
        # asyncio subprocess — shell=True로 한 명령
        proc = await asyncio.create_subprocess_shell(
            validated.command,
            stdout=asyncio.subprocess.PIPE,
            stderr=asyncio.subprocess.STDOUT,  # stderr를 stdout에 합침
            cwd=context.cwd,
        )
        
        try:
            stdout_bytes, _ = await asyncio.wait_for(
                proc.communicate(),
                timeout=timeout,
            )
        except asyncio.TimeoutError:
            proc.kill()
            await proc.wait()
            return f"Error: Command timed out after {timeout}s"
        
        # 출력 자르기
        truncated = ""
        if len(stdout_bytes) > MAX_OUTPUT_BYTES:
            stdout_bytes = stdout_bytes[:MAX_OUTPUT_BYTES]
            truncated = f"\n[Output truncated to {MAX_OUTPUT_BYTES} bytes]"
        
        output = stdout_bytes.decode("utf-8", errors="replace") + truncated
        
        if proc.returncode != 0:
            return f"Exit code: {proc.returncode}\n{output}"
        
        return output if output else "(no output)"
```

3.5에서 본 **진짜 BashTool의 보석들** — `preparePermissionMatcher`, `MAX_SUBCOMMANDS_FOR_SECURITY_CHECK = 50`, tree-sitter 합성 명령 분해 — **전부 OUT**. 미니의 BashTool은 **그냥 명령을 실행한다**. 안전 검사 없음. **위험하다**.

그래서 9.4의 권한 시스템이 결정적이다 — `BashTool.is_read_only() → False`가 권한 시스템한테 "이거 묻고 실행해"라고 알린다. **Fail-safe by default**.

**timeout도 한 층 더 정교하다**. 진짜 Claude Code의 `utils/timeouts.ts`는 `DEFAULT_TIMEOUT_MS = 120_000` (2분) 외에도 `MAX_TIMEOUT_MS = 600_000` (10분 cap)을 둔다 — 사용자가 **아주 큰 timeout을 요청해도 10분에서 잘린다**. 그리고 둘 다 환경 변수 (`BASH_DEFAULT_TIMEOUT_MS`, `BASH_MAX_TIMEOUT_MS`)로 오버라이드 가능 — 프로덕션이 빌드 없이 튜닝할 수 있게. 미니는 **cap도 없고 env도 없음**. 사용자가 `timeout_sec=99999`를 요청하면 그대로 받아준다. **MAX cap 한 줄을 추가하는 것이 우리의 다음 자연스러운 진화 방향**.

> 💡 **`shell=True`의 위험과 미니의 입장.** 일반적으로 `subprocess.run(cmd, shell=True)` 는 명령 주입 위험 때문에 권장되지 않는다. 사용자 입력을 그대로 shell에 넣으면 임의 명령 실행. 그런데 BashTool의 목적 자체가 임의 명령 실행이다 — 정상 사용에서도 `cd /tmp && ls -la | grep foo` 같은 합성 명령을 받아야 한다. 그래서 **반드시 `shell=True`**. 안전성은 **호출자(권한 시스템)**한테 미룬다. **임의 명령 실행 도구의 자연스러운 책임 분리**.

### 진짜로 돌려보기

```bash
$ mkdir -p /tmp/play && cd /tmp/play
$ uv run mini-claude
mini-claude 시작 (Ctrl+D로 종료)
> hello.py 라는 파일을 만들어서 print('hello world') 한 줄을 넣어줘

[Write] {'file_path': 'hello.py', 'content': "print('hello world')\n"}
hello.py 파일을 만들었어. 21자, 2줄.

> 그 파일을 실행해줘

[Bash] {'command': 'python hello.py'}
hello world

라고 출력되었어.

> hello.py 를 다시 읽어서 print 안의 문자열을 'goodbye, mini' 로 바꾸고 다시 써줘

[Read] {'file_path': 'hello.py'}
[Write] {'file_path': 'hello.py', 'content': "print('goodbye, mini')\n"}
hello.py 의 print 문자열을 바꿨어.

> 다시 실행

```

**5분 만에 진짜로 사용 가능한 미니 Claude Code**. 한 턴 안에 **Read → Write** 같은 연쇄 도구 호출도 자연스럽게 작동한다 — 9.2의 `while True:` 루프가 알아서 처리.

**근데 위험하다**. **Write** 도, **Bash** 도, 사용자한테 한 번도 안 묻고 실행된다. Claude가 "`rm -rf ~` 좀 실행해줘" 같은 걸 받아도 그대로 실행. 9.4에서 **권한 시스템**이 그걸 막는다.

---

## 핵심 정리

- **Pydantic 모델 한 클래스**가 **입력 검증 + JSONSchema + 타입 힌트**를 한 번에. `model_json_schema()` 한 메서드가 Anthropic API가 받는 형식을 그대로 만들어준다. 진짜 Claude Code의 `validateInput` 메서드가 **Pydantic 한 줄**로 끝남. **언어 생태계가 이미 잘 푼 문제는 그 위에 올라간다 — KISS의 정신**.
- **3.2의 47개 필드 → 5개**: `name`, `description`, `input_model`, `call`, `is_read_only`/`is_destructive`. 90%가 살, 10%가 본질. 우리는 그 10%를 만든다.
- **3개 도구의 복잡도 등급**: ReadTool(40줄, 읽기 전용) → WriteTool(50줄, 덮어쓰기 가능) → BashTool(60줄, 임의 명령). 위로 갈수록 위험.
- **ReadTool의 2단계**: 검증 → 실행. 진짜 FileReadTool의 UNC NTLM 차단, 부분 view, 청킹, 멀티모달은 **전부 OUT**. 우리는 80% 시나리오를 위해 짠다.
- **WriteTool의 부모 디렉토리 보장**. 진짜 Write의 Read-before-Write 강제, 외부 편집 감지, 백업 등은 OUT. **미니의 Write는 위험하다 — 9.4의 권한 시스템이 그래서 필요**.
- **BashTool의 60줄 미니멀** — `asyncio.create_subprocess_shell` + 타임아웃 + 출력 자르기. 3.5의 `preparePermissionMatcher`, 50 서브명령 보안 검사, tree-sitter 합성 명령 분해는 **전부 OUT**. **미니는 그저 명령을 실행한다 — 안전성은 권한 시스템 책임**.
- **`is_read_only`, `is_destructive`는 Fail-safe 기본값**. 모르면 위험하다고 가정. 9.4의 권한 휴리스틱과 9.5의 병렬 실행 결정에 사용.
- **`agent.py` 한 줄만 변경**. `tools=[tool_to_anthropic_schema(t) for t in tools]`. 골격이 잘 잡혀 있어서 9.2의 다른 코드는 한 줄도 안 바뀐다. **인터페이스의 힘**.
- **이 챕터의 결과물**: 진짜 파일을 읽고 쓰고 명령을 실행하는 mini-claude. 실용적. 그러나 위험. 9.4의 권한 체크가 반드시 필요한 이유.
