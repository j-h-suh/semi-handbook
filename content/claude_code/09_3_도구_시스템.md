# 9.3 도구 시스템 — Read, Write, Bash, Edit + Pydantic 스키마

---

## 이 챕터에서 배우는 것

- **Pydantic 모델** 한 클래스가 **입력 검증 + JSONSchema + 타입 힌트**를 모두 한 번에 주는 마법
- 3.2의 **47개 필드 Tool 인터페이스**를 5개로 압축하면서도 본질을 잃지 않는 법
- 4개 도구의 복잡도 그라디언트: ReadTool(단순) → WriteTool(중간) → BashTool(복잡) → EditTool(복잡+상태)
- 3.4의 **UNC NTLM 사고**나 3.5의 50 서브명령 보안을 미니에서 어디까지 흉내내고 어디서 멈출지
- **Edit 도구의 설계 철학** — 정규식 대신 정확 매칭, Read-before-Edit 강제, 에러 메시지가 모델을 가이드하는 디자인
- 9.3 끝의 결과물: 진짜 파일을 읽고 쓰고 편집하고 명령을 실행하는 mini-claude

## 사용자 경험에서 출발

9.2 끝에서 우리는 `EchoTool` 하나로 루프가 동작한다는 사실을 확인했다. 실용적이지는 않다 — 입력을 그대로 돌려주는 도구로 뭘 하겠는가.

이번 장 끝에서는:

```bash
$ uv run mini-claude
> /tmp/hello.txt 에 "Hello, mini-claude!" 라고 써줘

[Write] {'file_path': '/tmp/hello.txt', 'content': 'Hello, mini-claude!'}
파일을 작성했어. 19자, 1줄.

> 그 파일을 다시 읽어서 보여줘

[Read] {'file_path': '/tmp/hello.txt'}
파일 내용은 "Hello, mini-claude!" 야.

> "Hello"를 "Goodbye"로 바꿔줘

[Edit] {'file_path': '/tmp/hello.txt', 'old_string': 'Hello', 'new_string': 'Goodbye'}
수정 완료. "Hello" → "Goodbye".

> 그 파일을 wc -c 로 글자 수 세어줘

[Bash] {'command': 'wc -c /tmp/hello.txt'}
21자야 (개행 포함).
```

9.1에서 도구는 세 개라고 했다 — Read, Write, Bash. Edit/Glob/Grep은 Bash로 우회한다고. **그 판단의 80%는 맞다**. `grep`은 `Bash(grep -rn ...)` 로, `find`는 `Bash(find . -name ...)` 로 충분히 우회 가능하다.

**Edit은 다르다**. 왜 Bash(`sed`)로 우회가 안 되느냐면 — `sed`의 정규식을 LLM이 정확하게 생성한다는 보장이 없기 때문이다. 특수문자 이스케이프를 한 번이라도 빠뜨리면 파일이 깨진다. 그리고 **전체 파일을 Write로 덮어쓰는 것**은 더 위험하다 — 300줄짜리 파일에서 한 줄만 바꾸려고 300줄을 다시 생성하면, 나머지 299줄에서 hallucination이 발생할 확률이 급격히 올라간다.

진짜 Claude Code가 Edit 도구를 별도로 두는 이유가 정확히 이거다. **정확 문자열 매칭**으로 바꿀 부분만 콕 짚어서 바꾼다. 나머지는 건드리지 않는다. 미니에서도 이 도구는 필요하다.

## 본문

### Pydantic의 마법

진짜 Claude Code는 TypeScript의 `zod`로 도구 입력을 정의한다 (3.3의 `buildTool` 팩토리). 우리는 Python의 `pydantic`으로 같은 일을 한다 — 게다가 훨씬 적은 줄로.

```python
from pydantic import BaseModel, Field


class ReadInput(BaseModel):
    file_path: str = Field(
        ...,
        description="The absolute or relative path to the file to read.",
    )


# 마법: 한 줄로 JSONSchema 생성
print(ReadInput.model_json_schema())
# {
#   'properties': {
#     'file_path': {
#       'description': 'The absolute or relative path to the file to read.',
#       'title': 'File Path',
#       'type': 'string'
#     }
#   },
#   'required': ['file_path'],
#   'title': 'ReadInput',
#   'type': 'object'
# }
```

**`model_json_schema()` 한 메서드**가 **Anthropic API가 받는 정확한 형식**을 만들어낸다. 우리가 직접 dict를 손으로 짤 일이 없다.

게다가 공짜로 입력 검증까지 따라온다.

```python
ReadInput.model_validate({"file_path": "/etc/passwd"})  # ✅ OK
ReadInput.model_validate({"file_path": 42})              # ❌ ValidationError: int은 str 아님
ReadInput.model_validate({})                             # ❌ ValidationError: file_path required
```

진짜 Claude Code의 `validateInput` 메서드(3.4에서 본 것)가 **Pydantic 한 줄**로 끝난다. **이게 KISS의 정신** — 언어 생태계가 이미 잘 푼 문제는 그 위에 올라간다. 새로 짜지 않는다.

> 💡 **`Field(...)`의 첫 인자.** Ellipsis(`...`)는 **required**라는 뜻. 기본값을 안 주는 필드. `Field(default=None, ...)`처럼 기본값을 주면 **optional**이 된다. `Field(description=...)`의 description은 모델한테 보이는 자연어 힌트 — Anthropic API가 도구 호출을 결정할 때 이걸 읽는다. 그래서 좋은 description이 좋은 도구 사용으로 이어진다.

### Tool Protocol 정식화

9.1/9.2의 stub Tool Protocol을 살을 붙여 정식화한다. 3.2에서 본 47개 필드를 5개로 압축.

```python
# src/mini_claude/tools/base.py
from __future__ import annotations
from dataclasses import dataclass
from typing import Any, Protocol, runtime_checkable
from pydantic import BaseModel


@dataclass
class ToolContext:
    """도구 실행 시 주변 컨텍스트. 8.2의 ToolUseContext의 극단적 미니."""
    cwd: str
    # 9.4에서 permissions 추가


@runtime_checkable
class Tool(Protocol):
    """5개로 압축된 Tool 인터페이스. 3.2의 47개를 정신적으로 회수."""
    
    # ── 정적 메타 ────────────────
    name: str               # 도구 이름 (Anthropic API한테 보이는)
    description: str        # 모델한테 보이는 자연어 설명
    input_model: type[BaseModel]  # Pydantic 모델 = 스키마 + 검증
    
    # ── 메서드 ────────────────
    async def call(self, args: dict[str, Any], context: ToolContext) -> str:
        """실제 동작. 결과는 문자열 (Anthropic API가 받는 형식)."""
        ...
    
    def is_read_only(self) -> bool:
        """Fail-safe 기본값: 모르면 False (위험하다고 가정).
        
        9.4의 권한 시스템과 9.5의 병렬 실행 결정에 사용.
        """
        ...
    
    def is_destructive(self) -> bool:
        """파일을 지우거나 덮어쓸 수 있는가? 모르면 True."""
        ...


def find_tool(tools: list[Tool], name: str) -> Tool:
    """이름으로 도구 찾기."""
    for t in tools:
        if t.name == name:
            return t
    raise ValueError(f"Unknown tool: {name}")


def tool_to_anthropic_schema(tool: Tool) -> dict[str, Any]:
    """Pydantic → Anthropic API 도구 스키마 변환."""
    return {
        "name": tool.name,
        "description": tool.description,
        "input_schema": tool.input_model.model_json_schema(),
    }
```

3.2의 47개 필드와 비교해 어떤 것을 남기고 어떤 것을 뺐는지 보자.

| 3.2의 필드 | 9.3에서 | 이유 |
|---|---|---|
| `name`, `description` | ✅ 남김 | 본질 |
| `inputJSONSchema` | ✅ `input_model`로 대체 | Pydantic이 공짜로 만듦 |
| `call` | ✅ 남김 | 본질 |
| `validateInput` | ✅ Pydantic이 대체 | `model_validate` 한 줄 |
| `checkPermissions` | 🔁 9.4 분리 | 권한은 별도 챕터 |
| `isConcurrencySafe`, `isReadOnly` | ✅ `is_read_only` 한 개로 합침 | 9.5에서 사용 |
| `isDestructive` | ✅ 남김 | 9.4 권한 휴리스틱 |
| `isOpenWorld`, `searchHint`, `alwaysLoad` | ❌ OUT | 미니에서 의미 없음 |
| `prompt`, `userFacingName`, `renderToolUseMessage`, `renderToolResultMessage`, … | ❌ OUT | UI 없음 (5장 OUT) |
| `toAutoClassifierInput` | ❌ OUT | 자동 분류기 없음 |
| `mcpInfo`, `isMcp` | ❌ OUT | MCP 없음 (7.2 OUT) |
| `getPath`, `isReadOnlyByInput` | ❌ OUT | 동적 결정 없음 |

**5개로 압축**(name, description, input_model, call, is_read_only/is_destructive). 47 → 5. 90%가 살이고 10%가 본질. 우리가 만드는 건 그 10%.

### ReadTool — 한 페이지로 끝

가장 단순한 도구. 3.4에서 본 진짜 FileReadTool은 수백 줄이지만 — 핵심은 세 단계다 (3.4의 보석): **검증 → 권한 → 실행**. 미니에서는 권한 단계가 9.4에서 별도라 2단계.

```python
# src/mini_claude/tools/read.py
from __future__ import annotations
from pathlib import Path
from typing import Any
from pydantic import BaseModel, Field
from .base import ToolContext


class ReadInput(BaseModel):
    file_path: str = Field(
        ...,
        description="The absolute or relative path to the file to read.",
    )


class ReadTool:
    name = "Read"
    description = (
        "Read the contents of a file from disk. Returns the full text. "
        "Use this when you need to see the actual content of a file."
    )
    input_model = ReadInput
    
    def is_read_only(self) -> bool:
        return True
    
    def is_destructive(self) -> bool:
        return False
    
    async def call(self, args: dict[str, Any], context: ToolContext) -> str:
        # ① 검증 — Pydantic이 한다
        validated = ReadInput.model_validate(args)
        
        # ② 경로 해석 — 상대 경로면 cwd 기준
        path = Path(validated.file_path)
        if not path.is_absolute():
            path = Path(context.cwd) / path
        path = path.resolve()
        
        # ③ 존재 확인
        if not path.exists():
            return f"Error: File not found: {path}"
        if not path.is_file():
            return f"Error: Not a file: {path}"
        
        # ④ 읽기
        try:
            text = path.read_text(encoding="utf-8")
        except UnicodeDecodeError:
            return f"Error: File is not UTF-8: {path}"
        
        # ⑤ 읽은 파일 등록 — EditTool의 Read-before-Edit 게이트에 사용
        context.read_files.add(str(path))
        return text
```

40줄 안 된다. **이게 진짜 동작하는 ReadTool**. 마지막 줄의 `context.read_files.add(str(path))`가 EditTool과의 접점이다 — 이 한 줄이 "이 파일은 이미 읽었다"는 상태를 기록한다. 진짜 Claude Code에서는 `FileReadTool.ts`가 `readFileState.set()`을 호출하는 것과 같은 역할.

| 진짜 FileReadTool | 미니 | 이유 |
|---|---|---|
| UNC NTLM 자격 증명 누수 차단 | ❌ | Windows 전용 + 보안 깊이 — KISS |
| 부분 view 추적 (`isPartialView`) | ❌ | 부분 읽기 없음 — 항상 전체 읽기 |
| 큰 파일 청킹 (`offset`, `limit`) | ❌ | 컨텍스트 압축 없음 — 그냥 다 읽음 |
| 이미지/PDF/Jupyter 처리 | ❌ | 멀티모달 없음 |
| `readFileState` 전체 (timestamp, content, isPartialView) | `set[str]`만 | 존재 여부만 — 타임스탬프/내용 비교 OUT |

뺀 것마다 보석을 잃는다. 그러나 이 미니가 80%의 시나리오를 동작시킨다는 사실은 변하지 않는다. 나머지 20%는 당신이 직접 추가할 자리 — Part 10에서 본격적으로 다룬다.

### WriteTool — 부모 디렉토리 보장

```python
# src/mini_claude/tools/write.py
from __future__ import annotations
from pathlib import Path
from typing import Any
from pydantic import BaseModel, Field
from .base import ToolContext


class WriteInput(BaseModel):
    file_path: str = Field(
        ...,
        description="The absolute or relative path to write to.",
    )
    content: str = Field(
        ...,
        description="The full text content to write. Overwrites existing files.",
    )


class WriteTool:
    name = "Write"
    description = (
        "Write text content to a file, creating it if necessary. "
        "Overwrites existing files. Creates parent directories if needed."
    )
    input_model = WriteInput
    
    def is_read_only(self) -> bool:
        return False
    
    def is_destructive(self) -> bool:
        return True  # 덮어쓰기 가능
    
    async def call(self, args: dict[str, Any], context: ToolContext) -> str:
        validated = WriteInput.model_validate(args)
        
        path = Path(validated.file_path)
        if not path.is_absolute():
            path = Path(context.cwd) / path
        path = path.resolve()
        
        # 부모 디렉토리 보장 — 없으면 생성
        path.parent.mkdir(parents=True, exist_ok=True)
        
        # 쓰기
        try:
            path.write_text(validated.content, encoding="utf-8")
        except OSError as e:
            return f"Error: Failed to write {path}: {e}"
        
        line_count = validated.content.count("\n") + 1
        return f"Wrote {len(validated.content)} chars ({line_count} lines) to {path}"
```

**ReadTool보다 한 단계** 더 위험하다. `is_destructive() → True`. 9.4에서 권한 시스템이 이걸 **기본 deny**로 처리할 것이다 — 사용자한테 물어본 후에만 실행.

진짜 Claude Code의 `Write`는 훨씬 더 많은 안전 장치를 갖는다.
- **Read 전에는 Write 못함** (사용자가 의도치 않게 덮어쓰는 사고 방지) — 미니에서 OUT
- 디스크 변경 감지 — 외부 편집을 덮어쓰면 경고 — 미니에서 OUT
- 백업 만들기 — 미니에서 OUT
- 디렉토리 분리 권한 — 미니에서 OUT

**미니의 Write는 위험하다**. 9.4의 권한 시스템이 그래서 필요한 것이다.

### BashTool — 가장 복잡

3.5의 BashTool은 1,144줄. 우리는 60줄.

```python
# src/mini_claude/tools/bash.py
from __future__ import annotations
import asyncio
from typing import Any
from pydantic import BaseModel, Field
from .base import ToolContext


# 기본 타임아웃 — 진짜 Claude Code는 2분, 우리도 같음
DEFAULT_TIMEOUT_SEC = 120
MAX_OUTPUT_BYTES = 64 * 1024  # 64KB로 자름


class BashInput(BaseModel):
    command: str = Field(
        ...,
        description="The shell command to execute.",
    )
    timeout_sec: int | None = Field(
        default=None,
        description=f"Timeout in seconds (default: {DEFAULT_TIMEOUT_SEC}).",
    )


class BashTool:
    name = "Bash"
    description = (
        "Execute a shell command. Returns combined stdout/stderr. "
        f"Default timeout {DEFAULT_TIMEOUT_SEC}s, output capped at {MAX_OUTPUT_BYTES // 1024}KB."
    )
    input_model = BashInput
    
    def is_read_only(self) -> bool:
        # Fail-safe: 명령어 분석 안 함, 그냥 위험하다고 가정
        return False
    
    def is_destructive(self) -> bool:
        return True
    
    async def call(self, args: dict[str, Any], context: ToolContext) -> str:
        validated = BashInput.model_validate(args)
        timeout = validated.timeout_sec or DEFAULT_TIMEOUT_SEC
        
        # asyncio subprocess — shell=True로 한 명령
        proc = await asyncio.create_subprocess_shell(
            validated.command,
            stdout=asyncio.subprocess.PIPE,
            stderr=asyncio.subprocess.STDOUT,  # stderr를 stdout에 합침
            cwd=context.cwd,
        )
        
        try:
            stdout_bytes, _ = await asyncio.wait_for(
                proc.communicate(),
                timeout=timeout,
            )
        except asyncio.TimeoutError:
            proc.kill()
            await proc.wait()
            return f"Error: Command timed out after {timeout}s"
        
        # 출력 자르기
        truncated = ""
        if len(stdout_bytes) > MAX_OUTPUT_BYTES:
            stdout_bytes = stdout_bytes[:MAX_OUTPUT_BYTES]
            truncated = f"\n[Output truncated to {MAX_OUTPUT_BYTES} bytes]"
        
        output = stdout_bytes.decode("utf-8", errors="replace") + truncated
        
        if proc.returncode != 0:
            return f"Exit code: {proc.returncode}\n{output}"
        
        return output if output else "(no output)"
```

3.5에서 본 **진짜 BashTool의 보석들** — `preparePermissionMatcher`, `MAX_SUBCOMMANDS_FOR_SECURITY_CHECK = 50`, tree-sitter 합성 명령 분해 — **전부 OUT**. 미니의 BashTool은 **그냥 명령을 실행한다**. 안전 검사 없음. **위험하다**.

그래서 9.4의 권한 시스템이 결정적이다 — `BashTool.is_read_only() → False`가 권한 시스템한테 "이거 묻고 실행해"라고 알린다. **Fail-safe by default**.

**timeout도 한 층 더 정교하다**. 진짜 Claude Code의 `utils/timeouts.ts`는 `DEFAULT_TIMEOUT_MS = 120_000` (2분) 외에도 `MAX_TIMEOUT_MS = 600_000` (10분 cap)을 둔다 — 사용자가 **아주 큰 timeout을 요청해도 10분에서 잘린다**. 그리고 둘 다 환경 변수 (`BASH_DEFAULT_TIMEOUT_MS`, `BASH_MAX_TIMEOUT_MS`)로 오버라이드 가능 — 프로덕션이 빌드 없이 튜닝할 수 있게. 미니는 **cap도 없고 env도 없음**. 사용자가 `timeout_sec=99999`를 요청하면 그대로 받아준다. **MAX cap 한 줄을 추가하는 것이 우리의 다음 자연스러운 진화 방향**.

> 💡 **`shell=True`의 위험과 미니의 입장.** 일반적으로 `subprocess.run(cmd, shell=True)` 는 명령 주입 위험 때문에 권장되지 않는다. 사용자 입력을 그대로 shell에 넣으면 임의 명령 실행. 그런데 BashTool의 목적 자체가 임의 명령 실행이다 — 정상 사용에서도 `cd /tmp && ls -la | grep foo` 같은 합성 명령을 받아야 한다. 그래서 **반드시 `shell=True`**. 안전성은 **호출자(권한 시스템)**한테 미룬다. **임의 명령 실행 도구의 자연스러운 책임 분리**.

### EditTool — 상태를 가진 도구

Read, Write, Bash까지는 **stateless**했다. 매 호출이 독립적. 이전에 무슨 도구가 불렸든 상관없이 동작한다.

Edit는 다르다. **"이 파일이 이미 Read된 적이 있는가?"를 기억해야 한다**. 진짜 Claude Code의 `FileEditTool.ts:275`에 이 검사가 있다.

```typescript
// src/tools/FileEditTool/FileEditTool.ts:275
const readTimestamp = toolUseContext.readFileState.get(fullFilePath)
if (!readTimestamp || readTimestamp.isPartialView) {
  return {
    result: false,
    behavior: 'ask',
    message: 'File has not been read yet. Read it first before writing to it.',
    errorCode: 6,
  }
}
```

```python
# Python 등가 — Read-before-Edit 강제 (hallucination 방지)
read_timestamp = tool_use_context.read_file_state.get(full_file_path)
if not read_timestamp or read_timestamp.is_partial_view:
    return {
        "result": False,
        "behavior": "ask",
        "message": "File has not been read yet. Read it first before writing to it.",
        "error_code": 6,
    }
```

왜 이런 제약을 두냐면 — LLM이 파일을 읽지 않고 편집하면, `old_string`을 **기억에서 재구성**한다. 기억은 부정확하다. 이전 대화에서 본 것, 비슷한 프로젝트에서 본 것, 훈련 데이터에서 본 것을 섞는다. **Read 강제가 hallucination을 절반으로 줄인다**. 실제로 파일을 보고 나서야 비로소 정확한 old_string을 쓸 수 있다.

미니의 EditTool. 80줄 안에 핵심 세 가지 — 유일성 검증, Read-before-Edit, replace_all.

```python
# src/mini_claude/tools/edit.py
from __future__ import annotations
from pathlib import Path
from typing import Any
from pydantic import BaseModel, Field
from .base import ToolContext


class EditInput(BaseModel):
    file_path: str = Field(
        ...,
        description="The absolute or relative path to the file to modify.",
    )
    old_string: str = Field(
        ...,
        description="The text to replace (must be unique in the file).",
    )
    new_string: str = Field(
        ...,
        description="The text to replace it with (must differ from old_string).",
    )
    replace_all: bool = Field(
        default=False,
        description="Replace all occurrences of old_string (default false).",
    )


class EditTool:
    name = "Edit"
    description = (
        "Replace exact string occurrences in a file. "
        "The file must have been Read first. "
        "old_string must be unique unless replace_all is true."
    )
    input_model = EditInput
    
    def is_read_only(self) -> bool:
        return False
    
    def is_destructive(self) -> bool:
        return True
    
    async def call(self, args: dict[str, Any], context: ToolContext) -> str:
        validated = EditInput.model_validate(args)
        
        # 경로 해석
        path = Path(validated.file_path)
        if not path.is_absolute():
            path = Path(context.cwd) / path
        path = path.resolve()
        
        # ① Read-before-Edit 강제
        if str(path) not in context.read_files:
            return (
                "Error: File has not been read yet. "
                "Read it first before editing."
            )
        
        # ② 파일 존재 확인
        if not path.exists():
            return f"Error: File not found: {path}"
        
        content = path.read_text(encoding="utf-8")
        
        # ③ old_string == new_string 차단
        if validated.old_string == validated.new_string:
            return "Error: old_string and new_string are the same."
        
        # ④ old_string 존재 확인
        if validated.old_string not in content:
            return (
                f"Error: String to replace not found in file.\n"
                f"String: {validated.old_string}"
            )
        
        # ⑤ 유일성 검증
        match_count = content.count(validated.old_string)
        if match_count > 1 and not validated.replace_all:
            return (
                f"Error: Found {match_count} matches, but replace_all "
                f"is false. Provide more context to uniquely identify "
                f"the instance, or set replace_all to true.\n"
                f"String: {validated.old_string}"
            )
        
        # ⑥ 치환
        if validated.replace_all:
            new_content = content.replace(
                validated.old_string, validated.new_string
            )
        else:
            new_content = content.replace(
                validated.old_string, validated.new_string, 1
            )
        
        # ⑦ 쓰기
        path.write_text(new_content, encoding="utf-8")
        
        # read_files 타임스탬프 갱신 (편집 후에도 계속 편집 가능)
        context.read_files.add(str(path))
        
        if validated.replace_all and match_count > 1:
            return (
                f"Replaced all {match_count} occurrences in {path}."
            )
        return f"Successfully edited {path}."
```

**80줄이 넘었다**. Read(40줄), Write(50줄), Bash(60줄) 보다 길다. 왜? **검증 단계가 많기 때문**이다. 실행 자체는 `content.replace()` 한 줄이지만 — 그 전에 5개의 게이트를 통과해야 한다. **도구가 복잡한 이유는 '하는 일'이 복잡해서가 아니라 '안 되는 조건'이 많아서**다. 진짜 `FileEditTool.ts`의 `validateInput`이 160줄인 이유도 같다 — `call`은 짧고 `validate`가 길다.

#### 에러 메시지가 모델을 가이드한다

각 에러 메시지를 다시 보자.

| 에러 조건 | 메시지 | 모델이 배우는 것 |
|---|---|---|
| Read 안 됨 | "Read it first before editing" | → 다음엔 Read를 먼저 호출 |
| old_string 없음 | "String to replace not found" | → old_string을 재확인하거나 Read로 최신 내용 확인 |
| 복수 매칭 | "Found N matches... provide more context" | → 더 긴 old_string으로 재시도 |
| old == new | "old_string and new_string are the same" | → 불필요한 호출, 스킵 |

이게 진짜 Claude Code의 `validateInput`이 상세한 에러 코드(errorCode 1~9)를 두는 이유다. **에러 메시지가 곧 모델한테 주는 few-shot 힌트**. "실패했습니다"만 보여주면 모델이 같은 실수를 반복한다. "이렇게 고치면 된다"를 보여주면 다음 턴에 고친다.

> 💡 **`findActualString` — 진짜 Edit이 가진 추가 마법.** 진짜 `FileEditTool`의 `utils.ts:73`에는 `findActualString` 함수가 있다. 파일에 **curly quote**(', ")가 있고 모델이 **straight quote**('", ')를 보낸 경우 — 자동으로 노멀라이즈해서 매칭한다. Claude는 curly quote를 출력하기 어렵기 때문. 미니에서는 OUT — 우리는 정확 매칭만. 하지만 이 패턴이 보여주는 원칙은 기억할 만하다: **LLM의 한계를 도구가 보상한다**.

#### `ToolContext`에 상태 추가

Read-before-Edit를 위해 `ToolContext`에 `read_files` 상태를 추가한다.

```python
# src/mini_claude/tools/base.py — read_files 추가
@dataclass
class ToolContext:
    """도구 호출 시 주변 컨텍스트."""
    cwd: str
    permissions: Any
    read_files: set[str] = field(default_factory=set)  # ← NEW
```

그리고 `ReadTool.call()` 끝에 한 줄 추가.

```python
# ReadTool.call() 마지막에:
context.read_files.add(str(path))   # ← Edit 도구를 위한 상태 기록
return path.read_text(encoding="utf-8")
```

이게 **도구 간 상태 공유의 최소 단위**다. 진짜 Claude Code에서는 `toolUseContext.readFileState`가 이 역할 — 파일 경로를 키로, 읽은 시각(`timestamp`)과 내용(`content`)과 부분 뷰 여부(`isPartialView`)를 저장한다. 우리는 `set[str]` 하나. **타임스탬프 비교와 부분 뷰 추적은 OUT** — 미니는 외부 편집 감지도, 큰 파일 부분 읽기도 안 하니까.

| 진짜 readFileState | 미니 read_files | 이유 |
|---|---|---|
| `timestamp` (편집 후 외부 수정 감지) | ❌ | 미니는 단일 사용자 — 외부 편집 없다고 가정 |
| `content` (수정 전 내용 비교) | ❌ | 롤백 없음 |
| `isPartialView` (부분 읽기면 Edit 차단) | ❌ | offset/limit 없음 — 항상 전체 읽기 |
| `Map<string, …>` | `set[str]` | 존재 여부만 필요 |

## 핵심 정리

- **Pydantic 모델 한 클래스**가 **입력 검증 + JSONSchema + 타입 힌트**를 한 번에. `model_json_schema()` 한 메서드가 Anthropic API가 받는 형식을 그대로 만들어준다. 진짜 Claude Code의 `validateInput` 메서드가 **Pydantic 한 줄**로 끝남. **언어 생태계가 이미 잘 푼 문제는 그 위에 올라간다 — KISS의 정신**.
- **3.2의 47개 필드 → 5개**: `name`, `description`, `input_model`, `call`, `is_read_only`/`is_destructive`. 90%가 살, 10%가 본질. 우리는 그 10%를 만든다.
- **4개 도구의 복잡도 그라디언트**: ReadTool(40줄, 읽기 전용) → WriteTool(50줄, 덮어쓰기) → BashTool(60줄, 임의 명령) → EditTool(80줄, 상태 의존). 위로 갈수록 위험하고, **EditTool에서 처음으로 도구 간 상태 공유가 등장**한다.
- **ReadTool의 2단계**: 검증 → 실행. 진짜 FileReadTool의 UNC NTLM 차단, 부분 view, 청킹, 멀티모달은 **전부 OUT**. 우리는 80% 시나리오를 위해 짠다.
- **WriteTool의 부모 디렉토리 보장**. 진짜 Write의 Read-before-Write 강제, 외부 편집 감지, 백업 등은 OUT. **미니의 Write는 위험하다 — 9.4의 권한 시스템이 그래서 필요**.
- **BashTool의 60줄 미니멀** — `asyncio.create_subprocess_shell` + 타임아웃 + 출력 자르기. 3.5의 `preparePermissionMatcher`, 50 서브명령 보안 검사, tree-sitter 합성 명령 분해는 **전부 OUT**. **미니는 그저 명령을 실행한다 — 안전성은 권한 시스템 책임**.
- **EditTool의 핵심 설계**: 정규식 대신 **정확 문자열 매칭** (LLM hallucination 방지), **Read-before-Edit 강제** (읽지 않은 파일은 편집 불가), **유일성 검증** (복수 매칭이면 에러). 진짜 `FileEditTool.ts`의 `validateInput` 160줄을 5개 게이트로 압축.
- **에러 메시지가 모델을 가이드한다**. "String not found" → 모델이 old_string을 재확인. "Found N matches" → 더 긴 컨텍스트로 재시도. **에러 메시지 = few-shot 힌트**. 이게 진짜 Claude Code의 errorCode 1~9의 설계 의도.
- **`is_read_only`, `is_destructive`는 Fail-safe 기본값**. 모르면 위험하다고 가정. 9.4의 권한 휴리스틱과 9.5의 병렬 실행 결정에 사용.
- **`agent.py` 한 줄만 변경**. `tools=[tool_to_anthropic_schema(t) for t in tools]`. 골격이 잘 잡혀 있어서 9.2의 다른 코드는 한 줄도 안 바뀐다. **인터페이스의 힘**.
- **이 챕터의 결과물**: 진짜 파일을 읽고 쓰고 편집하고 명령을 실행하는 mini-claude. 실용적. 그러나 위험. 9.4의 권한 체크가 반드시 필요한 이유.
