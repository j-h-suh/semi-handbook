# 핸드북 보완 항목 리스트업 (claude_code)

> 목적: claude_code 핸드북 마크다운 전반에 걸쳐 사용자가 발견한 수정/보완 항목을 누적.
> 진행: 항목 누적 → 반영 방향 협의 → 실제 수정.
>
> 코드–핸드북 갭 (mini_claude 실행 중 발견)은 별도 파일 `_revisions.md`에서 관리.

## 항목 구조

```
### [N.M / 신규] 한 줄 제목
- **위치**: 챕터 N.M, 어디 (선택)
- **요청**: 사용자가 말한 수정/보완 내용
- **클로드 의견**: 동의/대안/주의점/관련 챕터 영향 등
- **상태**: [pending] / [decision-needed] / [done]
```

상태 라벨:
- `[pending]` — 협의 전, 일단 적어둠
- `[decision-needed]` — 어디에/어떻게 반영할지 정해야 함
- `[in-progress]` — 반영 작업 중
- `[done]` — 반영 완료

### [신규 6.5 + 6.6] Hooks 두 챕터 추가

- **위치**: 6장 확장. 현재 핸드북에서 hooks가 빠져 있음.
- **요청**: Claude Code의 주요 기능인 **hook** (PreToolUse / PostToolUse 등)에 대한 설명 챕터를 추가하고 싶음.
- **결정 (2026-05-05)**: **6.5 + 6.6 두 챕터로 분할, 6장 안에 추가**.
  - 권한 시스템(6.3 + 6.4)과 같은 패턴 — 메커니즘 1챕터 + 실전 1챕터
  - 6.4 권한 규칙 매칭 → 6.5 Hook → 6.6 Hook 실전 → (기존 7장으로 연결)
  - 한 챕터로는 빡빡함 (이벤트 8종 + 입출력 + matcher + 권한과의 관계 + 실무 예시)
- **챕터 분할안**:
  - **6.5 Hook 시스템 — 이벤트와 입출력 메커니즘**
    - Hook 이벤트 종류 8종: `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `Notification`, `SessionStart/End`, `PreCompact`
    - stdin JSON 스키마 (이벤트별)
    - exit code 의미 (`0`=통과, `2`=차단), stdout JSON 응답 (`decision`, `reason`, `additionalContext`, `hookSpecificOutput`)
    - 권한 시스템(6.3 / 6.4)과의 상호작용 — PreToolUse hook이 allow/deny/ask와 어떻게 합쳐지는지
  - **6.6 Hook 실전 — matcher와 사용 사례**
    - Matcher 매칭 규칙 (도구 이름, 정규식, 글로벌)
    - settings.json 통합 (8군데 우선순위와의 합산)
    - 실무 예시 4~5개: 자동 포맷터, 위험 명령 차단, 세션 종료 알림, 컨텍스트 주입, 로깅
    - 보안 모델, 디버깅, 실패 시 동작
- **연결 챕터**: 6.3 권한 모드, 6.4 권한 규칙 매칭 (PreToolUse 결합), 4.3 allowedTools (도구 통제의 다른 축).
- **부수적 고려**: hooks를 mini_claude (9장)에서도 구현할지는 별개 결정. 사용자가 "핸드북 마크다운만 대상"이라고 했으므로 일단 보류, 추후 9장 확장 여부는 따로 논의.

### [0.1] "이게 전부다" 톤 모호함 — 하네스의 위상을 명확히

- **위치**: 0.1 "도구를 쓸 줄 아는 챗봇" — Claude Code를 한 줄로 요약하면.
- **요청**: 챕터가 "하네스가 중요하다"는 건지 "별것 아니다"는 건지 스탠스가 모호. "이게 전부다", "본질은 변하지 않는다" 같은 환원적 톤이 강해서 독자가 "그럼 Claude Code는 뭘 하는 거지?"로 빠짐. 방향을 정해야 함.
- **현재 0.1의 구조 진단**:
  1. 한 줄 요약 → 50줄 Python 의사코드 (강한 환원적 프레이밍)
  2. "52만 줄은 살" 테이블 — 8개 항목 나열 ("UI 예쁘게", "도구 안전하게", "MCP 연결" 등). **살이 비조직적 부속품으로 보임**.
  3. "잠깐, 너무 단순한 거 아닌가?" 반박 섹션 — 4개 예시(권한, 스트리밍, 병렬, 압축)로 하네스의 중요성 변호. **방어적 후속**으로 들리고, 이미 굳어진 환원적 인상을 뒤집기엔 늦음.
  4. 핵심 정리 다시 환원적 톤("본질은 변하지 않는다")으로 마감.
  - **문제의 정수**: 하네스가 "기능 목록"으로만 묘사되어 **알고리즘적 구조가 안 보임**. 독자가 "이걸 다 합쳐서 뭐가 되는 건데?"라는 질문에 답을 못 받음.
- **결정 (2026-05-05)**: **(A) 레이어드 아키텍처 다이어그램 + (B2) 2단계 OS 비유**.
  - **외층 비유**: LLM = CPU, 하네스 = OS. CPU 혼자는 컴퓨터가 아니다 → LLM 혼자는 agent가 아니다. 하네스의 **존재 이유**를 보편적 비유로 설명.
  - **내층 비유**: "OS에도 종류가 있다 — monolithic vs microkernel. Claude Code의 하네스는 microkernel 스타일." 50줄 루프 = 마이크로커널 핵심 / 위의 권한·스트리밍·UI·MCP·압축 = user-space service.
  - **레이어드 다이어그램**: OS의 레이어드 아키텍처(CPU → 커널 → 서비스 → user app)와 닮은 모양으로 그려서 비유와 시각화가 이중으로 작동.
- **방향 후보 (참고용 — B1/B3는 비채택)**:
  - **(B1) 환원 프레이밍 뒤집기** — "이게 전부다" → "하네스가 가치"로 메인 스토리 전환. 너무 큰 시점 변화로 챕터 정체성("한 줄 요약")을 잃을 위험. 비채택.
  - **(B3) Production reality 진입** — 4가지 production 문제로 시작해 역추론. 0.1 전체 갈아엎어야 함, 비용 대비 이득 작음. 비채택.
- **구체 수정 그림**:
  - **새 섹션 1 (외층 비유)**: "LLM은 CPU다" 식의 단락 추가. 현재 "Claude는 그저 문자열을 입력으로 받고 문자열을 출력하는 LLM이다" 부분을 확장 — CPU가 명령어 받고 결과 뱉듯, LLM은 텍스트 받고 텍스트 뱉는다. 둘 다 자체로는 사용자 시스템이 아니다.
  - **새 섹션 2 (내층 비유 + 다이어그램)**: "OS에도 종류가 있다" 단락 → microkernel 소개 → Claude Code의 하네스가 마이크로커널 스타일임을 설명 → 레이어드 다이어그램 제시.
  - **테이블 교체**: 기존 "52만 줄은 살" 8개 항목 테이블을 **레이어드 다이어그램**으로. 중앙: 50줄 루프 (마이크로커널). 주변 5~6개 레이어:
    - 입력 처리 (슬래시 명령, 시스템 프롬프트 주입) — 4장
    - 도구 실행 (권한, 보안, 병렬, MCP) — 3, 6, 7장
    - 응답 처리 (스트리밍, 파싱, UI) — 2, 5장
    - 메모리 (압축, 세션) — 6, 7장
    - 다중 에이전트 (재귀, IDE) — 8장
  - **톤 조정**: "이게 전부다" → "**이게 마이크로커널이다. 그 위에 시스템이 산다.**" 환원과 부풀림 사이 균형.
  - **"잠깐, 너무 단순한 거 아닌가?" 섹션**: 다이어그램의 인트로로 격상 — 방어가 아니라 본 챕터의 두 번째 본론.
  - **핵심 정리**: 마지막 줄에 "**Part 9의 미니에서 마이크로커널을 만들고, 다른 Part에서 레이어를 한 겹씩 본다**" 식의 책 전체 지도 한 줄.
- **부수 효과**:
  - 0.0 (왜 이 책을 썼는가)와 정합성 강화 — 책의 가치 명제가 "하네스 분석"임을 첫 챕터에서 재확인
  - 1장 부트스트랩, 2장 에이전트 루프, 3장 도구, 5장 UI 등으로의 챕터 안내가 자연스러워짐 — 각 Part가 어느 레이어인지 다이어그램에 명시
  - CS 배경 독자(이 책의 타겟)에게 OS/CPU 비유는 즉각 통함
