# 4.1 슬래시 명령은 일반 채팅과 어떻게 다른가 — 같은 입력창, 다른 길

---

## 이 챕터에서 배우는 것

- `/commit`을 칠 때와 "커밋 좀 해줘"라고 말할 때 정확히 무엇이 다른가
- 슬래시 명령이 클라이언트 측 디스패치라는 사실 — LLM에 도달하기 전에 잡힌다
- 어떤 명령은 **LLM에 닿지도 않는다** (`/clear`, `/cost`)
- 어떤 명령은 세심하게 만들어진 프롬프트로 변환된다 (`/commit`)
- 입력창은 하나인데 길은 두 개가 갈라지는 자리

---

## 사용자 경험에서 출발

평소에 입력창에 그냥 친다.

```
> 이 함수 좀 리팩토링해줘
```

Claude가 받는다. 도구를 호출한다. 응답이 흐른다. 2장에서 본 그 흐름이다.

근데 가끔 `/`를 누른다.

```
> /commit
```

엔터를 친다. 일어나는 일이 다르다. LLM이 "/commit이 무슨 뜻이지?"라고 생각하지 않는다. 갑자기 git 명령들이 돌고, diff가 나오고, 완성된 커밋 메시지가 한 번에 흘러나온다. 마치 누가 미리 시나리오를 짜둔 것처럼.

맞다. 미리 짜둔 시나리오다. 그게 슬래시 명령이다. 이 챕터에서 그 시나리오가 어디에, 어떻게 짜여 있는지를 본다.

---

## 본문

### 일반 채팅의 길

먼저 일반 채팅. 입력 → LLM. 단순하다.

```
사용자: "이 함수 좀 리팩토링해줘"
                ↓ (그대로)
PromptInput 컴포넌트
                ↓
messages.push({ role: 'user', content: "이 함수 좀 리팩토링해줘" })
                ↓
query.ts (2장의 에이전트 루프)
                ↓
LLM이 본다: "이 함수 좀 리팩토링해줘"
```

**사용자가 친 텍스트가 LLM이 보는 텍스트와 같다.** 입력은 투명하다.

### 슬래시 명령의 길

`/commit`을 친 순간, 완전히 다른 길이 열린다.

```
사용자: "/commit"
                ↓
PromptInput 컴포넌트
                ↓
"앗, /로 시작하네 — 명령 디스패처로 보내자"
                ↓
COMMANDS 레지스트리 조회
                ↓
commit 명령 객체를 찾음 (src/commands/commit.ts)
                ↓
"이건 type: 'prompt' 명령이네"
                ↓
getPromptForCommand("") 호출 → 진짜 프롬프트가 *생성됨*
                ↓
생성된 프롬프트:
   "## Context
    - Current git status: <git status 결과>
    - Current git diff: <git diff 결과>
    - Recent commits: <git log 결과>
    
    ## Git Safety Protocol
    - NEVER update the git config
    - ...
    
    ## Your task
    Based on the above changes, create a single git commit:
    1. Analyze all staged changes...
    ..."
                ↓
messages.push({ role: 'user', content: <위 거대한 프롬프트> })
                ↓
query.ts (2장의 에이전트 루프) — 여기서부터는 일반 채팅과 같음
                ↓
LLM이 본다: <위 거대한 프롬프트>
```

**사용자가 친 텍스트(`/commit`)와 LLM이 보는 텍스트가 완전히 다르다.** 사용자는 버튼을 눌렀고, 코드가 진짜 프롬프트를 만들었다. 입력은 불투명하다.

### 진짜 코드 — `commit.ts`

`src/commands/commit.ts`. 진짜 코드는 93줄로 짧다.

```typescript
import type { Command } from '../commands.js'

const ALLOWED_TOOLS = [
  'Bash(git add:*)',
  'Bash(git status:*)',
  'Bash(git commit:*)',
]

const command = {
  type: 'prompt',
  name: 'commit',
  description: 'Create a git commit',
  allowedTools: ALLOWED_TOOLS,
  progressMessage: 'creating commit',
  source: 'builtin',
  
  async getPromptForCommand(_args, context) {
    const promptContent = `## Context
- Current git status: !\`git status\`
- Current git diff: !\`git diff HEAD\`
- Recent commits: !\`git log --oneline -10\`

## Git Safety Protocol
- NEVER update the git config
- ...

## Your task
Based on the above changes, create a single git commit:
1. Analyze all staged changes...
`
    // !`...` 패턴을 진짜 셸 실행으로 치환
    const finalContent = await executeShellCommandsInPrompt(
      promptContent, context, '/commit'
    )
    return [{ type: 'text', text: finalContent }]
  },
} satisfies Command

export default command
```

세 가지가 눈에 띈다.

**(1) `type: 'prompt'`** — 명령의 종류. 다음 챕터(4.2)에서 본격적으로 본다. 일단은 "이 명령은 LLM에 보낼 프롬프트를 생성하는 종류"라고만 알고 가자.

**(2) `getPromptForCommand`** — 진짜 프롬프트를 런타임에 만든다. 정적 문자열이 아니라 함수다. 함수라서 — 호출되는 그 순간의 git 상태를 끌어와서 그때그때 다른 프롬프트를 만든다.

**(3) `!\`git status\`` 패턴** — 프롬프트 문자열 안에 셸 명령 호출이 박혀 있다. `executeShellCommandsInPrompt`가 이 백틱 안 명령을 진짜로 실행하고, 결과로 치환한다. 즉 LLM은 "git status를 돌렸다"가 아니라 **"git status를 돌린 결과"**를 본다. 일종의 프롬프트 템플릿 엔진.

> 💡 **Python 비유:** Jinja2나 f-string과 비슷하다. 문자열 안에 코드 실행 마커(`!`)가 있고, 렌더링 시점에 그 마커가 결과로 바뀐다. 차이는 — Jinja는 일반 변수를 채우고, 이건 셸 명령을 실행해서 채운다.

> ⚙️ **위 코드는 단순화한 거다 — 진짜 `commit.ts`는 한 가지를 더 한다 (4.3 떡밥).** 실제(`commit.ts:67-86`)에서는 `executeShellCommandsInPrompt`의 두 번째 인자가 **그냥 context**가 아니라 **getAppState()를 오버라이드한 wrapper context**다. 그 wrapper가 `alwaysAllowRules.command`에 `ALLOWED_TOOLS`를 주입한다 — 즉 **이 셸 실행 동안에는 위 3개 Bash 패턴이 자동 허용**된다는 뜻. **`allowedTools`가 단순한 선언이 아니라 런타임에 권한 시스템에 강제로 박히는 값**이라는 게 여기서 드러난다. 이 메커니즘이 4.3의 본질이다 — 지금은 "이 두 줄이 권한 시스템과 직접 연결되어 있구나" 정도로만 알고 가자.

### 슬래시 명령의 세 가지 종류

`commit`은 `type: 'prompt'`다. 근데 모든 슬래시 명령이 LLM에 가는 건 아니다. `src/types/command.ts:205-206`를 보면 세 가지 종류가 있다.

```typescript
export type Command = CommandBase &
  (PromptCommand | LocalCommand | LocalJSXCommand)
```

| 종류 | LLM에 가나? | 예시 | 한 줄 설명 |
|---|---|---|---|
| `prompt` | ✅ 간다 | `/commit`, `/init`, `/review` | 프롬프트를 만들어서 LLM에 보냄 |
| `local` | ❌ 안 감 | `/cost`, `/clear`, `/exit` | 클라이언트가 직접 결과를 만듦 |
| `local-jsx` | ❌ 안 감 | `/config`, `/permissions`, `/agents` | **React 컴포넌트**를 띄움 (대화형 UI) |

다음 챕터(4.2)가 이 셋을 본다. 지금은 셋이 다 있다는 사실만 기억하자. 

핵심은 — **슬래시 명령이라고 다 LLM에 가는 게 아니다**. `/clear`를 치면 LLM은 그게 일어났는지도 모른다. `/cost`를 치면 클라이언트가 토큰 카운터를 직접 읽어서 직접 출력한다. **LLM이 알 필요가 없으니까**.

### 디스패치 자리는 어디인가

`PromptInput.tsx` 컴포넌트는 사용자 입력만 받는다. 분기는 그 다음 단계 — `utils/handlePromptSubmit.ts:229` 의 한 줄에서 일어난다.

```typescript
if (!skipSlashCommands && finalInput.trim().startsWith('/')) {
  // ... 슬래시 명령 디스패치
}
```

이 줄을 펼쳐서 의사코드로 보면:

```typescript
// 단순화한 골격
async function onSubmit(text: string) {
  if (text.startsWith('/')) {
    const [name, ...args] = text.slice(1).split(' ')
    const command = COMMANDS().find(c => c.name === name || c.aliases?.includes(name))
    
    if (!command) return showError(`Unknown command: ${name}`)
    
    switch (command.type) {
      case 'prompt': {
        const content = await command.getPromptForCommand(args.join(' '), ctx)
        messages.push({ role: 'user', content })  // → query.ts로 흘러감
        break
      }
      case 'local': {
        const result = await command.load().then(m => m.call(args.join(' '), ctx))
        showLocalResult(result)  // → LLM에 안 감
        break
      }
      case 'local-jsx': {
        const node = await command.load().then(m => m.call(onDone, ctx, args.join(' ')))
        showJsxOverlay(node)  // → React 컴포넌트로 띄움
        break
      }
    }
    return
  }
  
  // 일반 채팅
  messages.push({ role: 'user', content: text })  // → query.ts로 흘러감
}
```

**`/`로 시작하는지가 전부다.** 그 한 줄의 분기로 길이 갈라진다. 같은 입력창, 다른 길.

### 왜 슬래시 명령이 필요한가 — 세 가지 이유

"그냥 자연어로 '커밋 좀 해줘' 라고 말하면 안 되나?" 된다. 근데 슬래시 명령이 낫다. 세 가지 이유.

**(1) 결정적이다 (deterministic).** `/commit`은 항상 같은 시나리오를 따른다. **git status → diff → log → 메시지 작성 → commit**. 자연어는 LLM이 기분 따라 다르게 해석한다. 어떤 날엔 hooks 옵션을 끄고, 어떤 날엔 모든 파일을 add하고, 어떤 날엔 리뷰만 하고 commit을 안 하고. 슬래시 명령은 템플릿이 확정되어 있어서 그 변동이 없다.

**(2) 안전 정책을 함께 가져온다.** `commit.ts`의 `allowedTools = ['Bash(git add:*)', 'Bash(git status:*)', 'Bash(git commit:*)']`. **이 명령이 도는 동안에는 이 세 가지 Bash 패턴만 허용된다**. `rm -rf`나 `git push`를 LLM이 시도하면 — 거부된다. 자연어 "커밋 좀 해줘"에는 이런 안전망이 없다. LLM이 "하는 김에 push도 하자" 하면 그대로 푸시된다. 4.3에서 자세히 본다.

**(3) 토큰을 아낀다.** `/cost`나 `/clear` 같은 간단한 작업은 LLM에 갈 필요 자체가 없다. 클라이언트가 직접 처리하면 0 토큰. 자연어로 "지금까지 얼마 썼어?"라고 물으면 LLM이 한 번 굴러가야 하고, 답하기까지 토큰이 든다. 작은 차이지만, 매일 수십 번 쓰는 명령이라면 누적이 크다.

> 🔬 **Deep Dive — `/commit`은 왜 prompt고 `/cost`는 왜 local인가?** 결정 기준은 "LLM의 추론이 필요한가". `/commit`은 diff를 읽고 변경의 의미를 파악해서 적절한 메시지를 짠다 — LLM의 자연어 능력이 핵심이다. `/cost`는 숫자 두 개를 더하는 일 — LLM이 굳이 할 필요 없다. 이 기준이 명령 설계의 출발점이다. "이 작업의 본질이 추론인가, 아니면 결정적 계산인가." 후자라면 `local`로 만들어 토큰과 지연을 아끼고, 전자라면 `prompt`로 만들어 LLM의 강점을 쓴다.

## Python으로 옮기면

슬래시 명령 디스패치의 골격을 Python으로 옮기면 이렇게 생겼다.

```python
from __future__ import annotations
from dataclasses import dataclass
from typing import Awaitable, Callable, Literal, Any


# ─── 명령 타입 정의 ────────────────
@dataclass
class PromptCommand:
    name: str
    type: Literal["prompt"] = "prompt"
    allowed_tools: list[str] = None
    get_prompt: Callable[[str], Awaitable[str]] = None


@dataclass
class LocalCommand:
    name: str
    type: Literal["local"] = "local"
    call: Callable[[str], Awaitable[str]] = None


Command = PromptCommand | LocalCommand


# ─── 명령 레지스트리 ────────────────
async def commit_prompt(args: str) -> str:
    import subprocess
    status = subprocess.check_output(["git", "status"]).decode()
    diff = subprocess.check_output(["git", "diff", "HEAD"]).decode()
    return f"""## Context
- git status: {status}
- git diff: {diff}

## Your task
Create a single git commit based on the staged changes.
"""


async def cost_call(args: str) -> str:
    return f"Tokens used so far: {get_token_count()}"  # LLM 안 거침


COMMANDS: list[Command] = [
    PromptCommand(
        name="commit",
        allowed_tools=["Bash(git add:*)", "Bash(git status:*)", "Bash(git commit:*)"],
        get_prompt=commit_prompt,
    ),
    LocalCommand(name="cost", call=cost_call),
]


# ─── 디스패처 ────────────────
async def handle_input(text: str, messages: list[dict]) -> None:
    if not text.startswith("/"):
        # 일반 채팅 — 그대로 LLM에
        messages.append({"role": "user", "content": text})
        return
    
    # 슬래시 명령 디스패치
    parts = text[1:].split(" ", 1)
    name = parts[0]
    args = parts[1] if len(parts) > 1 else ""
    
    cmd = next((c for c in COMMANDS if c.name == name), None)
    if cmd is None:
        print(f"Unknown command: {name}")
        return
    
    match cmd:
        case PromptCommand():
            content = await cmd.get_prompt(args)
            messages.append({"role": "user", "content": content})  # LLM에 감
        case LocalCommand():
            result = await cmd.call(args)
            print(result)  # LLM 안 거치고 직접 출력
```

**핵심은 `handle_input` 함수의 첫 분기다**: `if text.startswith("/")`. 그 한 줄로 일반 채팅의 길과 슬래시 명령의 길이 갈라진다. 슬래시 명령이라면 어떤 종류인지 보고 다시 분기 — `prompt`면 프롬프트를 만들어서 LLM에 보내고, `local`이면 직접 처리.

> 💡 **`PromptInput`이 디스패처라는 사실의 의미.** 슬래시 명령은 서버 기능이 아니다. **LLM이 알아서** 하는 것도 아니다. **클라이언트가 직접 처리한다.** 사용자 입력 → 클라이언트 분기 → 그 다음에서야 (필요하면) LLM. 이 클라이언트 우선 구조가 4.2에서 본격적으로 풀린다.

## 핵심 정리

- 일반 채팅은 투명하다 — 사용자가 친 텍스트와 LLM이 보는 텍스트가 같다.
- 슬래시 명령은 불투명하다 — 사용자가 친 건 버튼 이름이고, 진짜 프롬프트는 클라이언트 코드가 만든다 (`getPromptForCommand`).
- 디스패치 자리는 `utils/handlePromptSubmit.ts:229`: `if (finalInput.trim().startsWith('/'))`. PromptInput 은 입력을 받기만 하고, 분기는 한 단계 뒤에서 일어난다. 같은 입력창에서 길이 갈라지는 곳.
- 슬래시 명령은 세 가지 종류: `prompt`(LLM에 감), `local`(클라이언트가 직접), `local-jsx`(React 컴포넌트 띄움). 다음 챕터(4.2)에서 본격적으로.
- 슬래시 명령이 필요한 이유 세 가지: **결정적**(같은 시나리오 반복), **안전 정책 동봉**(`allowedTools` — 4.3에서), **토큰 절약**(`local`은 LLM에 안 감).
- 명령 설계의 결정 기준: "이 작업의 본질이 추론인가 계산인가". 추론이면 `prompt`, 계산이면 `local`.
