# 2.2 비동기 제너레이터 파이프라인 — Python의 `async for`로 풀어보기

---

## 이 챕터에서 배우는 것

- `query.ts`가 왜 AsyncGenerator로 만들어져 있는가
- TypeScript의 `async function*`이 Python의 `async def gen()`과 어떻게 같고 어떻게 다른가
- 여러 레벨의 함수가 `yield*` 체인으로 어떻게 연결되는가
- "흘러나오는 것"이라는 사용자 경험이 코드 구조로 그대로 표현된다는 사실

---

## 사용자 경험에서 출발

뭔가를 시키면 응답이 흐른다. 한꺼번에 펑 나오지 않는다.

```
> 이 디렉토리 구조 좀 설명해줘

확인해볼게요. ←  (한 글자씩 흘러나옴)

⠋ Bash: ls -la
✓ Bash: ls -la

루트에는 다음 파일들이 있네요: ←  (또 한 글자씩)
- src/ ...
```

이 흐름이 단순한 "여러 번 print"가 아니다. 한 함수가 계속 결과를 내보내고, 다른 함수가 계속 받아서 화면에 그린다. 마치 파이프(`|`)로 연결된 두 프로그램처럼.

이 흐름을 코드로 표현하는 가장 자연스러운 방법이 **제너레이터**다. Python을 쓰는 사람이라면 이미 익숙한 그 패턴.

## 본문

### 일반 함수 vs 제너레이터 함수 (Python 복습)

Python의 일반 함수는 한 번에 하나의 결과를 반환한다.

```python
def collect_evens(n):
    result = []
    for i in range(n):
        if i % 2 == 0:
            result.append(i)
    return result

evens = collect_evens(10)  # [0, 2, 4, 6, 8] 통째로 반환
```

제너레이터 함수는 결과를 내보내며 진행한다.

```python
def yield_evens(n):
    for i in range(n):
        if i % 2 == 0:
            yield i  # 하나씩 내보냄

for x in yield_evens(10):
    print(x)  # 0, 2, 4, 6, 8 — 받는 즉시 처리
```

차이는 결과를 모아두고 한 번에 반환하느냐, 결과가 나올 때마다 흘려보내느냐. **흐름이 본질인 작업에는 후자가 자연스럽다.**

### 비동기 제너레이터 — `async def` + `yield`

여기에 비동기가 더해지면 그게 비동기 제너레이터다.

```python
async def stream_tokens(prompt: str):
    response = await api.call(prompt)  # 네트워크 대기
    async for chunk in response:        # 스트리밍 청크 수신
        yield chunk.text                # 받는 즉시 외부로 흘려보냄

async def main():
    async for token in stream_tokens("hello"):
        print(token, end="", flush=True)
```

이게 LLM 스트리밍 응답을 처리하는 가장 자연스러운 패턴이다. "네트워크에서 토큰이 도착할 때마다 호출자에게 흘려보낸다"가 한 줄로 표현된다.

여기서 한 가지 짚어둘 것 — `response = await api.call(prompt)` 의 `response` 는 **완성된 텍스트가 아니다**. 일반 HTTP 호출(`requests.get(...)`) 이라면 본문 전체를 받은 객체가 들어오겠지만, 스트림 호출은 다르다 — `await` 로 받는 건 **서버로 열려 있는 수신 채널 객체** 일 뿐이고, 본문 데이터는 아직 서버 쪽에 있다. 그 다음 줄의 `async for chunk in response:` 가 그 채널에서 한 청크씩 끌어온다.

비유: 일반 HTTP 가 **편지 수신** 이라면 (편지지 = 데이터), 스트림은 **전화 통화** 다. `response` = 손에 든 수화기, 상대방의 말은 통화 동안 흘러온다.

### 흐름 한 그림 — 누가 누구에게 흘려보내는가

위 코드의 데이터 흐름을 한 그림으로 그리면 이렇다.

```
[API 서버]
   │ chunk 도착
   ↓
[OS kernel TCP 버퍼]    ← 도착한 chunk 가 잠시 머무는 자리
   ↓ pull
[response 채널]         ← await api.call(...) 로 받은 그것
   ↓ async for chunk
[stream_tokens()]       ← chunk.text 만 yield
   ↓ yield 전달
[main()]                ← async for token, print
```

읽는 방향은 아래에서 위로 — `main()` 의 `async for` 가 `print()` 한 번 호출하기 위해, 한 단계씩 위로 끌어올리는 모양. **뽑기(pull) 흐름**이다. `stream_tokens` 가 chunk 를 미리 모아두고 호출자에게 던지는 게 아니라, `main` 이 다음 token 을 요구할 때 비로소 chunk 가 한 단계씩 끌려온다.

그래서 각 단계가 자기 속도로 처리해도 자연스럽게 동기화된다. `main` 이 `print` 에 시간이 걸려도, `stream_tokens` 는 그동안 chunk 를 더 끌어오지 않고 가만히 기다린다 — 이게 **backpressure**(역압) 의 자연스러운 표현이다.

<details>
<summary>🔬 Deep Dive — race condition 은 왜 안 생기는가</summary>

> 한 가지 의문 — `await api.call(prompt)` 로 채널만 받고, `async for chunk in response:` 로 들어가기 전 사이에 서버가 chunk 를 보내면 어떻게 되나? 그 chunk 는 사라지나?
>
> 사라지지 않는다. 도착한 chunk 는 **OS kernel 의 TCP 수신 버퍼** 에 쌓인다. 운영체제가 소켓 단위로 자동으로 받아두는 버퍼다. 우리 Python/JS 코드가 아직 읽지 않아도, kernel 이 한동안 들고 있는다 (버퍼 크기 한도까지).
>
> `async for chunk in response:` 가 시작되면, response 채널은 그 kernel 버퍼에서 한 청크씩 끌어온다(pull). 그래서 코드가 느리게 시작해도 누수가 없다 — 흘러간 데이터가 사라진 게 아니라 kernel 에서 기다리고 있던 것.
>
> 단 kernel 버퍼 한도를 초과할 만큼 늦게 시작하면 TCP 흐름 제어가 작동해 서버 쪽에 "그만 보내라" 신호를 보낸다 (TCP window size). 데이터가 떨어지는 게 아니라 서버가 잠시 멈춘다. 이게 TCP 레벨의 backpressure.

</details>

### TypeScript도 똑같다

TypeScript에는 `async function*` 문법이 있다. "비동기 제너레이터 함수"라는 뜻.

:::tabs

```typescript
async function* streamTokens(prompt: string) {
  const response = await api.call(prompt)
  for await (const chunk of response) {
    yield chunk.text
  }
}

// 호출자
for await (const token of streamTokens("hello")) {
  process.stdout.write(token)
}
```

```python
# Python 등가 — 거의 한 줄씩 대응
async def stream_tokens(prompt: str) -> AsyncIterator[str]:
    response = await api.call(prompt)
    async for chunk in response:
        yield chunk.text

# 호출자
async for token in stream_tokens("hello"):
    print(token, end="", flush=True)
```

:::

Python 코드와 거의 한 줄씩 대응된다. `async def` → `async function*`, `yield` → `yield`, `async for` → `for await`. 다른 점은 — 진짜 거의 없다. **개념도 똑같고 사용법도 똑같다.**

> 💡 **타입 표기 비유:**
> - Python: `AsyncIterator[str]` (또는 `AsyncGenerator[str, None]`)
> - TypeScript: `AsyncGenerator<string>` 또는 `AsyncIterable<string>`
>
> 둘 다 "문자열을 흘려보내는 비동기 시퀀스"라는 같은 의미. 이름만 다르다.
>
> Python 에도 `AsyncGenerator[T, None]` 이 있지만, 함수 반환 타입에는 보통 더 일반적인 `AsyncIterator[T]` 를 쓴다 — `asend` / `athrow` / `aclose` 같은 generator 추가 메서드가 필요 없을 때는 더 약속이 가벼운 `AsyncIterator` 가 적절하다.

### query.ts의 골격

이 패턴이 `query.ts` 안에 어떻게 들어가 있는지 보자. 심하게 단순화하면 이렇다 — 진짜 시그니처는 `query(params: QueryParams)` 로 객체 한 개에 13개 필드(`messages`, `systemPrompt`, `canUseTool`, `toolUseContext`, ... 등) 가 들어 있다. 아래 코드는 그 중 핵심 두 개(`messages`, `tools`) 만 별도 인자처럼 풀어서 적은 큰 그림용 단순화 (2.1 참조).

:::tabs

```typescript
async function* query(messages: Message[], tools: Tool[]) {
  while (true) {
    // 1. API 호출 (스트리밍)
    const apiStream = await callAnthropicAPI(messages, tools)
    
    // 2. 토큰 단위로 받아서 그대로 yield
    let assistantContent = []
    for await (const event of apiStream) {
      if (event.type === 'text_chunk') {
        yield { type: 'text', text: event.text }  // ← 호출자에게 흘려보냄
        assistantContent.push(event)
      }
      if (event.type === 'tool_use') {
        assistantContent.push(event)
      }
    }
    
    // 3. 메시지 히스토리에 응답 추가
    messages.push({ role: 'assistant', content: assistantContent })
    
    // 4. 도구 호출 처리
    const toolUses = assistantContent.filter(b => b.type === 'tool_use')
    if (toolUses.length === 0) {
      return  // 끝
    }
    
    const toolResults = []
    for (const toolUse of toolUses) {
      yield { type: 'tool_start', toolUse }              // ← spinner 시작
      const result = await executeTool(toolUse)
      yield { type: 'tool_result', toolUse, result }     // ← 결과 도착
      toolResults.push({ type: 'tool_result', ...result })
    }
    messages.push({ role: 'user', content: toolResults })
    // → while 위로 다시 (다음 API 호출)
  }
}
```

```python
# Python 등가 — query.ts 내부 루프의 골격
async def query(messages: list[dict], tools: list[dict]) -> AsyncIterator[dict]:
    while True:
        # 1. API 호출 (스트리밍)
        api_stream = await call_anthropic_api(messages, tools)

        # 2. 토큰 단위로 받아서 그대로 yield
        assistant_content = []
        async for event in api_stream:
            if event["type"] == "text_chunk":
                yield {"type": "text", "text": event["text"]}
                assistant_content.append(event)
            elif event["type"] == "tool_use":
                assistant_content.append(event)

        # 3. 메시지 히스토리에 응답 추가
        messages.append({"role": "assistant", "content": assistant_content})

        # 4. 도구 호출 처리
        tool_uses = [b for b in assistant_content if b["type"] == "tool_use"]
        if not tool_uses:
            return  # 끝 — generator 종료

        tool_results = []
        for tool_use in tool_uses:
            yield {"type": "tool_start", "tool_use": tool_use}
            result = await execute_tool(tool_use)
            yield {"type": "tool_result", "tool_use": tool_use, "result": result}
            tool_results.append({"type": "tool_result", **result})

        messages.append({"role": "user", "content": tool_results})
        # → while 위로 다시
```

:::

핵심 포인트.

1. **`async function*`** — 이 함수는 제너레이터다.
2. **여러 종류의 `yield`** — 토큰, 도구 시작, 도구 결과를 각각 yield. 호출자가 종류를 보고 다르게 처리할 수 있다. (실제로는 type-tagged가 아니라 `Message` 객체 단위로 yield한다 — `createUserMessage(...)`, `createAssistantAPIErrorMessage(...)` 같은 helper들이 만들어주는 객체. 타입은 `StreamEvent | RequestStartEvent | Message | TombstoneMessage | ToolUseSummaryMessage` (`query.ts:222-226`).)
3. **`while (true)`** — 2.1에서 본 내부 루프. 도구 결과가 LLM에 다시 들어가고, 또 호출되고, 또 yield되고...
4. **`return`** — 더 이상 도구 호출이 없으면 그냥 return. 제너레이터가 끝남.

### 호출자(REPL)는 이렇게 받는다

(`runTurn` / `run_turn` 은 호출자 쪽 코드 모양만 단독으로 보여주려 분리한 교육용 함수다. 진짜 Claude Code 에서는 `REPL.tsx` 의 `handleSubmit` 안에서 같은 `for await` 가 일어난다 — 1.2 메시지 흐름 다이어그램 참조.)

:::tabs

```typescript
async function runTurn(userInput: string) {
  messages.push({ role: 'user', content: userInput })
  
  for await (const event of query(messages, tools)) {
    switch (event.type) {
      case 'text':
        appendStreamingText(event.text)  // UI 상태 업데이트
        break
      case 'tool_start':
        showSpinner(event.toolUse)
        break
      case 'tool_result':
        hideSpinner()
        showResult(event.result)
        break
    }
  }
  // 루프가 끝나면 한 턴 끝
}
```

```python
# Python 등가 — REPL(호출자)이 이벤트를 소비하는 쪽
async def run_turn(user_input: str) -> None:
    messages.append({"role": "user", "content": user_input})

    async for event in query(messages, tools):
        match event["type"]:
            case "text":
                print(event["text"], end="", flush=True)
            case "tool_start":
                print(f"\n[{event['tool_use']['name']}]...", flush=True)
            case "tool_result":
                print(f" done.", flush=True)
    # async for가 끝나면 한 턴 끝
```

:::

이게 핵심 패턴이다. **`query()`는 생성하고, REPL은 소비한다**. 둘 사이의 인터페이스는 **yield되는 이벤트의 종류**. 명확하고 단순하다.

### `yield*` — 여러 레벨의 체인

진짜 `query.ts`는 한 함수가 아니라 여러 레벨의 제너레이터로 쪼개져 있다. 그것도 **세 파일에 걸쳐서, 5+ 레벨로**.

```
query()                       ← (query.ts:219) wrapper, 큐 명령 lifecycle 알림
   yield*
queryLoop()                   ← (query.ts:241) 진짜 while 루프 + 상태 머신
   yield* (deps.callModel)
                              ↓ 의존성 주입으로 끊어진 자리 (테스트를 위해)
                              ↓ 프로덕션에서는 queryModelWithStreaming
queryModelWithStreaming()     ← (services/api/claude.ts:752) export wrapper
   yield*
withStreamingVCR()            ← (vcr.ts) 녹화/재생 wrapper (테스트용)
   yield*
queryModel()                  ← (claude.ts:1017) 진짜 API 호출 + 스트리밍 + SSE 파싱
   yield ...
```

`yield*`는 Python의 `yield from`과 같다. "내가 직접 yield하지 말고, 하위 제너레이터가 yield하는 것을 그대로 전달해라"라는 뜻.

:::tabs

```typescript
async function* outer() {
  yield 'start'
  yield* inner()    // inner가 yield하는 것 모두 그대로 전달
  yield 'end'
}

async function* inner() {
  yield 'a'
  yield 'b'
}

// 호출자가 받는 순서: 'start', 'a', 'b', 'end'
```

```python
# Python 등가 — yield* 는 Python의 yield from과 같다
async def outer() -> AsyncIterator[str]:
    yield "start"
    async for item in inner():  # Python에는 async yield from이 없어서
        yield item              # async for + yield로 수동 위임
    yield "end"

async def inner() -> AsyncIterator[str]:
    yield "a"
    yield "b"

# 호출자가 받는 순서: 'start', 'a', 'b', 'end'
```

:::

**왜 이렇게 쪼갤까?** 한 함수에 몰아넣으면 `query.ts` 의 1,730줄 + `claude.ts` 의 관련 부분이 한 덩어리가 되어버린다. 책임별로 쪼개면:

- **`query()`** (`query.ts:219`): **얇은 wrapper**. `queryLoop` 가 큐에서 소비한 명령(`prompt`, `task-notification`)의 UUID 를 모아뒀다가, `queryLoop` 가 정상 종료되면 `'completed'` lifecycle 알림을 보낸다. 에러·취소로 중단되면 `yield*` 아래 코드에 도달하지 못해 `'completed'` 가 발생하지 않으므로, 원격 클라이언트(VS Code 확장 등)가 "시작은 했지만 완료되지 않은 명령"을 구분할 수 있다.
- **`queryLoop()`** (`query.ts:241`): 전체 턴의 흐름. 도구 호출 디스패치, 메시지 히스토리 관리, 상태 머신 (autocompact, 재시도, max_output_tokens 폴백).
- **`queryModelWithStreaming()`** (`claude.ts:752`): **API 호출 진입점**. VCR wrapper 를 통과시킴.
- **`withStreamingVCR()`** (`vcr.ts:349`): 녹화/재생. 테스트에서 API 응답을 녹화해두고 다시 재생할 수 있게 한 wrapper. 프로덕션에서는 통과 wrapper.
- **`queryModel()`** (`claude.ts:1017`): **진짜 API 호출** + 재시도 + 폴백 + 스트리밍 SSE 파싱. 토큰 카운팅도 여기서.

각자 자기 일을 하면서, 자기 결과를 yield. 상위는 `yield*`로 그대로 전달. **호출자(REPL) 입장에서는 한 평면의 이벤트 스트림처럼 보인다.** 내부가 5+ 단으로 쪼개져 있고 세 파일에 걸쳐 있다는 사실은 상관없다.

> ⚙️ **의존성 주입으로 끊어진 한 자리** — `query.ts` 와 `claude.ts` 사이는 `deps.callModel` 이라는 주입 가능한 함수 로 연결되어 있다 (`query/deps.ts`):
>
> ```typescript
> export type QueryDeps = {
>   callModel: typeof queryModelWithStreaming
>   microcompact: typeof microcompactMessages
>   autocompact: typeof autoCompactIfNeeded
>   uuid: () => string
> }
> ```
>
> 프로덕션에서는 `productionDeps()` 가 진짜 `queryModelWithStreaming` 을 꽂아준다. 테스트에서는 가짜 generator 를 꽂아서 전체 query loop 의 동작을 검증한다. **5단 generator 체인을 끊었다 이었다 할 수 있는 자리.**

> ⚠️ **함정:** 제너레이터는 한 번 소비하면 끝이다. 같은 제너레이터를 두 번 `for await` 하면 두 번째는 아무것도 안 나온다. 다시 받으려면 함수를 다시 호출해서 새 제너레이터를 만들어야 한다. Python도 똑같다.

## Python으로 옮기면

`query.ts`의 골격을 Python으로 거의 한 줄씩 옮기면 이렇게 생겼다.

```python
from dataclasses import dataclass
from typing import AsyncIterator

@dataclass
class TextEvent:
    text: str

@dataclass
class ToolStartEvent:
    name: str
    args: dict

@dataclass
class ToolResultEvent:
    name: str
    result: str

Event = TextEvent | ToolStartEvent | ToolResultEvent


async def query(messages: list, tools: list) -> AsyncIterator[Event]:
    while True:
        # 1. API 호출 (스트리밍)
        stream = await call_anthropic_api(messages, tools)
        
        assistant_content = []
        async for chunk in stream:
            if chunk.type == "text":
                yield TextEvent(chunk.text)
                assistant_content.append(chunk)
            if chunk.type == "tool_use":
                assistant_content.append(chunk)
        
        messages.append({"role": "assistant", "content": assistant_content})
        
        tool_uses = [b for b in assistant_content if b.type == "tool_use"]
        if not tool_uses:
            return  # 한 턴 끝
        
        tool_results = []
        for tu in tool_uses:
            yield ToolStartEvent(tu.name, tu.input)
            result = await execute_tool(tu.name, tu.input)
            yield ToolResultEvent(tu.name, result)
            tool_results.append({"type": "tool_result", ...})
        
        messages.append({"role": "user", "content": tool_results})
        # → while 위로


async def run_turn(user_input: str):
    messages.append({"role": "user", "content": user_input})
    async for event in query(messages, tools):
        match event:
            case TextEvent(text):
                print(text, end="", flush=True)
            case ToolStartEvent(name, args):
                print(f"\n⠋ {name}: {args}")
            case ToolResultEvent(name, result):
                print(f"\n✓ {name} done")
```

`query.ts`와 거의 한 줄씩 대응한다. **TypeScript의 `async function*` ↔ Python의 `async def`** + `yield`. **`yield*` ↔ `yield from`**. **`for await ... of` ↔ `async for ... in`**. 개념은 똑같다.

<details>
<summary>🔬 Deep Dive — 왜 콜백이나 옵저버가 아니라 제너레이터인가?</summary>

> 같은 효과를 콜백으로도 낼 수 있다. `query(messages, tools, on_text, on_tool_start, on_tool_result)` 식으로. 또는 EventEmitter 패턴으로. 그런데 제너레이터가 두 가지 면에서 더 낫다. **(1) 호출자가 흐름을 통제한다.** `for await` 안에서 `break`로 멈출 수 있고, `await asyncio.sleep(...)`으로 속도를 조절할 수도 있다. 콜백은 호출자가 그냥 받기만 한다. **(2) 타입 시스템이 잘 표현한다.** `AsyncIterator[Event]` 한 줄로 "이 함수는 Event를 흘려보낸다"가 표현된다. 콜백 시그니처 4개를 매개변수로 받는 것보다 깔끔하다.

</details>

## 핵심 정리

- `query.ts`는 **AsyncGenerator**로 만들어져 있다. TypeScript의 `async function*` + `yield` 패턴.
- 이 패턴은 Python의 `async def f() -> AsyncIterator: yield ...` + `async for x in f(): ...` 와 **개념과 사용법이 동일**하다. 이름과 키워드만 다르다.
- "흘러나오는" 사용자 경험이 코드 구조로 그대로 표현된다. 한 함수가 생성하고, 다른 함수가 소비하는 파이프 모양.
- 진짜 `query.ts` 의 generator 체인은 **5+ 레벨, 세 파일** (`query.ts` ↔ `services/api/claude.ts` ↔ `services/vcr.ts`) 에 걸쳐 있다: `query` → `queryLoop` → (`deps.callModel` 주입 자리) → `queryModelWithStreaming` → `withStreamingVCR` → `queryModel`. 책임별로 쪼개진 함수들이 호출자에게는 한 평면의 이벤트 스트림처럼 보인다.
- `query.ts` 와 `claude.ts` 사이는 **`deps.callModel` 의존성 주입** 으로 끊어져 있다. 테스트에서 가짜 generator 를 꽂아 전체 루프를 검증할 수 있는 자리.
- **콜백 대신 제너레이터를 쓴 이유**: 호출자가 흐름을 통제할 수 있고, 타입 시스템이 잘 표현해서.
- 다음 챕터(2.3)에서는 이 흐름 안에 끼어 있는 복구 경로 10가지를 본다. 재시도, 폴백, 자동 압축, ...
