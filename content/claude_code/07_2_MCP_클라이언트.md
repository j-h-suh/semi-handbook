# 7.2 MCP 클라이언트 — 외부 서버에서 도구를 발견하는 법

---

## 이 챕터에서 배우는 것

- **MCP**(Model Context Protocol)가 플러그인 시스템이다 — 누구든 도구를 추가할 수 있는 표준
- 8가지 전송 방식(stdio/HTTP/WebSocket/in-process …)을 한 인터페이스로 통일하는 법
- `tools/list` **단 한 번의 호출**로 외부 서버의 모든 도구를 발견하는 메커니즘
- 외부 도구가 어떻게 **3.2의 47개 필드 Tool 객체로 변환**되는지 — 같은 형태로 위장
- `mcp__<server>__<tool>` 네이밍이 권한 시스템과 어떻게 맞물리는지

---

## 사용자 경험에서 출발

3.1에서 한 약속을 기억해. **"도구는 함수가 아니라 마이크로서비스다"**. FileRead, BashTool, Edit — 모두 같은 인터페이스를 따른다. 그래서 LLM이 도구를 호출하는 코드는 도구가 어떤 종류인지 모른다.

근데 좀 이상한데. 내장 도구는 16개 정도다. Claude Code 안에 컴파일되어 들어 있는 거. 그럼 내가 만든 도구는 어떻게 추가하지?

답: **MCP 서버를 띄운다**.

```bash
# ~/.config/claude/mcp.json
{
  "mcpServers": {
    "github": {
      "command": "uvx",
      "args": ["mcp-server-github"]
    }
  }
}
```

`claude`를 다시 띄우면 — 마법처럼 `mcp__github__create_issue`, `mcp__github__list_prs` 같은 도구들이 자동으로 LLM의 도구 목록에 나타난다. 내가 만든 적도 없는 도구들이.

이 챕터에서 — 이게 어떻게 가능한지 본다. 답: **8가지 전송 방식 위에 하나의 발견 프로토콜. 그리고 외부 도구를 내장 도구처럼 위장하는 변환 함수.**

---

## 본문

### 8가지 전송 방식

`src/services/mcp/types.ts` 에 8가지 서버 타입이 union으로 묶여 있다.

```typescript
// types.ts:124-134 verbatim (코멘트 한국어 번역만 추가)
export const McpServerConfigSchema = lazySchema(() =>
  z.union([
    McpStdioServerConfigSchema(),         // 1. 로컬 서브프로세스 (stdin/stdout)
    McpSSEServerConfigSchema(),            // 2. HTTP Server-Sent Events
    McpSSEIDEServerConfigSchema(),         // 3. IDE 확장 (VSCode/JetBrains 내부)
    McpWebSocketIDEServerConfigSchema(),   // 4. IDE 확장 (WebSocket)
    McpHTTPServerConfigSchema(),           // 5. HTTP REST
    McpWebSocketServerConfigSchema(),      // 6. 일반 WebSocket
    McpSdkServerConfigSchema(),            // 7. SDK 임베디드 (in-process)
    McpClaudeAIProxyServerConfigSchema(),  // 8. Claude.ai 프록시
  ]),
)
```

이게 왜 이렇게 많지? 왜냐하면 MCP는 연결 방식을 강제하지 않는다. stdio가 가장 흔하다 — 프로세스를 띄워서 stdin/stdout으로 JSON-RPC 메시지를 주고받는다. HTTP는 원격 서버용. WebSocket은 실시간 양방향. **in-process**는 같은 프로세스 안에서 메모리 채널로(!) 연결한다.

근데 호출자 코드는 차이를 모른다. 모두 같은 MCP `Client` 객체를 받고, 같은 `client.request({method: 'tools/list'})` 를 부른다. 8가지 형태가 하나의 인터페이스로 가려진다. 익숙한 풍경이지? 7.1의 4개 SDK와 같은 정신.

### 연결 — `connectToServer`

`client.ts:595` 의 `connectToServer`는 **memoize된** 함수다. 같은 서버 이름은 한 번만 연결한다. 한 번 연결되면 캐싱.

```typescript
} else if (serverRef.type === 'stdio' || !serverRef.type) {
  transport = new StdioClientTransport({
    command: finalCommand,
    args: finalArgs,
    env: { ...subprocessEnv(), ...serverRef.env },
    stderr: 'pipe',  // MCP 서버의 stderr가 UI에 안 새도록
  })
}
```

stdio 케이스. `uvx mcp-server-github` 같은 명령을 서브프로세스로 띄우고, 그 프로세스의 stdin/stdout을 양방향 채널로 쓴다. **`stderr: 'pipe'`** — 그냥 전송 옵션이 아니라 **UX 보호** 다. MCP 서버가 디버그 메시지를 stderr로 뿜으면 그게 터미널 UI를 깨버린다. 그래서 stderr를 가로채서 별도 로그로 빼돌린다.

연결 상태는 5단계 상태 머신이다 (`MCPServerConnection` union):

| 상태 | 의미 |
|---|---|
| `pending` | 연결 시도 중. `reconnectAttempt` + `maxReconnectAttempts` 카운터를 들고 있음 — 재시도 한계까지 같이 추적. |
| `connected` | 정상. `client`, `capabilities` 객체를 들고 있음. |
| `failed` | 실패. `error` 메시지 보존. |
| `needs-auth` | OAuth 필요. 사용자가 토큰을 발급해야 함. (다음 챕터 7.3) |
| `disabled` | 사용자가 명시적으로 끔. |

5개 상태가 모두 다른 필드를 갖는다 — 이건 **판별 union**(discriminated union)이다. `if (client.type === 'connected')` 로 좁히면 TypeScript가 `client.client`, `client.capabilities` 같은 필드를 알아서 풀어준다. Pydantic의 `Discriminator` 와 같은 정신.

### 도구 발견 — `tools/list`

연결이 되면 — 그 다음이 진짜 마법이다. `fetchToolsForClient` (`client.ts:1743`):

```typescript
// (축약: searchHint, alwaysLoad, prompt, toAutoClassifierInput, isOpenWorld,
//        isSearchOrReadCommand, checkPermissions, callMCPToolWithUrlElicitationRetry
//        retry 로직 등 많은 메서드 생략. 실제 함수는 200+ 줄)
export const fetchToolsForClient = memoizeWithLRU(
  async (client: MCPServerConnection): Promise<Tool[]> => {
    if (client.type !== 'connected') return []
    if (!client.capabilities?.tools) return []

    const result = await client.client.request(
      { method: 'tools/list' },
      ListToolsResultSchema,
    )

    const toolsToProcess = recursivelySanitizeUnicode(result.tools)
    
    return toolsToProcess.map((tool): Tool => {
      const fullyQualifiedName = buildMcpToolName(client.name, tool.name)
      return {
        ...MCPTool,                              // ← 기본값 spread (3.3과 같은 패턴!)
        // 실제 코드: name: skipPrefix ? tool.name : fullyQualifiedName
        // (CLAUDE_AGENT_SDK_MCP_NO_PREFIX env var 뒤의 SDK 모드에서 builtins 오버라이드용)
        name: fullyQualifiedName,                // mcp__github__create_issue
        mcpInfo: { serverName: client.name, toolName: tool.name },
        isMcp: true,
        // ... 47개 필드를 반환된 스키마로 채움
        inputJSONSchema: tool.inputSchema as Tool['inputJSONSchema'],
        async description() { return tool.description ?? '' },
        isConcurrencySafe() { return tool.annotations?.readOnlyHint ?? false },
        isReadOnly() { return tool.annotations?.readOnlyHint ?? false },
        isDestructive() { return tool.annotations?.destructiveHint ?? false },
        async call(args, context, _, parentMessage, onProgress) {
          // ... MCP request 전달, retry 로직 ...
        },
      }
    })
  },
)
```

이게 핵심이다. **MCP 서버의 도구가 3.2의 Tool 객체로 변신**. 같은 47개 필드, 같은 형태. 그래서 호출자 코드는 차이를 모른다 — 똑같이 `tool.call(input, context)` 한다.

세 가지가 같이 일어난다.

1. **`...MCPTool` spread** — 3.3에서 본 **fail-closed 기본값**과 같은 패턴. MCPTool은 모든 필드의 안전한 기본값. 거기에 외부 서버에서 받은 정보를 덮어 씀. (`MCPTool` 자체가 `tools/MCPTool/MCPTool.ts:27` 의 `buildTool({...})` 로 만들어진 객체다 — 즉 7.2의 변환층은 **3.3의 buildTool 패턴 위에 다시 buildTool 패턴**을 쌓는 **2단 빌드**다. 한 패턴으로 통일된다는 게 이런 의미.)
2. **`buildMcpToolName(serverName, toolName)`** — 접두사 정규화. `github` 서버의 `create_issue` 도구는 `mcp__github__create_issue` 가 된다. **이중 언더스코어 구분자**(`__`)는 우연이 아니다 — 일반 도구 이름과 겹치지 않게.
3. **`tool.annotations?.readOnlyHint`** — MCP 서버가 직접 안전성을 선언. `?? false` 로 **fail-closed**. 선언 안 했으면 위험하다고 가정.

> 💡 **이중 언더스코어 — 코드도 인정하는 한계.** `mcpStringUtils.ts:14-17` 에 직접 적힌 코멘트: **"Known limitation: If a server name contains '__', parsing will be incorrect — but server names with '__' are unlikely in practice."** 즉 **이름을 만드는 방향**(`buildMcpToolName`)은 문제 없음. 하지만 반대 방향 — 풀 네임을 다시 `{서버, 도구}` 로 파싱하는 `mcpInfoFromString` — 은 서버 이름에 `__` 가 들어있으면 어디서 자를지 모른다. 코드는 이걸 알면서 받아들였다 — 현실에서는 안 일어난다는 가정. 추상화의 솔직한 트레이드오프 사례.

### 네이밍이 곧 권한이다

`mcp__github__create_issue` 라는 이름이 그냥 식별자가 아니다 — 권한 시스템의 키다.

```typescript
// mcpStringUtils.ts:60
export function getToolNameForPermissionCheck(tool: {
  name: string
  mcpInfo?: { serverName: string; toolName: string }
}): string {
  return tool.mcpInfo
    ? buildMcpToolName(tool.mcpInfo.serverName, tool.mcpInfo.toolName)
    : tool.name
}
```

6.4의 권한 매처가 이 풀 네임에 매칭한다. 사용자가 `mcp__github__*` 라는 와일드카드 규칙을 쓰면 — github 서버의 모든 도구가 자동으로 허용된다. `mcp__*__create_*` 는 어느 서버든 `create_*` 도구만 허용. 6.4의 7단계 와일드카드 변환이 외부 도구에도 그대로 작동한다. 

이건 우연이 아닌 설계다. 코멘트가 친절하다:

```typescript
// Returns the name to use for permission rule matching.
// For MCP tools, uses the fully qualified mcp__server__tool name so that
// deny rules targeting builtins (e.g., "Write") don't match unprefixed MCP
// replacements that share the same display name.
// Falls back to `tool.name`.
```

첫 줄과 마지막 줄도 의미가 있다. **첫 줄**: 이 함수의 유일한 목적이 권한 매칭이라는 명시. **마지막 줄**: MCP 도구가 아니면 **그냥 `tool.name`** — 즉 내장 도구는 접두사 없는 이름으로 매칭한다. **두 가지 매칭 경로가 한 함수**에 합쳐져 있다.

악의적인 MCP 서버가 `Write`라는 이름의 도구를 노출했다고 하자. 사용자가 **내장 Write**에 대해서는 deny 규칙을 가지고 있다. **그 deny 규칙이 MCP 서버의 가짜 Write에도 적용되어야 한다.** 그래서 **모든 MCP 도구는 풀 네임**으로 권한 검사한다 — 사용자의 deny 규칙이 가짜를 잡아낼 수 있도록.

> 💡 **In-process 전송 — Chrome MCP, Computer Use.** 진짜 재밌는 케이스가 **in-process** 다. `client.ts:920` 근처에서 Chrome MCP와 Computer Use는 같은 프로세스 안에서 MCP 서버를 띄운다. `createLinkedTransportPair()` — 메모리 채널 한 쌍을 만들어서 서버와 클라이언트가 같은 메모리에서 통신한다. 왜? 외부 의존성도, IPC 오버헤드도 없이 **MCP 인터페이스의 통일성을 유지**하기 위해. 외부 서버든 in-process든 — 호출자는 같은 코드. **추상화가 비용을 만들지 않은 좋은 사례**.

## Python으로 옮기면

같은 패턴을 Python으로 옮기면:

```python
from __future__ import annotations
import asyncio
from dataclasses import dataclass, field
from functools import lru_cache
from typing import Any, Literal, Protocol


# ─── 8가지 서버 설정 (판별 union) ────────────────
@dataclass
class StdioServerConfig:
    type: Literal["stdio"] = "stdio"
    command: str = ""
    args: list[str] = field(default_factory=list)
    env: dict[str, str] = field(default_factory=dict)


@dataclass
class HttpServerConfig:
    type: Literal["http"] = "http"
    url: str = ""
    headers: dict[str, str] = field(default_factory=dict)


# … 6개 더 …

ServerConfig = StdioServerConfig | HttpServerConfig  # | …


# ─── 5단계 연결 상태 (역시 판별 union) ────────────────
@dataclass
class ConnectedServer:
    type: Literal["connected"] = "connected"
    name: str = ""
    client: "MCPClient" = None  # type: ignore
    capabilities: dict = field(default_factory=dict)


@dataclass
class FailedServer:
    type: Literal["failed"] = "failed"
    name: str = ""
    error: str = ""


# … 3개 더 …

ServerConnection = ConnectedServer | FailedServer  # | …


# ─── 도구 (3.2 의 Tool 인터페이스) ────────────────
class Tool(Protocol):
    name: str
    
    async def description(self) -> str: ...
    def is_concurrency_safe(self) -> bool: ...
    def is_read_only(self) -> bool: ...
    def is_destructive(self) -> bool: ...
    async def call(self, args: dict, context: Any) -> Any: ...


# ─── 발견 함수 ────────────────
@lru_cache(maxsize=20)
async def fetch_tools_for_client(client: ServerConnection) -> list[Tool]:
    """외부 도구를 내장 도구 형태로 변환."""
    if client.type != "connected":
        return []
    if not client.capabilities.get("tools"):
        return []
    
    # JSON-RPC 한 번
    result = await client.client.request("tools/list")
    
    return [_mcp_tool_to_native(client, t) for t in result["tools"]]


def _mcp_tool_to_native(client: ConnectedServer, tool: dict) -> Tool:
    """MCP 스키마 → Tool 인터페이스 변환."""
    full_name = build_mcp_tool_name(client.name, tool["name"])
    annotations = tool.get("annotations", {})
    
    class _MCPNativeTool:
        name = full_name
        mcp_info = {"server_name": client.name, "tool_name": tool["name"]}
        is_mcp = True
        input_schema = tool["inputSchema"]
        
        async def description(self) -> str:
            return tool.get("description", "")
        
        def is_concurrency_safe(self) -> bool:
            return annotations.get("readOnlyHint", False)  # ← fail-closed
        
        def is_read_only(self) -> bool:
            return annotations.get("readOnlyHint", False)
        
        def is_destructive(self) -> bool:
            return annotations.get("destructiveHint", False)
        
        async def call(self, args: dict, context: Any) -> Any:
            return await client.client.request(
                "tools/call",
                {"name": tool["name"], "arguments": args},
            )
    
    return _MCPNativeTool()  # type: ignore


def build_mcp_tool_name(server_name: str, tool_name: str) -> str:
    """권한 시스템의 키. 풀 네임이 곧 deny 규칙의 매칭 대상."""
    return f"mcp__{_normalize(server_name)}__{_normalize(tool_name)}"
```

핵심 셋이 다 있다.

1. **판별 union** (`Literal["connected"]` 디스크리미네이터) — `if conn.type == "connected":` 로 좁히면 mypy가 `conn.client` 를 알아준다. TypeScript의 union narrowing과 같은 정신.
2. **`@lru_cache`** — `fetchToolsForClient` 의 `memoizeWithLRU(20)` 와 1:1.
3. **3.2의 Tool 인터페이스로 변신** — 외부 도구가 내장 도구처럼 보이도록. 호출자는 차이를 모른다.

> 💡 **`Protocol` 다시 등장.** 7.1에서 본 그 `Protocol` 이 또 나왔다. 외부에서 들어오는 객체가 우리 인터페이스를 만족하는지 확인하는 가장 자연스러운 방법. MCP 서버 개발자가 우리 코드를 import 할 일이 없다 — 형태만 맞으면 통과하는 게 맞다. ABC였다면 작동 안 했을 것.

## 핵심 정리

- **MCP**는 Claude Code의 플러그인 시스템. 누구든 도구를 추가할 수 있는 표준 프로토콜. JSON-RPC 기반.
- 8가지 전송 방식 — stdio, HTTP, SSE, WebSocket, IDE 변형, in-process(SDK), Claude.ai 프록시. **하나의 `Client` 인터페이스로 통일**. 호출자는 차이를 모른다.
- 연결 상태는 5단계 머신(`pending`/`connected`/`failed`/`needs-auth`/`disabled`) — **판별 union**. TypeScript 컴파일러가 안전성 보장.
- **도구 발견은 `tools/list` JSON-RPC 한 번**. 응답을 받아서 **3.2의 47개 필드 Tool 객체로 변환**. `...MCPTool` spread로 **fail-closed 기본값** 깔고, 받은 스키마로 덮어 씀.
- **`mcp__<server>__<tool>` 네이밍이 곧 권한 시스템의 키.** 6.4의 와일드카드 매칭이 외부 도구에도 그대로 작동. `mcp__github__*` 같은 규칙으로 서버 단위 허용/차단 가능. 풀 네임 강제는 **악성 MCP 서버가 내장 도구 deny 규칙을 우회**하는 걸 막는다.
- **In-process 전송**(Chrome MCP, Computer Use)은 같은 프로세스 안에서 메모리 채널로 MCP 인터페이스를 사용. 추상화가 비용 없이 통일성을 유지한 좋은 사례.
- 외부 도구가 들어와도 3.1의 약속("도구는 함수가 아니라 마이크로서비스")이 깨지지 않는다 — 그게 가능한 이유가 바로 이 변환층.
